# Codex native integration: research for the HarnessHub redesign

Date: 2026-11-14. Installed: `codex-cli 0.169.0` (`/opt/homebrew/bin/codex` → Homebrew cask `Caskroom/codex/0.169.0/bin/codex`, a native binary).
Scope: read-only. No thread or turn was started, no prompt was sent, nothing under `~/.codex` was edited. The probes only started `codex app-server`, called `initialize` and read-only methods, and closed stdin. Every probe process exited; the two app-servers still running on the machine belong to OpenClaw and were left alone.

Labels used below: **[schema]** = generated from the installed 0.169.0 binary; **[probe]** = seen on this Mac; **[doc]** = official README / docs; **[T3]** = T3 Code source at d19467a5; **[ours]** = this repo; **[unconfirmed]** = inferred, not verified.

## 0. Summary

- `codex app-server` over stdio is the right and only sensible interface. It is the same JSON-RPC surface the Codex desktop app, the VS Code extension and the CLI TUI (in-process) use. 0.169.0 exposes **184 client requests (109 stable + 75 experimental), 11 server requests (1 experimental) and 86 notifications** [schema].
- The stable surface only grew between 0.162.1, 0.166.0 and 0.169.0 (+4 requests, +2 notifications, nothing removed) [schema, committed schemas on GitHub]. But fields do disappear: `thread/rollback` is gone (use `thread/revert`), `on-failure` is gone from `AskForApproval`.
- Our `src/adapters/control/codex.ts` already covers the core loop well: start, resume, fork, turns with images and files, steer, interrupt, compact, plan mode, approvals for commands and patches, questions, sub-agents, usage and titles. The main gaps: **MCP elicitations and permission requests are refused with -32601**. **Any turn-scoped notification that arrives while no Hub turn is active aborts the whole connection.** No `thread/revert` (so edit-and-resend has no native path). Most per-turn settings are unused. Agent-message `phase` is ignored, so commentary gets merged into the reply. No rate limits are read. Several stable notifications are unhandled, `thread/closed` among them.
- T3 Code also runs one app-server per T3 thread, hosting that thread's sub-agents and forks. It always declares `experimentalApi`, sends every setting on every `turn/start`, and keeps a set of field-tested workarounds: writer lock, archived threads, revert needing paginated history, usage totals that go down, additional context lost on compaction. Its "managed" runtime and shadow homes do not apply to us: we use the user's own login and `~/.codex`.
- Recommendation: keep stdio and one app-server per Hub conversation for now. Rebuild the driver around a thread-routed host so pooling can come later. Generate the schema from the installed binary at startup (80 ms) and gate features on it.

## 1. Protocol surface of 0.169.0

### How it was produced
`codex app-server --help` lists `generate-json-schema` and `generate-ts`, both with `--experimental`. I generated four bundles: stable and experimental, JSON Schema and TypeScript (JSON: 39 / 47 top-level files plus `v2/`; TS: 98 / 105 top-level files plus 847 v2 types). Generating the experimental JSON schema takes **0.08 s** [probe]. The docs say "Each output is specific to the Codex version you ran" [doc: learn.chatgpt.com/docs/app-server, "Message schema"].

"Experimental" below means present only with `--experimental`, i.e. available only when `initialize.capabilities.experimentalApi = true`. Without it the server answers e.g. `-32600 "collaborationMode/list requires experimentalApi capability"` [probe]. Notifications are not split by the generator: all 86 appear in both bundles. Doc comments mark some as experimental (`item/plan/delta`, `thread/realtime/*`, `item/autoApprovalReview/*`, `app/list/updated`), and the README says `thread/readState/changed` is delivered only to experimental clients.

## 2. Process model

- **One app-server, many threads: yes.** Every thread request carries `threadId`. `thread/loaded/list` lists loaded threads. The docs mention "threads in the same app-server process" [doc]. The desktop and IDE clients run one server for all conversations. T3 says so in code: "One app-server serves every Codex thread on an instance" (`CodexAdapterV2.ts:1558-1561`), and it passes the T3 thread id through per-thread config, "not its env" (`:1470-1473`).
- **What T3 actually spawns**: one app-server per T3 provider session, i.e. per T3 thread, hosting that thread's native sub-agents and forks (`CodexAdapterV2.ts:1709-1757`, `ProviderSessionManager.ts:2911`). It launches `app-server -c thread_unload_delay_secs=0` (`codexLaunchArgs.ts:12-18`) and releases idle sessions after 30 min (`ProviderSessionManager.ts:65`). Capability flag: `supportsMultipleProviderThreadsPerSession: true` (`:257`).
- **Ours**: one app-server per Hub connection, i.e. per Hub conversation. A fork gets its own extra process (`codex.ts:646-661`). Relay declaration: `execution: "process"` (`codex.ts:33`).
- **Startup cost** [probe]: spawn → `initialize` answered in **30–240 ms**. The first `model/list` in a process can take **3.2–4.2 s** (catalog refresh over the network); later calls take 1 ms, and a second process got it in 1 ms (shared `models_cache.json`). Idle RSS after `model/list` is **~85 MB**, plus a short-lived `git` child. `thread/start` / `thread/resume` cost was not measured (it loads MCP servers; T3 sets `mcp_optional_startup_grace_ms=10000` because "the 1 s default excludes cold npx/uvx servers from the first model request", `CodexAdapterV2.ts:1430-1437`). Exit after stdin EOF took 12 ms with no thread loaded [probe]. Our docs note ~1.1 s with a thread (`docs/contracts/native-hosts.md:109`).
- **Cross-process writer lock**: Codex holds one writer lock per thread per `CODEX_HOME` (`codex-rs/rollout/src/writer_lock.rs:1-3, 45-83` @ rust-v0.169.0: "thread {id} already has an active writer"). T3: "Codex holds a per-thread writer lock for as long as a thread stays loaded in any app-server sharing the same CODEX_HOME" (`CodexAdapterV2.ts:366-374`). So a thread open in the Codex desktop app or the IDE cannot be resumed by the Hub (`-32600`), and two Hub processes cannot both load one thread. This fits the product rule (Hub-owned sessions are not continued natively at the same time); it needs a clear error message.
- **Unloading**: `thread/unsubscribe` unloads after an idle grace ("60 seconds by default") [doc], controlled by `thread_unload_delay_secs`; Codex then sends `thread/closed`. Resuming while it is still closing fails with "thread … is closing" (T3 waits for `thread/closed`, `CodexAdapterV2.ts:7311-7318`).
- **Transports**: `--listen stdio://` (default, newline-delimited JSON; the docs give no caveat), `unix://[PATH]` (WebSocket over a Unix socket), `ws://IP:PORT` ("experimental and unsupported"; non-loopback listeners are unauthenticated by default; `--ws-auth capability-token|signed-bearer-token`), `off` [help, doc]. There is also `codex app-server daemon …` plus `proxy` for a managed, auto-updating daemon on a control socket; the TUI attaches to it implicitly when it exists (`codex-rs/app-server-daemon/README.md`, experimental). **Use stdio**: no auth surface, process lifetime tied to ours, and no sharing with the user's daemon (which would break Hub ownership).
- **Concurrency inside one process**: the protocol allows turns on several threads at once (all routed by `threadId`). I did not measure parallel turns in one process [unconfirmed]. On WebSocket transports, full queues return `-32001 "Server overloaded; retry later."` [doc].

## 6. Our `codex.ts`: covered and missing

**Covered well** (line refs in `src/adapters/control/codex.ts`): handshake and version (318-341); effective config read and the user's own developer instructions merged (450-457); paged model catalog with efforts, tiers and modalities (358-395); auth status (345-349); skills as `/skill:` commands and skill input (597-614, 699-728); MCP status and plugins (616-644); thread start/resume with model, approval, sandbox, tier, instructions and the Hub MCP server, checking that reported settings match (464-548); fork (646-661); title (411-417); native session list and import (550-595); turns with images, audio and file pointers plus client id (685-764); compact, export and Hub clear (676-684, 730-739, 800-814); steer (773-798); interrupt with the F4 retry (824-843); command and patch approvals, questions (1097-1153); rich item mapping incl. sub-agent nesting, review, compaction, image outputs (922-1093); typed failure classes (246-256); per-request usage and context size (1056-1070).

**Gaps (concrete):**
1. **MCP elicitations and permission requests are answered `-32601`** (`codex.ts:1099-1100`, via `json-rpc-process.ts:399-400`). Codex app or connector tool approvals and sandbox escalation requests (network, extra write roots) cannot be answered. What Codex does with -32601 is [unconfirmed]; most likely the tool call fails.
2. **A turn-scoped notification with no active Hub turn aborts the connection**: `scope(…, true)` throws `INVALID_STATE` (`codex.ts:863`), and any throw in dispatch aborts (`json-rpc-process.ts:376`). Possible triggers: goal auto-continuation turns on a resumed or imported thread, late output from background terminals, items completing after `turn/completed` (T3 handles "late completions" and between-turn sub-agent completion) [triggers unconfirmed on device].
3. **`thread/revert` unused**: no native edit-and-resend and no "fork at turn N" (`lastTurnId` unused, `codex.ts:653`).
4. **Per-turn settings unused**: model changes, permission-level changes and `serviceTierForTurn` all need a new open. `summary` is never sent, so a catalog default of `none` hides reasoning (T3 `:846-848`). Only `effort` and `collaborationMode` go per turn (`codex.ts:740-742`).

No `optOutNotificationMethods` (`turn/diff/updated` is received and dropped).

8. **Command-approval detail dropped**: `kind` (humanCommand, writeStdin), `networkApprovalContext`, the proposed exec-policy and network amendments, `additionalPermissions`, `commandActions`; the object decisions are filtered out (`codex.ts:1107-1110`).
9. **Unhandled stable notifications** fall through to "Unsupported Codex notification" (`codex.ts:1091-1092`): `thread/closed` (the thread was unloaded; should invalidate the connection's thread), `thread/archived|unarchived|deleted`, `thread/reverted`, `thread/goal/*`, `item/commandExecution/terminalInteraction`, `item/autoApprovalReview/*`, `turn/moderationMetadata`, `model/verification`, `model/safetyBuffering/updated`, `mcpServer/oauthLogin/completed`, `thread/compacted` (deprecated).
10. **No rate limits**: `account/rateLimits/updated` is passive (`codex.ts:240`); `account/rateLimits/read` and `account/usage/read` are never called, so quota errors have no reset time.
11. **Usage edge cases**: decreasing totals clamp to 0 (`codex.ts:1062`) where T3 falls back to `last`; sub-agent threads' usage is dropped as foreign [unconfirmed impact].
12. **`on-failure` still offered** (`codex.ts:110, 185-186`), but 0.169.0 no longer accepts it; "auto" maps to `never` + workspace-write (`flavors/codex.ts:16`), so network-needing commands fail silently (§8).
13. **Clear**: the abandoned thread is never unsubscribed (harmless with one process per conversation, a leak once processes are pooled). The next `thread/start` is not marked `sessionStartSource:"clear"`, so the user's SessionStart hooks see "startup" (`codex.ts:676-684`).
14. **Resume errors not mapped**: "already has an active writer" (thread open in the Codex app or IDE) and "session is archived" end in a generic failure instead of a clear message or an `unarchive`.
15. **Import is text-only** (`codex.ts:583-586`): tools, commands, diffs and reasoning are dropped although `thread/turns/list itemsView:"full"` returns them. `sourceKinds` includes `appServer` (`codex.ts:116`), so Hub-created threads are offered for import too [unconfirmed whether filtered elsewhere].
16. **Presentation left on the table**: `commandActions` (read, search, list), `webSearch.action`, `fileChange.kind` (add, delete, move; `fileDiff` builds headers from the path only, `codex.ts:100-104`), `durationMs`, MCP `appContext` / `_meta`.
17. **No review start** (`review/start`), although review items are already rendered.
18. **Fork in a separate process**: with the cross-process writer lock, forking a thread loaded by the conversation's own process from another process is [unconfirmed]; doing it on the same connection avoids the question.

## 7. Risks and drift detection

- **Experimental APIs**: plan mode (`collaborationMode`, `collaborationMode/list`), `additionalContext`, `dynamicTools`, `thread/settings/update`, `item/plan/delta`, profiles and queues are all ✱ and can change without notice. Keep each behind a probe and a fallback: plan mode → read-only sandbox only; additionalContext → developerInstructions; dynamic tools → MCP.
- **Field-level breakage** happens even in "stable" (`thread/rollback`, `on-failure`). The method list alone is not enough; the driver depends on specific fields (`clientId` echo, `serviceTiers`, `historyMode`, `availableDecisions`…).
- **Codex writes the user's config on `thread/start`**: it persists project trust for directories with a project-root marker or a Git checkout (README 0.169.0 "Project trust"). `~/.codex/config.toml` holds **54** `[projects.…]` sections, including **1 for an `hh-` worktree path and 2 for temp paths** [probe: counted with grep, nothing printed]. Attribution to the Hub's own threads is likely but unconfirmed. Every Hub worktree adds an entry. Whether a per-thread `config` override suppresses this is [unconfirmed]. Worth asking the user (this is Codex's own behaviour, not ours).
- **Writer lock** with the user's Codex desktop app, IDE extension, and other tools that bundle their own Codex (OpenClaw runs its own app-servers on this Mac) when they share `~/.codex`.
- **Auto-updating daemon**: if the user enables `codex app-server daemon`, the TUI attaches to it. Our stdio process is unaffected, but the binary on PATH can change under a long-lived host, so re-check the version when a process is (re)spawned.
- **Network-dependent startup**: the first `model/list` takes 3–4 s; account routing discovery can error (`account/read` returns an error, never an "unrestricted" success) [doc].

**Detecting protocol changes on upgrade (recommended):**
1. At every spawn, read the version from `initialize.userAgent` (`codex/0.169.0 …`). Cache per version.
2. On a version not seen before, run `codex app-server generate-json-schema --experimental --out <tmp>` (80 ms). Extract the method lists, then the fields the driver uses (a small checked-in list: e.g. `TurnStartParams.{clientUserMessageId, effort, model, summary, serviceTierForTurn, collaborationMode}`, `ThreadItem.userMessage.clientId`, `AskForApproval` values, `ServerRequest` methods). Compare with the snapshot the driver was last verified against. Missing → capability off, with one diagnostic line; new → logged for us. No "unverified version" prompts to the user (memory: adapt to the latest).
3. In development, generate TS bindings from the installed binary (`generate-ts --experimental`) into an ignored folder and type-check a thin typed facade against them (`pnpm build` would catch drift). Unlike T3, generate from the **installed** binary, not a pinned upstream ref.
4. Keep one replay fixture per scenario recorded from the real Codex (T3: `scripts/record-codex-app-server-replay-fixture.ts`) as the smoke test.

## 8. Recommendation for the redesign's Codex driver

1. **Interface**: `codex app-server --listen stdio://` from the user's install, `CODEX_HOME` untouched, nothing ever written through the API (blocklist the W methods in the facade). Launch with `-c thread_unload_delay_secs=0` only if we keep one process per conversation (it does not matter then); otherwise leave the default.
2. **Process model**: keep one app-server per Hub conversation for now (≈0.2 s start, ~85 MB idle, failure isolation, simple per-session Hub-tool credentials). Write the driver as a **host that routes by `threadId`** and hosts that conversation's forks, branches and sub-agents on the same connection: no separate fork process. That way a later pool (one host per `CODEX_HOME` for many conversations) is a host-layer change. When pooling, move the Hub tool credentials into the per-thread `config` (HTTP url + header like T3, or `env` in `mcp_servers.<name>`), and `thread/unsubscribe` on clear and close.
3. **Always declare `experimentalApi: true`** with `optOutNotificationMethods: ["turn/diff/updated"]` (the Hub has its own checkpoints). Use ✱ fields only when the schema probe confirms them.
4. **Send settings on every `turn/start`**: `model`, `effort`, `summary` (the user's `model_reasoning_summary` or `auto`), `approvalPolicy`, `approvalsReviewer`, `collaborationMode` (always, both modes, as T3 does), `serviceTierForTurn` when the user picked a speed for one turn. Set the sandbox as the thread-level `sandbox` mode at start/resume rather than per-turn `sandboxPolicy`, which would reset `networkAccess` and `writableRoots`. A level change mid-conversation → resume on the same connection with the new mode [verify on device], or ✱ `thread/settings/update`.
5. **Level mapping** (Hub plan / ask / auto-edit / auto / full):
   - plan = collaboration `plan` + `read-only` + `on-request` (unchanged).
   - ask = `untrusted` + `workspace-write` (unchanged; T3 uses read-only, which would also ask before every in-workspace write).
   - auto-edit = `untrusted` + `workspace-write`, with the Hub accepting file-change approvals (unchanged).
   - **auto = `on-request` + `workspace-write` + `approvalsReviewer:"auto_review"`** (T3's choice, native, zero user operations). If auto-review is unavailable or too slow, keep `on-request` and let the Hub accept escalations by policy and show a hint. Today's `never` silently fails anything that needs the network. Needs a device check.
   - full = `never` + `danger-full-access` (unchanged).
   - Drop `on-failure`.
6. **Answer every server request**: command (all decision shapes; show `networkApprovalContext` and amendments), file change, **permissions** (grant subset, `scope` turn or session), **MCP elicitation** (T3's mapping; decline `url` mode), questions (blocking, plus async questions as message replies). Honour `serverRequest/resolved`. Decline `item/tool/call` unless dynamic tools are on.
7. **Never abort on stray notifications**: route by `threadId`/`turnId`. Attach unsolicited turns (goal continuations) to the current Hub run, or record them as a native-initiated turn. Late items go to the run they belong to. Unknown methods → diagnostic only.
8. **Edit-and-resend and branch**: `thread/revert {beforeTurnId}` on the loaded paginated thread, then `turn/start`; files from Hub checkpoints. Branch = `thread/fork {lastTurnId}` on the same connection. Legacy-history threads → fall back to the Hub's relay (new thread plus packet).
9. **Items with identity**: carry the Codex item id, `phase`, timestamps and `commandActions` into the unified protocol (text and thinking segments by id; commentary as progress, final answer as reply).
10. **Usage and limits**: T3's delta-with-fallback turn usage; context = `last.totalTokens` / `modelContextWindow`; read `account/rateLimits/read` at start and merge `account/rateLimits/updated`; attach `resetsAt` to quota failures.
11. **Clear**: `thread/start {sessionStartSource:"clear"}`, plus `thread/unsubscribe` of the old thread once pooled.
12. **Resume hygiene**: map "active writer" to a clear message ("this conversation is open in another Codex window"), auto-`thread/unarchive` for archived threads, and wait for `thread/closed` when a thread is closing.
13. **Import**: full item history via `thread/turns/list itemsView:"full"` (tools, diffs, reasoning), excluding `appServer` threads the Hub already owns.
14. **Optional, later**: `review/start` as a `/review` thread operation; `thread/inject_items` to place a relay packet as model-visible history before the user's words (stable, no model call) [delivery evidence unconfirmed]; ✱ `dynamicTools` to serve Hub tools over the same connection without an MCP process.
15. **Ask the user** about Codex persisting project trust for Hub worktrees in `config.toml`. It is native behaviour but touches the user's config.
