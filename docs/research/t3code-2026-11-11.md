## 0. 结论先行

1. **T3 不是“不解决”，而是解决了同一个问题，骨架和我们几乎同构。** V2（2026-10-15 的 v0.1.0 转正）允许同一线程换 provider/账号/模型：应用侧自存规范对话（SQLite），每个 provider 一个原生会话（带指针），切换时给目标发“自它上次所见以来”的增量；回到原来那家就续它的原生会话再补增量；续不上或放不下就开新原生会话发全量。【源码：`Orchestrator.ts:2193-2315`、`ProviderTurnStartService.ts:838-1412`；文档：`docs/orchestration-v2/provider-switching-and-context.md`】
2. **但机制数量和内容复杂度比我们小一个量级。** 交接内容不是摘要、不调模型，是“预算内挑选原文”（最近一条用户、最近一条助手、第一条用户优先，再由新到旧，整条放不下就整条省略、从不截断）加一段“如何用 MCP 工具读回被省略部分”的指针。送达账只是每份交接单上的三值标记（pending / injected / inline）；水位不存，现算（目标线程最后被送达的 Run 序号）。核心 7 个文件共 1,393 行（连同接线约 2.3k 行）。没有同意、没有脱敏、没有转义、没有事后核对、没有按功能的运行时探针门控（只有静态能力声明和版本公告）；handoff 相关的用户配置只有 1 个环境变量。
3. **“简”换来了真实的线程卡死类缺陷，而且正好集中在我们已经认真建模的几处**：
   - 预算估算（把目标原生用量减出来，未知时用字节当 token）：单报错串 “Insufficient context allowance” 就有 27 个 issue，修复 PR #19414 自 10-14 起仍未合并。
   - 待定标记误判：一次启动失败后，T3 丢弃了一个 55 万 token 的 Claude 原生会话（#22198）。
   - 取消的回合被过滤：新 provider 收不到上一轮的提问与回答，且省略计数是 0（#34009，2026-11-10 才修）。
   - 静默开新原生会话，界面毫无痕迹（#28178）。
   - 回到“又大又冷”的原生会话，一次 55 万 token 缓存重写（#23086）。
4. **官方自己也不把换 provider 当主路径。** v0.1.0 发布说明把它标成“支持，但不是组合多家 Harness 的推荐方式；handoff 有损”，推荐改用 `delegate_task`（让 agent 在另一家开子线程，不复制父历史，只给任务提示）。【文档：https://github.com/pingdotgg/t3code/releases/tag/v0.1.0】
5. **对我们**：T3 证明“确定性挑选 + 覆盖说明 + 指针 + 增量 + 回原会话续”这个骨架够用。它没有的：同意/厂商识别、脱敏、转义、事后核对、按功能探针门控、多设置项、叙述化与分档、纪元/下限/四状态机；其中同意/隐私/脱敏/泄露类我做了标题级检索，结果为 0，交接文本质量类也没找到，其余项我没有逐项检索，只是在抽查的几十条切换相关 issue 里没看到。它做得粗糙且用户确实受伤的：永不卡死的预算、省略账目、未知送达别丢原生会话、对用户可见、取消/失败回合的处理、命令回合不捎带、不转移运行中的工具。后一组正是我们多做且应保留的。具体见第 8 节。

## 1. 它是什么

- **形态**：“agent harness control surface”。本机（或远程机）跑一个 Node WebSocket 服务，包住各家 Harness 的 CLI/SDK；客户端有 web（`t3` 命令本地托管，另有 app.t3.codes）、Electron 桌面、iOS/Android 手机；远程靠 T3 Connect（Cloudflare 隧道）、Tailscale 或局域网配对。官方 FAQ 自称“不是 harness”。【文档：`README.md`、`AGENTS.md`、`docs/user/faq.md`】
- **技术栈**：TypeScript monorepo（pnpm + Vite+ `vp`），服务端基于 Effect，SQLite 持久化（`statev2.sqlite`），Node 26.12.1；web 用 React（React Compiler）、手机用 React Native/Expo、桌面用 Electron；少量 Rust（资源监控）。【源码：`package.json`；文档：`docs/internals/overview.md`】
- **规模**：TS/TSX 非测试代码约 97 万行（server 24.3 万、web 30.2 万、mobile 15.1 万、desktop 4.4 万、packages 23.0 万，已排除生成代码），测试约 66 万行。【实测】
- **成熟度**：版本 0.1.x；Orchestrator V2 的 PR #2829 从 2026-05-27 开到 2026-10-02 合并，+380,729 / −203,651 行、1,912 个文件；提交极密（2026-10-18 与 10-25 两个周分别 2,621、2,383 个提交，日均约 340–370）；issue 累计 7,928 个、其中 4,431 个创建于 V2 发布之后（2026-10-02 起）。`AGENTS.md` 自述“大多数贡献由 T3 Code 自己产生”，issue 里大量 “Grok / Claude responding on behalf of …” 的自动分诊评论，说明维护高度 agent 化。【GitHub API；PR：https://github.com/pingdotgg/t3code/pull/2829】自述“50 万以上用户”未独立核实。【文档：`AGENTS.md`】
- **支持哪些**：Codex、Claude Code、Cursor、Grok Build、OpenCode（1.x/2.x）、Google Antigravity、fx、Pi、Muse Code、Kiro，加 ACP Registry（Devin、Cline、Kimi、Droid 等）。没有 Hermes / OpenClaw / DeepSeek 的原生适配；Hermes 有人经通用 ACP 在试，目前报初始化超时（#33104，open）。【文档：`README.md`、v0.1.0 发布说明；issue：https://github.com/pingdotgg/t3code/issues/33104】
- **安装**：`curl -fsSL https://t3.codes/install.sh | sh` 后运行 `t3`；macOS `brew install --cask t3-code`；另有 winget、scoop、AUR、nixpkgs、`.deb`、`npx t3@latest`。需要先在本机装好并登录至少一家 Harness（各用各的登录）。【文档：`README.md`】

- **会话持久化：两者并存。** T3 自存规范对话（标准化的 turn item：消息、命令及输出、文件变更、计划、错误…，进 SQLite 投影表）；同时每个 provider 线程存原生指针（`nativeThreadRef`、`nativeConversationHeadRef`、`provider_session_runtime`）用于原生恢复。事件日志只留约 1 天，投影才是真相；原始 provider 帧只进有上限的诊断日志。写路径：命令 → 事件 + 投影 + 回执 + outbox 在同一事务提交 → 之后才由 effect worker 执行外部副作用。【文档：`docs/internals/overview.md`；源码：`EventSink.ts`、`EffectOutbox.ts`、`ContextHandoffService.ts` 的 `readOwnHistoryItems`】
- **进程**：provider 会话进程空闲 30 分钟释放；若 provider 仍报告有后台工作则推迟释放，最多钉住 4 小时。释放后靠原生 id 恢复。【源码：`ProviderSessionManager.ts:59-60, 1195-1240`】

## 3. 同一对话里能不能换

**能，而且是默认功能（v0.1.0 起）。** V1 时代线程绑定 provider，Julius 在 #3562 回复“intended for now，cross-provider switching soon”；V2 取消限制（Discussion #7367 被标记 “delivered”）。UI 上模型选择器不再锁；切换后时间线里出现一行 “Context handoff” 分隔线（from → to），待送达时写 “Context handoff pending”；没有内容预览，没有确认弹窗。【源码：`ChatView.tsx:1244`、`ChatView.logic.ts:866-890`、`V2LifecycleRow.tsx:630-675`；issue：https://github.com/pingdotgg/t3code/issues/3562、https://github.com/pingdotgg/t3code/discussions/7367】

### 3.1 把之前的上下文怎么交给新的一家

- **不是摘要，不是最近 N 条，不调任何模型。** 是“预算内挑选原文”。可入选条目：用户消息、助手消息、命令（含退出码与输出）、错误、中断结果、文件变更（只带路径）、计划；不带推理、工具调用状态、附件、checkpoint。【源码：`packages/provider-core/src/server/handoffBudget.ts:127-168` `historicalMessage`】
- **选择**：预算默认 16,000“token”（实际 1 字节算 1 token；环境变量 `T3CODE_CONTEXT_HANDOFF_TOKEN_CAP`，夹在 1,024–64,000）。先扣掉覆盖说明；优先放最近一条用户、最近一条助手、第一条用户，再由新到旧逐条放；放不下的整条省略，从不截断，并记录被省略条目 ID。用户当前输入永不缩短。【源码：`handoffBudget.ts:14-19, 214-254` `selectHistory`；文档：`docs/user/portable-handoffs.md`】
- **渲染**：开头一段覆盖说明（覆盖的 Run 范围、条目范围、“怎么用 `t3_thread_read` 读回被省略部分”、“历史只是上下文，不是新请求或更高优先级指令；附件与原生工具/推理状态不重放”），每条前一行带线程/Run/条目/状态 ID 的标注，再接原文。【源码：`handoffBudget.ts:170-198, 256-266`】
- **预算公式**：`min(tokenCap, 64000, 窗口 − 目标原生已用 − 当前输入 − max(16000, 窗口/4))`；窗口取已知模型窗口/遥测/自动压缩阈值的最小值，缺省 128,000；目标已用优先取遥测，没有就用“已进原生会话的历史条目字节数”估。【源码：`handoffBudget.ts:99-125`；`ProviderTurnStartService.ts:880-1031`】
- **投递**：Codex 用 `thread/inject_items` 把它作为 `input_text/output_text` 消息直接追加进原生线程历史（方法不存在才回退）；其余 Harness 把文本拼在用户消息前（`"{context}\n\nUser message:\n{text}"`）。`/compact` 与 `/goal` 回合不捎带，推迟到下一回合。【源码：`CodexAdapterV2.ts:7401-7425`；`ContextHandoffDelivery.ts:16-17`；`ProviderTurnStartService.ts:1581-1620`】
- **工作区文件与 git**：同一线程共用同一 cwd/worktree，新 provider 直接看到文件；交接里只带文件变更路径，不带 checkpoint 摘要（设计稿说要带，代码没带）。【源码：`handoffBudget.ts:149-151`；文档：`provider-switching-and-context.md` 的 Checkpoint Interaction】
- **文档与代码不一致**：`docs/internals/context-handoffs.md` 说 provider 交接每条压成 ≤240 字符，但那是 fork 合并回来/侧聊摘要的路径（`summarizeDeltaItem`/`compactText`）；provider 切换走的是上面的全文挑选。用户文档 `portable-handoffs.md` 与代码一致。设计稿还说交接单会被回退标成 `superseded`，代码里 `ContextHandoff.status` 四个构造处全写 `"ready"`。【源码：`ContextHandoffService.ts:107-115, 207-224, 486-562`】

### 3.2 增量与“它看到了哪里”的记账

- 水位现算：`lastDeliveredRunForProviderThread` = 目标 provider 线程上最后一个“已送达”的 Run（completed，或有对应 provider turn）。覆盖范围 = 序号在（该 Run，最新可交接 Run]且 ≥ `contextBoundary` 的 Run；`isHandoffSourceRun` = completed / failed / interrupted / 已开始的 cancelled。【源码：`Orchestrator.ts:1103-1124`、`2193-2215`；同样的选择谓词在 `dispatchMessage` 里又写了一份 `7440-7520`】
- 目标没有原生线程 → `full_thread_summary`（名字叫 summary，用的仍是同一套挑选，只是范围是全量）；否则 `delta_since_target_last_seen`。【源码：`Orchestrator.ts:2212-2219`】
- 已送达条目 ID 来自同一原生线程上已落定的交接单的 `delivery.itemIds`，交付时再用 `seen` 去重。【源码：`ProviderTurnStartService.ts:915-927`；`ContextHandoffDelivery.ts:55-62`】
- 能力闸：目标要声明 `canConsumeHandoffSummaries`、`acceptsSyntheticUserContext`、`supportsDeltaHandoff` / `supportsFullThreadHandoff`，否则切换在派发时被拒。【源码：`CommandPolicy.ts:335-377`】

### 3.3 回到原来那家

`ProviderTurnStartService.start`：先 `resumeThread` 续原生会话；成功后用预算判断增量交接放不放得下，放得下就在原会话继续；放不下、恢复失败、或存在“送达不确定”标记，就开新原生会话（`forceNewNativeThread`），挂一份 `full_thread_summary` 恢复交接，写 `context-handoff.updated` / `context-transfer.updated` 事件——但不产生时间线条目（据 #28178 的代码分析；我只确认了这里只写事件，没有逐条核对时间线渲染路径）。唯一不回退的情形：原生线程正被别的进程占用（`ProviderAdapterThreadInUseError`），直接失败以免分叉对话。【源码：`ProviderTurnStartService.ts:1257-1412`；`ProviderAdapter.ts:255-271`】

### 3.4 同一家里换模型

适配器 `planSelectionTransition`：Codex、Claude、Cursor、Muse、OpenCode、Pi 都返回“下一回合生效”，原生会话照续；ACP 要求会话声明能切模型否则拒绝。`decideProviderSessionTransition` 五种结果：`reuse` / `switch_model_in_session` / `restart_and_resume`（实例、运行模式或工作区变了但 continuation 键相同，仍原生续）/ `create_with_handoff`（driver 或 continuation 键不同）/ `reject`。时间线只在模型或强度变化时插一行“A → B”。Claude 多账号只有 `CLAUDE_CONFIG_DIR` 相同才能原生续，否则走交接。【源码：`ProviderSessionTransitionPolicy.ts:32-88`、`selectionTransition.ts`、`modelSwitch.ts`；文档：`docs/user/providers-claude.md`】

### 3.5 不能时怎么限制

仅对未声明 `supportsProviderSwitchingViaHandoff` 的线程，模型选择器提示 “Start a new chat to switch providers”。现在主要适配器（Claude、Codex、OpenCode、Muse、Cursor、ACP）都声明 true，所以基本不触发。【源码：`ChatView.logic.ts:866-890`；各 adapter 的 capabilities】

### 3.6 官方的另一条路：`delegate_task`

agent 通过 T3 的 MCP 在任意 provider 开子线程；子线程只收到任务提示（可附角色指令），不复制父历史，结果回传、父线程被唤醒。发布说明把它列为组合多家 Harness 的推荐方式。【文档：`docs/orchestration-v2/orchestrator-mcp-server.md`、v0.1.0 发布说明】

## 4. 逐条对照：它不解决、或用极简办法绕过的

| 问题 | T3 的做法（来源） | 评价 |
|---|---|---|
| **送达确认** | 每份交接单带 `delivery{nativeThreadId, status: pending→injected\|inline, itemIds, omittedItemIds}`。先落 pending，再注入/随提示发出，provider 接受后落 injected（Codex 以 `thread/inject_items` 成功为准）或 inline（其余以 `startTurn` 没报错为准）。**不核对原生历史里是否真有**：`readThreadSnapshot` 只在各 adapter 内部定义，编排层未发现调用点。落盘失败或注入模糊失败，pending 残留，视为“送达不确定”：不重发，下一回合直接换新原生会话。只有 provider 在读提示之前就拒绝的 5 个已知错误标签（全是 Claude 的）会把 pending 撤回。【源码：`ContextHandoffDelivery.ts:112-131`；`ProviderTurnStartService.ts:106-116, 1257-1280, 1618-1656`；grep 无调用点】 | 最小的“前后记账 + 失败关闭”。教训：标签列表不全，MCP 注册超时曾让它丢掉一个 55 万 token 的原生会话（#22198，标签后来补进去了）。 |
| **重复注入** | `alreadyDeliveredItemIds` + `seen` 集合；pending 永不重发（测试 “does not redeliver after ambiguous injection failure”）。【源码：`ContextHandoffDelivery.ts:55-62`；`ContextHandoffBudget.test.ts:579-604`】 | 靠“宁可不发”保证不重复，代价是丢原生会话。 |
| **原生 `/clear`** | 不探测，改为**接管**：T3 的 `/clear` = “下一条消息开新原生会话，之前消息仍可见”，Run 带 `freshContext`，`contextBoundaryOrdinal` 之前的 Run 以后永不再交给任何 provider；有 T3 `/clear` 时把 provider 自带的 `/clear` 从斜杠菜单藏起。更早把 `/clear` 透传给 Claude 时出过严重 bug：Claude 在进程内换了新 session id，T3 仍存旧 id，重启后“复活”清空前的 70 万 token 会话。【源码：`Orchestrator.ts:1026-1047`；`useComposerMenuItems.ts:265, 298-302`；`ChatView.tsx:2500`；文档：`docs/user/composer.md`；issue：#19356、#20078、#24152（open）】 | 把“未知”变成“我们自己定义的命令”，省掉整类推断；但接管后必须同步更新“当前原生会话 id”。 |

| **密钥脱敏** | **交接内容不脱敏。** 命令输入与输出原样入选（`Command: …\nExit code: …\n<output>`）。脱敏只见于诊断日志（`[REDACTED]`）与失败信息（Bearer/`sk-` 等正则）。另有 “secret request” 卡片让 agent 索要密钥时不进对话。open 提案 #24790：把 T3 自己注入子进程环境的秘密值从持久化工具输出里精确替换。【源码：`handoffBudget.ts:136-142`；`CodexAdapterV2.ts:1530-1564`；`failure.ts:199-254`；文档：`docs/user/secrets.md`；issue：#24790】 | 与我们“排除法（Hub 交给任何绑定的值）”同构，但它还没做。 |
| **交接超出对方上下文窗口** | 预算见 3.1。续上的原生线程放不下 → 开新原生会话带有界历史（“不用手动 compact”）；连新会话也放不下用户输入 → 报错，不截断用户消息。这个预算机制是它最大的 bug 源（27 个 issue 含 “Insufficient context allowance”；#19875、#23275、#15997 都是“每条消息都失败、`/compact` 也救不了”的卡死）。【源码：`ProviderTurnStartService.ts:1286-1331`；issue：#19875、#23275、#15997、#22636、#23142；PR：https://github.com/pingdotgg/t3code/pull/19414（open）】 | 我们“永不因历史长度 blocked、降档或只发原话”的不变量被它的反例验证。 |

## 5. 并行与隔离

- **多线程并行**：一个服务里多线程并行，每线程独立服务端队列（持久，重启后保序）、独立 Run 与 provider 会话；侧栏按 working / waiting / limited / failed 排序；可对运行中的线程“引导（steer）”或“排队”。【文档：v0.1.0 发布说明、`docs/user/thread-sidebar.md`】
- **worktree**：一等公民。“New worktree”为线程建独立 worktree（在 T3 home 的 `worktrees/` 或自定义路径），macOS 有 APFS 写时复制的“快速检出”（beta），自动清理按天数/结算/删线程；`withWorkspaceLease` 让清理与 turn 启动互斥；worktree 目录缺失时 turn 启动会按分支重建。Agent 可经 MCP `t3_worktree_handoff` 把运行中的线程迁到 worktree（与 provider 交接无关，但同名，也有一批 bug，如 #22971）。【源码：`ProviderTurnStartService.ts:166-227, 1733-1739`；文档：`docs/user/project-settings.md`、`thread-sidebar.md`、`faq.md`】
- **权限审批**：每线程四档（Supervised / Auto-accept edits / Auto / Full access），**默认 Full access**；各家只提供它自己原生强制的档位，T3 不模仿缺失的档位；管理员策略可设上限。审批在对话里：时间线行（`TimelinePendingApprovalRow.tsx`）+ 输入框上方操作按钮（`ComposerPendingApprovalActions.tsx`），子 agent 的审批冒泡到父线程（`ChildThreadApprovals.tsx`）；agent 不能批准自己的审批。切换 provider 时遗留的问题卡片会失配（#31029）。【文档：`docs/user/permission-modes.md`、`docs/internals/adding-a-provider.md`；源码：上述组件；issue：#31029】
- **多账号**：FAQ 明说 T3 不是管理一堆账号的地方，若做自动切换怕触发 ToS，账号池建议放在 T3 之外（自托管代理）。社区提的“自动备援到另一个实例”PR #3482 因 V2 重写无法 rebase 而关闭（维护者注明这不是对改动本身的否定）。FAQ 的立场与我们“不隐式改换 Harness/Provider”一致。【文档：`faq.md`；PR：https://github.com/pingdotgg/t3code/pull/3482】

## 8. 对我们的启示（直说）

### 8.1 总判断

- **是的，我们有几处做重了，但 T3 的反例同样清楚：它省掉的那几块恰好是它用户受伤最多的地方。** 所以建议“选择性减法”，不是整体向 T3 看齐。
- 证据：同口径我们的量级约是 T3 的 2–4 倍（第 6 节）；T3 把同一件事压在约 2.3k 行里、有大量用户在用，说明骨架可以很小。但我读到的切换相关 issue（几十条，非全量统计）大多集中在预算、待定标记、取消回合的覆盖、可见性、`/clear` 的会话指针——也就是我们已经逐格建模的那些地方。
- 两个前提要摆在桌面上：T3 的维护能力远大于我们（476 位贡献者、日均数百提交、agent 化分诊），它能承受复杂度，我们未必；T3 的官方立场是“换 provider 有损、不推荐”，而对我们这是核心卖点，质量门槛要比它高。

### 8.2 T3 比我们简单且够用，可以照抄

1. **内容 = 原文挑选 + 覆盖说明 + 指针。** 不叙述化、不分档、不调模型。够用的证据：自称 50 万用户的产品（未核实），抱怨集中在“丢内容”（预算/过滤 bug）而不是“内容写得不好”（标题级检索未发现后一类）。叙述化与多档位、框架约定是质量投资，不是正确性必需（见 8.5 第 4 条）。
2. **水位现算，不存。** “目标线程最后被送达的 Run 序号” + 交接单上的已送达条目 ID，再加 Hub 级边界（`freshContext`）代替清空下限。没有纪元、四状态、状态×事件表。代价：现算依赖 Run / attempt / provider turn 记录齐全、谓词写对（#34009 就是谓词漏了一种终态，整轮静默丢失），而且 T3 的 `/clear` 之后会话指针错位（#19356 系列）正是“没有显式纪元”的那类问题【推断】。
3. **`/clear` 由 Hub 接管**（对所有 Harness，藏起 provider 自带的）。这把“探测原生清空”整类未知变成“我们自己定义的命令”。注意：T3 的 #19356 / #24152 说明接管后必须同步更新“当前原生会话 id”，否则重启后复活旧会话——我们的“绑定谱系/纪元”在这点上更明确，别丢。
4. **指针 + 拉取。** 覆盖说明里告诉 agent 怎么读回被省略部分，预算就不必“尽量塞满”，降级路径变简单。我们把它放在 v1.1/v1.2；T3 的经验是可用，但有三个坑：读回视图要带游标和终止条件（#27072），默认不含推理项（#23881），MCP 凭据要随绑定重发（#16565）。
5. **Codex 的 `thread/inject_items`。** 把交接作为原生历史追加，用户消息保持逐字节不变，也不依赖回合，自然解决“命令回合不捎带”。仅 Codex 有；只有“方法不存在”才能安全回退，其余失败按“模糊”处理。我们的 Codex Driver 如果走 app-server，值得单独评估。
6. **静态能力声明 + 版本公告**取代运行时探针门控；handoff 的用户可见配置只有一个环境变量。
7. **测试**：录制真实 provider 转录、回放到真实编排器和 SQLite，只替换传输层。与我们的测试原则一致，可借它的录制脚本思路。

### 8.3 我们多做、T3 完全没有、用户似乎也没人提（候选可砍）

| 机制 | T3 | 我的看法 |
|---|---|---|
| 同意 + 厂商识别（按 Driver 解析端点的厂商键、`vendor_changed`、撤回） | 无；标题检索 0 条 | 可大幅降级，但不建议归零：T3 的 provider 都是用户自己订阅的主流服务，我们的集合含 DeepSeek 与可能的第三方路由，数据出境敏感度不同。建议降成“目标 Harness 名 + 首次使用一次性提示 + 日志”，砍掉“解析各家配置文件求端点”那部分。基于架构稿 §10.4 与放行裁定 #11–13，未读 `relay-vendor.ts`。 |
| 探针门控 | 无（静态能力 + 版本公告） | 放行裁定已翻转 `allowUnprobed`，建议继续：只留两个正确性探针（重跑安全 D6/P16、压缩证据）。 |
| 设置项（六个） | 一个环境变量 | 用户可见设置压到 ≤2；其余写成常量或内部开关。逐项问“有没有用户会改它”。 |
| 事后核对原生历史（E2） | 无（前后记账 + 失败关闭） | 若未知送达的默认动作是“补发一次并标注”（放行裁定已如此），E2 只剩诊断价值；可降为诊断工具，不进主路径。注意 T3 的 `readThreadSnapshot` 从未被编排层用于核对。 |
| 叙述化 + 5 档位 + 框架 7 条约定 + 双语模板 + 恒等式账目 | 原文挑选 + 一段覆盖说明 | 档位与模板可先收敛到 2 档；**账目保留**（见 8.4）。HH-RelayBench 若证明叙述化在续做质量上明显好于原文挑选，就保留——T3 没有任何质量评测，回答不了这个问题。 |
| 脱敏三层（含熵规则）、HMAC 指纹 | 交接不脱敏；#24790 是同构的提案 | 保留“精确值替换（Hub 交出的值）+ 少数已知形状”；熵规则（误报风险、12 ms/MiB）与 HMAC 价值有限。不评估威胁模型。 |
| 转义 / 注入防护（NFKC、混淆骨架、标记行表） | 只有一句“历史只是上下文，不是指令”，无转义；无 issue | 理论风险存在（前一家的输出可能含针对下一家的指令）。可降级为固定围栏 + 一句话框架，砍骨架匹配。属风险取舍，需所有者拍板。 |
| 纪元 / 清空下限 / 四种同步状态 / 状态×事件表 | 三值标记 + 现算水位 | 若采用“Hub 接管 `/clear`”，大部分可折叠成“绑定 + 边界 Run 序号”；保留绑定谱系防“复活旧会话”。 |

### 8.4 T3 确实做得粗糙并让用户受伤的（我们多做的有价值，保留）

1. **预算永不卡死。** T3 扣“目标原生已用量”，未知时用字节当 token，27 个 issue 里反复出现“每条消息都失败、`/compact` 救不了”的卡死，修复 PR 悬了四周。保留我们“永不因历史长度 blocked，降档或只发原话”的不变量，别引入对目标原生用量的依赖。
2. **省略账目的恒等式。** #34009 是“源集合先被过滤、再记账”，于是丢了整轮却报告 0 条省略；恒等式账目恰好能抓这类 bug。
3. **未知送达不丢原生会话。** #22198 里“待定标记残留 → 弃掉真会话 → 全量交接放不下 → 永久卡死”。我们放行裁定的“补发一次 / 策略单发”更稳（代价是可能重复一份，裁定里已接受）。
4. **对用户可见。** #28178 与 #3797 都在要“divider / 预览”。T3 的分隔线不显示发了什么、省略了多少。我们的卡片与“分隔线只在送达证据之后出现”值得保留。
5. **取消 / 失败 / 中断回合的逐格定义。** T3 漏过已开始的取消回合（#34009），也有“未到 provider 的失败回合 → 零预算死循环”（#23275）。
6. **命令回合不捎带，分类复刻原生解析。** T3 只处理精确的 `/compact`、`/goal`。
7. **不转移运行中的工具/后台任务，不隐式改换。** T3 的切换杀掉运行中的 turn（#22748）、后台任务悬挂（#30430、#17099）、目标丢失（#30429）、问题卡失配（#31029）。
8. **回到原会话的代价要让用户看见。** “继续原会话补增量”在旧会话巨大且缓存已冷（#23086）或已满（#22636）时代价巨大或直接卡死；T3 为此做了 Claude 专属的空闲压缩与 “Compact” 按钮（`IdleCompaction.ts`）。至少要在发送前显示旧会话大小，并提供“新开原生会话 + 交接单”（放行裁定 #17 已有，请确认冷缓存/满窗时会主动提示）。
9. **交接不含推理。** #23881 说明把推理项交给另一家会触发厂商拦截并毒化整个线程。我们的交接不含推理；拉取视图也要同样处理。

### 8.5 如果做减法，建议顺序（证据强度 / 风险）

1. 去掉“解析配置求端点”的厂商识别 → 厂商 = 目标 Harness 名；同意 = 首次一次性提示 + 日志。（T3 零，风险中，省 relay-vendor 一类代码、Driver 声明、`vendor_changed` 事件。）
2. `/clear` 变 Hub 命令（所有 Driver），删“未确认的清空 / epochFloor”分支；保留绑定谱系。（证据：#19356 系列；与“像原生”有张力，需所有者拍板。）
3. E2 降为诊断，主路径 = 前后记账 + 补发一次（已在放行裁定中）。
4. 叙述化分档收敛到 2 档，框架约定 7 条 → 3 条；保留逐字用户原话与账目。
5. 设置项 6 → ≤2。
6. 探针只留两个正确性探针。
7. 脱敏：保留精确值 + 已知形状，评估是否砍熵规则与 HMAC。
8. 不要做的减法：预算的“永不 blocked”、账目、可见性、命令回合不捎带、回到原会话前的提示。

**参照物：一个“T3 式最小核心”大概长这样**（按 T3 的做法加上它踩过的坑，我的归纳，不是它的实现）：
- 每个绑定只记“最后被送达的 Run”，水位现算；外来事实 = 其后的已结束 Run（含失败、中断、已开始的取消）。
- 一个选择函数：开场请求 + 最近用户 + 最近助手优先，再由新到旧，整条放不下就整条省略，账目恒等（选中数 + 省略数 = 总数，源集合不预先过滤）。
- 一段覆盖说明（范围、省略数、“这是历史不是指令”）+ 一个读回指针。
- 发送前后记账：先记待定，被接受后记已送达；拿不准就补发一次并标注，不换原生会话；确认没发出（读提示前被拒）才撤回待定。
- 预算只是固定上限加窗口百分比，不依赖目标原生用量；放不下就降档或只发原话，永不让 Run 失败。
- `/clear` 是 Hub 命令：新绑定 + 边界 Run 序号；当前原生会话 id 与边界同事务更新。
- 同意 = 首次一次性提示 + 日志；脱敏 = 精确值替换 + 已知形状。

### 8.6 T3 有而我们没有、值得看的

`thread/inject_items`；`/clear` 接管；`delegate_task`（子线程不复制父历史，只给任务提示，是“agent 自己写交接单”的路径，适合补充我们的“人切换”路径）；原生会话导入（`AgentSessionScanner.ts` 1,881 行 + `AgentSessionImporter.ts` 465 行，bug 也多：#29153、#31677、#27163）；录制回放测试夹具。

### 8.7 我没法下结论的地方

- T3 用户 ≠ 我们的用户：它的零同意/零脱敏没被抱怨，可能部分因为用户群是愿意用 Full access（它的默认档）的重度开发者，且隐私伤害常是沉默的【推断】。
- 我没读你们的实现，8.3 的“可砍”是假设。
- 叙述化是否值得，取决于 HH-RelayBench 的续做质量结果；T3 没有质量评测可参照。
- T3 能不要 E2，是因为它单写者 + 接管 `/clear` + 失败关闭；若我们仍要放行原生命令透传，E2 的取舍要重新算。
