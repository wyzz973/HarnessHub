## 看到的问题

- **被拒绝的改动，两家的状态词不一样。** 同样是用户拒绝了审批，Codex 的那条改动记为“已拒绝”，Claude Code 的记为“失败”（它在被拒后把这次工具调用报成了出错）。审批条目本身两家都记对了。要在归一里补一条：审批被拒的那个动作，状态是“已拒绝”，之后 Harness 再报出错也不改回去。
- **启动的次序。** 应用先打开对话库（这时已经备份并升级），之后的检查（锁目录的权限）失败时，启动失败而库已经升级。升级本身没问题，但对真实数据这是最不想要的状态。已改（`465bf86`）：不依赖所有权的检查挪到打开对话库之前；开库之后的步骤失败时，报错里说明对话库已升级、备份在哪。

- **同一个版本号下表结构变过。** 试用数据根是今天早些时候由较早的提交升到 v14 的；之后“全文索引回填”给一张表加了一列，版本号没变。现在的构建打开那个根，后台回填一跑就出 SQLite 错误，整个存储进入失败状态，服务起不来，报错只有一个错误码。4317 的数据是 v12，会由最终的构建一次升到位，不受影响。在修：派生数据的后台工作失败不拖垮存储；v14 的表结构写指纹、开库时核对（以后改表结构必须升版本并写迁移）；启动失败要说原因。
- **照文档恢复备份之后起不来。** 把试用数据根恢复到升级前的备份再启动，被拒绝：恢复回来的对话库的所有权代数是备份那一刻的值，比管理库记住的小。主分支的旧构建有同一条检查，所以升级之后新构建只要启动过两次以上，回退就会卡在这里。在修：做一条回退命令（把现在的库挪开、复制备份、把代数接上），并用旧构建真的打开来演练。
- **输入框的一处疑点。** 换 Harness 之后马上输入，输入框显示是空的，再输入一遍后发出去的消息里这句话出现了两遍。可能是自动化输入的时机造成的，先复现。
