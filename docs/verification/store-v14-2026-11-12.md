## 回退（提交 `0489806`）

回退命令 `pnpm sessions restore-backup --data-dir <数据根>` 在试用数据根上真的跑了一遍：

- 先停掉 4318 上的试用服务。命令拿到所有者锁，把现在的库（v14，12 个回合）复制成 `backups/gateway-v14-set-aside-<时间>.sqlite`，把升级前的备份复制回来，只改一个数：所有权代数从 3 改成 10（对话库、管理库、能力库三处记着的最大值）。备份留在原处，没有删任何文件。
- 再用新构建启动：照常再次备份并升级（先前那份备份改名 `…-earlier-<时间>` 保留，不覆盖），服务起来，页面打开那个对话是 11 个回合。回退之后新增的那个回合（第 12 个）不在恢复后的库里，在被留下的那份 v14 库里——这是命令输出里明说的后果。

“恢复之后用旧构建启动”这一步在试用数据根上做不了（它的备份是 v13，没有哪个发布过的构建读 v13）；那一步由合成测试用主分支 `5c5f12f` 单独构建出来的旧构建演练：照旧文档手工恢复，旧构建的命令行与网页服务都被拒；用回退命令恢复后，旧构建列出同样的对话、内容与升级前相等、能接着发回合。

一处观察：恢复之后在原来那个浏览器标签页里打开这个对话，页面把输入框里记着的选择（之前选的 Codex）重新应用了一次，对话的 Harness 从恢复出来的 Claude Code 又换成了 Codex。这是主分支上就有的做法（每个标签页记着每个对话输入框里的草稿与选择，打开时与服务端不一致就应用），只在“服务端回到过去”时才看得见。没有改。

## 看到的问题

- **被拒绝的改动，两家的状态词不一样。** 同样是用户拒绝了审批，Codex 的那条改动记为“已拒绝”，Claude Code 的记为“失败”（它在被拒后把这次工具调用报成了出错）。审批条目本身两家都记对了。已修并在真机上确认（`688134c`）：审批被拒的那个动作记“已拒绝”，之后 Harness 再报出错也不改回去。
- **启动的次序。** 应用先打开对话库（这时已经备份并升级），之后的检查（锁目录的权限）失败时，启动失败而库已经升级。升级本身没问题，但对真实数据这是最不想要的状态。已改（`06a0317`）：不依赖所有权的检查挪到打开对话库之前；开库之后的步骤失败时，报错里说明对话库已升级、备份在哪。

- **同一个版本号下表结构变过。** 试用数据根是今天早些时候由较早的提交升到 v14 的；之后“全文索引回填”给一张表加了一列，版本号没变。现在的构建打开那个根，后台回填一跑就出 SQLite 错误，整个存储进入失败状态，服务起不来，报错只有一个错误码。4317 的数据是 v12，会由最终的构建一次升到位，不受影响。在修：派生数据的后台工作失败不拖垮存储；v14 的表结构写指纹、开库时核对（以后改表结构必须升版本并写迁移）；启动失败要说原因。
- **照文档恢复备份之后起不来。** 把试用数据根恢复到升级前的备份再启动，被拒绝：恢复回来的对话库的所有权代数是备份那一刻的值，比管理库记住的小。主分支的旧构建有同一条检查，所以升级之后新构建只要启动过两次以上，回退就会卡在这里。已修（`0489806`）：回退命令，见上面“回退”一节；记着代数的库有三个（对话库、管理库、能力库）。
- **输入框的一处疑点。** 换 Harness 之后马上输入，输入框显示是空的，再输入一遍后发出去的消息里这句话出现了两遍。可能是自动化输入的时机造成的，先复现。
