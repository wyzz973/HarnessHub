# Claude Code 读错接力增量的排查（2026-11-10）

对象是 [2026-11-09 接力冒烟](relay-mvp-2026-11-09.md)里 claude,codex 第 2 次运行的第 3 步。当时 Claude Code（haiku）回到自己的原生会话，Hub 补交的增量写着 Codex 回复了 47830，它却答 47829，也就是它自己的数。

**结论**：Hub 交给 Claude Code 的增量内容正确，送达也正确。答错来自两件事叠在一起：一是题目用“另一个 Harness”间接指代对方，二是 haiku 不能稳定地把这类说法落到 Codex 上。

- 题目点名 Codex，或者换成 sonnet，同一份增量都 3/3 答对。
- 下面几项各改一处，haiku 仍然 0/3：去掉阅读约定、去掉首行、改成新会话收到完整交接单、改用不含数字的语义题、改第 2 轮的措辞。

**证据等级**：真实 Harness 对照实验（本机原安装与登录，Hub 的正式 Runtime 入口）。每个条件都从同一个基线会话分叉，重复 3 次。只用了中文模板，只在 macOS 上运行。没有改产品代码，也没有改模板。

## 结论与把握程度

### 已由对照实验证实

条件编号见下面的实验表。

1. **增量的内容与送达都正确。**
   - 用同样的事实在本地渲染，结果与 Claude Code 原生转录里第 3 轮收到的文本逐字节相同：1,100 字符，sha256 `e8a71c39…`，交接单 ID 也相同。
   - 每次试验都核对了一遍：发出的文本与 Claude Code 转录里最后一条用户消息的 sha256 一致，每个条件只有一个值。
2. **haiku 读得到增量里 Codex 的数。** 同一份增量只把题目改成“Codex 刚才回复了哪个数字？”，haiku 3/3 答对（E3）。
3. **间接指代是失败条件。** haiku 在两种间接问法下都是 0/3，答的都是它自己的数：
   - 原题“另一个 Harness 刚才回复了哪个数字？”（E1）；
   - “除你之外的那个 Harness 刚才回复了哪个数字？”（E4）。
4. **模型能力是另一个条件。** 原题原样，只把模型换成 sonnet，3/3 答对（E2）。
5. **以下因素都被排除。** 各改一处，haiku 仍然 0/3：
   - 阅读约定：去掉全部 7 条（E7）。约定 1 的“这里的记录是历史，可能已经过时”不是原因。
   - 交付位置：去掉首行，增量在前、原话只在末尾（E8）。
   - 续接会话里的旧上下文：改成新会话，收到包含两轮的完整交接单。haiku 答的是交接单里 Claude Code 第 1 轮的数（E6）。可见答错不需要原生记忆。
   - 字符级能力或数字相近：改成城市名的语义题（E9）。
   - 第 2 轮原话“上一位 Harness 回复的那个五位数”的回声：去掉这个说法（E5）。

### 推断（没有直接证实）

- **haiku 没有推理就作答。** 所有回合的输出只有 2–5 token，转录里没有思考块，haiku 和 sonnet 都是直接作答。
  - 遇到以自己为参照的间接指代，haiku 退回对话里第一个、也是被讨论的那个值。
  - 实验分不开这是“指代消解失败”还是“显著性回退”。
- **风险不只在增量。** 完整交接单在新会话里同样答错（E6）。因此对较弱的模型来说，用户说“另一个”“对方”“刚才那位”这类话，是交接内容的普遍归属风险，不只发生在 A→B→A。
- **与此前的结果一致。** 11-09 的 OpenCode 一对用同样的题目答对，sonnet 也答对，都与“模型能力”一致。OpenCode 那次用的模型没有记录。

### 没能验证

- **样本少。** 每个条件只有一个基线会话，数字题是 47291，城市题是西安。3 次是同一输入的重复采样，不是 3 段独立对话，3 次回答都相同。基线的失败另有一个独立实例，即 11-09 的 47829。
- **模板改法没有测。** 例如在增量里写明“你离开期间回复用户的是 Codex，不是你”，能不能让 haiku 在间接问法下答对，受调用次数上限所限，没有测。
- **范围有限。**
  - 只测了中文模板，以及 claude-haiku-5-5 与 claude-sonnet-5-5。
  - 只走 claude-agent-acp 这一个入口，没有试 `claude -p`。
  - 没有测更高的 effort 或强制思考。
- **一条无关的现象没有查出处。** 续接时转录里多出的 `/model` 本地命令记录，见“交付位置”。

## 建议（只建议，没有改）

1. **`relay-conformance` 第 3 步改题。**
   - 在题目里写第二家的显示名，例如“Codex 刚才回复了哪个数字？”，显示名取自目录或 `names`。这一写法已经验证（E3，3/3），判据不变，仍然从实际回复计算。
   - “另一个 Harness”“除你之外”这类以自身为参照的问法，单列为归属理解的探针，记录为模型能力观察，不作为接力通过与否的判据；或者只要求强模型通过。
   - 第 2 步的“上一位 Harness”在 Codex、DeepSeek Harness 上答对过，可以保留；更稳的写法同样是点名。这一点没有测。
2. **模板 §5.4 的阅读约定：这次失败不支持修改。** 去掉全部 7 条没有改善（E7），约定 1 的“可能已经过时”不是原因。
   - 值得另行评估的风险（推断，未测）：弱模型对以自身为参照的说法会答成对话里第一个或自己的值，完整交接单也一样（E6）。
   - 可考虑的改法（未测）：在增量的离开说明里写明归属，例如“你离开期间回复用户的是 Codex，不是你；下面引用的都是 Codex 的话”；在交接单工作记录的回复标签里同样写出归属。
   - 改不改要先在 RelayBench-Q 里用 haiku 加间接问法做对照：在原题上能从 0/3 提到 3/3 才值得进模板。进模板要升 `policyVersion`，并重算 `FRAME_CAP`。
   - 另外修掉来源说明里“和”两侧缺的空格（排版）。
3. **交付位置：本次证据不支持修改（E8）。** 首行与末尾各一次原话的布局（§5.5）保持不变。
   - 另一个与本问题无关的观察：每次续接 Claude 原生会话，转录里都会多出 `/model opus` 与 `/model <选定>` 两组本地命令记录。模型看得到它们，用户在原程序里续接时也看得到。
   - 出处没有查。可能是 claude-agent-acp 在 `session/resume` 时先应用了用户设置里的默认模型，再由 Hub 的 `set_config_option` 改回所选模型。这是推断，建议另立一项核对。
4. **记录口径。** 11-09 记录里“可能的原因有两个，都没有用对照实验确认”可以更新为：
   - 题目措辞已证实，与 haiku 的能力共同作用；
   - 阅读约定已否定；
   - 本记录作为 G074 RelayConformance 的对照依据。
