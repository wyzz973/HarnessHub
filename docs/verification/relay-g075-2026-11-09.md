# 存储优化前置片（G075）的合成验证（2026-11-09）

对象是 [ADR-055](../decisions/0055-relay-and-context-scheduling.md) 的存储优化前置片 G075，范围见[终稿](../proposals/relay/relay-architecture.md)第 11.2 节与第 17 节，存储约定写在[存储与事件契约](../contracts/storage-events.md) R0。

**证据等级**：代码完成，合成测试通过，参考机上实测达到性能目标。没有运行任何真实 Harness，只在 macOS 上运行。业务库仍是 v12，表结构与快照格式都不变。

## 环境

- 分支：`cc/relay-design`，代码随本记录同一提交；改动前的对照点是 `6ed6901`。
- 参考机：Apple M5 Pro，64 GiB 内存，macOS 27.0.1；Node 26.13.0（内置 SQLite 3.54.0），pnpm 10.12.3。
- 测试数据：只用临时目录与进程内的零延迟假 Harness，结束后删除；没有碰 4317 服务与任何 `data/` 目录。

## 改了什么

终稿列了五项，这次做了前三项与第四项的内存部分，其余按计划推迟：

1. **提交前不再重读**（`runtime.ts`）：Runtime 记住每个 Session 最后读到或提交得到的 version，直接用它做 CAS。有人绕过 Runtime 经 Store 提交过时，Store 在执行 mutate 之前就报 VERSION_CONFLICT；Runtime 这时先读一次再提交，mutate 最多执行一次，所以这不是无依据的重试。
2. **按 version 缓存已校验的快照**（新文件 `snapshot-cache.ts`，接进 `sqlite-store.ts`）：
   - 缓存的键是 (version, lastSeq)。读取时，只有 SQLite 行上的两项与缓存项完全一致才命中，否则丢掉该项按未命中处理。
   - 按持久化字节计的 LRU，上限 96 MiB；只在 COMMIT 成功之后放入，列表读取不放入。
   - 别的连接提交过（`PRAGMA data_version` 变化）、存储失败、所有者丢失或关闭时清空；迁移与恢复绕过缓存。
   - 同一版本由所有读者共享，所以 Store 返回的快照深冻结，原地修改会抛 TypeError。`src` 里没有原地修改快照的代码。
3. **不重复解析未变的终态 Run**（`state.ts`）：事务里，新快照中与当前快照同一位置、同一个冻结对象、由 `publicRun` 生成且已终结的 Run 原样保留，`assertSessionTransition` 对同一对象直接放行。其余部分，以及跨 Run、消息、切换、命令的关系校验，照常全量执行。
4. **事件字节计数，只做了内存部分**：日志字节随每次提交累计，缓存未命中时用一次 `SUM(octet_length(...))` 重算，32 MiB 上限仍按字节守住。持久的计数列需要 DDL，并入 G066（v13）。
5. **finalize 复用 prePlan 的快照**：没有做，留给 G072。

长度查询从 `length(CAST(snapshot AS BLOB))` 改成结果相同的 `octet_length`，不必把 8 MiB 的内容读出来。`octet_length` 从 SQLite 3.43 起提供。

## 性能

计划的验收条件是“8 MiB 时受理→派发 p95 ≤400 ms 写进验证记录”。测量走正式的 `SessionRuntime` 与真实的 `SqliteSessionStore`。Harness 是进程内的零延迟假实现，画法同 [R6 第 2.6.4 节](../proposals/relay/round1/r6-performance-caching.md)，所以只计 Hub 自己的工作。每个会话先写入 236 个已结束的回合，使快照接近 8 MiB，再连续发 20 条；15 个会话共 300 个样本。

正式入口（CI 里这一条只断言次数；设了 `G075_SESSIONS` 才断言 p95 ≤400 ms）：

```bash
G075_SESSIONS=15 node --test dist/tests/performance/session-store-commit.test.js
```

| 本提交，15 个会话共 300 个样本 | 结果 |
|---|---|
| 快照大小 | 8,343,242 B（7.96 MiB） |
| 受理→派发 p50 / p95 / 最大 | 255.7 / 281.7 / 378.7 ms |
| `send()` 返回（受理提交）p50 | 38.0 ms |
| 整个回合 p50 / p95 | 407.9 / 447.5 ms |
| 断言 | 通过，p95 ≤400 ms；每回合的提交、load 与解析次数都等于基准 |

改动前后的对照用同一画像的测量脚本 `bench-g075.mjs`，分别对 `6ed6901` 与本改动的构建产物各跑 300 个样本。脚本放在会话的临时目录，没有入库：

| 每回合（快照约 7.96 MiB） | 改动前 `6ed6901` | 改动后 |
|---|---|---|
| 受理→派发 p50 / p95 / 最大 | 959.0 / 1078.2 / 1785.5 ms | 263.8 / 297.8 / 309.6 ms |
| `send()` 返回 p50 / p95 | 168.1 / 188.7 ms | 39.3 / 44.8 ms |
| 整个回合 p50 / p95 | 1577.3 / 1752.9 ms | 421.5 / 473.1 ms |
| 派发前的提交 / load | 7 / 20 | 7 / 13 |
| 整个回合的提交 / load | 11 / 34 | 11 / 23 |

- 改动前，每次 load 与每次提交都要重读并校验整份快照，每回合 45 次；改动后，回合里的整份重读为 0 次（缓存未命中为 0）。
- 缓存上限降到 32 MiB 时 p95 为 309.2 ms，与 96 MiB 相近：单个会话连续发言时，缓存只需要放下当前会话。
- 去掉第 3 项、让终态 Run 照旧逐个解析时，p95 为 348.2 ms（100 个样本）。

计划用例与测试的对应：

| 用例 | 文件 | 测试 |
|---|---|---|
| G075-C01 8 MiB 快照上受理→派发，逐回合计数 | `tests/performance/session-store-commit.test.ts` | 每回合断言：派发前 7 次提交、13 次 load；整个回合 11 次提交、23 次 load、11 条事件；重新解析与事件读取都是 0 次。参考测量另断言 p95 ≤400 ms |
| G075-C02 version 变化即失效；并发事务不读到旧快照 | `tests/integration/snapshot-cache.test.ts` | 7 条，见下 |
| G075-C03 跳过终态 Run 校验时提交无效转换（无效样例） | `tests/integration/snapshot-cache.test.ts` | 保持原样的终态 Run 不再解析；逐一构造的无效转换仍全部被拒绝 |

G075-C02 的 7 条测试：
- 按 version 命中；其他任何 version，包括本连接自己写的，一律未命中。
- 别的连接提交之后整体失效，即使 version 没变；数据损坏照样能被发现。
- 事务只读已提交的状态：既不会读到旧快照，也不会读到回滚事务写过的快照。
- Runtime 的并发提交，以及绕过 Runtime 经 Store 直接提交，都不会在旧快照上继续构建。
- 缓存的所有者是 Store，预算不超过 96 MiB，列表读取不占缓存。参考测量结束时缓存里有 12 份快照、95.7 MiB，淘汰 3 次，未命中 0 次。
- 随提交累计的事件日志字节等于 SQLite 自己的求和，32 MiB 上限精确到字节。
- 所有者丢失后立即清空缓存（审查后补充）。

改过的现有测试只有一条，而且是改严：`session-store` 的“读取的快照与事件数据是独立副本”原来断言“改返回的快照不影响存储”，现在断言“原地修改直接抛 TypeError”。

回退变异：把编译产物逐项改回旧行为或改错，共 11 个，每一个都被测试拦下。前 10 个由变异脚本逐个执行：
- 第 1、2 项改回旧做法：提交前先读；不用缓存。
- 缓存出错的三种：不认所问的 version；提交之前就放入缓存；看不见别的连接的提交。
- 第 3 项的跳过条件改错三种：所有终态 Run 都跳过转换检查；不要求是同一对象；信任 `before` 里任何冻结的 Run。
- 第 4 项的计数不随提交累计。
- 去掉 VERSION_CONFLICT 之后的那次重读。

第 11 个是审查后补的“所有者丢失时不清缓存”。第 3 项只影响速度，改回旧做法不改变行为，它的效果见上面的性能对照。变异脚本放在会话的临时目录，没有入库。

## 独立审查

由一个没有参与实现的代理对照规格审查一轮，提出 3 条，均已修正：
- **F1**：参考目标原来只打印、不断言，参考测量即使超标也会通过。现在设了 `G075_SESSIONS` 的参考测量断言 p95 ≤400 ms，CI 仍只断言次数。
- **F2**：所有者丢失之后，缓存仍持有快照直到关闭。现在丢失时立即清空，并补了测试；把这一行改回去，测试会失败。
- **F3**：存储契约没有写共享冻结快照与缓存失效规则。现已补进[存储与事件契约](../contracts/storage-events.md) R0。

修正由测试和主负责人的全量重跑核实，没有再做第二轮独立审查。

## 已知局限

- 事件字节的持久计数列没有做，要等 G066 的 v13。在那之前，进程启动后或缓存未命中后的第一次提交，仍要对该会话的事件做一次求和扫描。
- finalize 复用 prePlan 的快照没有做，留给 G072。
- 缓存只在一个 Store 实例内有效；只读的 Reader 不共享它。
- 测量用的是零延迟的假 Harness，不含真实 Harness 的启动与模型耗时；p95 目标只在参考机上断言，CI 只断言次数。
