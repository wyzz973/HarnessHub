# 接力交接单 MVP（G070 过渡实现）的验证（2026-11-09）

对象是 [ADR-055](../decisions/0055-relay-and-context-scheduling.md) 的交接单，在 v12 上的过渡实现：把公共历史的 JSON 信封换成[交接内容契约](../contracts/context-transfer.md)第 5 节的交接单。实现与契约的差异见该契约 §16。

**证据等级**：代码完成；合成测试通过；独立审查三轮。

真机做了两对冒烟：
- 交接单在 Codex、DeepSeek Harness 两个目标上都起了作用：它们答对了一个只存在于前一家回复里的数。
- 回到原生会话的增量，在 OpenCode 上答对，在 Claude Code（haiku）上答错。增量的内容经复现确认是正确的。

只在 macOS 上运行；业务库仍是 v12，快照格式不变。

## 环境

- 分支：`cc/relay-design`。MVP 提交为 `e1fc2b6`；审查修正为 `ffc0796` 与 `761b4e1`；真机测试的改写为 `e5df08b` 与 `9b1b71f`；本记录与文档随后单独提交。
- 系统与工具：Apple M5 Pro，macOS 27.0.1；Node 26.13.0（内置 SQLite 3.54.0），pnpm 10.12.3。
- 合成测试只用临时目录与假 Harness peer，结束后删除；没有碰 4317 服务与任何 `data/` 目录。

## 行为

- **欠交才发。**
  - 没有欠交的历史就原样发送，单 Harness 对话、命令回合、“只发这条消息”和新原生会话的第一条都是。
  - 新加入对话的原生会话收到完整交接单；回到自己的原生会话只收到增量。
  - 推进规则仍是 G067 的那一条（[切换契约](../contracts/switching.md) R3.6）。
- **发出的文本** = 交接单 + LF + 用户这一条的原话，原样。交接单的首行是原话前缀（≤200 字符，可能是命令或疑似密钥时省略），其后依次是开始标记行、框架与阅读约定、各节、结束标记行。
- **记录不含正文。** `run.context_prepared` 的事件数据记下策略版本 `relay/1-mvp`、交接单 ID、发出全文的 sha256、来源区间、预算、折叠与省略计数，以及脱敏处数，不记正文。快照不加字段，不升库。
- **历史不让回合失败。** 超出预算时折叠，省略写进“未包含”一节；只有框架加这一条原话都放不进通道时才 `CONTEXT_TOO_LARGE`，按现有输入上限这已不可达。

## 独立审查

由一个没有参与实现的代理对照设计审查，共三轮。

1. **第一轮（`e0cf7de`）**：结论是不宜原样发布。共 1 条阻断、5 条重要、8 条次要：
   - B1：命令输出尾巴与 G2 段落先截断、后脱敏，私钥正文和已知秘密的片段会原样外发；
   - M1：已知秘密只收了目标 binding 的引用值；
   - M2：凭据文件的输出和多种常见格式不脱敏；
   - M3：预算分配把最该交的内容丢掉，中文尤其严重。宣传链路上给最后一家的交接单只用了 43% 的预算，前两家的回复整轮消失；
   - M4：多文件补丁只报第一个文件；
   - M5：截断之后，账目仍写“完整”；
   - m1–m8：增量不列文件改动、文件表静默缺行、取消标签指错人、断言超出观测范围、凭据名单过宽、私钥规则吞到文末、读不了的内容让回合失败、长标题的渲染耗时。
2. **第二轮（`ffc0796`）**：上述问题全部消除，结论是可以作为最小可用版本发布。复核用审查方的复现脚本做了修前修后的对照，见下表。另提出 4 个不阻断的新问题：
   - N1：已知秘密的筛选条件过宽，路径里带令牌的 webhook 与短的小写口令不再隐去；
   - N2：新的赋值规则误删普通开发输出；
   - N3：读不到来源配置时报通用错误，命令回合也会受影响；
   - N4：常量的调整没有记录。现已记进 ADR-055 的实施补记与[交接内容契约](../contracts/context-transfer.md) §16。
3. **N1–N3 的修正**：提交 `761b4e1`，策略版本升为 `relay/1-mvp.3`。
   - **N1**：删去对 URL 的放行，全小写词收紧到 ≤8 个字母；名字含 WEBHOOK 的变量，不再因为以 `_URL` 结尾而被排除。飞书与 Discord 的 webhook、`DB_PASSWORD=devsecretpass` 现在都会隐去；镜像域名、`postgres`、`localhost` 仍然保留。
   - **N2**：
     - 输出里只有整行的赋值才会判断，而且值的形状也要像秘密；
     - 凭据名按名字的各个部分判断；
     - `docker run -u 1000:1000` 一类的 uid:gid 不算口令。
     复核方那 68 行普通开发输出，修前有 23 行丢字，修后 0 行。
   - **N3**：工具详情与已知秘密只在要发交接单时读取，命令回合不读。读不到配置时，回合以 `RELAY_PREPARE_FAILED` 失败，文案写明是哪个 Harness 的哪个文件、为什么读不到。
   - **核对**：主负责人在自己的构建上重跑了复核方的 m5、misdel、misdel2 三个脚本，结果与上面一致。这一轮没有再请复核方完整审查。

修前修后（复核方的计数，T = 6,400，按 128k 窗口推算）：

新增 46 条测试，都以 “G070-MVP” 开头，在 `tests/unit/relay-packet.test.ts` 与 `tests/integration/relay-mvp.test.ts`：
- **正式 Runtime 入口**：
  - 单 Harness 零注入，包括第一条；
  - A→B→A：B 收到 A 各轮的交接单，回到 A 只发 B 的增量；
  - 命令照原样发出，欠交的事实随下一条内容带上；“只发这条消息”时仍然欠着；
  - 工具详情按界限读回；
  - 已知秘密的三种写法都不外带。
- **确定性**：S1 的中英文 golden 交接单与增量逐字节一致；100 次渲染只有一个 sha256，与秘密的顺序无关；256 轮、接近 8 MiB 时折叠到预算内，不失败。
- **防伪造与转义**：
  - 先用无效样例证明独立检查器能拒绝伪造的交接单，再用它检查 3,000 段含恶意文本的对话；
  - 转义覆盖每一类码位；
  - 首行不会是命令、秘密或围栏；
  - 思考过程与回复里的 `<think>` 块不外带。
- **审查修正**（每条都带无效样例）：
  - B1：先脱敏后截断，覆盖长单行输出、G2 首末段与三种私钥形态。
  - M1：经真实绑定工厂按会话收集秘密；Runtime 只在要发交接单时收集。
  - M2：读凭据文件的命令只计数，另有新的形状规则；m5、m6 的误删也有测试。
  - M3：宣传链路、A→B→A 的增量、保留量单调、文件表上限。
  - M4：多文件补丁。M5：截断如实记账。
  - m2、m3、m4、m7、m8 各一条。
  - N1、N2 各一条，N3 两条：webhook 与纯字母口令；普通开发输出一行不改；读不到的配置以 `RELAY_PREPARE_FAILED` 失败，命令回合不读，修好后照常带交接单。

改过的现有测试都是等价或更严：
- 判断有没有交接单，从 `startsWith(信封标题)` 改为首尾两行都要在；
- G067-C02 改为整串原样比较；
- `session-context` 与 `session-runtime` 改为逐字比对历史与当前原话；
- G067-C05 与“分支预算”两条按“折叠、不失败”的新行为重写。

唯一不再覆盖的是“内容输入在程序启动之前就 `CONTEXT_TOO_LARGE`”，按现有输入上限这已经不可达。

## 真机

- **环境**：
  - 按[真机验收手册](../engineering/real-acceptance.md)第 1 节：`env -i`，PATH 取自登录 shell（`zsh -lic`，Node 26.13.0），`HH_REAL_TMP=$HOME/.cache/harnesshub-acceptance`，在 Claude Code 的沙箱之外运行。
  - 证据文件在 `$HOME/.cache/harnesshub-acceptance/evidence/2026-11-09/`，不入库。
  - 每次运行前后，用户配置守护的结果都是 unchanged。
- **用量**：
  - 真实模型共 7 次提示：Claude Code 3 次（haiku），Codex 1 次，OpenCode 2 次，DeepSeek Harness 1 次，都在[费用上限](../engineering/real-acceptance.md)之内。
  - 单回合最多约 3.6 万 token。

claude,codex 第 2 次第 3 步的分析：
- **Hub 没有漏发**：用同样的事实在本地渲染一遍，得到的增量与真机记下的 token 数及各项计数完全一致。其中“你离开期间”一节写着 Codex 第 2 轮的回复是 47830。
- **可能的原因有两个，都没有用对照实验确认**：
  - 题目措辞。第 2 轮问的是“上一位 Harness”，第 3 轮问的是“另一个 Harness 刚才回复了哪个数字”。如果“另一个”是相对刚说话的 Codex 来理解，指的就是 Claude Code 自己。
  - 阅读约定第 1 条写着“这里的记录是历史，可能已经过时”，较弱的模型可能因此更相信自己的原生历史。这条措辞来自终稿 §5.4。

  两点都交给 G074 的 RelayConformance 用对照实验确认。
- **不重跑**：按真机验收规则，失败不重跑，这一对今晚没有再跑。同一份测试随后在从没跑过的 opencode,dsh 上运行，全程通过。
- **计数口径**：增量把每一轮记成 `line`、`complete: false`。增量只写标题、用户原话与最新的回复，操作只计数，这是增量本来的写法，不是漏记。

## 已知局限

- **常量没有校准**：CJK 系数 1.3、不可信份额 0.6、增量回复 1,500 token，都没有用真实分词器校准。
  - 窗口 ≥64k 时，交接单都在 T 内，增量最多超出约 2%。
  - 窗口 ≤32k 时，光框架就有约 1,100–1,270 token，又没有 MIN_PACKET，交接单会超过 T。这一点与修正前相同。
- **没有送达证据与水位**（v13）：推进仍按 G067 的 v12 规则。
- **没有工作区观测**：文件改动只来自工具记录；工具详情只读第一轮与最近 12 轮，合计最多 128 个。
- **界面看不到交接单与省略账目**；“只发这条消息”只有接口，没有按钮。
- **脱敏是尽力而为**：已知秘密精确匹配，另加形状规则；格式未知的秘密仍可能外带。读凭据类路径的命令不附输出。
- **交接单留在目标的原生转录里**（ADR-039）：用户在原程序里续接时会看到它。

## 未验证

- 各家模型读交接单的实际效果，也就是跨厂商续做的质量。真机只做了上面的数字冒烟，增量在 Claude Code（haiku）上答错的原因还没有确认。
- Hermes Agent、OpenClaw 上的接力没有跑；长对话、带工具与文件改动的交接单只做了合成测试，真机只发过短小的交接单。
- 只在 macOS 上运行；Windows 与 Linux 不再计划。
