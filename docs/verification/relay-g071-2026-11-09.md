# 工作区观测器（G071）的合成验证（2026-11-09）

对象是 [ADR-055](../decisions/0055-relay-and-context-scheduling.md) 的 G071：交接边界上对工作区做一次有界、不执行工作区任何程序的观测。范围见[终稿](../proposals/relay/relay-architecture.md)第 10.6 节与第 17 节，安全约定见[安全契约](../contracts/security.md)“工作区观测子进程的环境”，类型见终稿第 4 节的 `WorkspaceObservation`。

**证据等级**：代码完成，合成测试通过（真实 `/usr/bin/git` 与真实文件系统），参考机上测得观测时延分布。观测器还没有接进运行时与交接单（G072），没有运行任何真实 Harness，只在 macOS 上运行。

## 做了什么

新文件 `src/infrastructure/session/workspace-observer.ts`，导出 `createWorkspaceObserver`、`canonicalDirectory`、各项上限常量，以及按终稿第 4 节定义的 `Fingerprint` 与 `WorkspaceObservation`（注释写明：与终稿 §4 一致，合并 G066 后改为从 `src/contracts/relay.ts` 导入，由主负责人做）。另在 `plan/slices.json` 的 relay 切片 `allowed_files` 里登记了这一个文件（切片说明要求任务开工时登记，否则设计检查拒绝 `src/` 下的新文件）。

一次观测的顺序：

1. **排队与上限**：每个观测器最多 4 个观测同时持有名额（`MAX_PARALLEL_CONVERSATIONS`）；上限（默认 250 ms，见取舍 15）从调用算起，排队时间也算在内，排队中到时的观测不启动任何进程。
2. **工作区与根目录**：工作区按 `canonicalDirectory` 规范化（realpath 折叠大小写；`/System/Volumes/Data/…` 的写法在与去掉前缀的路径 `(st_dev, st_ino)` 相同时换成后者）。不存在或不是目录记 `no_workspace`；是 `/` 记 `root_is_fs`；是用户 HOME 或它的上级（按 `(st_dev, st_ino)` 比较）记 `root_is_home`。这些都在启动任何进程之前判定。
3. **数据根**：数据根与工作区互相包含（数据根解析后的路径与写出的路径，沿父目录比较 `(st_dev, st_ino)`，两个方向都查），或工作区根目录下有所有权标记 `.harness-gateway.json`，记 `data_root_in_workspace`，不观测。
4. **git 从哪来**：创建观测器时把 PATH 里每个绝对目录及其中的 `git` 解析成 realpath 记下（相对目录与空项跳过）；每次观测取第一个“目录与文件都不在该工作区内”的记录。没有可用的就是 `unavailable{error}`。之后不再查 PATH。
5. **第一段（并行）**：`rev-parse --show-toplevel --git-dir --git-common-dir --show-object-format --verify -q HEAD` 与 `config --list -z --show-origin`（≤64 KiB）同时启动；驱动名按 `.git/config` 与 `.git/config.worktree` 的 lstat（dev、ino、大小、mtime、ctime）缓存，命中时不再列配置。
   - 不是仓库（`not a git repository`）→ tree 模式。
   - toplevel 不等于规范化后的工作区，或 gitdir、common dir 不在工作区内、路径上有符号链接 → `gitdir_outside`。
   - 配置输出超过 64 KiB、含 `include.path` / `includeIf.*.path`、出现仓库自己配置文件以外的来源、驱动名不匹配 `^[A-Za-z0-9._-]{1,64}$`、或驱动超过 256 个 → 退回 tree 模式并记 `partial`。
6. **复用**：`HEAD` 的提交、`.git/HEAD` 文件内容、`.git/index` 的 (ino, mtime)、驱动名列表都与上次相同，且距上次观测 ≤60 s，就原样返回上次的观测（同一个对象）。复用路径仍跑第一段，所以 toplevel 与 gitdir 每次都重新核对。
7. **第二段（并行）**：`status --porcelain=v2 -z --branch --no-ahead-behind --untracked-files=normal --ignore-submodules=all -- .` 与 `diff --numstat -z --no-color --no-ext-diff --no-textconv --ignore-submodules=all -- .`，都带 `--attr-source=<该对象格式的空树>`。
8. **第三段（只在有已跟踪的改动时）**：`check-attr -z --stdin filter` 判定列出的已跟踪改动里哪些是 LFS 文件，记 `lfs: true`，行数记 null（“未核验”）。
9. **结果**：排除 `.tmp/` 与含所有权标记的未跟踪目录；已跟踪的改动在前、未跟踪的在后，各按路径排序，最多存 1,000 项，另存总数与覆盖全部项的 sha256 指纹；凭据类路径（沿用 `redaction.ts` 的 `namesCredentialFile`，改名的两端都查）标 `credentialPath`；观测前后 `.git/index` 的 (ino, mtime) 不同则记 `partial` 且不进复用缓存。

每个 git 子进程的环境恰好是：`HOME=<Hub 私有空目录>`、`LC_ALL=C`、`GIT_CONFIG_NOSYSTEM=1`、`GIT_CONFIG_GLOBAL=/dev/null`、`GIT_OPTIONAL_LOCKS=0`、`GIT_TERMINAL_PROMPT=0`、`GIT_CEILING_DIRECTORIES=<工作区父目录>`、`GIT_CONFIG_COUNT` 及其 `KEY_n` / `VALUE_n`。配置项固定四条 `core.fsmonitor=false`、`core.hooksPath=/dev/null`、`core.attributesFile=/dev/null`、`diff.autoRefreshIndex=false`，第二、三段再对每个驱动加 `filter.<n>.clean=`、`.smudge=`、`.process=`、`.required=false`。没有 PATH：git 按记下的绝对路径执行。

**tree 模式**：从工作区广度优先读目录，每个目录的项按名字排序，所以超出上限时读到的总是同一批项。最多读 2 万项；不进入 `.git`、根目录下的 `.tmp`、含所有权标记的目录；只用 lstat，不跟随链接，读目录前后核对它仍是同一个目录（不是则不用读到的内容）。按 mtime 从新到旧存 1,000 项，另存读到的项数、文件数与全量指纹；读到上限、列表被截断、读不了的目录都记 `partial`。

**超时与资源**：每个 git 都在自己的进程组里（`detached`）。到上限（默认 250 ms）时对观测启动过的每个进程组发 SIGKILL，结果立即是 `unavailable{timeout}`；`released` 在这些进程组确认为空之后兑现（Darwin 上一组只剩僵尸时 `kill(-g, 0)` 报 EPERM，这时用 `ps` 快照交给 `process-group.ts` 的 `exitedGroupSnapshotIsQuiescent` 判定）。名额要等进程确认退出才归还，所以“≤4”数的是真实进程。停止之后，观测自己的其余步骤（文件系统调用）最多再等 3 s 就去确认进程，挂死的网络卷也拖不住 `released`；一组进程在 SIGKILL 之后 3 s 仍不空则记“unconfirmed”，计入 `stats()`。`close()` 停掉在途与排队的观测（结果 `unavailable{error}`），等全部进程退出后兑现；之后的 `observe()` 以 `OBSERVER_CLOSED` 拒绝。本机实测（C02）：阻塞的观测在调用后 252.5 ms 得到结果，进程组在 253.0 ms 确认为空。

## 设计取舍

1. **原因码定为 `data_root_in_workspace`**（终稿第 4 节写的是 `data_root_inside`，用例 G071-S01 写的是 `data_root_in_workspace`）。理由：受理时的 `409 RELAY_UNAVAILABLE{reason:"data_root_in_workspace"}`、公共 API 契约、安全契约、INV-36、ADR-055 正文、测试矩阵和现有代码 `dataRootPlacement` 都用这个名字，只有终稿第 4 节（及其第二版前身）用 `data_root_inside`；同一件事在观测、受理拒绝和启动告警里用同一个词，G072 可以原样转述；409 的这个原因码本来就覆盖两个方向的互相包含，观测这里也一样。于是用例不用改，类型里这一个字面量与终稿第 4 节不同，已在类型注释里写明。建议主负责人合并 G066 时把 `src/contracts/relay.ts` 与终稿第 4 节的这个字面量一并改成 `data_root_in_workspace`。
2. **数据根在工作区里时不观测**，结果就是 `unavailable{data_root_in_workspace}`，而不是“排除数据根后照常观测”：第 4 节的类型只能用 unavailable 的原因码报告这件事，排除后照常观测等于把它瞒下；结果自然不含数据根下的任何东西。代价是同厂商交接在这种工作区里拿不到观测，交接单会写“工作区未核验”。“观测排除数据根”在实现里落为：含所有权标记的目录（照 409 文案复制走数据之后留在工作区的旧副本）与 `.tmp/` 从不列出。
3. **git 的解析分两步**：创建时把候选全部解析成 realpath 记下（“解析一次”），观测时只按工作区在记下的候选里挑。原因是一个 Hub 里的会话可以有不同的工作区，创建观测器时还不知道每次观测的工作区；记下之后不再查 PATH，事后放进 PATH 目录里的程序也不会被用上。
4. **环境里没有 PATH**：终稿列的是“git 的绝对路径”，这里理解为按绝对路径执行、不传 PATH。git 对自己的子命令用内置的 exec-path，本次用到的命令都是内建命令。
5. **超出终稿命令行的参数**，都只让结果更确定或更封闭：
   - `diff.autoRefreshIndex=false`：实测 git 2.54.0 上 `GIT_OPTIONAL_LOCKS=0` 只管得住 `status`，`git diff` 遇到只改了 mtime 的文件仍会重写 `.git/index`（G071-S01 的 index 用例里有这个无效样例）。没有这一条，“`.git/index` 的 mtime 不变”做不到。
   - `status` 加 `--branch --no-ahead-behind` 取分支与 HEAD；加 `--untracked-files=normal`，仓库配置 `status.showUntrackedFiles=no/all` 既藏不住、也撑不爆未跟踪文件。
   - `diff` 加 `-z`（路径不转义）、`--no-color`，以及 `--ignore-submodules=all`：不加时 `diff` 检查子模块是否有改动会在子模块里再启动 git，读的是子模块自己的配置，那里的驱动没有被中和。
   - 全部命令加 `--no-pager`。
6. **common dir 也必须在工作区内**、`.git` 本身是符号链接一律拒绝（`gitdir_outside`）：`.git/commondir` 可以把配置、引用与对象指到工作区外，`.git` 链接同理。`.git` 文件指向工作区内的目录照常观测（WS-04 里的对照）。
7. **复用键比终稿多两项**：`.git/HEAD` 的内容（只切换分支、提交不变时也算 HEAD 变了）与驱动名列表（配置新增驱动后不复用旧结果）。index 用 (ino, mtime)。
8. **LFS 判定**用 `check-attr`（不带 `--attr-source`，读工作区与 `.git/info/attributes` 的属性，只读不执行）。`--attr-source=<空树>` 让 `status`/`diff` 看不到工作区里的 `filter=lfs`，中和后又不跑 LFS 过滤器，所以 LFS 文件的状态与行数都不可信，只能标“未核验”。
9. **`attributesIncluded`** 定义为 `.git/info/attributes` 是非空的普通文件：`--attr-source` 挡不住这个文件（原型 F3），所以观测是在它的属性下得出的。第二版正文曾把它和 include 回退写在一起，但 include 回退的结果是 tree，tree 没有这个字段。
10. **`partial` 的含义**：存下的结果不完全代表看到的状态，或有一部分没看到。git：列表截断、有路径不安全被丢弃、LFS 判定失败、观测期间 index 被改。tree：读到上限、列表截断、读不了的目录或文件、由 git 回退而来。
11. **tree 模式到上限也是 `unavailable{timeout}`**，不返回读了一半的列表：超时是硬上限的统一语义，按 mtime 排的半份列表会误导；2 万项的读取上限才是 partial 的来源。
12. **结果先返回，资源后确认**：终稿写“超时 SIGKILL 整个进程组并等待退出，在 execute 的 finally 中等待”。所以 `observe()` 在 250 ms 时返回结果，等待交给 `released`，调用方在 finally 里等它；`close()` 等全部。
13. **tree 模式的读法**：在 `node:test` 进程里，每个 promise 都要过 async hook，按“每项一个 promise”的写法读 2 万项要 190–250 ms，压着硬上限。改为每 1,024 项异步读一次目录、其余从缓冲区同步取（不发系统调用），lstat 用回调、每批 256 个、最多 4 批在途，同时预读后面 8 个目录。2 万项：普通进程首次约 112 ms、之后约 40 ms；测试进程里首次约 115–121 ms、之后约 47 ms。没有用一次读完整个目录的 `readdir`，因为它对超大目录的内存没有上界。
14. **`process-group.ts` 只读复用**：它导出的 `exitedGroupSnapshotIsQuiescent` 被直接复用；判断进程组是否还有成员的 `groupAlive` 没有导出，而导出的 `darwinExitedGroupIsQuiescent` 用的是同步 `execFileSync("/bin/ps")`，会阻塞事件循环最多 1.5 s，所以观测器自己写了等价的异步判定。建议 G031 以后导出一个异步版本，届时这里改用它。
15. **上限做成选项，默认 250 ms**：`WorkspaceObserverOptions.timeoutMs`，1 到 60,000 ms，不给就是 250 ms，Hub 不给它。只查“观测看到了什么”的测试给 10 s；上限本身在默认值上测（C02 用模拟的 `setTimeout` 精确核对 249 ms 时仍在等、250 ms 时超时），需要先走到 `git status` 再超时的两条（杀进程组、八个并发）给 2 s。原因是实测：整套 `pnpm test` 约 120 个文件同时跑时，小观测会被挤过 250 ms——收尾时连跑的几次里，一次有 2 条、一次有 14 条观测器用例全部因 `unavailable{timeout}` 失败（当时 1 分钟负载均值约 12），另一次 1 条。按“检查失败就修，不放宽断言”，断言一条没改，改的是这些用例交给被测对象的上限这一输入；先前加过的预热（每个文件先观测一次、先跑一次 `git status`）治标不治本，已去掉。参考测量仍用真实的 250 ms 并计超时数。

## 偏离设计之处

- 原因码 `data_root_inside` → `data_root_in_workspace`（取舍 1）。
- 类型字段按第 4 节自己的约定全部 `readonly`（第 4 节正文为篇幅省略了 readonly）。
- 命令行多出的参数与配置项（取舍 5），common dir 检查与 `.git` 链接拒绝（取舍 6），复用键多出的两项（取舍 7）。
- 对外接口多了 `released` 与 `stats()`（取舍 12；`stats()` 给出在用名额、排队数、峰值与未确认退出的次数，供诊断与测试），以及可选的 `timeoutMs`（取舍 15，默认就是终稿的 250 ms）。

## 性能

计划的验收条件是“3k 文件 p95 ≤60 ms、2 万文件 ≤200 ms 写进验证记录（含大文件与冷缓存一组）”。CI 只断言计数与确定性，毫秒数不作门槛（终稿第 11.1 节）。

参考测量（设了 `G071_SAMPLES` 才跑满样本，用真实的 250 ms 上限并计超时数；CI 默认每组 5 个、冷缓存组 4 个，上限 10 s，只断言计数与确定性）：

```bash
pnpm build && G071_SAMPLES=300 node --test dist/tests/performance/workspace-observer.test.js
```

合成仓库：每组都有三个过滤驱动（含一个带点的名字）映射到全部文件、40 个改过的已跟踪文件与 10 个未跟踪文件；3k 组 3,000 个小文件，2 万组 20,000 个，大文件组 1,000 个小文件加 4 个 16 MiB 的二进制文件，其中 2 个按原大小重写（git 必须对它们求哈希），冷缓存组见下。每个样本都是完整观测：注入的时钟每次前进 61 s，不复用；先观测 2 次让本进程的代码编译、git 启动过一次，不计入。`observeMs` 取观测结果的 `durationMs`，从调用算起。每组 300 个样本，p95 附 1,000 次重抽样的 bootstrap 95% 区间；样本不到 1,000，不报 p99。测量时本机还开着其他程序（另一个代理在并行的工作区里工作），1 分钟负载均值开始时 5.12、结束时 4.70；整次测量 4 分 37 秒，2 / 2 通过。测量跑在 `836a6e4` 上；之后的两处代码改动（停止之后 3 s 内释放、上限做成默认 250 ms 的选项）都不碰按时完成的观测走的路径，参考测量用的也仍是默认的 250 ms。

| 组（每组 300 个样本） | p50 | p95（95% 区间） | 最大 | 超时 | 目标 |
|---|---|---|---|---|---|
| 3k 文件 | 31.61 ms | 37.75 ms（37.39–38.33） | 40.03 ms | 0 | p95 ≤60 ms，达到 |
| 2 万文件 | 65.46 ms | 73.28 ms（71.47–75.36） | 78.52 ms | 0 | p95 ≤200 ms，达到 |
| 大文件（2 × 16 MiB 需求哈希） | 82.15 ms | 86.79 ms（86.16–89.76） | 92.42 ms | 0 | 硬上限 250 ms 内 |
| 冷缓存（3k 文件，每次重新挂载） | 82.62 ms | 89.30 ms（87.69–92.86） | 145.39 ms | 0 | 硬上限 250 ms 内 |

复用路径（同一时钟刻度内第二次调用，即只跑第一段与几次 lstat，交给 G072 的“复用 ≤ 观测 p95 + 15 ms”）：3k p50 / p95 8.70 / 9.54 ms，2 万 7.38 / 8.70 ms，大文件 7.37 / 8.15 ms。

CI 那一档在整套测试并行时（`pnpm test`，约 120 个测试文件同时跑）也记过：3k p50 约 65–98 ms，2 万约 82–109 ms，大文件约 106–109 ms，冷缓存 4 个样本中位数约 78–123 ms、最大 240 ms；毫秒数不作门槛。

**冷缓存的取法**：macOS 上清页缓存的 `purge` 需要 sudo，不用。冷缓存组把 3k 仓库放在一个 512 MiB 的 APFS 稀疏磁盘映像里（`hdiutil create -fs APFS -type SPARSE`，不需要 sudo），每个样本之前 `hdiutil detach -force` 再 `attach`。卸载会丢掉这个卷上所有文件的 vnode、名字缓存与页缓存，所以每次都是第一次看到这些文件；映像文件本身在宿主卷上，它的页可能仍在宿主的页缓存里，所以这测的是“冷元数据与冷文件页”，不是“冷磁盘”。强制卸载是因为新卷常被系统的索引占着；每次卸载前观测器的进程已确认退出（`released`）。

## 已知局限与残余风险

- **配置的检查与使用之间有窗口**：`config --list` 与 `status`/`diff` 之间约 10 ms，若这期间有进程往 `.git/config` 加了新驱动，git 会读到这个没被中和的驱动。git 没有不读仓库配置的开关，这个窗口无法在观测器里关掉；终稿第 10.6 节没有讨论它。缓解只能是缩短窗口，或在第二段之后复查配置并把结果记 partial（已经执行的程序收不回）。
- **tree 模式里目录换成链接的竞态**：Node 没有 `openat` / `fdopendir`，读目录时无法用 O_NOFOLLOW 打开。实现在读前读后各 lstat 一次核对身份，能发现读的过程中被替换、又没换回来的情形，窗口内换走又换回的情形发现不了。
- **复用规则会漏掉不经过 index 的改动**：按设计（RT3 P07），60 s 内只改文件内容、没有任何东西刷新 index 时，返回的是上次的观测。C03 用例把这一点写成了断言，使它可见。
- **新程序第一次执行要多约 0.5 s**：本机实测，新写入的可执行文件第一次执行要被系统检查一次（450–520 ms），之后约 10 ms。`/usr/bin/git` 不受影响；git 刚被安装或升级（例如 Homebrew）之后的第一次观测可能超时，之后正常。测试里的包装脚本因此先执行一次再交给观测器。
- 子模块一律不观测（`--ignore-submodules=all`）；被 `.gitignore` 与 `.git/info/exclude` 忽略的文件看不到，这是 git 的语义。
- `lease_not_held` 由 G072 产生，观测器自己从不给出。
- **机器忙时 250 ms 容易超**：同一台参考机，空闲时 3k 仓库 p95 约 38 ms，整套测试并行时同类小观测会过 250 ms（见取舍 15）。目标 Harness 启动与观测并行（终稿第 6.1 节），本身就在抢 CPU 与进程创建；G072 应把 `unavailable{timeout}` 当作常见结果来写交接单。
- **`git worktree` 建出的工作区观测不到**：它的 `.git` 是指向主仓库 `.git/worktrees/…` 的文件，gitdir 在工作区外，按规则记 `gitdir_outside`。子模块的检出目录同理。本仓库的开发工作区（如本任务所在的 `HarnessGateway-g071`）就是这种情形。

## 后续修正：测试仓库的后台自动 gc（2026-11-10）

- **现象**：G071-C04（3,000 与 20,000 个文件、大文件）在两次全量 `pnpm test` 里各失败过一次（一次在 G069 实现者的运行里，一次在主负责人对 `92e9817` 的运行里），报错都是清理临时仓库时 `ENOTEMPTY: directory not empty, rmdir …/20k/.git`；单独重跑该文件都通过。失败那次留下的目录里只剩 `.git/info/refs` 与 `.git/objects/info/` 下的文件。
- **原因**：测试夹具用 `git add -A`、`git commit` 建 20,000 个文件的仓库，松散对象数超过 `gc.auto` 的默认阈值，git 于是在后台分离启动 `git gc --auto`；gc 打包并运行 `update-server-info`（写 `info/refs`）的同时，测试的清理正在删除这个目录，两者撞上。触发 gc 的是夹具建仓库的提交，不是观测器。
- **复现**：一次性脚本在临时目录里按夹具的同样方式建两个 20,000 个文件的仓库，8 秒后查看：默认设置的那个出现 1 个 pack 与 `info/refs`，带 `-c gc.auto=0 -c maintenance.auto=false` 的那个都没有。脚本不入库，临时目录已删除。
- **修正**：四个观测器测试文件（`tests/{performance,integration,security,platform}/workspace-observer.test.ts`）的 `SETUP` 加上 `-c gc.auto=0 -c maintenance.auto=false`。只改测试夹具，观测器的代码不变。
- **重跑**（主负责人，`pnpm build` 之后，经 serial 排队）：四个观测器测试文件连跑两遍，各 26/26；全量 `pnpm test` 1,142 个用例，1,141 通过、1 跳过（G066 的 1 GiB 参考测量）、0 失败；`pnpm check` 退出码 0；`os.tmpdir()` 下没有留下 `g071-*` 目录。偶发失败本身不能靠几次通过证明已消除，但它的起因已经去掉。
