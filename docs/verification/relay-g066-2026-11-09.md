## 迁移计时

参考测量（`G066_MIGRATION_GIB=1`）：生成的 v12 库每个会话是 d1 夹具加上流式回复的 `run.output` 事件，接近每会话 16,384 条与 32 MiB 的上限。

| 项 | 值 |
|---|---|
| 库大小 | 1,159,413,760 B |
| 会话 / 事件 | 34 / 557,056 |
| 生成用时 | 3,440 ms |
| 打开到可用（备份、迁移、恢复） | 2,443 ms |
| 其中备份（写出、回读、发布，按备份文件的修改时间计） | 约 1,190 ms |
| 其中迁移与恢复 | 约 1,254 ms |
| 备份 / WAL | 1,157,029,888 B / 473,832 B |
| 磁盘峰值（库、WAL、共享内存与备份之和，打开完成后量） | 2,316,950,248 B，库大小的 2.0 倍 |

做法：在同一进程里打开 Store 计时；WAL 在迁移事务里不会被检查点截断，打开后量到的文件大小即它的峰值。另在本机用临时脚本量过 1,500 个小会话、约 30 MB 的库：打开到可用约 0.5 s（同一构建、同一机器，只作量级参考，脚本不入库）。结论：这个量级不需要按会话分批，迁移在开始服务之前一次完成；空间需求约为库大小的两倍，已写进 ADR-049 的补充。

## 变异核对（人工，跑完还原）

在 `migrate.ts` 上一次改一处、重新构建，跑 `relay-migrate.test.js` 与 `relay-store.test.js`：

- 交接单的水位取来源的最大 seq（不要求连续覆盖）：1 个用例失败（G067 之前 D1 的专门用例）。
- 本绑定的内容回合不检查欠交就推进：1 个失败。
- 被拒、失败或结果未知的携带回合也算送达：2 个失败。
- 命令回合不使绑定 suspect：2 个失败（含 C01 的 reset + D1）。
- 不按 v12 位置截断：0 个失败。属性测试加入 G067 之前的位置形状之前，这一变异让 3 个用例失败；现在其余条件（送达证据、连续覆盖、欠交检查）已足以让水位不超过位置，截断在现有数据上与之等价。保留它，是因为“只降不升”由它直接保证，不依赖其余条件。
- 把“来源历史已送达”一律当真：0 个失败——本数据里 G067 的 `carriedOrigin` 与 v12 的 `owesOrigin` 一致，这一变异在现有数据上等价，没有为它另造数据。
