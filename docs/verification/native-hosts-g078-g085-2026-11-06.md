# 原生宿主契约（G078）与关闭链、私有 TMPDIR（G085）的合成验证（2026-11-06）

对象是 [ADR-056](../decisions/0056-native-hosts-and-sessions.md) 的前两个实施任务：G078（契约层类型、解析器与 `resolveHostBudgets`），G085（关闭宽限 ≥1.5 s、先 EOF 再核对离组后代的关闭链、每个宿主类一个私有 TMPDIR）。契约见[原生宿主与会话租借契约](../contracts/native-hosts.md)，实现时的取舍见 ADR-056 的“实施记录”。本记录写的是同日两轮独立审查修正之后的状态：第一轮 F1 为 major、F2–F4 为 minor；第二轮 N1–N3 为 minor、N4–N5 为 nit，另有一个顺带修的 Runtime 问题（R）。修正前后的对照见“审查修正”与“时延”两节。

**证据等级**：代码完成，合成测试通过。没有运行任何真实 Harness，“真实引擎通过”一栏为空；只在 macOS 上运行。业务库仍是 v12，回合快照与 `run.ended` 的 `cleanup` 格式不变。

## 环境

- 分支：`cc/relay-design`，基点 `71cf15b`，代码随本记录同一提交。
- 系统与工具：macOS 27.0.1（26A434，arm64），Node v26.11.1，pnpm 10.12.3；依赖沿用已安装的 `node_modules`。
- 测试数据：测试与时延脚本只用各自的临时目录、临时租约目录与夹具子进程（`node` 脚本），结束后删除。没有碰 4317 服务、任何 `data/` 目录与用户配置；完整测试与时延脚本运行之后，用户共享的命名空间（系统临时目录下的 `harnesshub-hosts-501`、`/tmp/harnessgateway-workspaces-501/hosts`）都不存在。

## 改了什么

- **G078 契约**（`src/contracts/native-host.ts`，新文件）：
  - 品牌 ID `HostId`、`SessionLeaseId`、`HostClassKey` 与解析器。
  - `HostCapabilities` 与 `parseHostCapabilities`：缺项取最保守值；未知值、未知字段、类型错误、重复与矛盾拒绝。
  - `hostKind`，只看 `sessions`、`sessionMemory`、`sessionRelease`。
  - 类型 `HostState`、`HostCloseReason`、`StaleReason`、`FreshnessVerdict`、`HostedSession`、`HostHealth`、`CloseStage`、`HostCleanup`、`HostCloseEvidence`、`NativeHost`、`SessionLeaseRequest`、`SessionLease`、`HostPool`、`HostPoolMetrics`，以及宿主事件名与数据。
  - `resolveHostBudgets` 与 `HOST_BUDGET_BOUNDS`、`HOST_CLASS_CAP_BOUNDS`，含审查后新增的 `hostTmpdirMaxEntries`（256–65,536，默认 4,096）与 `hostTmpdirCloseWaitMs`（1–60 s，默认 5 s）。
  - `control.ts` 只增加可选的 `openSession`、`closeSession`、`switchSession` 声明（无实现）与 `ControlOptions.closeOutsideWaitMs`。
  - `session.ts` 改 `PreparedSessionBinding` 注释，并增加可选的 `WorkspaceLeaseProvider.namespace` 与 `SessionBindingFactory.close`。
- **G085 关闭链**（`src/infrastructure/control/host-shutdown.ts`，新文件；`json-rpc-process.ts`、`process-group.ts` 经 G031）分两段：
  - `quiesce`：需要证据时，趁领头进程还在先读一次离组后代；然后关 stdin，宽限内等组清空，之后才 SIGTERM、再 SIGKILL。`JsonRpcProcess.close()` 只等这一段，仍只返回原来的四个字段。绑定关闭、只读探测、`run:harness` 与 `probe` 都只等 `close()`。
  - `confirmOutside`：按 pid 加启动时间复查读到的离组后代，仍在运行的最多再等 `closeOutsideWaitMs`（默认 10 s）。只有 `JsonRpcProcess.closeEvidence(signal?)` 等这一段。它由 `JsonRpcProcess` 持有，有上限、可等待、可中止；中止时还有在运行的，记 `remaining: null`。先由 `close()` 开始、没有采样的关闭，记 `unknown`。目前没有生产调用方，等 G079 的 `native.host_closed`。只经 `closeEvidence()` 开始的关闭失败时，拒绝只交给它的调用方，不留未处理的 rejection（N1）。
  - 两段都不向离组后代发信号。保留进程的关闭照旧：Runtime 在关闭前后各读一次进程表，记 `native.process_closed{outside}`。
  - 回合已结算（settling）后收到的停止只记录命令与 `run.cancel_requested`，不改结果、不提前关闭（R，`runtime.ts` 经 G028；公开会话契约同步）。
  - `process-group.ts` 抽出 `outsidersOfGroup`、`stillRunning`，`PosixProcessGroups` 改为调用它们，行为不变。
- **G085 关闭宽限**：binding factory 的回合进程与只读探测、`run:harness` 与 `probe` 命令都取 `resolveHostBudgets` 的 1.5 s，不再写死 500 ms；组合根解析一次预算。
- **G085 私有 TMPDIR**（`src/infrastructure/session/host-tmpdir.ts`，新文件；`binding-factory.ts`、`session-application.ts`、`control.ts` 命令经 G059，`workspace-lease.ts` 经 G026）：
  - 每个类一个 0700 目录。命名空间默认在系统临时目录下的 `harnesshub-hosts-<uid>`；显式租约目录时，在该目录下的 `hosts`。
  - 目录名与记录：
    - 启动文本包括 Harness、入口、工作区和除 TMPDIR 外的启动环境，不含安装。
    - 目录名取启动文本在命名空间密钥下的 HMAC-SHA256，用前 16 位十六进制。
    - 旁边的记录 `<名>.json` 只有启动与安装两个完整 HMAC。
    - 密钥是命名空间里 32 字节随机的 `.key`（0600），先写在旁边，再链接进来。
    - 启动文本只在内存里；服务日志只写目录名与错误码。
  - 以下情况回合以 `HOST_TMPDIR_FAILED` 失败，不启动程序，也不跟随、不修复：建不了、是链接、权限放宽、不可写，或与数据目录互相包含。
  - 记录里的安装 HMAC 不同（升级）或没有记录时，在下一个宿主启动前换成空目录。
  - 归还时清空的条件：没有同类持有者，且按磁盘块超过 256 MiB 或条目超过 4,096。同时列出的目录共享一个计数，越过任一上限就停，最多数到 4,097 项（N4）。
  - 清空与替换都把目录改名为 `.<名>.<uuid>.trash`（一次 rename）。`HostTmpdirs` 的一个后台工作一个接一个地删除：自己的遍历，不跟随链接，每个目录的项 16 个一组并行删除，能删的先删完，可在下一步停下；删除失败只记服务日志。
  - 服务关闭时 Runtime 最后调用 `SessionBindingFactory.close()`，即 `HostTmpdirs.close()`：最多等 `hostTmpdirCloseWaitMs`，之后停下，剩下几个记一条诊断，留给下次启动的清扫（N3）。
  - 命名空间锁 `.lock.sqlite`（SQLite，0600）：
    - 有活宿主的进程持有共享锁。
    - Hub 启动时的清扫要独占锁，拿不到就这次不清扫。
    - 宿主启动最多等清扫 2 s：不等待地读、每 20 ms 再试，不占事件循环；到时仍拿不到，回合以 `HOST_TMPDIR_BUSY` 失败，有单独的提示文字（N2）。
    - 清扫先把残留的墓碑交给后台删除，再移走 7 天未用的类目录与记录，并删除没有目录的记录与没写完的临时文件；一次最多改动 256 项，其余留给下次启动（N2）。随目录一起删掉的记录之后再遇到时，不再记成诊断。
  - 持有中的目录每小时重写一次记录，长期存在的保留进程不会被当作未用。

主负责人复核时的补充：

- **删除不跟随链接。** 第二轮把 `fs.rm` 换成了自写的 `removeTree`。它用 `readdir` 列目录，而 `readdir` 会跟随链接。如果待删的路径本身在列出之后变成了链接，就会列出、删除链接所指目录里的内容。
- **修法。** 每次进入一个目录之前先 `lstat`：路径已不存在就算删完；不是目录就只删除这个链接本身。剩下的竞态窗口与 Node 自带的 `fs.rm` 相同。
- **测试。** 新增用例 “removing what was moved aside never follows a link…”：一个墓碑本身是指向外部目录的链接，另一个墓碑里含有这样的链接；清扫之后，外部目录与其中的文件原样保留。
- **反向验证。** 在编译产物上去掉这道检查，这条用例失败；恢复之后通过。

## 已知局限

- **升级与超限的清空，跨 Gateway 仍靠工作区租约。** 这两种清空只看本进程的持有数。共享一个租约目录的 Gateway 之间，回合在租约下准备与归还宿主，这时该类在别处没有活宿主，所以安全。命名空间锁只保护清扫。进入宿主池（G079）后，空闲宿主不持租约，这个论证不再成立，需要按类的跨进程锁。
- **清扫可能被长期推迟。** 共享命名空间的任一 Gateway 有活宿主时，清扫拿不到独占锁，这次不清扫。保留进程长期存在时，过期目录要等到某次启动时没有活宿主才删；一次最多 256 项，过期目录很多时要几次启动才清完。
- **清扫持锁时，准备宿主最多等 2 s，之后回合以 `HOST_TMPDIR_BUSY` 失败，不自动重试。** 等待不再占事件循环；清扫有 256 项的上限，持锁时长见“时延”，正常等不满 2 s。
- **清空时离组后代可能还在用旧目录。** `close()` 不再等离组后代。超限或升级清空时，仍在运行的离组后代（例如 MCP 服务器：实测 Codex 的 MCP 服务器在组清空后 0.57–1.14 s 才退）的临时文件会随墓碑被删。
- **服务关闭与关闭对话仍会取消已结算的回合。** R 只改了用户的停止（`cancel`）。服务关闭或关闭对话走 `cancelPending`，照旧给未结束的回合设 `cancelRequested` 并提前关闭，所以正在 settling 的回合在这两种情况下仍记成 cancelled。
- **服务关闭最多多等 `hostTmpdirCloseWaitMs`（5 s）。** 只在还有后台删除时才等；到时剩下的留给下次启动的清扫。
- **`stage`、`closeMs` 与按回合的 `outside` 目前没有持久记录，`closeEvidence()` 也还没有生产调用方。** 服务关闭时中止这段等待，要由 G079 传入信号。
- **只读探测仍每次新建私有 TMPDIR**，冷启动不受益。
- **TMPDIR 路径比每回合的目录长 7 个字符**（本机 94 个），向 TMPDIR 建 Unix 套接字的工具余量相应减少。
- **预算里有些参数还没有使用方**：除宽限、离组等待与 TMPDIR 上限以外，都等 G079 接入。在那之前 Runtime 仍用自己的 `KEPT_LIMIT`、`KEPT_IDLE_MS`。

## 未验证

- 真实 Harness 上的关闭时长与离组后代（设计 H8 的生产关闭链部分），以及持久 TMPDIR 在生产启动上的提速：实测只做过 initialize 变体，正式验证排在 G083。
- 各家 TMPDIR 实际的条目数：一家的缓存若超过 4,096 项，每次归还都会被清空，持久 TMPDIR 对它就没有效果；上限可经 `hostTmpdirMaxEntries` 调整。
- 只靠代码审查、没有测试的三项：
  - 每小时刷新记录：间隔 1 h，没有可注入的时钟；
  - 两个 Gateway 同时删除同一个墓碑（一个归还时移开，另一个启动时清扫）：删除遍历把“已经没了”（ENOENT）当作删掉；
  - 仍在运行的程序往墓碑里写：删除遍历在目录删不掉（ENOTEMPTY）时最多再列两次。
- 宿主池、登记、Driver 声明与多会话、界面（G079–G082）尚未实现。
