04 / WHO OWNS WHAT

连续性来自公共上下文

HarnessHub 组织能交接的工作记录；不同 Agent 的内部会话仍有各自的身份与能力边界。

HarnessHub 的公共工作记录

目标中的连续性
  • 对话与目标用户输入、公共回复、正在推进的工作目标
  • 进展与决定已完成事项、待办、已确认的选择与约束
  • 工作成果关联工作区、已修改文件、登记产物及完整性信息
  • 执行记录每段 Agent、模型、工具、权限、费用和结果归属

Agent 的原生会话

现有基础
  • 后端身份原生 Session ID 与可验证的恢复材料
  • 内部状态Agent 自己的上下文表示与执行状态
  • 运行资源Worker、引擎和工具进程的实际归属
交接时要定义：把哪些公共上下文，怎样交给下一个 Agent。

候选材料包括相关对话、进展摘要、工作区状态、已有产物和待办。是否复用或新建原生 Session、如何补入其他 Agent 已完成的工作，均需设计和验证。公共上下文接续不等于原生会话无损迁移。

EVIDENCE 01

执行是否正常结束

Agent 与 Runtime 的执行状态、停止原因、取消与期限。

EVIDENCE 02

任务结果是否达标

文件存在或 Agent 回复不能单独证明正确。当前独立评分主要在 Benchmark。

EVIDENCE 03

资源是否清理确认

Worker、工具进程和在途调用的清理结果单独表达。

当前已有持久事件、SSE 回放、文件产物和执行观测。按 Run 的模型调用归属依赖 Session Key 路径，并非所有旧路径都已覆盖。

接下来需要定清楚的五个问题

点击展开
Chat、任务、一段执行、Session／Run 怎样对应？

Chat 的身份应持续。任务是否独立成实体、一条 Chat 如何处理多个目标、每段执行怎样关联现有 Run，以及原生 Session 的创建和复用规则，尚待设计。

切换 Agent 时，哪些上下文需要交接？

明确相关消息、摘要、约束、工作区变化、产物与待办的选择、版本和大小边界。不能只复制最后一句回复，也不能默认所有 Agent 能理解相同的内部会话格式。

执行中提出切换，什么时候才真正生效？

区分模型请求、工具运行、权限等待和结果结算。选择等待还是取消、如何确认停止、清理未确认时怎样阻止资源串用，必须有明确状态和证据。

切换 Agent 或 Provider 后，工具与模型选择怎样继承？

两个选择维度独立；默认保留什么、采用 Agent 自己默认值还是要求重选，需要明确。不可用的协议、模型、工具或上下文能力应说明原因并拒绝，不能静默换一个组合。

怎样证明切换后仍在推进同一项工作？

每段执行关联同一 Chat，记录所用上下文、配置、实际模型、工作成果和结果。测试需要覆盖 Agent A → B → A、只切 Provider、执行中切换、失败、重启与真实 Agent 组合；页面模拟不构成这些证据。

Chat 保持连续。Agent 与模型资源可以更换。
