# AI 参与开发的工作流

状态：2026-11-11 起的做法，取代此前“冻结契约、登记任务与文件归属、逐级门禁”的流程。约定以仓库根的 [AGENTS.md](../../AGENTS.md) 为准。

## 一个功能点怎么走

1. 说清这个功能点做完后用户能做什么、怎么在真机上试。
2. 做出能跑的最小实现，带测试（真实存储、真实进程通信，只替代外部的 Harness 和模型）。修缺陷先写一个会失败的测试。
3. `pnpm check` 与 `pnpm test` 通过后本地提交；动了界面再跑 `pnpm test:web`。
4. 在真实 Harness 上试。发现的问题当场修，或记成下一个小片。
5. 汇报：代码完成、合成测试通过、真机通过分开说，没验证的直说。

## 并行

多个代理并行时，每个写代码的代理有自己的 worktree 和分支，只做自己那一片；合并由主负责人做，合并后重跑检查与测试。交给子代理的说明写清目标、范围、怎么验证，以及不能碰的东西（真实配置、正在运行的服务、用户数据）。子代理自报的结果不是证据，主负责人提交前自己重跑。

## 什么时候慢下来

- 改持久格式或迁移、改“会不会丢内容”的逻辑：做一轮独立审查，再提交。
- 推送、升级正在运行的服务、动用户的真实数据、花钱超出预期：先问用户。
- 拿不准的产品取舍：直接问用户，给出推荐。

## 不做的

不设审批代理；不维护任务地图、文件归属、测试用例登记和不变量表；不为每个决定写 ADR；不因为内部流程反复向用户要许可。
