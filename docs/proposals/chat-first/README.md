# 以 Chat 为中心，从零定义实施链路

日期：2026-10-08。状态：分步规划稿。用户已确认以连续 Chat 为中心、Harness Agent 与 Provider/模型可独立切换，并要求按新项目重新拆分步骤，再逐个优化。本篇定义规划顺序和每步验收目标；不表示具体接口、存储、交接方案已经采纳或实现。

现有功能与证据见 [功能地图](../../features/user-journeys.md)，交互解释见 [流转网页](../../features/chat-flow.html)。旧代码用于研究协议、适配经验和验证用例，功能分组与旧 Session 绑定方式不作为新产品的默认约束；要复用的实现也必须通过新契约的验收。旧程序继续遵循 [现行设计基线](../../../DESIGN.md)，本规划不隐式更改它。

## 1. 先定主线，再决定怎么写

主线是：用户进入 Chat → 选择 Harness Agent 与 Provider/模型 → 准备上下文 → Agent 执行 → 模型与工具往返 → 结果回到 Chat → 按需切换后继续。

两类核心用户使用同一组资源与执行语义：个人开发者从界面进入，工具与平台开发者从程序接口进入。资源管理为这条主线服务。

### 已确认的产品方向

- Chat 是持续对话和推进工作的公共容器，身份不随 Agent 或 Provider 改变。
- Harness Agent 是可选择的执行者，负责自己的规划和工具调用。
- Provider/模型是可独立选择的推理资源，不与某个 Agent 固定捆绑。
- 公共对话、进展、工作成果和执行证据由 HarnessHub 关联起来。
- 用户能随时提出切换；执行中切换的生效边界和交接机制需要显式设计。

### 第一轮建议采用的对象划分

| 对象 | 回答的问题 | 建议责任 |
|---|---|---|
| Chat | 我正在继续哪段对话和工作？ | 公共身份、消息、目标与进展、执行和成果的关联 |
| Message | 用户或系统在这段对话中说了什么？ | 内容、来源、顺序，以及是否已持久接收 |
| Execution | 这一次由谁、按什么选择做了什么？ | Agent、Provider/模型、工具与配置快照、状态、调用、产物和清理结果 |
| Agent 原生 Session | 当前执行者怎样保有它自己的后端状态？ | 由适配与运行层管理；创建、复用、恢复规则明确，不直接充当 Chat 身份 |
| Workspace | 工作文件在哪里、谁正在修改？ | 文件位置、写入归属、修改与产物关系 |
| Resource | 有哪些执行者、模型、凭据和工具可以选择？ | 一处登记、能力与可用性说明、可追溯版本 |

这是一份待细化的对象方案。第一版可先把“任务”表示为 Chat 中的工作目标，是否另设独立 Task 实体、一个 Chat 如何承载多个目标，进入第 2 步明确。Execution 与现有 Run 的映射不在这里预先假定。

## 2. 拆成八个功能步骤

| 顺序 | 功能步骤 | 输入 | 输出 | 完成判据 |
|---|---|---|---|---|
| 1 | 准备可用资源 | 本机 Agent、模型上游、凭据、工具内容与工作区 | 可选择的 Agent、Provider/模型、工具与能力说明 | 用户能判断哪些资源可用、哪些组合支持；配置错误明确报告 |
| 2 | 建立 Chat，接收消息与执行选择 | 用户消息、Agent、Provider/模型、工作区与工具选择 | 持久的 Chat/消息身份、本段执行意图与选择快照 | 刷新后对话仍在；两种选择独立；重复提交不重复创建；不可用选择不静默替换 |
| 3 | 准备执行上下文 | 公共对话、目标、进展、已有文件与成果 | 有来源、有边界、适合所选 Agent 的上下文 | 第一次执行、多轮继续和换 Agent 都能说明交给了它什么；超限或不支持明确失败 |
| 4 | 启动并监督 Harness Agent | 执行意图、上下文、适配能力、工作区与工具配置 | 归属明确的 Agent 执行与生命周期事件 | 能启动、等待、停止和报告失败；配置隔离与进程清理有证据 |
| 5 | 通过统一入口调用 Provider/模型 | Agent 的模型请求、本段模型选择与调用身份 | 模型回复、工具调用请求与模型调用记录 | 请求确实发往所选上游；协议、凭据、错误、用量与费用来源可核对 |
| 6 | 执行工具与处理权限 | 模型提出的工具操作、工具能力、实际权限选项 | 工具结果、工作区变化、允许或拒绝记录 | 权限决定、后端应用、工具结果分别可查；模型—工具循环可继续 |
| 7 | 结算结果，回到同一 Chat | 后端结束证据、在途调用、输出文件与资源状态 | 执行结果、产物、用量、错误、清理状态与公共进展 | 执行结束、结果达标和清理确认分开表达；订阅断线后仍可查询与回放 |
| 8 | 切换 Agent 或 Provider，并接续 | 用户的新选择、当前执行状态、公共上下文与成果 | 关联同一 Chat 的下一段执行 | Agent A→B→A、只换 Provider、只换模型和同时切换都保持工作连续；执行中交接边界明确 |

步骤 1 是前置准备；步骤 2–7 构成一次输入到结果的闭环；步骤 8 复用步骤 3–7，形成连续工作。步骤 5、6 可以在一段执行中多次往返。

取消、超时、权限等待和失败是这条链路的正常分支，不能留到最后再补。

## 3. 逐步建设，但每一步都走完整的纵向链路

每一步都按“用户行为与边界 → 契约与状态 → 最小实现 → 真实入口验证 → 文档与证据”推进。单个模块完成、页面能点或假模型给出回答，均不能代替该步的验收。

界面和程序接口共用所属应用服务；有持久状态的步骤从开始就保存到权威存储。不能先用浏览器临时状态冒充公共 Chat，或先造一个独立的演示执行循环再接真实 Runtime。

### 功能顺序与实施依赖

八步是用户可理解的功能流转顺序。后续步骤的必要契约可以先定义，不能把它解释成“先让 Agent 执行，再补模型入口和权限”。

| 实施范围 | 前置与验收边界 |
|---|---|
| 步骤 1–3 | 先定义并验证资源、持久输入和上下文；可以独立验收，不需要启动有副作用的 Agent 任务 |
| 步骤 4–6 的最小契约 | 在真实任务开始前共同具备：统一模型入口与调用归属、必要的权限处理、工作区归属、期限、取消和清理。不支持的工具或权限能力必须明确拒绝 |
| 步骤 4 的独立验收 | 可先用外部协议夹具验证生命周期，或对真实 Agent 验证初始化、停止和资源回收；这些证据不等于真实任务闭环通过 |
| 步骤 5–6 的逐项展开 | 在共同最小契约上，先验证文本模型往返，再扩展真实工具和权限往返；只有外部 Agent/模型可以由夹具替代，公共存储、接口与运行时保持真实 |
| 步骤 7–8 | 依赖前面的受控执行与证据链；先验证单段完整结算，再验证交接与下一段执行 |

步骤 4–6 需要作为一个最小运行闭环协调契约，再按职责逐项建设；独立能力验收与整条真实任务验收分别记录。

### 第 1 步：资源准备

需要先明确的内容：

- 一个 Agent 条目怎样表达已安装、可启动、可无人值守执行，以及支持哪些模型协议、工具、上下文和切换能力。
- Provider 是上游资源，模型是具体目标，凭据是独立秘密引用；选择 Agent 不应偷偷替换 Provider/模型。
- 安装发现、配置通过、连接检查、真实模型调用通过、真实 Agent 执行通过分别报告。
- 工具内容统一查找和选择，但指令、Skill、MCP、可执行命令保留各自的加载方式与信任边界。
- 资源版本、修改和停用怎样影响已经接受的执行；历史选择不能被热更新悄悄改写。

最小交付：能登记与查看资源、检查输入与能力、说明不可用原因，供下一步按身份引用。开始时只接入足以验证主线的资源，不追求 28 个 Agent 或全部 Provider 预设。

验收重点：有效配置可以被引用；无效配置被拒绝；不存在与不支持的组合明确失败；秘密不出现在公开配置、日志或事件中；不支持的平台能力如实说明。

### 第 2 步：Chat 与消息接收

先定义公共 Chat、消息和执行意图的身份、顺序与持久接收含义。输入中明确 Agent、Provider/模型、工作区、工具和预算等作用域；已经接收的选择形成可追溯快照。

最小交付：同一套应用入口供界面与 API 创建/继续 Chat、接收消息和选择、查询记录。接受输入不等于已经开始执行，更不等于完成任务。

验收重点：刷新、重启、重复提交、并发发送、资源被修改或移除、存储失败。消息草稿与已接收消息明确区分。

### 第 3 步：上下文准备

定义哪些公共信息交给 Agent、怎样体现来源与版本，以及何时增量补充或重建。原始消息和成果是事实；摘要和交接材料是可追溯的派生数据。

最小交付：一个有界的上下文准备入口，为首次执行、多轮继续和新执行者生成输入。不能把另一个 Agent 的内部状态假定为可直接读取或无损复制。

验收重点：跨 Agent 的待办与文件变化不丢失；旧摘要不覆盖新事实；超限不静默截断；上下文准备失败时不发起带副作用的执行。

### 第 4 步：Agent 执行

定义 Adapter/Driver 接口、私有配置、后端会话归属、工作区写入所有权、事件与结果证据、停止和清理入口。

最小交付：正式运行入口能驱动第一个 Agent，之后加入第二个 Agent 时共用应用与运行契约，入口不按产品名称写业务分支。

验收重点：启动失败、运行失败、取消、期限、进程崩溃、迟到事件、工作区冲突与清理未确认。操作系统隔离与独立进程监督分开验证。

### 第 5 步：模型调用

定义本段执行的模型目标如何映射到上游、调用身份怎样归属 Chat/Execution、凭据在哪里解析，以及流式与工具请求的协议契约。

最小交付：先接通一种必要协议、一条真实调用路径与账本，再按实际 Agent 需求扩展。所有受管理执行使用统一的模型访问路径，不保留未经声明的自带账号 fallback。

验收重点：实际上游与模型、认证失败、限流、流中断、取消、未知费用、账本失败。不能只依据配置名称证明调用已经到达目标。

### 第 6 步：工具与权限

定义 Agent 的原生工具、Library/MCP/命令的加载与调用责任，以及权限请求的实际选项、有效期、作用域、决定和确认。

最小交付：一次真实工具请求从 Agent 到用户或调用方，再回到 Agent，工具结果进入下一次模型请求；允许和拒绝都能走通。

验收重点：权限等待超时、重复或过期决定、后端未应用、工具失败、取消与工具进程清理。未上报的原生工具路径不能被宣称已受统一审批控制。

### 第 7 步：结果与证据

定义结算屏障、终态、事件顺序、文件产物、错误与费用来源，以及对话结果如何关联公共 Chat。

最小交付：输入到结果的一次完整闭环；界面与程序接口看到相同的持久事实。已提交状态和事件再对外发布。

验收重点：上游错误、无有效输出、缺产物、产物变化、取消与完成竞争、慢订阅与断线回放。完成执行和内容正确分别判断，未知费用不补零。

### 第 8 步：切换与接续

定义切换请求、实际生效选择、当前模型/工具/权限/进程的处理，以及后端会话与公共上下文的交接。用户随时能提出请求；具体生效边界必须明确可观察。

最小交付：同一 Chat 中两个 Agent、两个 Provider/模型可以独立切换并继续完成工作，每段的实际选择与结果都能追溯。

验收重点：A→B→A、同 Agent 换 Provider/模型、同时切换、执行中请求、交接失败、资源未清理、重启，以及其他执行者已改动文件的场景。切换失败不能伪造空会话恢复成功，也不能自动重跑未知结果。

## 4. 四项基础从第一步贯穿

| 基础 | 贯穿要求 |
|---|---|
| 数据与身份 | 公共事实由单一逻辑写入者管理；身份与作用域明确；持久提交先于发布；格式有版本，迁移有证据 |
| 安全与权限 | 管理和执行入口从开始就有明确认证；秘密只以引用保存；不支持的能力明确拒绝；不改并发任务共享环境 |
| 事件、错误与恢复 | 每段操作有归属与停止方式；失败和未知结果可查询；取消确认不冒充清理确认；未知执行不自动重跑 |
| 界面与程序接口 | 共用应用服务、校验和状态语义；界面状态可从持久数据重建；SDK 是正式接口使用方，不另建业务规则 |

这些内容是建设原则建议，需要在相关步骤形成具体契约；“新项目”不构成绕过真实存储、进程监督、权限与错误处理的理由。

## 5. 第一版最小闭环的范围

建议用一个工作区、两个 Harness Agent、两个 Provider/模型，以及一个能请求权限的工具完成端到端验证：

1. 在同一 Chat 发送目标，由 Agent A 与 Provider X 分析。
2. 用一次工具请求验证允许或拒绝，再取得结果与调用证据。
3. 切到 Agent B，先保持 Provider X，基于公共上下文继续工作。
4. 保持 Agent B，换到 Provider Y/模型继续。
5. 回到 Agent A，能理解其他执行者已经完成的工作。
6. 在执行中提出切换、取消或遇到失败，能解释真正生效的选择、停止原因和清理结果。

所有切换组合按实际适配能力验证；不支持的组合明确拒绝。真实模型与真实 Agent、假上游与夹具、各操作系统是不同证据范围。

路由分类器、订阅接入、图像生成、跨机共享、Workflow、Benchmark、多 Agent 同时并行比较等，按后续需求纳入；它们不是验证连续 Chat 主线的前置条件。模型调用的必要权限、凭据保护与账本不能因此推迟。
