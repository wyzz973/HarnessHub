# 开源版 ADR

状态：2026-10-02 所有者确认了许可证、名称、仓库策略、默认联网与维护模式，并授权 AI 维护者全程负责开发与维护；P01–P11 据此标为 accepted；P12 在所有者选择沿用现有仓库后标为 accepted。结构遵循 [ADR 模板](../../templates/adr.md)。新 `main` 建立后，按模板拆成 `docs/decisions/NNNN-*.md`；被推翻的决定保留并标 superseded。

## ADR-P01 语言与运行时

Status: accepted（2026-10-02）

**问题**：开源版要覆盖 Magpie 的模型平面与 Agent 平面，同时保留 HarnessHub 的执行平面。Magpie 用 Go，单文件约 15 MB；HarnessHub 现有 TypeScript 源码约 3.6 万行、测试约 2.8 万行，运行契约、事件存储、Worker 监督、ACP 驱动、工具包都已实现并经过多平台验证。

**决定**：继续使用 TypeScript（strict、ESM）与 Node.js 24 LTS，以 Node 单可执行文件（SEA）作为主要分发形式，npm 包与容器镜像为辅。

**考虑过的替代方案**：

| 方案 | 收益 | 代价 | 结论 |
|---|---|---|---|
| Go 重写 | 单文件小、交叉编译简单、与 Magpie 同构 | 重写运行时、驱动、存储、工具包与全部测试，估计 40–60 人周才能回到现有能力；ACP 官方 SDK 与多数被管理的 Agent 属于 Node 生态 | 不采用 |
| Rust 核心 + TypeScript 外围 | 网关热路径性能与内存最好 | 两套语言与构建链，贡献门槛高；网关附加延迟目标用 Node 已可达到（待基准验证） | 不采用，网关基准不达标时重新评估 |
| 维持现状（Node + Next.js 多进程） | 零迁移成本 | 需要用户预装 Node，控制台单独进程，分发复杂 | 不采用 |

**后果**：复用现有资产，M1 即可交付模型平面。代价是单文件 98–131 MB（OSS-008 在五个平台实测，其中 Node 运行时约占 96%）、冷启动慢于 Go（CI runner 上每组 30 次的 p95 为 0.35–1.32 s，本机 macOS arm64 约 0.16 s）。重新评估条件：M0 打包验证中冷启动超过 1.5 s 或体积超过 150 MB；或 M1 网关基准的附加延迟 p99 超过目标。

**验证要求**：M0 在 macOS（arm64、x64）、Linux（x64、arm64）、Windows（x64）上构建 SEA 文件，测量体积与冷启动，并跑通 `hh serve` 加一次假上游网关调用。OSS-008 已完成：五个平台构建与端到端检查通过，体积与冷启动都在重新评估条件之内（运行 37002564159，每组 30 次），实测数字与未验证的情形见 [SEA 可行性验证](sea-spike.md)。2026-10-04 可执行文件改为运行 `hh` 的全部命令后，本机复测见该文第 10 节：体积 130.9 MB，首次运行与已解包的 p95 为 309.6 ms 与 319.5 ms，仍在条件以内；冷启动约为 10-02 的两倍，同机 node 基线同样增长，增量来自守护进程的启动工作。

## ADR-P02 许可证

Status: accepted（2026-10-02，所有者决定）

**问题**：现有自有代码尚未指定许可证（见 [第三方声明](../../../THIRD_PARTY_NOTICES.md)），开源前必须选定。项目希望被个人与企业广泛采用，并接受外部贡献。

**决定**：MIT 许可证；贡献使用 DCO（Signed-off-by），不要求 CLA。所有者确认现有全部自有代码的权利归其所有。

**考虑过的替代方案**：Apache-2.0（有明确的专利授权与专利报复条款，企业法务更容易放行，但需要维护 NOTICE 与修改说明）；AGPL-3.0（能防止闭源托管，但会显著降低采用意愿，本项目不运营 SaaS，不需要这种保护）。

**后果**：与 Magpie、claude-code-router、CC Switch 等同类项目一致，使用与再分发门槛最低，维护成本几乎为零。没有明确的专利授权；从 Apache-2.0 组件并入的代码按原许可证保留 LICENSE 与 NOTICE。重新评估条件：企业用户因专利条款提出明确需求。

**验证要求**：CI 中的许可证扫描对全部依赖通过白名单；所有源文件带 `SPDX-License-Identifier: MIT`。

## ADR-P03 共享网关与作用域 Gateway Key

Status: accepted（2026-10-02）

**问题**：现状是每个 Session 的 Worker 内各起一个私有网关，靠随机令牌做结构性归因，但全局接线的 Agent 需要一个稳定地址。Magpie 只有一个共享入口，回环来源带任意 token 都放行，无法按调用方归因，也无法限制权限。

**决定**：守护进程内只有一个网关入口（默认 `127.0.0.1:3180/v1`）。每个调用方持有作用域明确的 Gateway Key：`agent:<id>`（全局接线）、`session:<id>`（执行平面）、`client:<name>`（外部工具），以及团队版的用户 Key。回环来源同样必须带有效 Key；Key 只存哈希，可设置模型白名单、额度与过期时间，可单独吊销。

**考虑过的替代方案**：保留每 Session 私有网关（归因最直接，但全局接线需要第二套网关，路由与账本也要分散到各个 Worker）；完全照搬 Magpie 的回环放行（最省事，但同机任意进程都能消耗用户的上游额度，也无从审计）。

**后果**：一套路由与账本服务两种接线模式。全局接线时 Key 会写进 Agent 的配置文件；能用环境变量引用的 Agent 一律用环境变量，否则写入文件，并把该 Key 限定为回环可用、只允许该 Agent。

**验证要求**：一致性测试覆盖“无 Key、错误 Key、吊销 Key、超额 Key、越权模型”五种拒绝；账本中每条调用都能对应到唯一的 Key 作用域。

## ADR-P04 两种接线模式

Status: accepted（2026-10-02）

**问题**：Magpie 的价值在于改写用户自己的 Agent 配置；HarnessHub 现有的隔离做法从不触碰用户配置，适合无人值守执行。两类用户都需要支持。

**决定**：同时提供全局接线与隔离接线。全局接线必须经过“差异预览、写前备份、原子写入、回读校验、记录 applied”五步，并提供 `hh unwire` 还原；隔离接线只用于执行平面的 Session，不写用户文件。

**考虑过的替代方案**：只做隔离接线（安全，但失去与 Magpie 对标的核心场景）；只做全局接线（执行平面会受用户配置漂移影响，结果不可复现）。

**后果**：Adapter 需要同时描述两种模式。全局接线要处理格式保真编辑与漂移，这是 Magpie 投入最多修复的领域，需要充分的一致性测试。

**验证要求**：每个稳定级 Adapter 在固定版本上满足“接线后 Agent 的请求到达网关”“还原后配置文件与接线前逐字节一致”。

## ADR-P05 路由、重试与故障转移

Status: accepted（2026-10-02）

**问题**：现状的网关零重试，还关掉了 Codex 自身的重试，瞬时上游故障直接导致整轮失败。Magpie 在首字节前做跨候选转移与有限重试，并在上游点名拒绝字段时自动剔除重发、在进程内记住。

**决定**：故障转移与重试只发生在首个字节送达客户端之前；只针对可证明的瞬时失败（连接失败、408、500、502、503、504、529，以及带 Retry-After 且不超过上限的 429）；次数、退避与上限由路由组配置，并有全局上限；每次尝试都写入证据。客户端断开或 Run 取消时不转移。认证失败、余额不足、没有 Retry-After 的 429、模型未开通这类归因于具体 Credential 的失败，不重试同一候选，但允许转到路由组中使用其他 Credential 的候选。上游点名拒绝可选字段时，默认不自动剔除重发，由 provider 级的显式开关启用，体检会给出建议。具体次数、退避、熔断与扣留窗口见 [03 模型平面](03-model-plane.md#5-路由故障转移与重试)。

**考虑过的替代方案**：零重试（行为最可预测，但可用性差，而且无法利用多 provider）；完全照搬 Magpie 的自适应（成功率最高，但行为随学习状态漂移、难以复现，也可能悄悄改变请求语义）。

**后果**：可用性接近 Magpie，同时保留可审计性。重新评估条件：一致性测试或用户反馈显示显式开关的配置负担过高。

**验证要求**：脚本化上游覆盖“503 后成功”“首字节后断流不重试”“400 不重试”“取消期间不再发请求”“Retry-After 超过上限不重试”。

**修订（2026-10-04）**：对标 Magpie 后，重试只在最后一个还能尝试的候选上进行，限流类 429 没有 Retry-After 时也在那里按 1、2、4 秒重试；失败按类别休息。见 [ADR 0025](../../decisions/0025-magpie-routing-parity.md)。

## ADR-P06 存储

Status: accepted（2026-10-02）

**问题**：本机需要零配置，团队服务器需要并发、备份与高可用。

**决定**：本机使用 `node:sqlite`，团队服务器使用 PostgreSQL，两者共用同一个 Store 接口、同一套只进不退的版本化迁移，以及同一套一致性测试。事件存储依然是唯一事实来源，导出与观测从事件重建。

**考虑过的替代方案**：只用 SQLite（团队版的并发与高可用受限）；引入 ORM（会弱化现有对事务与序号的精确控制）。

**后果**：Store 实现要成对维护，迁移需要双后端测试。

**验证要求**：同一套 Store 一致性测试在两个后端上通过；迁移在两个后端上可以从任一已发布版本升级到最新版本。

## ADR-P07 插件协议

Status: accepted（2026-10-02）

**问题**：provider 认证、Adapter 扩展、导出器需要社区扩展，且不能拖垮守护进程。

**决定**：插件运行在独立进程中，经 stdio 使用 JSON-RPC 2.0，握手时协商协议版本并声明能力与权限；守护进程负责监督、超时与重启。

**考虑过的替代方案**：进程内 JS 模块（性能最好，但崩溃与恶意代码会直接影响守护进程）；WebAssembly（隔离好，但网络与文件访问需要大量宿主函数，生态尚不成熟）。

**后果**：插件可以用任何语言编写，每次调用多一次进程间往返，热路径上的 provider 变换需要做基准测试。

**验证要求**：插件崩溃、超时、返回非法数据时，守护进程保持可用，相关请求以明确的错误失败。

## ADR-P08 遥测默认关闭

Status: accepted（2026-10-02）

**问题**：项目需要了解安装量与功能使用情况；用户代码与提示词高度敏感。

**决定**：默认不发送任何遥测数据。首次运行时询问是否同意匿名统计；同意后只发送版本、平台、启用的功能开关与计数，绝不包含提示词、代码、路径、Key 或模型输出。`DO_NOT_TRACK=1` 始终生效。

**考虑过的替代方案**：Magpie 的默认开启并可关闭（数据更全，但与“默认安全”的定位冲突）。

**后果**：统计样本偏少，需要配合 GitHub 下载量与问卷。

**验证要求**：网络捕获测试证明未同意时没有任何外发请求。

## ADR-P09 订阅复用进核心

Status: accepted（2026-10-03 修订；原决定“订阅复用不进核心”于 2026-10-02 采纳，所有者在对标 Magpie 时改为内置）

**问题**：Magpie 把 Claude Code、Codex（ChatGPT）、Copilot 等订阅登录作为 provider 共享给其他 Agent，是其最受欢迎的功能之一；但部分厂商的服务条款限制订阅在其官方客户端之外使用，用户账号存在被限制或封禁的风险。

**决定**：订阅 provider 内置进核心，按账号逐个显式启用。启用前与控制台中持续显示该厂商条款风险的明确提示，由用户自行决定；账本按实际应答的账号记录用量。实现只使用以下方式：厂商公开支持的登录与令牌刷新流程，或驱动用户本机已安装的官方客户端；不实现以伪造客户端身份、指纹或请求特征来规避厂商检测的手段。每个订阅 provider 在文档中写明所用机制与已知风险。

**考虑过的替代方案**：只作为社区插件（原决定，风险最低，但对“只想用订阅”的用户缺少吸引力）；完全不支持。

**后果**：项目需要跟踪各厂商条款与接口变化；当某种机制被厂商明确禁止或封堵时，对应 provider 标为不可用并在发布说明中说明，而不是寻找绕过方式。

**验证要求**：每种订阅 provider 有使用假令牌与本机回环假上游的测试；测试与开发过程不读取开发者本机真实的登录凭据。

**后续（2026-10-04）**：ChatGPT 经 OpenAI 的 Sign in with ChatGPT for open-source apps 实现；Copilot 计划经官方 Copilot SDK（用户自己的 `copilot` 登录或细粒度 PAT）。Claude 订阅标为不可用、不实现：Anthropic 的 [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance) 写明不允许第三方开发者“route requests through Free, Pro, or Max plan credentials on behalf of their users”，把其他 Agent 的请求经用户的 `claude` 发出属于这种情形，终端用户的例外只覆盖使用未修改的 Claude Code 本身。见 [ADR 0026](../../decisions/0026-subscription-accounts.md) 与 [订阅账号](../../subscriptions.md)。

## ADR-P10 控制台改为内嵌静态单页

Status: accepted（2026-10-02）

**问题**：现有 Next.js 控制台需要单独的 Node 服务进程与代理层，与单文件分发冲突。

**决定**：控制台改为 React + Vite 构建的静态单页，由守护进程直接提供，同源调用 `/api/v1`。复用现有组件与设计令牌。

**考虑过的替代方案**：保留 Next.js 并打进同一进程（构建与运行时复杂度高，服务端渲染对本机工具没有价值）。

**后果**：需要迁移路由与数据获取层；控制台与 API 同源，CSRF 与 Origin 校验仍然必需。

**验证要求**：控制台浏览器回归测试在真实守护进程上通过，并进入必需检查。

## ADR-P11 API 版本与兼容承诺

Status: accepted（2026-10-02）

**问题**：SDK、CLI、插件与第三方集成都依赖 API，需要可预期的变更规则。

**决定**：管理与执行 API 使用路径版本 `/api/v1`，1.0 起在同一大版本内只做向后兼容的增加；弃用的字段与端点至少保留两个次版本，并在响应头 `Deprecation` 与 `Sunset` 中声明。OpenAPI 3.1 契约由代码生成，CI 用上一个发布版本的契约做兼容性比对。模型网关端点跟随上游协议，不承诺超出上游的稳定性。

**考虑过的替代方案**：按日期的版本头（灵活，但对 CLI 与插件的心智负担更大）。

**后果**：破坏性变更需要新的大版本与迁移指南。

**验证要求**：CI 中的 OpenAPI 兼容检查对删除字段、改变类型、收紧枚举报错。

## ADR-P12 仓库与历史

Status: accepted（2026-10-02，所有者选择）

**问题**：现有仓库 `wyzz973/HarnessHub` 已经公开，包含比赛与公司交付材料、约 480 MB 第三方归档和大量开发机路径。GitHub 仓库名不区分大小写，同一账号下不能再建 `harnesshub`；组织名 `HarnessHub` 已被一个无关项目占用。

**决定**：沿用 `wyzz973/HarnessHub`。开源版的 `main` 是一条新的孤立分支，初始提交是一份经过秘密扫描与人工审查的干净快照，按 [12 路线图与迁移](12-roadmap-migration.md) 的去留表迁入代码。旧历史完整保留在 `archive/competition` 分支，并在 `324c9e8` 打 `competition-final` 标签；已发布的 `competition-latest`、`offline-dev-latest` 等 Release 原样保留，下载链接不变。切换前先推送归档分支与标签，确认无误后再替换 `main`。

**考虑过的替代方案**：新建 GitHub 组织（适合长期社区化，但需要所有者在网页上创建，且优选名称已被占用）；把旧仓库改名后在账号下新建（新仓库占用旧名后，旧 Release 链接的自动重定向会失效）。

**后果**：仓库地址、Star 与 Release 不变；`main` 的历史从干净快照开始，旧的提交与讨论仍可在归档分支中查到。`main` 的替换是一次性强制推送，执行前必须确认归档分支与标签已在远端。

**验证要求**：切换前远端存在 `archive/competition` 与 `competition-final`，且指向预期提交；新 `main` 的全部历史经 gitleaks 扫描无发现；默认分支切换后，旧 Release 资产仍可下载。
