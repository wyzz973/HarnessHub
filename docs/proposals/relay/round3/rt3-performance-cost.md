# RT3 · 第一版架构红队审查：性能与成本

审查员 RT3（性能与成本），2026-11-03。对象：[v1-architecture.md](v1-architecture.md)。基线 `cc/relay-design`（基点 `07a0825`），`file:line` 按该基点核对。只写本文件；没有运行任何 Harness 的会话或提示，没有做网络调研，没有碰 4317 服务与 `data/`。

标注：【事实】代码或报告原文；【实测】本机测量（R4、R6 的，或本评审的：Apple M5 Pro、macOS 27.0.1、Node 26.11.1、SQLite 3.53.4，见第 4 节）；【文档常量】；【推算】按公式由前两者得出；【推断】；【建议】。价格用 R6 §2.1（2026-11-02），生命期费用用 J2 的 C = T·[p_w(1+k) + p_r(R−1−k)]，(R,k) 取 (80,0)、(80,5)、(300,0)、(300,15) 四点。

## 0 总评

骨架与“派发前、首个输出前 +0 次整份提交”成立；但预算解析器在长历史、CJK、高 R/k 与价格悬崖下会把交接判成 `RELAY_INPUT_LIMIT`，有界核对会把“没扫到”当成“没送达”，relay 行越界会让整个 Runtime 致命；构建、缓存、首回合时延与估算器四项目标在现有数据布局与测量方法下不可信或测不出。4 个 blocker（P01–P04）修正之前不宜进入实现。

## 1 重算

**1.1 切换路径。**【事实】新启动的回合在派发前有以下整份快照提交：受理一次，加上 `run.preparing`（runtime.ts:1332）、`run.context_prepared`（:1341）、`run.protocol`（:1369）、`native.binding_prepared`（:1384）与 `run.authorized`（:1389），派发本身在 :1415。复用保留进程时换成 `native.process_reused`（:1349）。v1 把 context_prepared 移到 open 之后，并把 relay 行并入该事务，提交次数不变；E1 并入 `run.first_output`（:1175），因此“+0”成立，而且还能再省一次（P15）。以下时延不在任何目标里（P07）：
- 复用进程时观测不被启动遮住：启动约 7 ms（R6[S29]），观测两条命令约 34 ms（3k 文件，R6），2 万文件时约 200 ms。
- 返回时的核对 RPC、`costly` 核对（≤5 s）、排在 `run.ended` 前的 after_turn 核对（≤2 s），以及懒重建等待（≤1 s）。
- 每次 await 之后 `continue()`→`owned()`→`load()` 会重读整份快照（runtime.ts:995–1011），7.6 MiB 时约 35 ms（R6 §2.6.3）。

**1.2 构建与内存（本评审微基准）。**

**1.4 预算解析器的边界行为。** capCost = $0.20/π（token）：

| 目标 | (80,0) | (80,5) | (300,0) | (300,15) |
|---|---:|---:|---:|---:|
| Opus 5.5，API key 5m | 9,615 | 4,464 | 3,086 | 1,461 |

| gpt‑6.1‑sol / Sonnet 5.5 | 19,230 | 8,928 | 6,172 | 2,923 |

以 Claude 为目标、乘 1.3 估算时，必含块最小约 1.35k：框架 601，状态节约 340，结束行约 50，账目 ≤300，再加一条短原话。

**悬崖**：v1 的公式是 capCliff = cliff − contextUsed − 15k − 16k。按此计算，Haiku 5.5 在 contextUsed ≥67.8k、OpenAI 在 ≥239.8k 时 hardCap 低于 1,200，交接在启动前被判 blocked。

**窗口未知**：一律按 128k 计，标准档为 6,400。伪代码 `src == "assumed" ? 0.05 : 0.05` 的两支取值相同。

**CJK**：用户原话的上限按“字”定，同一上限在中文里约等于英文的 4 倍 token。

**1.5 存储。**【实测，JSON 长度】`binding.relay` 的长度：fresh 187 B、synced 347 B、suspect 377 B、pending 476 B。`run.relay` 218 B，加上 `contextReadyAt` 30 B 与 `backend.input` 22 B，约 270 B。RunDigest 典型约 6 KiB/Run（合成），每个会话都要写。

## 2 发现

### P01（blocker）必含块没有上界，长历史重新停摆
- **章节**：5.1 第 2 节、5.3、6.3、10.4“只交目标”、16 S4。
- **触发**：
  - 首次交给新目标且历史长（S4）。
  - B 连做约 13–23 轮后返回 A。
  - 同意处选择“只交目标”（约 10 轮即超）。
  - 中文的长首条需求。
- **证据**：6.3 规定 `mustHave = fixed + goals(首条 + 自上次送达以来的用户消息 + 钉住 + 附言)`，并且 `mustHave > budget.T → blocked`。新目标没有任何送达记录，“自上次送达以来”就等于全部用户消息。
  - S4：200 条 × 150–267 token（R6 成本模型 / 长回复画像），远超 8k。
  - 增量：`DELTA_USER_CAP` 为 4k，而末单元必须照录，超过就只能走到 blocked。
  - 中文首条 2,000 字乘 1.3 约 2.5k，单条就挤满 `MUST_HAVE_CAP`。
  - 增量的 goals 每次都重复首条原话，而 5.6 样例里没有。
  - 重锚样例带首条，与 `REANCHOR_CAP` 600 冲突。
  - prePlan 只检查通道上限，这类失败要到 open 之后才发现，违反 K8，白白启动 1.3–5 s。
- **修正**：
  - 用户原话改用按 token 计的独立预算 U：标准档 2.5k、精简档 1.5k、只交目标 1.2k、增量 1.0k、重锚 0.4k。填入顺序为：首条（头尾截到 U/3）→ 钉住与附言 → 自上次送达以来的消息从新到旧；其余按回合区间记入账目，C9 允许用词表挑选要保留的约束句。
  - goals 按 kind 区分：delta 不含首条。
  - `RELAY_INPUT_LIMIT` 只在“框架 + 当前输入”超过通道上限时出现，并在 prePlan 中判定。
  - J3 M8 改写为“放得下时全部保留，放不下时从新到旧保留并计数”。
  - 属性测试：在 ≤256 Run、全部档位与 kind 下，只要当前输入放得进通道，就不出现 blocked。

### P02（blocker）费用、时延与悬崖上限会把 T 压到必含块以下
- **章节**：6.2、6.3、7.3。
- **触发**：
  - 目标是 API key 登录、R/k 高的 Claude。
  - 返回到上下文 ≥约 68k 的 Haiku 5.5 绑定，或 ≥约 240k 的 OpenAI 绑定。
  - 目标是窗口未知的本地小窗口模型。
- **证据**：
  - `T = min(TIER_CAP, hardCap, min(capLatency, capCost))` 之后再与 mustHave 比较，超出就 blocked（数字见 1.4）。这违反 C2“费用与时延上限只能调低档位”。
  - 悬崖项里的 contextUsed 来自 usage，已经包含固定前缀，公式又扣了一次 15k；已经越过悬崖的绑定 capCliff 为负，同样 blocked。注释“只可能是窗口极小或原话过长”不成立。
  - `plan(run, binding, budget)` 先拿到预算，再判断 `need = ∅`。照伪代码实现，单 Harness 的 Haiku 会话上下文到约 68k 之后每一轮都会被拒，违反 G3 与 INV-30。
  - 订阅用户也按 API 美元价压档。
  - 窗口未知时按 128k 估算，对 16–32k 的本地模型（Codex `--oss`，以及 OpenClaw、OpenCode 的本地 Provider）会让首回合溢出。
- **修正**：
  1. `need = ∅ ∧ ¬reanchor` 时先原样发送，不进入 chooseBudget。
  2. 硬上限只保留通道与窗口两项。
  3. 费用与时延只在“标准 / 精简 / 只交目标”之间选档，最低落到“只交目标”或 mustHave；超出时照发，并在卡片上显示估算。
  4. 悬崖只在 `contextUsed < cliff ≤ contextUsed + S_B·[新会话] + T + 0.2T + 2k` 时压档；已经越过的不压档，费用按悬崖价计并提示。
  5. 窗口未知且 Provider 为本地或未知时按 32k 估算；`documented(model)` 表集中维护，带日期与来源。
  6. 订阅或认证未知时不用美元上限。
  7. 属性测试：在任意 (R̂, k̂, 价格, 窗口, contextUsed) 下，只要放得进通道就不 blocked；原样路径断言不调用 chooseBudget。

### P03（blocker）有界核对把“没扫到”判成“没送达”
- **章节**：7.1–7.4、8.1。
- **触发**：
  - Claude 中被取消的工具密集回合（用户条目之后写入超过 2 MiB）。
  - 返回 A 时，A 最后一个标记之后已经写入超过 2 MiB。
  - OpenClaw 一回合产生超过 200 条转录。
- **证据**：
  - 8.1 规定 Claude 只扫 JSONL 尾部 ≤2 MiB。
  - OpenClaw 只取 `TRANSCRIPT_WINDOW = 200`（openclaw.ts:18、:442），现有代码在窗口不够时已经会报“本回合更早的条目未对账”（:446–447）。
  - 7.1 规定 `absent → not_recorded`；7.3 让 synced 且核对便宜的绑定每次返回都核对；7.4 判 `marker_absent` 后在派发前停下，默认整份补发。
  - 结果是重复注入：Opus 8k、R=300、k=15 时每次多花 $1.09。或者每次返回都弹出选择，损害“像原生”。
- **修正**：
  - 改为按位置核对。派发前把原生位置记入 `relay_deliveries`：
    - Claude：`startText` 之前 stat 一次 JSONL 的字节长度，并在 open 时缓存文件路径，免得每次在至多 4,096 个项目目录里查找（claude.ts:11、:81）。
    - OpenClaw：用已有的 `before`（openclaw.ts:429）。
    - Codex：用 turnId 或 clientId。
  - 核对只读该位置之后的首条用户条目，代价 O(1)。
  - 窗口没覆盖到该位置时一律记为 `unknown(verify_unavailable)`；只有该位置存在、且是另一条用户条目时才算 absent。
  - RelayConformance 增加一项：回合超过窗口时，核对结果只能是 present 或 unknown。
  - verifyMs 目标：本机读 p95 ≤20 ms，RPC p95 ≤300 ms。

### P04（blocker）行尺寸上限只靠 SQLite CHECK，越界会让整个 Runtime 致命
- **章节**：4、9、11.1、14.1。
- **触发**：
  - 文件数超过约 3,500 的非 git 工作区，做任何一次交接。
  - 改动或未跟踪文件超过约 2,600 的 git 工作区。
  - CJK 内容把 RunDigest 推过 64 KiB。
- **证据**：
  - relay 行与快照在同一个 `transact` 里写（3.2）。`commit()` 把不在白名单内的错误交给 `fail()`（runtime.ts:791–797）；`fail()` 停掉所有执行，并把会话标为 blocked（:804–822）。
  - `files_json` 的上限是 262,144 B。tree 观测按设计至多扫描 2 万项，每项约 75 B，所以约 3.5k 项就会越界。
  - 摘要的字段上限按“字”定，中文最坏情况约 92 KB；本评审的微基准按 `.length` 定尺寸时就撞上了这条 CHECK。
  - v1 只为 `run.ended` 写了隔离规则。
- **修正**：
  - 所有 relay 行在进入 `transact` 之前在内存中序列化，用 `Buffer.byteLength` 校验，并按字段的字节预算截断。
  - 观测只存有界摘要：改动优先、≤1,000 项，另存计数与全量指纹；越界时记为 `partial`。
  - relay 写入失败统一映射为 `RELAY_PREPARE_FAILED`，保证不进入 `fail()`。
  - 测试：2 万文件的非 git 目录、5k 未跟踪文件的仓库、字段打满的中文摘要，三种情况下交接都照常完成。

### P05（major）构建成本是 O(|need| × 摘要大小)，不是 O(预算)
- **章节**：6.3、9、11.1、14.1。
- **触发**：256 Run 的工具密集或中文为主会话。
- **证据**：
  - size 与 cumulative 都存在 `digest_json` 里，第一遍定档要逐条解析（实测见 1.2）。
  - 省略账目共 13 类，前缀和只覆盖其中 5 类。
  - 所引依据“buildPublicContext 1.84 ms”不含读库、叙述化、脱敏与哈希。
  - 冷路径懒重建：最坏 256 Run × 128 个详情 × 0.1 ms（R4 M5）约 3.3 s，“p95 ≤1 s”在最坏情况下不成立。
- **修正**：
  - 把 size、13 类计数与前缀和放进约 200 B 的窄列，排在 `digest_json` 之前，或单独成表。
  - 只对选为 G1、G2、G3 的单元读整条摘要。
  - 懒重建分两级：G3 与区间行只用快照里的 `PublicRun.tools`，只有尾部与锚点才读工具详情（约 12 条 × 128 个详情，约 0.15 s）。
  - 目标改为：在上限尺寸的中文摘要下，定档 p95 ≤2 ms，组装＋脱敏＋哈希 p95 ≤10 ms，额外堆 ≤4 MiB。合成会话生成器必须包含打满上限的摘要。

### P06（major）预取 LRU 的“复用字节”在定义上无法命中
- **章节**：5.1 首行、5.5、6.4、11.1、12.1 T2/T3。
- **证据**：
  - 首行是当前输入的前 200 字，打开选择器时这条输入还不存在。
  - 第 1、5 节来自派发时的观测，ID 又依赖两者，所以“预取命中 ≤2 ms”达不到。
  - T2 的“sha256 与实际发送一致”几乎每次都会变成 T3 的“发送时已更新”。
  - 选择器为每个候选在主线程渲染一次，候选数没有上限。
- **修正**：
  - 预取只缓存与输入、观测无关的第 2–4、6–10 节及其尺寸。
  - finalize 拼接首行与第 1、5 节并计算 ID，p95 ≤5 ms。
  - 选择器的规模估算只跑定档，不渲染；每次打开选择器总 CPU ≤20 ms，分片执行。

### P07（major）返回 A 与回合结束路径上的时延没有预算
- **章节**：6.1、6.4、7.3、8.1、11.1。
- **触发**：A→B→A 复用保留进程；Claude、Codex、OpenClaw 的交接回合结束；OpenCode 重发。
- **证据**：见 1.1。11.1 的“CPU ≤10 ms”不含观测与 E2；“首回合时延”只算预填充。原生续接本来几乎零开销。
- **修正**：
  - 新增目标“接力造成的受理→派发增量”，用零延迟假 Harness 测量，并断言 load 次数：新启动时 p95 ≤ max(0, 观测 − 启动) + 15 ms；复用进程返回时 p95 ≤50 ms（3k 文件）。
  - 切换生效或用户开始输入时就启动观测；派发时若 HEAD 与 `.git/index` 的 mtime 未变、观测距今 ≤60 s，就直接复用。
  - 核对按位置进行（P03）。
  - `costly` 核对不进派发路径。
  - E1 或 E3 已经定论时，`run.ended` 不等 after_turn 核对。
  - finalize 复用 prePlan 读到的快照。

### P08（major）原始 Harness 第一次被换回时判成整份 packet
- **章节**：6.3、7.2、5.6、14.3 INV-30、16 S2。
- **触发**：最常见的 A→B→A，A 是对话开始时的 Harness。
- **证据**：
  - 7.2 没有“fresh 状态下的本绑定普通回合”这一转换，A 一直停在 fresh；6.3 中 fresh 一律判成 packet，约 1.6–2.1k。
  - S2 却写成 synced、增量约 520；增量框架引用的 basePacketId 对 A 来说并不存在。
  - INV-30 的字面（“从未收到交接单的绑定逐字节相同”）会禁止向 A 发任何增量，违反 INV-14。
  - 费用差见 1.3：订阅 1h 下是 3.1 倍。
- **修正**：
  - 只在本纪元该绑定没有执行过任何 Run 时判为 packet；否则发 delta，缺少基准交接单时附一段 ≤120 token 的规则行。
  - goals 只取外来 Run 的用户原话。
  - INV-30 改为“外来事实为空时逐字节相同”。

### P09（major）单一乘数的 est/1 达不到 p90 ≤20%，样例数字也不是用它算的
- **章节**：6.2、13.1、5.4、5.6。
- **证据**：【实测，o200k，gpt-tokenizer 3.4.0，离线】
  - 118 段混合语料上 \|误差\| p50 9%、p90 29%。
  - 纯中文与 TypeScript 各高估 25%，英文高估 15%；交接单形态的文本只差 1–7%。
  - ASCII 的密度随内容变化：字母数字与空格约 0.17 token/字符，符号约 0.56。四系数模型在样本内 p90 为 17%。
  - 框架模板 462 / 446 token，超过 J3 M9 的 ≤400；S2 增量用了错误的系数。
  - Anthropic 的 1.3 与 DeepSeek 的 1.0 无本机分词器可核，只是假设。
- **修正**：
  - 每个模型族一组四系数（非负最小二乘），在 RelayBench-X 渲染出的交接单上拟合，用留出集验证。
  - 接近硬上限时按 est×(1+e90) 估算。
  - 写明校准工具：o200k 离线；Claude 用 `count_tokens`（独立凭据）；DeepSeek 用其分词器文件。
  - 系数版本纳入 `policyVersion`；文中样例数字由 CI 重算。

### P10（major）费用估算的输入与公式没有可执行定义
- **章节**：6.2 π、7.3、11.1、12.1 T0。
- **证据**：
  - R 是从交接到压缩或会话结束为止的请求总数（R6 公式 1）。“每回合工具调用数 + 1”只是单回合请求数 q 的上界，没有统计视界。
  - 决策时 R 与 k 都是未来量。用上界代理会把 capCost 压低（P02）。
  - 同一 T 在不同 (R,k) 下费用相差 6.6 倍。
  - T0 写的“约 +1.5 秒、$0.06”出自 R6 的公式；按 7.3 自己的 (S_A+T)·p_w，在 T=8k 时应为 $0.115、+2.9 s。
  - 用回合级时间判断“热”偏乐观：TTL 从最后一个请求的开始计起，而回合结束时间更晚。
- **修正**：
  - 每个包在窗口关闭时（压缩、清空、换纪元、空闲超过 24 h）把实现值 R = Σ(工具调用数 + 1) 与 k 只以计数形式写入 `relay_deliveries`。
  - R̂、k̂ 取同一（harness、模型族、认证类别）最近 50 个实现值的中位数；n < 20 时用 R=80、k=0，并标注“先验”。
  - 只用于显示与选档建议。
  - Driver 声明固定前缀能否跨会话命中，由同一函数生成 T0 文案。
  - 判“热”用 now − endedAt < 0.8·TTL。

### P11（major）缓存目标 ≥0.85 不可归因
- **章节**：11.1、13.3 P10。
- **证据**：
  - 按回合聚合的占比（control.ts:70–71、acp.ts:538–543）会被大包抬高。
  - DeepSeek 的缓存构建要几秒，且尽力而为（R6 §2.2），与接力无关就可能达不到。
  - 交接单被改写或重复写入，这个指标看不出来。
- **修正**：
  - 交接回合的 cacheWrite 减去配对的无交接首回合，应落在 T±20%。
  - TTL 内后续回合的 cacheWrite ≤ 新增输入 + 512（用 Codex 的 `last` 与 OpenClaw 逐条用量核对）。
  - 与原生会话配对的占比差 ≥−0.05。
  - 0.85 只作参考。

### P12（major）首回合时延“各跑一次取差”测不出 p50，P̂ 在生产中不可得
- **章节**：11.1、6.2 capLatency、20 Q13。
- **证据**：
  - 短提示的首字自身就在 4.2–5.9 s 之间波动（R6[S29]）。
  - 生产中的 `firstOutputAt` 含启动与思考，分离不出预填充，所以 P̂ 永远退回 8k，capLatency = 12k，永不生效。
- **修正**：
  - 改用回归设计：T ∈ {0, 2k, 4k, 8k, 16k}，每档每模型族 ≥30 个随机顺序的新会话（Haiku 5.5、dsh 闲时，约 $1–3）；测量派发到首个任意事件的时间。
  - 验收：T_标准 × 斜率的 95% 上界 ≤1.5 s。【推算】σ≈1 s 时，8k 的 95% 区间约 ±0.23 s。
  - P̂ 用离线值，标注日期。

### P13（major）RunDigest p95 ≤2 ms 没有依据
- **章节**：6.4、11.1。
- **证据**：
  - 所引的 0.06 / 0.75 ms 是插入一条 1 KiB 条目的耗时，不是抽取（与 J2 误读 8 相同）。
  - 同一行又允许“秘密扫描 ≤2 MiB”，实测约 19 ms，而且每个会话的每个回合都要付这笔开销。
- **修正**：
  - `run.ended` 内只对要存储的字段（≤64 KiB，约 1 ms）脱敏；size 在未脱敏的文本上计算，并为标签留出余量。
  - 最坏输入（1 MiB 中文回复、128 个工具、256 KiB 差异）的微基准：p95 ≤3 ms、p99 ≤8 ms，进入 CI。

### P14（minor）存储与内存数字与自定上限不符
- **证据**：
  - 1.5 节的实测值超过 384 / 160 B。
  - `relay_bodies` 只以 sha256 为主键，“≤16 MiB/会话”与“随会话删除”都无法执行；结构上界本来就是 256 包 × 256 KiB = 64 MiB。
  - R1 的快照缓存（8 MiB 快照约占 11.6 MiB，最多 8 个会话，约 93 MiB）不在内存预算里。
- **修正**：
  - 上限改为 ≤512 / ≤320 B，用最长 ID 断言；或缩减字段（`executedOn` 只存 nativeEpoch，`chain` 移到 relay 表）。
  - 主键改为 (session_id, sha256)，删除会话时同一事务回收。
  - 以结构上界作硬上限，永不因总量 blocked。
  - 快照缓存按字节设上限，并写进 11.1。

### P15（minor）派发前还能再省一次整份提交
- **证据**：context_prepared 移到 open 之后，紧接着就是 authorized。`assertSessionTransition` 只禁止在 running/settling 状态下改 contextThroughSeq（state.ts:448）。
- **修正**：两者合并为一个事务，事件按 context_prepared → authorized 排序。每个回合省一次整份提交：7.6 MiB 时约 144 ms，R1 后约 45 ms（R6 推算）。用基准断言提交次数等于现状减一。
