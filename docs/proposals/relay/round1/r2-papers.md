## 0 一页摘要

1. 【事实】输入变长本身就会降低表现，与“能不能找到信息”无关。2023–2026 年至少 8 个独立团队在检索、推理、编码、监控、搜索任务上得到同向结果：13 个号称支持 ≥128K 的模型里，11 个在 32K 时跌破自身短上下文基线的 50% [S3]；即使证据检索完美、无关 token 被 mask，长度增长仍带来 13.9%–85% 的下降 [S5]。【推断】现行“整段公共历史 JSON、≤1 MiB 即可交接”的标准与证据冲突：1 MiB 约为数十万 token，远在可靠区间之外。
2. 【事实】2026 年出现了直接研究“接手”的实证。结构化交接状态稳定地降低接手成本：后继的事件数降低 20–59%，prompt token 降低 42–63% [S59]。它对能否完成任务的提升较小，且随接收模型而变。完整历史放得下时，完整或原始历史的质量仍然最好 [S59][S60]。
3. 【事实】整体重写会让上下文坍塌（context collapse）。ACE 记录到一次重写把 18,282 token 的上下文压成 122 token，准确率从 66.7 跌到 57.1，低于不用任何上下文的基线 63.7 [S23]。Claude Code 的 `/compact` 一轮后保留 53% 的安全规则，五轮后只剩 10% [S18]。压缩还会丢掉“使用边界”和“未经核实”这类元数据 [S26][S27]。
4. 【事实】确定性方法并不输给模型摘要。observation masking 与 LLM 摘要的解决率相当，成本约减半；LLM 摘要反而让轨迹变长 13–15% [S14]。在 Factory 的探针评测里，所有 LLM 压缩方案得分最低的维度都是“文件/工件追踪”（2.19–2.45/5）[S25]。【推断】HarnessHub 已经持久化的工具、diff、计划、待办，恰好是 LLM 摘要最弱的部分，应由 Hub 确定性投影出来，不依赖任何模型。
5. 【事实】交接的方向和历史的作者会影响结果，两组独立的 2026 研究用不同任务和模型族得到了同向结论。由弱交给强时，应裁剪或摘要弱方的轨迹；由强交给弱时，应保留强方的原文 [S61][S62]。把弱模型的完整轨迹交给强模型，只能追回不到一半的质量差距，成本却是 2.2 倍 [S61]。
6. 【事实】“记录了”不等于“会照做”。结构化状态里明确写着某个更新已完成，接收方仍会重复执行（18 次，对照组 12 次）[S60]。后继也会过度相信前任的解释 [S59]。【推断】判断接力是否成功，必须用行为指标，不能用接收方的复述或自评。
7. 【事实】现有记忆产品在“新事实覆盖旧事实”上普遍失败。MemoryAgentBench 的多跳选择性遗忘中，多数方法只有 2–7%，最好的也只有 28% [S71]；各家在 LoCoMo 上的分数互相矛盾 [S38][S39]。【推断】工作状态里“谁取代了谁”，应由 Hub 基于事件和双时间轴确定性维护。
8. 【事实】KV-cache 或潜空间通信（C2C、KVCOMM、LatentMAS）需要读取模型内部状态，或为一对模型训练投影器 [S55]–[S58]。【推断】跨厂商的闭源 Harness 用不了这类方法。能借鉴的是“前缀稳定才能命中缓存”：提示缓存可降低 41–80% 的成本，并把 TTFT 缩短 13–31%；把动态内容排除在缓存前缀之外，收益更稳定 [S74]。
9. 【建议】骨架如下：
   - 事件溯源的工作账本：以确定性事实为主，模型叙述为辅；每条带双时间轴、出处与核实状态。
   - 按目标投影出三层交接单：L0 常驻约 4K token，L1 近期原文，L2 按需取用。
   - 在空闲期预构建（sleep-time），切换路径上不调用 LLM。
   - 用自建的接力基准（HH-RelayBench）按行为指标校准阈值和方向策略。

   本文出现的所有参数都是待测假设。

## 2 发现

### 2.1 长上下文退化：长度本身就是成本

**Lost in the Middle** [S1] 〔评审 TACL｜复现：位置效应被大量后续工作复现，但见 S4 的分歧〕
- 问题/方法：研究模型能否利用长输入中任意位置的信息。在多文档 QA 和 KV 检索任务里移动答案所在位置。
- 数字【事实】：GPT-3.5-Turbo 读 20 篇文档时，答案在第 1 篇准确率 75.8%，在第 10 篇 53.8%，在第 15 篇 55.4%，都低于闭卷的 56.1%；答案在末篇时为 63.2%。16K 扩窗版的结果几乎相同（75.7 / 54.1 / 63.1）。
- 用法【建议】：关键内容（当前任务、约束、待办）放在交接单末尾，指令放在两端；扩大窗口并不等于更会用上下文。

**RULER** [S2] 〔评审 COLM 2024｜复现：与 S3、S4 同向〕
- 问题/方法：用合成任务测“真实可用长度”，共 13 个任务，覆盖检索、多跳追踪、聚合、QA 四类，测了 17 个模型。
- 数字【事实】：所有模型都声称支持 ≥32K，但在 32K 时只有一半还能保持满意表现。在普通的 needle-in-a-haystack 上几乎都是满分，这个满分并不代表真实可用长度。
- 用法【推断】：交接预算应按“可靠长度”而不是“窗口大小”来定。

**NoLiMa** [S3] 〔评审 ICML 2025｜复现：同向〕
- 问题/方法：让 needle 与问题之间几乎没有字面重合，迫使模型做潜在关联，测了 13 个号称支持 ≥128K 的模型。
- 数字【事实】：在 32K 时，11 个模型跌破各自短上下文基线的 50%；GPT-4o 从 99.3% 跌到 69.7%。用思维链或推理模型同样会退化。
- 用法【推断】：交接单里的信息很少和接收方的下一步“字面匹配”，比如“改哪个文件”与“上次决定用哪个库”。这正是退化最严重的情形。

**Context Rot**（Chroma 技术报告）[S4] 〔博客｜复现：与 S2、S3、S5 同向〕
- 问题/方法：在 18 个模型上做可控的长度实验。
- 数字【事实】：
  - 即使是简单任务，表现也随长度下降。
  - needle 与问题的语义相似度越低，下降越快。
  - 干扰项会造成不均匀的伤害。
  - 把 haystack 的句子随机打乱后，18 个模型的表现反而都好于连贯文本。
  - LongMemEval 子集（306 个提示）上，聚焦提示约 300 token，完整提示约 113k token，所有模型在聚焦版上都显著更好。
  - 该报告中 needle 的位置没有明显影响。
- 用法【推断】：“信息怎么呈现”比“信息在不在”更重要；连贯的长叙事未必比结构化的短条目好用。

**Context Length Alone Hurts LLM Performance Despite Perfect Retrieval** [S5] 〔评审 EMNLP 2025 Findings｜复现：同向〕
- 问题/方法：在“检索完美”的前提下单独测长度的影响，覆盖 5 个模型和数学、QA、代码任务。
- 数字【事实】：
  - 长度增长带来 13.9%–85% 的下降。
  - 把无关 token 换成空白、甚至完全 mask 掉，下降依然存在；证据紧挨着问题时也会下降。
  - 缓解办法是让模型先复述（recite）相关证据再解题，在 RULER 上让 GPT-4o 最多提升 4%。
- 用法【建议】：交接单应尽量短，不能只靠“关键内容放末尾”；让接收方先复述要点，是一种有证据、成本低的做法（见 R2-12）。

**LLMs Get Lost in Multi-Turn Conversation** [S6] 〔预印本｜复现：未见独立复现，但与 S62、S67 机制同向〕
- 问题/方法：把同一信息分多轮给出，与一次给出相比较；20 万+ 次模拟对话，15 个模型。
- 数字【事实】：
  - 平均下降 39%：能力（aptitude）约降 16%，不可靠性（unreliability）约升 112%。
  - 模型在早期做出假设、过早作答后，会“迷路不回”。
  - SNOWBALL（每轮重述已知信息）只部分挽回，例如 GPT-4o-mini 从 50.4 升到 61.8；降低温度无效。
  - 作者给用户的建议是：先把已知信息汇总，再开一个新对话重试。
- 用法【推断】：交给一个很长、可能已经偏航的原生会话继续，未必优于“汇总后开新会话”。这为 A→B→A 时选择“返回原生会话”还是“重新水合”提供了间接证据（见 R2-20）。

**Classifier Context Rot** [S7] 〔预印本 2026-05｜复现：与 S8 同向〕
- 问题/方法：用 LLM 监控编码 Agent 的超长转录（>500K token）。
- 数字【事实】：危险动作出现在 80 万 token 的正常活动之后时，Opus 4.6、GPT 5.4、Gemini 3.1 的漏检率是该动作单独出现时的 2×–30×；在转录中周期性插入提醒可以部分缓解。
- 用法【推断】：长转录不仅让执行变差，也让审查变差。交接单中的“风险/审批”条目不能淹没在长历史里。

**Diagnosing and Mitigating Context Rot in Long-horizon Search** [S8] 〔预印本 2026-06/08/10｜复现：未见〕
- 问题/方法：4 个旗舰模型，3 个基准。
- 数字【事实】：
  - 控制任务难度后，“过早终止”（放弃，或给出不确定的错误答案）的比例随上下文长度上升，且远在窗口填满之前就出现。
  - 7 种上下文管理方法本质上起“测试时扩展”的作用，即减少过早终止。
  - 行为感知过滤带来 +2.6–4.9%。
- 用法【推断】：衡量接手质量时，要包括“是否过早宣布完成或放弃”。

**厂商一手指南** [S42][S43] 〔博客/文档〕
- 【事实】Claude 文档建议：长文档放在提示顶部、问题放在末尾，“在测试中最多提升 30%”；长文用 XML 标签附带来源元数据；先引用相关段落再作答。
- 【事实】OpenAI GPT-4.1 指南：长上下文时把指令同时放在开头和结尾效果最好，只放一处时放在上方；XML 或管道分隔格式表现好，**JSON 用于大量文档时表现特别差**。

【推断】这一节对交接单长度的含义：

1. 现行的 `buildPublicContext` 先写一句英文说明，再用 `JSON.stringify` 把全部历史序列化成一行，当前输入也埋在 JSON 里 [L1]。整体用 JSON 装大量历史，与 S43 的结论正好相反；指令只出现在开头，也不符合 S42、S43 的建议。
2. 接收方自身的系统提示、工具定义和读取的仓库内容，与交接单共用同一个预算。各家的具体占用本文没有核实，但“未超过 1 MiB 就能交接”这个判据本身不成立。
3. 由 S5 可知，“只把关键内容放末尾”不够，还必须控制总长度。

### 2.2 Agent 上下文压缩与折叠

**ReSum** [S9] 〔预印本 v3 2026-03｜复现：未见〕
- 问题/方法：解决长程搜索 Agent 的上下文溢出。周期性调用外部摘要工具，把历史压成摘要后继续工作；另有 ReSum-GRPO 训练版本。
- 数字【事实】：不训练时比 ReAct 高 4.5%，训练后再高 8.2%；用 1K 样本训练的 30B Agent 达到开源领先水平。
- 用法【推断】：不训练时收益有限。HarnessHub 无法训练 Harness 的模型，能借鉴的只是“以摘要作为续写起点”这种接口形态。

**MEM1** [S10] 〔预印本｜复现：未见〕
- 问题/方法：用 RL 训练模型，每轮把记忆与推理合并成一个大小恒定的内部状态。
- 数字【事实】：在 16 个目标的多跳 QA 上，MEM1-7B 相对 Qwen2.5-14B-Instruct 性能提升 3.5×，内存降低 3.7×。
- 用法【推断】：“常驻状态大小有上限”这个方向是对的。HarnessHub 应该用确定性账本实现它，而不是靠训练。

**Context-Folding** [S11] 〔预印本，ByteDance Seed/CMU/Stanford｜复现：未见〕
- 问题/方法：Agent 用 `branch(description, prompt)` 开一条子轨迹，用 `return(message)` 把子轨迹折叠成摘要后回到主线；FoldGRPO 用过程奖励训练这种行为。
- 数字【事实】（读 PDF 表 1）：
  - Seed-OSS-36B 在 32K 活动上下文、最多 10 个分支下，BrowseComp-Plus pass@1 为 0.620，SWE-Bench Verified 为 0.580。
  - 这优于同一模型的 327K ReAct（0.478 / 0.552，RL 后 0.540 / 0.574），也优于摘要 Agent（RL 后 0.527 / 0.550）。
  - **未经 RL 训练的折叠 Agent 只有 0.420 / 0.492，低于 327K ReAct。**
  - 训练后主轨迹约 8K token，总处理量超过 100K。
- 用法【推断】：折叠的收益主要来自训练。对现成模型，最值得借鉴的是“在子任务边界折叠，只保留 return 消息”。HarnessHub 的天然折叠单元是 Run：每个 Run 结束时 Harness 自己写的最终回复，就是现成的 return message，不需要额外调用模型（见 R2-15）。

**AgentFold** [S12] 〔预印本｜复现：未见〕
- 问题/方法：介于 ReAct 上下文饱和与全量摘要不可逆丢细节之间，做多尺度折叠（细粒度浓缩 + 子任务深度合并），只用 SFT 训练。
- 数字【事实】：30B-A3B 模型在 BrowseComp 上 36.2%，BrowseComp-ZH 上 47.3%，超过或持平 DeepSeek-V3.1-671B 与 o4-mini。
- 用法【推断】：支持“分层浓缩”优于“一次性全量摘要”。

**ACON** [S13] 〔评审 ICML 2026｜复现：未见〕
- 问题/方法：同时压缩观察与历史；**根据 Agent 的失败案例迭代修改自然语言形式的压缩准则**（不改模型参数），再把压缩器蒸馏到小模型。
- 数字【事实】：峰值 token 降低 26–54%；小模型作为长程 Agent 时最多提升 46%；测试集为 AppWorld、OfficeBench 和多目标 QA。
- 用法【建议】：可以直接移植。用接力基准中的失败案例离线修订交接单的模板和渲染规则，不需要训练（见 R2-17）。

**The Complexity Trap** [S14] 〔评审 NeurIPS 2025 DL4C 研讨会，作者 Lindenbauer 等｜复现：作者附了 OpenHands 泛化探针，未见独立复现；与 S15、S16 同向〕
- 问题/方法：在 SWE-agent 上比较三种上下文管理：observation masking（保留最近 M=10 个观察）、LLM 摘要（每 21 轮摘要一次，保留最近 10 轮），以及二者的混合。
- 数字【事实】：
  - masking 的成本约减半，解决率持平或略高。例如 Qwen3-Coder 480B：解决率 53.4% → 54.8%，单题成本 $1.29 → $0.61。
  - LLM 摘要让轨迹变长 13–15%，作者认为摘要掩盖了本应促使 Agent 停下的失败信号。
  - 摘要调用很少命中缓存，占总成本 0.65–7.2%。
  - 混合方案比 masking 再降 7%，比摘要再降 11%。
  - M 从 10 增到 20 时效果反而变差。
- 用法【建议】：交接单里的历史部分，优先用确定性方式“遮蔽旧工具输出，保留调用记录和引用”；LLM 摘要只作为最后手段（见 R2-16）。

**AgentDiet**（Reducing Cost of LLM Agents with Trajectory Reduction）[S15] 〔评审 FSE 2026｜复现：与 S14 同向〕
- 问题/方法：Agent 轨迹中普遍存在无用、冗余和过期的信息。在推理时自动删除这些信息。
- 数字【事实】：输入 token 降低 39.9–59.7%，总成本降低 21.1–35.9%，表现不变。
- 用法【建议】：投影账本时剔除过期内容，例如已被后续读写取代的文件读取、被重跑覆盖的测试输出。

**Less Context, Better Agents** [S16] 〔预印本 2026-06｜复现：单一企业场景，50 题，GPT-5，5 次平均〕
- 数字【事实】：
  - 保留完整历史：完成率 71.0%，消耗 148 万 token、14.56 小时。
  - 只留最近 5 对工具调用：79.0%，53.5 万 token。
  - 最近 5 对加摘要：91.6%，55.3 万 token。
- 用法【推断】：至少在工具密集的流程里，“近期原文 + 紧凑摘要”优于全量历史。

**What Does Context Compression Cost an Agent?** [S17] 〔预印本 2026-08，单作者｜复现：未见〕
- 问题/方法：指出只看完成率会漏掉“重新获取状态”的代价。在 24 轮的确定性规划环境中改变压缩强度。
- 数字【事实】：
  - 5× 压缩时，各组完成率都没有显著变化，但 6 组中的检索调用全部上升，其中 5 组经 Holm 校正后显著。
  - GPT-5.5 的完成率从 80% 升到 85%（p=1.0），检索调用却从 21.0 次增到 63.9 次（p=.002）。
  - 把保留的状态换成语义无关的内容，检索调用增加 57%。
  - 在 ALFWorld 中没有出现这种效应。
- 用法【建议】：接力基准必须计入“重新获取成本”（重读文件、重跑命令的次数），否则会把有损的交接误判为无损（见 R2-22）。

**When Can Agents Forget Their Reasoning?**（方法名为 ICLR，不是会议名）[S19] 〔预印本 2026-09｜复现：未见〕
- 问题/方法：按冻结代理模型的熵删除推理块，保留动作、工具调用与观察。
- 数字【事实】：
  - 在 260 个 WorkBuddyBench 任务上，奖励从 0.699 升到 0.718；输入 token 降低 25.5%，输出 token 降低 14.4%，缓存读取降低 33.3%。
  - 机理分析显示：派生状态一旦外化到代码、文件或工具输出，历史推理就更容易被替代。
- 用法【推断】：交接单不需要搬运推理文本，这与“不复制隐藏状态”的约束一致；应该搬运已外化的状态，即 diff、测试结果和决定。基准名中的 WorkBuddy 是否与我们的焦点 Harness 同源，我没有核实。

**VISTA**（LLM Agents Are Latent Context Managers）[S20] 〔预印本 v5 2026-07｜复现：未见〕
- 问题/方法：前沿模型无法仅凭提示可靠推断各块的大小、新旧程度和剩余预算。VISTA 把工作记忆存成类型化、可寻址的块，向 Agent 展示 token 用量、新旧、归档状态与剩余预算的“仪表盘”，归档块可以全保真取回。
- 数字【事实】：LOCA-Bench 上 Gemini-3-Flash 从 22.7% 升到 50.7%；BrowseComp-Plus 58.0%；消融实验显示仪表盘本身有独立贡献。
- 用法【建议】：交接单附一段“覆盖说明”，写明包含了哪些 Run、省略了什么、各部分的 token 数，以及如何取回省略的内容（见 R2-09）。

**HiAgent** [S21] 〔预印本 2024｜复现：未见〕
- 问题/方法：以子目标为单位组织记忆块；一个子目标完成后，用摘要替换该子目标下的动作-观察对。
- 数字【事实】：5 个长程任务上成功率翻倍，平均步数减少 3.8 步。
- 用法【推断】：支持“按任务单元折叠”。

**Git-Context-Controller (GCC)** [S22] 〔预印本 v3 2026-07｜复现：未见，属于自报 SOTA〕
- 问题/方法：用 COMMIT、BRANCH、MERGE、CONTEXT 四种操作管理 Agent 的上下文。
- 数字【事实】：自称在 SWE-bench Verified 上比长上下文基线相对提升 13% 以上，成功率超过 80%。
- 用法【推断】：它的操作与 HarnessHub 的会话分支、水位天然对应：账本条目可以带上分支来源，合并时显式标出。证据弱，只借概念。

【推断】这一组中最强的结果（S9–S13）大多依赖 RL 或 SFT 训练。HarnessHub 不能训练各家 Harness 的模型，只能采用其中不需要训练的部分：在边界处折叠、确定性剔除、优化压缩准则、提供仪表盘。

### 2.3 坍塌、简略偏置，以及压缩中丢失的“规则与出处”

**ACE: Agentic Context Engineering** [S23] 〔评审 ICLR 2026｜复现：坍塌现象与 S25、S18 同向〕
- 问题：已有的上下文自适应方法有两个缺陷。一是简略偏置（brevity bias）：为了简洁丢掉领域洞见。二是上下文坍塌（context collapse）：反复整体重写，让细节逐渐流失。
- 方法：把上下文当作不断演进的 playbook，由 Generator、Reflector、Curator 三个角色产生增量 delta。条目是带唯一 ID 和 helpful/harmful 计数的 bullet，由**非 LLM 逻辑确定性合并**，可以并行；grow-and-refine 用语义嵌入去重，精炼可以主动进行，也可以惰性进行。
- 数字【事实】：
  - Agent 基准 +10.6%，金融基准 +8.6%。
  - 坍塌实例（AppWorld，来自 Dynamic Cheatsheet 第 60 步）：18,282 token 的上下文准确率为 66.7；下一步被重写成 122 token 后准确率 57.1，**低于不做自适应的基线 63.7**。
  - 适配延迟平均降低 86.9%。AppWorld 离线场景对比 GEPA 降低 82.3%；FiNER 在线场景对比 DC 降低 91.5%，成本从 $17.7 降到 $2.9。
  - 在 GPT-5.1 的测试中，91.8% 的输入 token 来自缓存。
  - 局限：依赖足够强的 Reflector；没有可靠反馈信号时会退化，例如 FiNER 无标签时得 67.3，比基线低 3.4。
- 用法【建议】：账本更新采用“带 ID 的 delta + 确定性合并 + 不做整体重写”（见 R2-13）。这是“旧摘要不覆盖新事实”最直接的机制依据。

**Dynamic Cheatsheet** [S24] 〔预印本｜复现：ACE 复现了其增益，也复现了其坍塌〕
- 问题/方法：给黑盒模型一份推理时可演进的记忆，存放策略、代码片段和洞见。
- 数字【事实】：
  - Claude 3.5 Sonnet 在 AIME 上的准确率翻倍以上。
  - GPT-4o 在 Game of 24 上从 10% 升到 99%。
  - Claude 在 GPQA-Diamond 上 +9%，在 MMLU-Pro 上 +8%。
- 用法【推断】：“经验教训”这类内容有价值，但 ACE 记录的坍塌正是出自 DC 的整体重写，所以必须用 delta 来管理。

**Factory：Evaluating Context Compression for AI Agents** [S25] 〔博客，厂商自评｜复现：未见；“整体重写会漂移”与 S23 同向〕
- 方法：
  - 数据为 36,611 条生产会话消息，覆盖数百个压缩点。探针分为 recall、artifact、continuation、decision 四类；由 GPT-5.2 盲评，6 个维度各 0–5 分。
  - 比较三种方案：Factory 的“锚定式迭代摘要”，OpenAI 的 `/responses/compact`（输出不可读），Anthropic SDK（每次整体重写）。
  - Factory 的方案只摘要新截断的片段，合并进固定栏目：会话意图、文件修改、已做决定、下一步。每个栏目必须填写，或明确标为空。
- 数字【事实】：
  - 总分：Factory 3.70，Anthropic 3.44，OpenAI 3.35。
  - **artifact 维度三家都最低，分别为 2.45、2.33、2.19**。作者认为这个问题还没解决，建议在脚手架里单独维护工件索引或文件状态。
  - 整体重写会在多次压缩中漂移；三家的压缩率相近，在 98.6–99.3% 之间。
- 用法【建议】：文件和工件状态必须由 Hub 从工具事件确定性生成。“每栏必填或标空”可以直接用作 L0 模板的规则，防止静默遗漏。

**The Compaction Cliff** [S18] 〔评审 CIKM 2026｜复现：与 S26、S27 同向〕
- 问题：安全规则与流水日志共用同一个 token 预算，被以同样比例压缩。
- 方法：Knowledge Triage，按类型选择保留策略。TypeCompact 按类型分级保真；TypeDecompose 拆分时把适用的规则复制到每个分区；TypeRetrieve 检索时把规则置顶。
- 数字【事实】：
  - Claude Code 的 `/compact`（Sonnet 4.6）在 20 个生产配置上，一轮后保留 53% 的安全规则，五轮后只剩 10%。
  - TypeCompact 保留的规则是对照方法的 2–4 倍，五轮后召回率 96%。
  - TypeRetrieve 的 recall@50 为 100%，对照为 73%。
  - 研究语料包含 396,934 个 Agent 配置。
- 用法【建议】：约束、用户决定和审批永远不进入任何有损压缩，用类型标记“逐字保留”（见 R2-03）。

**Facts Without Rules** [S26] 〔预印本 2026-08｜复现：与 S27 同向〕
- 问题：交接摘要保留了事实，却丢掉了事实的使用边界，包括受众限制、披露条件、保留意见和归属。
- 方法：36 个场景、72 个边界标记、5 种交接条件、3 个模型；judge 的一致性 κ=0.74。
- 数字【事实】：
  - 自由文本交接时，边界标记的存活率 σ_b 约为 0.80；限制在 25 个词以内时降到 0.56–0.69，而操作事实的存活率保持在 0.97–1.0。两者的相关性接近零。
  - 边界措辞模糊时，GPT 的泄露率为 73%，DeepSeek 为 50%；措辞明确时都低于 15%。
  - 经过三跳、且每跳只部分回放记忆时，损失会显著累积（GPT-5-mini 为 −0.381）。
  - 只靠提示或精确字符串脱敏都只部分有效：语义残留分别有 31/288 和 39/288。
  - **类型化的受众白名单可把泄露降到 0/48**；但白名单写错时，泄露回到 44/48。
- 用法【建议】：事实带 `audience/scope` 字段；跨厂商交接时按字段过滤，不靠提示词（见 R2-25）。

**Silence Is Endorsement** [S27] 〔预印本 2026-07｜复现：同上〕
- 问题：交接保留了“已授权”的说法，却丢掉了“未经核实”这一状态。
- 方法：测试 9 个开源监控模型和 2 个托管模型。
- 数字【事实】：
  - 去掉“未核实”的表述后，风险动作的批准率大幅上升：Llama-3.1-8B 从 5% 升到 60%，Qwen2.5-14B 从 9% 升到 98%。
  - 在完整的 proposer→summarizer→memory→monitor 流水线中，批准率为 57–81%。
  - 提示监控模型“拒绝未核实的授权”并不可靠。
- 用法【建议】：“已审批”“测试通过”这类声明必须带核实状态和证据引用，通过结构字段而不是文字传递（见 R2-26）。

**What to Keep, What to Forget** [S28] 〔预印本 2026-07｜复现：无；实验数字未核实〕
- 问题/方法：把 KV 逐出、提示剪枝、有界状态、Agent 记忆合并统一成一个率失真（rate–distortion）问题。
- 【事实】作者指出：现有的保留/丢弃信号在查询未知时就做出决定，会不可逆地丢掉后来需要的信息；Agent 的“反复压缩”很少被测量。
- 搜索摘要称其小实验中，可逆的检索式记忆召回率约 0.95，不可逆摘要为 0.33–0.56。**我没能在原文中核实这组数字。**
- 用法【推断】：支持“可取回的压缩优先”。

### 2.4 记忆体系：哪些结构适合“工作状态”

**MemGPT / Letta** [S29] 〔预印本｜复现：作为基线被广泛使用〕
- 问题/方法：仿照操作系统做虚拟上下文。主上下文含模型可自编辑的核心记忆块，外部存储分为 recall 和 archival 两层，用函数调用换入换出，用中断控制流程。
- 用法【推断】：“常驻核心块 + 可检索外存”正是 L0/L2 分层的原型。但让模型自编辑核心块作为工作状态的权威，有漂移风险，应改为由 Hub 投影、由用户编辑。

**A-MEM** [S30] 〔评审 NeurIPS 2025｜复现：未见〕
- 问题/方法：Zettelkasten 式笔记（描述、关键词、标签）+ 自动链接 + “记忆演化”，即新记忆会更新旧笔记的属性。
- 数字【事实】：摘要只说在 6 个基础模型上优于基线，没有给具体数字。
- 用法【建议】：采用条目之间的链接（决定↔文件↔测试）；**拒绝**原地演化，因为它违反 INV-22 的不可覆写要求。

**Mem0** [S31] 〔预印本｜复现：有争议〕
- 问题/方法：面向生产的长期记忆，流程为抽取、合并、检索，另有图变体。
- 数字【事实】：
  - LoCoMo 上的 LLM-judge 分数比 OpenAI memory 相对高 26%；p95 延迟比全上下文低 91%，token 成本低 90% 以上；图变体再高约 2%。
  - 争议：Letta 用“文件 + 搜索”的 Agent 在 LoCoMo 上得到 74.0%（GPT-4o mini），高于 Mem0 报告的最佳成绩 68.5% [S38]。
  - Zep 的博客称 Mem0 对 Zep 的复现有实现错误，修正后 Zep 为 75.14%（仅搜索摘要）[S39]。
  - 第三方审计称 LoCoMo 的 1,540 道题中有 99 道答案有误，占 6.4%（仅搜索摘要）[S78]。
- 用法【推断】：这些面向“用户事实与偏好”的记忆产品，其分数不足以支撑选型，更不能作为工作状态的权威。

**Zep / Graphiti** [S32] 〔预印本｜复现：未见独立复现〕
- 问题/方法：时序知识图谱，分三层子图：episode（原始输入，无损保存）、语义实体与事实边、社区。
  - **双时间轴**：T 记录事实在现实中何时成立（`t_valid` / `t_invalid`），T' 记录系统何时写入或作废它（`t'_created` / `t'_expired`）。
  - 新边与旧边矛盾时，把旧边的 `t_invalid` 设为新边的 `t_valid`——作废而不是删除。
- 数字【事实】：
  - DMR 上 94.8%，MemGPT 为 93.4%。
  - LongMemEval：gpt-4o 从 60.2% 升到 71.2%（+18.5%），gpt-4o-mini 从 55.4% 升到 63.8%；延迟从 28.9 s 降到 2.58 s；上下文从 115k token 降到 1.6k token。
  - 但 single-session-assistant 类问题下降，gpt-4o 上为 −17.7%。
- 用法【建议】：账本条目采用双时间轴：`validFromSeq/validToSeq` 用公共 seq，`recordedAt/supersededAt` 记录写入时间。发生矛盾时作废旧条目、链接到新条目，旧条目保留不改（见 R2-13）。这是“旧摘要不覆盖新事实”在数据结构上的答案。

**MemoryOS** [S33] 〔评审 EMNLP 2025（经搜索确认收录）｜复现：未见〕
- 问题/方法：面向个性化的长期记忆，分短期、中期、长期三层。短期到中期按对话链 FIFO 晋升，中期到长期按分段页面组织。
- 数字【事实】：LoCoMo（GPT-4o-mini）上 F1 平均提升 49.11%，BLEU-1 提升 46.18%。另一来源写的是 48.36%，两处不一致。
- 用法【推断】：分层与晋升规则可以借鉴到 L1→L0 的晋升，例如被多次引用的文件进入常驻索引。但它面向用户画像，不面向任务状态。

**MIRIX** [S34] 〔预印本｜复现：未见〕
- 问题/方法：六类记忆——Core、Episodic、Semantic、Procedural、Resource、Knowledge Vault，由多个 Agent 协调更新与检索。
- 数字【事实】：ScreenshotVQA 上比 RAG 高 35%，存储减少 99.9%；LoCoMo 上 85.4%。
- 用法【建议】：作为交接单栏目的检查表：
  - Core → 目标与约束；
  - Episodic → Run 事件；
  - Semantic → 已核实的事实与决定；
  - Procedural → 如何构建、测试、启动（命令）；
  - Resource → 文件与产物的引用；
  - **Knowledge Vault（凭据等敏感信息）→ 明确排除在交接单之外**（INV-17）。

**Memory-R1** [S35] 〔预印本 v5 2026-01｜复现：未见〕
- 问题/方法：用 RL 训练 Memory Manager 执行 ADD、UPDATE、DELETE、NOOP 四种操作，Answer Agent 先筛选记忆再推理。
- 数字【事实】：只用了 152 个 QA 对训练；在 LoCoMo、MSC、LongMemEval 和 3B–14B 的模型上优于基线，摘要没有给具体数字。
- 用法【建议】：借用它的操作词表来定义账本事件：add、supersede、retract、confirm、noop。**拒绝**让模型决定删除。

**ReasoningBank** [S36] 〔评审 ICLR 2026｜复现：未见〕
- 问题/方法：从成功和失败的经验中提炼可泛化的推理策略，测试时检索使用；MaTTS 用更多采样制造对比信号。它优于只存原始轨迹或只存成功流程的记忆。
- 用法【推断】：“失败与教训”值得在交接单中单独成栏，但内容应来自可追溯的失败事件。

**记忆综述** [S37] 〔预印本 2026-03，单作者〕
- 【事实】把 Agent 记忆形式化为 write–manage–read 循环，从三个维度分析：时间范围、表示载体、控制策略。归纳了五类机制：上下文内压缩、检索库、反思式自我改进、分层虚拟上下文、学习得到的管理策略。列出的开放问题包括持续合并、因果检索、可信反思和学习式遗忘。

**结构选择表（【推断】）**

| 结构 | 代表 | 适合“工作状态”吗 | 理由 |
|---|---|---|---|

### 2.5 把上下文当作环境：按需取用与预计算

**Recursive Language Models (RLM)** [S40] 〔预印本 v3 2026-05｜复现：未见〕
- 问题/方法：把长提示存为 Python REPL 中的变量，模型写代码检视、切分，并递归调用子模型处理各部分。
- 数字【事实】：
  - 能处理超出窗口两个数量级的输入。
  - 以 GPT-5 为底座，中位数比 compaction 高 26%，比带子调用的 CodeAct 高 130%，比 Claude Code 高 13%，成本相当。
  - 后训练的 RLM-Qwen3-8B 比基座平均高 28.3%。
- 用法【推断】：把公共历史当作“可查询的环境”而不是一次性注入，是 L2 层的理论依据；但收益依赖接收模型的代码与工具能力。

**Letta Context-Bench** [S46] 〔博客 2025-10-30｜复现：未见〕
- 问题/方法：测“智能体式上下文工程”能力。只给 `open_files` 和 `grep_files` 两个工具，在由虚构实体构成的半结构化文本中做多跳查找。
- 数字【事实】：Claude Sonnet 4.5 得 74.0%（成本 $24.58），GPT-5 得 72.67%（$43.56），GPT-5-mini 64.33%，Kimi K2 55.13%，DeepSeek V3 11.97%。
- 用法【推断】：不同接收模型的“按需取用”能力相差极大，所以关键事实不能只放在 L2，L0 必须自足。

**ContextBench** [S47] 〔预印本 2026-02｜复现：未见〕
- 问题/方法：测编码 Agent 的上下文检索能力。1,136 个 issue，来自 66 个仓库、8 种语言，均有人工标注的 gold context。
- 【事实】：
  - Agent 脚手架对检索的增益很小。
  - 模型偏重召回、轻视精度。
  - 探索过的上下文与实际用上的上下文差距很大。
- 用法【推断】：接手方自行探索仓库既费成本又不精确；交接单给出“相关文件清单及理由”有价值。

**Claude 平台的上下文编辑与记忆工具** [S44] 〔博客 2025-09-29〕
- 【事实】在内部的 agentic search 评测中：
  - 记忆工具加上下文编辑比基线高 39%，只用上下文编辑高 29%。
  - 在 100 轮的 web 搜索中，token 用量降低 84%。
  - 上下文编辑负责清除旧的工具调用和结果；记忆工具是一个客户端的文件目录。

**Claude 提示文档中的“多上下文窗口”建议** [S42] 〔文档〕
- 【事实】
  - 第一个窗口用来建立框架（测试、脚本），之后的窗口按待办清单迭代。
  - 可以考虑开新窗口而不是压缩，文档原话是最新模型“非常擅长从本地文件系统发现状态”。
  - 结构化状态用 JSON，进度用自由文本，用 git 追踪状态。
  - 可以通过工具来“水合”上下文。
- 用法【推断】：对编码类 Harness，工作区本身（git log、diff、测试）是第一状态载体；交接单应指向它，而不是复制它。

**Manus 的上下文工程经验** [S45] 〔博客 2025-07-18〕
- 【事实】
  - KV-cache 命中率是生产环境 Agent 最重要的指标。以 Claude Sonnet 为例，缓存输入 $0.30/MTok，未缓存 $3/MTok，相差 10 倍；输入与输出 token 之比约 100:1。
  - 保持前缀稳定、只追加、确定性序列化（例如固定 JSON 键序）。
  - 把文件系统当外部记忆，压缩必须“可恢复”：保留 URL 或路径，就可以丢掉正文。
  - 用 todo.md 复述目标，把它推到上下文末尾。
  - 保留错误轨迹；避免让重复的模式诱导模型模仿。
- 用法【建议】：交接单遵循“可恢复压缩”原则，任何被省略的内容都附上 ContentRef 或路径。

**Sleep-time Compute** [S41] 〔预印本，Letta/UC Berkeley｜复现：未见〕
- 问题/方法：在用户提问之前，先对已知的上下文离线推理。
- 数字【事实】：
  - 在同等准确率下，测试时计算量约降为 1/5（Stateful GSM-Symbolic、Stateful AIME）。
  - 加大 sleep-time 计算量，准确率最多提升 13% 和 18%。
  - 多个查询共享时，单个查询的成本降为 1/2.5。
  - **查询越可预测，收益越大。**
- 用法【建议】：接手方的“查询”几乎总是“继续这项工作”，可预测性很高。适合在每个 Run 结算后的空闲期增量维护账本、预先渲染候选交接单；切换路径上只做渲染与校验（见 R2-14）。

### 2.6 多 Agent 交接与通信

**MAST：Why Do Multi-Agent LLM Systems Fail?** [S48] 〔评审 NeurIPS 2025（neurips.cc 有海报页）｜复现：分类法已被后续工作引用，统计未见独立复现〕
- 问题/方法：用 150 条轨迹建立失败分类法（人工标注者间 κ=0.88），扩展成覆盖 7 个框架、1,600+ 条轨迹的 MAST-Data，由 LLM-as-judge 批量标注。共 14 种失败模式，分为 3 类。
- 数字【事实】：与交接和信息丢失直接相关的失败模式及占比如下。
  - FM-1.3 重复步骤 15.7%
  - FM-2.6 推理与行动不一致 13.2%
  - FM-1.5 不知道终止条件 12.4%
  - FM-1.1 违反任务约束 11.8%
  - FM-3.3 验证有误 9.1%
  - FM-3.2 无验证或验证不完整 8.2%
  - FM-2.3 任务偏离 7.4%
  - FM-2.2 不请求澄清 6.8%
  - FM-3.1 过早终止 6.2%
  - FM-1.4 丢失对话历史 2.8%
  - FM-2.1 对话重置 2.2%
  - FM-2.5 忽视其他 Agent 的输入 1.9%
  - FM-2.4 隐瞒信息 0.85%

  在 ChatDev 上增加一个高层目标验证步骤带来 +15.6%，修改角色与流程带来 +9.4%。作者认为这类战术修补不够，需要结构性的改变：多级验证、通信协议、记忆与状态管理。
- 用法【推断】：接力中最高频的风险不是彻底丢失历史（2–3%），而是**重复已完成的步骤、不知道何时算完成、缺少验证**。所以交接单必须显式携带“已完成（不可重复）”“验收标准”和“验证状态”三项。

**Chain-of-Agents** [S49] 〔评审 NeurIPS 2024，Google｜复现：未见〕
- 问题/方法：多个 worker 依次处理长输入的各个分段，传递“通信单元”，最后由 manager 汇总；每个 Agent 只看一小段上下文。
- 数字【事实】：在 QA、摘要和代码补全上，比 RAG、全上下文和其他多 Agent 基线最多高 10%。
- 用法【推断】：在“读长文”类任务里，顺序接力加紧凑消息可以胜过全上下文。但这些任务没有副作用，而且每一棒都要额外调用模型，HarnessHub 目前没有自有模型。

**Magentic-One** [S50] 〔预印本/微软技术报告｜复现：未见〕
- 问题/方法：Orchestrator 维护两本账。
  - Task Ledger：已给定或已核实的事实、待查事实、待推导事实、有根据的猜测、计划。
  - Progress Ledger：每步回答五个问题——请求是否已满足、是否在循环、是否有进展、下一个由谁做、给它什么指令。

  停滞计数超过 2 时回到外循环重新规划。**每次计划更新后，所有 Agent 清空上下文、重置状态。**
- 数字【事实】：GAIA 38.00%（GPT-4o + o1）。把 Orchestrator 换成 GroupChat（即去掉两本账、规划、进度跟踪和循环检测），性能约降 31%。
- 用法【建议】：账本把“已核实事实”和“猜测”分开存放（见 R2-07）；进度五问加停滞计数，可以作为将来“建议交接”（R05）的信号（见 R2-21）。

**Anthropic 的多 Agent 研究系统** [S51] 〔博客 2025-06-13〕
- 【事实】
  - 多 Agent 系统在内部研究评测上比单 Agent 的 Opus 4 高 90.2%。
  - 在 BrowseComp 上，token 用量解释了约 80% 的表现方差。
  - Agent 的 token 用量约为聊天的 4 倍，多 Agent 约为 15 倍。
  - 子 Agent 把产出写入外部存储，只回传轻量引用，以避免“传话游戏”式的信息丢失。
  - 接近窗口上限时，把计划存入记忆，再用干净的上下文启动新的子 Agent，并做谨慎的交接。
  - 模糊的委派会导致重复工作。
- 用法【建议】：“传引用、不传副本”；交接说明要写明目标、输出形式、工具与来源指引，以及边界。

**Cognition：Don't Build Multi-Agents** [S52] 〔博客 2025-06-12〕
- 【事实】
  - 两条原则：共享完整的上下文和完整的 Agent 轨迹，而不只是单条消息；“行动带有隐含的决定，相互冲突的决定会带来坏结果”。
  - 推荐单线程的线性 Agent；长任务再加一个专门压缩历史的模型。作者说这“很难做对”，他们为此微调了小模型。
- 用法【推断】：隐含的决定（例如选了哪个库、用了哪种目录结构）必须从行动中提取出来，显式写进账本，否则接手方可能做出冲突的决定。

**When Do Multi-Agent Systems Help?（信息瓶颈视角）** [S53] 〔预印本 2026-07｜复现：未见〕
- 问题/方法：理论上，带宽不受限的中继可以让多 Agent 完全复制单 Agent。因此多 Agent 的优势只来自“有界中继”：压缩带来的收益与信息损失之间的权衡，参数 β 反映模型能力。论文做了 18 个受控实验，覆盖 5 个基准、3 种模型规模。
- 【事实】中继接近充分时，多 Agent 稳定受益，弱模型尤其明显；中继有损时，收益缩小甚至反转，**强模型尤其如此**，因为强模型本可以从冗余的上下文中自己提取信息。
- 用法【推断】：对强接收方，在预算内宁可多给原文；对弱接收方，紧凑的结构更划算。

**Attention Tax, Handoff Tax** [S54] 〔预印本 2026-10｜复现：未见〕
- 问题/方法：一个程式化的可靠性模型。分解（交接）可以免去长上下文的“注意力税”，但要付出“交接税”；只有被免去的注意力代价大于交接代价时，分解才划算。
- 数字【事实】：在账本对账任务上拟合，交叉点在深度 10；模型预测深度 20、50、100 时分解获胜，实测与预测的差距都在 9 个百分点以内。
- 用法【推断】：“何时值得换人或开新上下文”可以量化。会话越深，“重开 + 交接单”越划算；交接单越有损，越不划算。

**KV-cache 与潜空间通信**
- C2C [S55] 〔评审 ICLR 2026〕：用神经网络把源模型的 KV-cache 投影并融合进目标模型，门控选择哪些层参与。比单个模型高 6.4–14.2%，比文本通信高 3.1–5.4%，延迟加速 2.5 倍。
- KVCOMM [S56] 〔评审 NeurIPS 2025〕：在多个 Agent 之间复用重叠内容的 KV-cache，用锚点估计不同前缀造成的偏移。复用率超过 70%；五 Agent 场景下最高加速 7.8 倍，TTFT 从约 430 ms 降到约 55 ms。
- LatentMAS [S57] 〔评审 ICML 2026 spotlight〕：Agent 在连续潜空间协作，共享潜在工作记忆。最多高 14.6%，输出 token 降低 70.8–83.7%，端到端快 4–4.3 倍。
- 异构模型的后续工作 [S58] 〔仅搜索摘要〕：XKV、LCF、dense latent 等仍然要求对齐的共享输入、匹配的层与头结构，或者训练好的翻译器。
- 用法【推断】：这些方法都需要读取模型内部状态（KV、隐藏层），而且多数要求同族模型或成对训练。七个焦点 Harness 都通过各自的 CLI 或协议调用闭源或托管模型，HarnessHub 拿不到 KV，跨厂商只能用文本。可以借鉴的有三点：
  - (a) 前缀稳定才能复用缓存——KVCOMM 处理的前缀偏移问题，在 API 层就表现为 prompt cache 失效；
  - (b) 传递共享工作记忆的引用，而不是重复编码，对应我们的 ContentRef；
  - (c) 这些工作量化了“文本中继是有损的”，支持把文本中继做得结构化、可校验。

### 2.7 2026 年的交接专项实证（最直接的证据）

**Handoff Debt** [S59] 〔预印本 v2 2026-08；搜索结果显示 ACL Anthology 有 EMNLP 2026 条目，未打开核实｜复现：未见〕
- 问题/方法：研究编码 Agent 被中断、换人接手时的“重新发现成本”。
  - 在固定点暂停前任、冻结仓库，后继在 4 种视图下继续：只有仓库、原始轨迹、摘要笔记、结构化笔记。
  - 75 个源任务，181 个交接点，每个后继模型接手 724 次；前任都是 Qwen，后继是 Qwen、Gemma、Devstral。
- 数字【事实】：
  - 带上下文的交接使后继的事件数中位数降低 20–59%，累计 prompt token 降低 42–63%。
  - **原始轨迹带来的解决率提升最大**：Qwen +6.1、Gemma +6.6、Devstral +14.9 个百分点；笔记类视图的提升较小，在 Qwen 和 Gemma 上不显著。
  - 初始提示的中位长度：原始轨迹 87k 字符，结构化笔记 10.0k，摘要笔记 9.8k，只有仓库 7.2k。
  - 结构化笔记的字段分两部分：
    - 确定性部分：改动的源文件、非源文件产物、最近的验证命令、最近的验证证据、续写状态标签；
    - 模型生成部分：问题理解、已完成的工作、观察到的证据、观察到的失败、剩余的不确定性、回滚说明、建议的下一步。
  - 笔记可能漏掉关键证据，例如确切的验证命令；后继会过度相信前任的解释。实验中的提示要求后继“把交接文本当作需要核实的历史证据”。
- 用法【建议】：
  - 字段拆分几乎可以照搬：确定性栏目由 Hub 生成，模型栏目由来源 Harness 生成并标注作者。
  - 交接单开头声明“这是历史证据，请对照工作区核实”。
  - 原始轨迹的质量最好，应通过 L2 提供按需取用（见 R2-01、R2-09）。

**HSC-Bench**（Benchmarking Task Takeover Across Agent Handoffs）[S60] 〔预印本 2026-10-27｜复现：与 S59 同向〕
- 问题/方法：
  - 共 1,039 题：300 道仓库证据恢复，739 道续写。所有题目使用同一段 GPT-5 源历史。
  - 由 GPT-4.1 从可观察的历史生成结构化状态，其中仓库状态是不超过 4,000 字符的 JSON。
  - 6 个接收方：GPT-5.4、Claude Sonnet 5、DeepSeek V3.2、Qwen 3.5 Plus、Gemini 3.5 Flash Lite、Kimi K2。
- 数字【事实】：
  - 仓库证据（line-F1）：结构化状态让 6 个接收方全部提升，幅度 +0.114 到 +0.162。
  - 续写：6 个接收方中有 5 个用结构化状态优于只给最近转录；Kimi K2 的均分下降 3.33，其中工具类题目下降 9.43。
  - **完整历史仍然最好**。以 GPT-5.4 为例（均分 / 全过率）：最近转录 89.73 / 44.7%，结构化状态 92.76 / 52.1%，完整历史 94.51 / 57.9%。
  - 对 GPT-5.4，结构化状态比叙述式摘要的均分高 5.42，全过率高 9.3 个百分点；给出目标状态时的参考上限是 98.30 / 85.3%。
  - **即使完成记录就在上下文里，接收方仍会重复已完成的更新**：结构化状态下对同一目标重复 18 次，只给最近转录时 12 次。
  - 均分与全过率可能朝相反方向变化。
- 用法【建议】：基准和指标设计可以直接借鉴，用二元准则检查：承诺、过时的值、不可重复的动作、文件工作的事实。“有完成记录不代表不会重做”，所以交接单要对不可重复的动作给出强标记，基准要检查接收方最初的几个动作（见 R2-04、R2-22）。

**The Handoff Tax** [S61] 〔预印本 2026-08｜复现：与 S62 同向〕
- 问题/方法：研究中途换模型的两个方向：升级（弱→强）和降级（强→弱）。
  - 模型对为 Claude Haiku 4.5 与 Opus 4.7，以及 GPT-5.6 的两个档位（文中称 Luna 与 Sol）。
  - 在 SWE-bench Verified 500 题上用 mini-SWE-agent，设 7 个切换点。
  - 交接接口分三种：Raw（完整轨迹）、Compact（压缩前缀或后缀）、Traj-drop（丢掉轨迹，只留仓库）。
- 数字【事实】：
  - 升级时，Raw 只追回 47%（Claude）和 36%（GPT）的质量差距。
  - Claude 的 Raw 升级每题花费 $1.61，是只用强模型（$0.72）的 2.2 倍，效果还不如“放弃，让强模型从头做”（79.2%，$0.90）。
  - Traj-drop 升级分别得到 72.4%（Claude）和 79.7%（GPT）。
  - 降级时，保留强模型轨迹（Raw 或 Compact）效果更好；丢掉轨迹则质量下降。
  - 注意：只测了同族切换，每种配置只跑一次，难题子集较小。
- 用法【推断】：“把弱者的完整轨迹交给强者”是个坏的默认；“强者交给弱者”时应尽量保留强者的原文。跨族切换（如 Claude→GPT）未测。

**New Model, Old Habits** [S62] 〔预印本 2026-10｜复现：与 S61 同向〕
- 问题/方法：多会话 Agent 换模型时，接收方会“继承”历史作者的推理与行动模式，包括查询写法、工具使用和验证习惯。给原始历史时这种继承最强，摘要可以显著减弱它。
  - 任务取自 MemoryArena 的 Web Shopping、Travel Planning、Web Search。
  - 模型包括 Qwen3.5-4B、Qwen3.5-27B、DeepSeek-V4.1-Flash 和 Gemma-4 系列。
- 数字【事实】：
  - 单次切换、强→弱时原始历史最好。例如 27B→4B：原始历史 28.6，剪枝 12.5，摘要 14.7。
  - 弱→强时摘要最好。例如 4B→27B：原始历史 23.7，摘要 29.9。
  - DASH 是一种方向与作者感知的摘要：弱→强时只摘要弱者写的轨迹，保留强者的原文。在重复切换实验中，它在每一格都胜过原始历史，在 11 个设置上胜过朴素摘要。
- 用法【推断】：它与 S61 在不同任务、不同模型族上得到同向结论。这是本轮最接近“已复现”的交接设计规律：**交接材料的保真度应随交接方向和历史作者而变**（见 R2-18）。

**Do Not Restart（CFRC）** [S63] 〔预印本 2026-09｜复现：未见〕
- 问题/方法：路由或级联中的交接必须保留三样东西：已接受的选择、已实现的效果、尚未完成的义务。CFRC 把剩余工作冻结成一份“剩余合同”，并遵守三条顺序规则：先固定目标再提方案；整体检查后再授权；有现场证据才能宣布成功。实验覆盖 5 个环境、2 对同厂商模型。
- 数字【事实】：宏观准确率与强大的全任务 Agent 相当，成本只有后者的 22.0–34.6%。
- 用法【建议】：账本的三个栏目直接采用这组概念：decisions（已接受的选择）、effects（已实现的效果，含外部副作用）、obligations（尚未完成的义务）（见 R2-04）。

**StateHarness** [S64] 〔预印本 2026-10｜复现：未见〕
- 问题/方法：为长程编码 Agent 维护项目状态，分为四类记录：
  - `task_state`：当前焦点，不超过 200 字符；
  - `breakthrough_log`：发现、编辑、测试、决定，以及被否定的假设和原因；
  - `file_relation_graph`：调用方、测试、文档、配置之间的关系；
  - `skill_states`：各流程的使用、核验、规避或冻结状态。

  **紧凑的工作简报由固定规则生成，不用 LLM 摘要**。行为信号累积到阈值时，由另一个模型的诊断会话复核，最多给出 3 条告警，且不能修改仓库。
- 数字【事实】（工作模型为 Claude Sonnet 5）：
  - RefactorBench 全链完成率 29.4% → 35.3%。
  - LHTB 从 0.427（Claude Code 基线）升到 0.576。
  - ChainSWE 修复率 35.1% → 39.5%，但回归从 16 个增到 23 个。
  - RefactorBench 上 token 从 25.6K 增到 33.1K，耗时从 383 s 增到 529 s。
  - 局限：只用了一个模型，比较时算力不对等，只追踪受支持的写操作。
- 用法【推断】：“用固定规则生成简报”在真实编码任务上有收益，也有成本和回归；而且记录了一个未解决的问题，并不保证 Agent 会去修。

**Structured State Reconciliation for Human-AI Task Handover** [S65] 〔预印本 2026-08，人机交接｜复现：未见〕
- 问题/方法：日志精确但片面，人工报告包含意图但会遗漏或记错。把两者转成共享的类型化状态，对齐、调和、标记冲突，再生成结构化的交接报告。样本为 13 个配对的任务状态。
- 【事实】两个来源结合优于任一单独来源；与端到端 LLM 相比，效用相近，错误信息显著更少；按任务渲染比穷举式渲染的每 token 效用更高。摘要没有给具体数字。
- 用法【建议】：Hub 观测的事实（相当于日志）与 Harness 的自述（相当于报告）分开存储，对齐后再渲染，冲突显式标出，而不是让模型“写一段总结”（见 R2-01）。

**ContinuityBench** [S66] 〔预印本 2026-07｜复现：未见〕
- 【事实】研究多 Provider 路由在故障切换时能否保住会话连续性，定义了两个指标：连续性保持率（CPR）和连续性时延开销（CLO）。在 750 次故障切换中，转发历史的有状态代理 CPR 为 99.20%，无状态代理接近 0%；需要带抖动的指数退避，防止重试风暴。
- 用法【推断】：“保住历史”在工程上不难，难的是质量和成本；指标可以借鉴它的拆分方式，把保持率与时延开销分开报告。

**Old Habits Die Hard（History-Echoes）** [S67] 〔评审 ICML 2026｜复现：与 S6、S62 机制同向〕
- 【事实】对话历史在隐空间中形成“几何陷阱”，使后续生成延续已有的行为；覆盖三个模型族、六个数据集，摘要中没有数字。
- 用法【推断】：为“必要时开新会话 + 交接单”提供了机制层面的解释。

**Anthropic：长时运行 Agent 的 harness** [S68] 〔博客 2025-11-26〕
- 【事实】
  - 问题：每个新会话都不记得之前发生过什么。
  - 初始化 Agent 负责建立 `init.sh`、`claude-progress.txt`、首次提交，以及一份 200+ 条的特性清单。清单用 JSON，初始全部标为失败，后续 Agent 只能修改 `passes` 字段——因为模型改 JSON 比改 Markdown 更不容易出错。
  - 之后每个会话的开工流程：`pwd` → 读 git log 和进度文件 → 选优先级最高的未完成特性 → 运行 `init.sh` 和基本的端到端测试，然后才开始新工作。
  - 观察到的失败模式：过早宣布完成、一次做太多、留下坏状态。
  - 文中没有量化结果。
- 用法【建议】：
  - 验收标准和待办状态用“只允许修改状态字段”的结构化表格。
  - 接手方开工前先做基线检查，对应 HarnessHub 的工作区指纹核验（见 R2-05）。

### 2.9 缓存与成本

- **Don't Break the Cache** [S74] 〔预印本 2026-01｜复现：未见〕
  - 【事实】覆盖 OpenAI、Anthropic、Google 三家的旗舰模型，在 DeepResearch Bench 上跑了 500+ 个会话，系统提示约 10K token。
  - 缓存使 API 成本降低 41–80%，TTFT 缩短 13–31%。
  - 把动态内容放在系统提示末尾、避免动态的函数定义、排除动态的工具结果，比“全量缓存”的收益更稳定；朴素的全量缓存甚至可能增加时延。
  - 达到各家缓存的最小 token 门槛后，收益随长度线性增长。
- **TokenPilot** [S75] 〔评审 EMNLP 2026 Findings〕
  - 【事实】文本剪枝或逐出会重排提示的布局，导致前缀缓存失效。TokenPilot 在内容进入时就压缩，以稳定前缀；再按生命周期、以批次为单位保守地逐出。
  - 成本降低：隔离模式下 56–61%，连续模式下 61–87%。准确率“具有竞争力”，摘要没有给数字。
  - 测试基准为 PinchBench 和 Claw-Eval，是否与 OpenClaw 生态相关未核实。
- 【事实】ACE 只追加 delta、不破坏前缀，91.8% 的输入 token 命中缓存 [S23]。LLM 摘要调用则很少命中缓存 [S14]。缓存与未缓存的价差约 10 倍，输入与输出之比约 100:1 [S45]。token 用量解释约 80% 的表现方差 [S51]。
- 【推断】交接是一次性的大块输入，交接单在接收方新会话的第一轮无法命中缓存；但此后每一轮都会把它当作前缀重读。所以“交接单不可变 + 之后只追加增量”，决定了整个会话的缓存命中率。HarnessHub 控制不了各 Harness 内部的提示布局，只能保证自己注入的字节稳定：不放时间戳、键序固定、条目顺序确定。

### 2.10 安全：压缩与交接是一道信任边界

- **MINJA** [S76] 〔预印本 v5 2026-02；二手来源称收录于 NeurIPS 2025，未核实〕【事实】攻击者只通过普通查询和观察输出，就能向 Agent 的记忆库注入恶意记录，手法是“桥接步骤 + 渐进缩短”。摘要页没有给成功率，二手来源称超过 95%，未核实。
- Silence Is Endorsement [S27]、Facts Without Rules [S26]、The Compaction Cliff [S18]：见 2.3。
- 【推断】交接单这条通道，会把一个 Harness 读到的不可信内容（网页、文件、工具输出）转交给另一个 Harness。如果交接单由模型摘要生成，注入的指令可能被“洗白”成交接方自己的陈述。结构性的缓解办法有三条：确定性投影，引用原文而不转述，每条带来源与核实状态字段。

### 2.11 跨领域证据：医疗交接 I-PASS

**I-PASS** [S77] 〔跨领域，评审 NEJM 2014；9 家医院、10,740 次住院；前后对照，非随机〕
- 问题/方法：使用标准化的交接口诀，并配套培训。口诀五项为：病情严重程度、患者概况、行动清单、情境意识与应急计划、**接收方复述（Synthesis by receiver）**。
- 数字【事实】：
  - 医疗差错从每 100 次住院 24.5 次降到 18.8 次（−23%）；可预防的不良事件从 4.7 降到 3.3（−30%）。
  - 交接时长没有显著变化（每名患者 2.4 分钟对 2.5 分钟）。
  - 书面和口头交接中，预设关键要素的出现率都显著提高。
- 用法【推断】：这是“结构化交接 + 接收方复述”能减少差错、又不显著拉长交接时间的最强人类证据。但它能否迁移到 LLM 尚未可知，而且复述只是一个可观察的信号，不能证明质量（见 R2-12）。

## 3 模式归纳

### 3.1 共性（按证据强度排列）

- **P1 长度本身就是成本**（强）：至少 8 组独立工作同向 [S1]–[S8]。影响不只来自“找不到”，推理本身也会受损 [S5]。
- **P2 整体重写会坍塌，压缩会丢掉非事实的元数据**（中强）：五组同向 [S23][S25][S18][S26][S27]。被丢掉的通常是规则、边界和核实状态，而操作事实往往保留下来，这让损失很难被察觉。
- **P3 在工件与事实上，确定性或结构化的状态胜过自由文本摘要**（中）：[S14][S15][S25][S59][S60][S64][S65]。
- **P4 可取回的压缩优于不可逆的压缩**（中）：[S20][S40][S44][S45][S59]。S28 的数字未核实。
- **P5 交接方向与历史作者决定了最佳保真度**（中）：两组独立的 2026 研究同向 [S61][S62]，但都是同族或小模型、每种配置只跑一次，未跨厂商。
- **P6 记录不等于行为**（中）：[S59][S60][S64][S48]。
- **P7 先把剩余工作合同化，再执行，可以降低成本**（弱至中）：[S63][S68][S50]。
- **P8 最强的压缩成果大多依赖训练**（强）：[S9]–[S13][S35][S40][S55]–[S57]。HarnessHub 只能采用其中不需要训练的部分。
- **P9 只看完成率会误判**（中）：[S17][S59][S60]。必须同时计算成本指标和过程指标。

### 3.2 分歧与边界

- **D1 完整历史还是精简状态**：HSC-Bench 和 Handoff Debt 显示完整或原始历史的质量最好 [S59][S60]；而 JetBrains、Less Context、AgentDiet 显示剪枝后持平或更好 [S14][S15][S16]。
  - 【推断】调和：前两项研究中的完整历史只有几十 k 字符，且来自同一个任务；后几项研究处理的是长工具流程里的大量过期观察。所以合理的结论是：在可靠长度内给原文；超出之后，剪掉过期的观察，保留结构化状态。阈值要按接收方实测。
- **D2 位置效应**：Lost in the Middle 测到 U 形曲线 [S1]，而 Chroma 的实验中 needle 位置没有明显影响 [S4]。
  - 【推断】新模型可能减弱了位置偏置。但“任务放末尾、指令放两端”几乎没有成本，厂商文档也仍然推荐 [S42][S43]，应保留。
- **D3 摘要的作用**：JetBrains 认为 LLM 摘要会拉长轨迹，且不划算 [S14]；Old Habits 认为摘要能阻断弱模型的坏习惯 [S62]；Handoff Debt 发现摘要笔记对解决率的提升不显著，但大幅节省成本 [S59]。
  - 【推断】摘要的价值在于隔离作者的习惯、节省 token，代价是丢细节。因此关键问题不是“要不要摘要”，而是“摘要谁写的部分、摘要哪些内容”。
- **D4 记忆系统的排名**：Mem0、Zep、Letta、MemoryOS 在 LoCoMo 上的报告互相矛盾 [S31][S32][S33][S38][S39]；MemoryAgentBench 和 MemoryArena 显示，这些系统在冲突消解和多会话任务上普遍偏弱 [S71][S72]。
- **D5 结构化格式对个别接收方有害**：Kimi K2 在 HSC-Bench 上的均分下降 [S60]；Gemma 在 Handoff Debt 的某些状态下，笔记带来轻微的负向影响 [S59]。
  - 【推断】交接单的格式需要按目标 Harness 和模型做 A/B 测试，不能一套模板通用。

## 4 对 HarnessHub 接力的启示（全部为【建议】）

### 4.0 现状与文献的对照

| 现状（[L1]、简报 §2） | 文献的判断 | 建议 |
|---|---|---|
| 把整段公共历史序列化为 JSON，作为用户消息发送 | 用 JSON 装大量文档效果差 [S43]；长度本身伤害表现 [S1]–[S5] | 分层 + XML 式分栏（R2-09、R2-11） |
| 不带工具、文件改动、计划和待办 | 工件追踪是 LLM 摘要最弱的维度，而 Hub 恰好握有确定性数据 [S25] | L0 必须带文件改动索引和最近的验证（R2-01、R2-05） |
| 超过 1 MiB 就报错 `CONTEXT_TOO_LARGE` | 1 MiB 远超可靠区间；按需取用可以替代一次性塞入 [S40][S59] | 显式降级为分层交接，而不是报错（R2-31） |
| 返回原 Harness 时补发 `throughRunId` 之后的 Run，格式同上 | 增量的方向是对的，但应以账本 delta 的形式呈现，并写明取代关系 [S23][S32] | 发送 delta 包（R2-19） |
| 派发后即推进水位 | “已送达”不等于“已派发” [S66] | 水位表示已送达并已被接受（R2-19） |

### 4.1 交接内容（Q1）

**R2-01 改造后采用：账本的事实分两类来源。**
- Hub 观测（确定性）：
  - Run 的结果；
  - 工具调用：标题、kind、exit code、ContentRef；
  - 文件改动：路径、操作、行数统计、diff 引用、最后修改它的 Run 与 Harness；
  - 计划和待办的状态、审批、用量、附件、产物 hash。
- Harness 自述（由模型写）：问题理解、假设、已否决的方案及原因、剩余的不确定性、建议的下一步。来源有两种：
  - 来源 Harness 在 Run 结束时已经写出的最终回复；
  - 用户选择时，由来源 Harness 用它当前的模型专门写一份“交棒说明”。
- 两类事实对齐后再渲染，冲突显式标出。例如 Harness 自述“测试已通过”，而 Hub 最近记录的 exit code 不为 0，就要标出来。

依据：Handoff Debt 的字段拆分 [S59]；人机交接中的状态调和 [S65]；Factory 中 artifact 维度最弱 [S25]；StateHarness 用固定规则生成简报 [S64]。待验证：在接力基准中比较“只有 Hub 事实”“Hub 事实 + 自述”“自由摘要”三种方式。

**R2-02 采用：每个条目都带出处和核实状态。**
- `sources[]`：runId、seq、toolRef、contentHash；
- `author`：`user`、`hub`，或 `harness:<id>` + 模型；
- `verification`：`observed`、`reported`、`user_confirmed`、`unverified`、`contradicted`；
- `audience`：默认为 `session`，可以标为 `local_only` 等。

依据：[S26][S27][S32]；Magentic-One 把事实与猜测分开 [S50]。

**R2-03 采用：约束、用户决定和审批逐字固定（pinned verbatim），永远不进入有损压缩。** 这些内容超出 L0 预算时，判为 `blocked` 并提示用户，不得裁剪约束。依据：Compaction Cliff 中一轮压缩后安全规则剩 53%、五轮后剩 10% [S18]；措辞明确的约束泄露率低于 15%，模糊的为 50–73% [S26]；MAST 中违反任务约束占 11.8% [S48]。

**R2-04 采用三栏“剩余合同”：**
- `decisions`：已接受的选择，包括从行动中提取出来的隐含决定；
- `effects`：已实现的效果。外部副作用（push、发消息、迁移等）标记为**不可重复**；
- `obligations`：尚未完成的义务，包括验收标准。

依据：CFRC [S63]；Cognition 关于隐含决定的论述 [S52]；HSC-Bench 中重复执行 18 次对 12 次 [S60]；MAST 中重复步骤占 15.7%、不知道终止条件占 12.4% [S48]。

**R2-05 采用：附上“最近的验证命令及结果证据”，以及“如何运行、如何测试”的程序性信息。** 依据：Handoff Debt 的确定性字段 [S59]；Anthropic 的 `init.sh` 与开工前检查 [S68]；MIRIX 的程序性记忆 [S34]。

**R2-06 采用：设“失败与已否决方案”一栏。** 内容来自失败的 Run、非零的 exit code 和用户的否决，并附上原因和引用。依据：Manus 主张保留错误轨迹 [S45]；ReasoningBank [S36]；Factory 观察到的失败模式“忘记试过什么” [S25]。

**R2-07 改造后采用 Magentic-One 的事实分区：** 分为“已核实的事实”“待查”“推测”三区；推测必须标注出来，不能写成陈述句。依据：[S50][S27]。

**R2-08 拒绝：搬运推理或思考文本（thinking），以及原生工具调用的 ID。** 依据：状态外化之后，历史推理可以被替代 [S19]；不变量要求不复制隐藏状态（简报 §4）；搬运原文还有行为迁移的风险 [S62]。

### 4.2 预算、分层与布局（Q2、Q3）

**R2-09 改造后采用三层交接单。**
- **L0 常驻账本**（必带）：目标与验收标准；固定的约束与决定；三栏剩余合同；文件改动索引；最近的验证；失败与否决；未决问题与待审批事项；覆盖说明（包含了什么、省略了什么、如何取回，以及水位、指纹、策略版本、token 估计）。
- **L1 近期原文**：最近几个 Run 的用户输入和最终回复，标注作者是哪个 Harness、哪个模型；近期工具事件各写一行摘要，输出只给引用。
- **L2 按需取用**：完整的公共历史、工具输出和 diff 原文、分支来源的历史。取用方式为 ContentRef、文件路径，或者在通道支持时注入的按会话只读工具。

依据：MemGPT 的主存/外存 [S29]；RLM [S40]；VISTA 的仪表盘 [S20]；Manus 的可恢复压缩 [S45]；Handoff Debt 中原始轨迹最好但长度不受控 [S59]。

**R2-10 初始参数（全部待基准校准，不得当作已验证）。**

| 参数 | 初值 | 依据 | 校准方式 |
|---|---|---|---|
| L0 大小 | 目标 ≤4K token，硬上限 8K；固定的约束超限时判为 `blocked` | HSC-Bench 中不超过 4,000 字符的仓库状态仍然显著有效 [S60]；Handoff Debt 中约 10k 字符的笔记即可省下 42–63% 的 token [S59]；ACE 反对过度简略 [S23] | 在基准中试 2K / 4K / 8K |
| L1 窗口 | 最近 3 个 Run 的原文 + 最近 10 条工具事件摘要行 | masking 在 M=10 时最好，M=20 时变差 [S14]；最近 5 对加摘要效果最好 [S16] | 试 1 / 3 / 5 个 Run |
| 全文直送阈值 | 渲染后的完整公共历史 ≤16K token 时，直接全文发送，L0 放在末尾 | 完整历史的质量最好 [S59][S60]；32K 起大范围退化 [S2][S3]，取其一半，给 Harness 自身的提示留出余量 | 按目标模型试 8K / 16K / 32K |
| 注入软上限 | 24K token | 同上 | 同上 |
| 方向策略 | 默认：标注作者，并把非目标作者写的长轨迹摘要化；用户可选“完整 / 精简 / 只有目标” | [S61][S62] | 在基准中测同族升级、同族降级和跨族交接 |
| 返回原生会话 | 增量 ≤4K token、且原生会话估计 <64K token 时，用 `native_resume` + delta；否则建议重新水合 | [S6][S50][S67]，均无直接实验 | A→B→A 场景对比 |

**R2-11 采用“长材料在前、任务在后、指令放两端”的布局。** 顺序如下：
1. 开头说明：谁交给谁；材料的性质是需要核实的历史证据；不要重做已完成的事；遇到冲突时以工作区和用户为准。
2. L2 的索引。
3. L1 近期原文，按时间顺序排列，标注作者。
4. L0 账本，用 XML 式标签分栏。
5. 重述固定的约束。
6. 当前用户的输入。
7. 结尾：要求接收方复述。

不再用 JSON 作为整段历史的容器，因为 JSON 用于大量文档时表现特别差 [S43]。L0 内部的状态表（待办、特性清单）可以用 JSON 或固定表格——Anthropic 正是用 JSON 防止模型误改 [S68]。依据：[S1][S42][S43][S45]。

**R2-12 改造后采用“接棒复述”**（I-PASS 的接收方复述，加上 recitation）：要求接收方在第一个回复里，先用不超过 5 行复述目标、下一步，以及阻塞或疑问，然后再开始行动。
- 用途：作为 UI 上可见的“接住了”信号，也作为基准中的过程指标。
- 不作为质量证明——AGENTS.md 规定不能把模型自评当作质量证明。
- 成本约 100–200 个输出 token。

依据：I-PASS 降低差错 23% 和 30%，交接时长不变 [S77]；复述带来最多 4% 的提升 [S5]；“先引用再作答” [S42]。待验证：复述究竟改善了行为指标，还是只多花了 token。

### 4.3 维护与调度（Q2、Q8）

**R2-13 采用：账本是事件溯源的派生物。**
- 每个 Run 结算后，按新事件增量追加 delta，每条带条目 ID，由确定性逻辑合并。
- 任何“修改”都表现为新条目取代（supersede）旧条目。双时间轴中，`validFromSeq/validToSeq` 用公共 seq，`recordedAt/supersededAt` 记录写入时间。
- 旧条目永不改写。

依据：ACE 的坍塌实例——18,282 token 被重写成 122 token，准确率从 66.7 降到 57.1，低于基线 63.7 [S23]；Graphiti 作废而不删除 [S32]；Factory 的锚定式迭代优于整体重写 [S25]；INV-13 与 INV-22。

**R2-14 采用：切换路径上不调用 LLM。**
- 账本以及面向各目标的候选渲染，都在空闲期预先构建（sleep-time）。
- 切换时只做四步：结算 → 校验水位与指纹 → 渲染 → 注入。

依据：sleep-time 计算把测试时计算降到约 1/5，共享时单查询成本降到 1/2.5，查询越可预测收益越大 [S41]；LLM 摘要调用很难命中缓存 [S14]。Q8 的目标建议：256 个 Run 以内，渲染 p95 <100 ms（纯计算，需实测）。

**R2-15 改造后采用：把“Run 结束时 Harness 自己写的最终回复”当作 Context-Folding 的 return message。**
- 每个 Run 就是一个折叠单元，不另外调用模型。
- 用户要求更高质量时，才发起一次可见的“交棒说明” Run。它使用来源 Harness 当前的模型，用户可见、可取消。

依据：Context-Folding 的 return 消息 [S11]；HiAgent 的子目标折叠 [S21]；简报中的约束“不能静默使用用户没选的模型”。

**R2-16 采用：优先用确定性剔除代替 LLM 摘要。** 已被后续读写取代的文件读取、被重跑覆盖的测试输出、重复的搜索结果，都只留引用。依据：JetBrains [S14]；AgentDiet 降低输入 token 39.9–59.7% [S15]；Claude 的上下文编辑 [S44]。

**R2-17 改造后采用 ACON 式的离线准则优化：** 用 HH-RelayBench 中的失败案例迭代修订渲染规则和交接说明的文字，每次修订记为一个新的 `strategyVersion`，不训练模型。依据：[S13]。

### 4.4 方向、作者与返回（Q4、Q10）

**R2-18 改造后采用方向与作者感知的策略。**
- 账本和 L1 中的每段原文都标注作者（Harness、模型、Run）。
- 默认情况下，对“非目标作者写的、很长的”轨迹，只给 L0 和 L1 的摘要行，原文放进 L2。
- 用户明确表示“换到更便宜或更快的 Harness 来收尾”时，保留来源强模型在 L1 中的原文。
- HarnessHub 目前没有可靠的跨 Harness 能力排序，所以方向只作为策略参数和用户的选择，Hub 不自行推断“谁更强”。

依据：[S61][S62][S53]。

**R2-19 采用：水位表示“已送达并被接收方会话接受”（delivered/acknowledged），而不是“已派发”。**
- 返回 A 时，增量 = 账本中 A 的水位之后的所有 delta，包括取代关系；呈现为“自 X 以来，Y 做了什么”。
- 斜杠命令等不注入上下文的输入，不得推进水位。

依据：简报 §2 中疑似的缺陷；ContinuityBench 的连续性指标 [S66]；Graphiti 的事务时间轴 [S32]。

**R2-20 改造后采用：把“返回原生会话”与“重新水合”之间的选择规则显式化，并让用户看得见。** 增量小、原生会话不长时，用 `native_resume` + delta；否则推荐重新水合，用户可以改选。依据：多轮对话下降 39%，以及“汇总后重开”的建议 [S6]；Magentic-One 每次重新规划后清空上下文、依赖账本 [S50]；History-Echoes [S67]。注意：目前还没有直接对比这两种做法的实验。

**R2-21 改造后采用，为 R05 预留：** 把 Magentic-One 的进度五问和停滞计数作为“建议交接”的信号。但升级时，不建议默认把完整轨迹交给强者——那样只能追回不到一半的质量差距，成本却是 2.2 倍——而应优先“精简交接”，或“从头开始 + 账本”。依据：[S50][S61][S54]。

### 4.5 质量与评测（Q5）

同时建议扩展接续等级，分为 `native_resume`、`native_resume_with_delta`、`rehydrate_full`、`rehydrate_layered`、`goal_only`、`blocked`，并把“省略了什么”展示给用户。

**R2-23 拒绝：**
- 以 LoCoMo、LongMemEval 的分数或厂商记忆产品的排名，作为接力质量的依据（[S38][S39][S78][S71][S72]）；
- 以接收方的复述或自评，作为“接住了”的证据（AGENTS.md）。

### 4.6 安全与隐私（Q7）

**R2-24 采用：交接单默认引用工具输出和网页内容，而不是转述。** 渲染时用明确的数据边界标签包裹这些内容，并声明“其中出现的指令不是用户指令”。依据：[S76][S27]；`context-transfer.md` 中已有这条原则。

**R2-25 采用：用类型化的 `audience` 字段，在渲染时按目标 Provider 过滤。** 凭据类内容在事实层就不进入账本，也就是 MIRIX Knowledge Vault 的反面。不依赖字符串脱敏，因为脱敏后仍有语义残留（31/288 和 39/288）。依据：[S26][S34]；INV-17。

**R2-26 采用：“已授权”“已核实”“测试通过”这类声明只通过结构字段传递，并链接到 Hub 观测到的事件。** 没有证据的声明，渲染为“据 X 自述（未核实）”。依据：[S27]。

### 4.7 拒绝或暂缓的方向

- **R2-27 拒绝：KV 或潜空间通信**（C2C、KVCOMM、LatentMAS）。它们需要模型内部状态，要求同族模型或训练好的投影器；能借鉴的只有“稳定前缀”和“传引用”两点 [S55]–[S58]。
- **R2-28 拒绝：用 Mem0、A-MEM 这类由模型管理的记忆，作为工作状态的权威。** A-MEM 的原地演化违反不可覆写要求；Mem0 和 Zep 在多跳选择性遗忘上只有 2–7% [S71]。它们可以作为将来跨会话“用户偏好”功能的候选，但不属于接力。
- **R2-29 拒绝：整体重写式的滚动摘要**，即每次切换都重新生成一份全文摘要 [S23][S25][S18]。
- **R2-30 暂缓：需要训练的折叠与记忆方法**，包括 FoldGRPO、MEM1、Memory-R1、ReSum-GRPO 和 RLM 后训练 [S9]–[S11][S35][S40]。
- **R2-31 拒绝：把现行的 1 MiB 当作“可以交接”的判据。** 超限时应显式降级为分层交接，而不是报错或静默截断。这会改变 `context-transfer.md` 中“超限即明确报 `CONTEXT_TOO_LARGE`”的写法，需要主负责人和审批代理决定 [S1]–[S5]。

### 4.8 存储与契约（Q11）

**R2-32 新实体草案（供契约组参考）：**
- `LedgerEntry`：
  - `{ id, kind: goal | constraint | decision | effect | obligation | fact | guess | failure | file_change | validation | question | approval, text, fields, sources[], author, verification, audience, validFromSeq, validToSeq?, supersedes?, supersededBy?, recordedAt, strategyVersion }`
- `RelayPacket`：
  - `{ id, sessionId, fromBinding, toBinding, throughSeq, workspaceFingerprint, layers{ L0, L1, L2Index }, omitted[], tokenEstimate{ method }, strategyVersion, policy{ direction, mode }, contentHash, deliveredAt?, ackedAt? }`

两者都不可变，都可以由事件重建。其中由 LLM 生成的叙述部分，要记录所用模型、提示版本和来源 Run，可以追溯，但不保证逐字重现。依据：[S32][S73]（原文追加 + 类型化派生 + 出处、范围、状态）；INV-13、INV-22。

## 5 风险与反模式

| 风险或反模式 | 证据 | 缓解办法 |
|---|---|---|
| 过度相信交接文本 | 后继沿用前任的解释，漏掉验证命令 [S59] | 开头声明“这是需要核实的历史证据”；开工前做基线检查 [S68] |
| 完成记录就在眼前，仍然重做 | 结构化状态下重复 18 次，对照组 12 次 [S60] | 给不可重复的动作打强标记；在基准中检查接收方最初的几个动作 |
| 简略偏置与上下文坍塌 | 18,282→122 token，准确率跌到基线以下 [S23] | 只追加 delta，不重写；每个栏目必须填写或明确标空 [S25] |
| 规则、边界、核实状态在压缩中蒸发 | 安全规则 53%→10% [S18]；边界存活率与事实存活率无关 [S26]；批准率 5%→60% [S27] | 类型化、逐字固定，用结构字段传递 |
| 摘要拉长轨迹、掩盖失败信号 | 轨迹变长 13–15% [S14] | 失败事件必须原样出现在 L0 |
| 行为迁移，被旧历史困住 | [S62][S67][S6] | 标注作者；按方向选择策略；必要时开新会话 |
| “窗口放得下”就当作“能用好” | [S2][S3][S5] | 预算按可靠区间计算，不按窗口大小 |
| “完整历史总是最好” | 只在可靠长度内成立；原始轨迹长度不受控、噪声大 [S59] | 设全文直送阈值，超出后分层 |
| 只看完成率 | 检索调用增至约 3 倍，完成率却不变 [S17] | 计入重新获取成本 |
| 基准与 judge 不可靠 | [S38][S39][S78] | 优先确定性判定；judge 与人工校准 κ |
| 误用依赖训练的成果 | 未经训练的折叠低于全上下文 [S11] | 只采用不需要训练的部分 |
| 破坏缓存 | 时间戳、不稳定的键序、每次切换都重新渲染全文 [S45][S74][S75] | 交接单不可变；之后只追加增量；确定性序列化 |
| 在切换路径上调用 LLM | 增加时延，并有“静默使用模型”的风险 | 预先构建；交棒说明以用户可见的 Run 进行 |
| 注入内容被洗白 | [S76][S27] | 引用原文而不转述；附来源和核实状态 |
| 记忆系统无法可靠处理被取代的事实 | 多跳 2–7% [S71]；更新传播 0/3 [S73] | 由 Hub 确定性地标记取代关系 |
| 结构化格式对个别接收方有害 | Kimi K2 均分下降 [S60]；Gemma 轻微负向 [S59] | 按目标 Harness 和模型做 A/B |
| 把单组预印本的结论外推 | 本报告中多数 2026 年的结论尚未复现 | 先用 HH-RelayBench 复核，再确定参数 |

## 6 未解决的问题

1. **跨厂商、跨 Harness 的交接实验几乎是空白。** S61 只测了同族切换，S62 用的是小模型。七个焦点 Harness 的工具和提示格式各不相同，“非原生轨迹”带来的影响未知。
2. **“强”与“弱”如何定义？** 同一 Harness 下的不同模型、不同 Harness 的不同脚手架，都会影响能力。拿不到能力排序时，方向策略的默认值应该怎么设？
3. **各项阈值都没有 Harness 级别的数字**，包括全文直送阈值、L0 和 L1 的上限、返回原生会话与重新水合之间的切换点。文献给不出这些数字，必须按目标模型实测。
4. **叙述部分由谁来写？** Run 的最终回复是否足够？专门的“交棒说明” Run 成本和收益各是多少？它会不会破坏“像原生”的使用体验？
5. **接棒复述能否真正提升行为质量？** I-PASS 是针对人类的证据。在不信任模型自评的前提下，复述应如何利用？
6. **L2 按需取用的通道在各 Harness 中是否可用？** 例如按会话注入 MCP、文件、嵌入资源。这需要 R1 或原生通道组确认；Context-Bench 显示各模型的取用能力差距很大。
7. **LLM 生成的派生物如何满足 INV-22 的“可重建”？** 实际上只能做到“可追溯 + 可重新生成（不保证结果相同）”，需要在契约层面给出定义。
8. **隐含决定如何显式化？** 从行动中自动提取决定需要模型；Hub 没有自有模型时，只能依靠 Harness 的自述或用户确认。
9. **外部对工作区的改动如何与账本调和？** 改动可能来自用户或其他程序。S65 给出了框架，但具体的冲突处理策略还没定。
10. **多次交接的累积损失如何？** Facts Without Rules 显示，在只部分回放记忆的情况下，三跳后损失会显著累积 [S26]。A→B→C→A 这类路径需要实测。
11. **Hub 的外部账本如何与原生压缩协同？** 各家模型正在通过训练获得折叠或压缩能力（例如原生的 compaction）。这个问题与 R1 关于原生压缩的调研交叉。
12. **2026 年新论文的可靠性。** 大多是单组的 v1 预印本，下一轮需要跟踪是否出现复现或撤回。
