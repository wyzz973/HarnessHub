# 写入阶段发现的终稿矛盾

第四轮“写入”阶段，6 位文档作者按终稿写 ADR-055、契约、不变量与计划时，报告了终稿内部的矛盾与无法落实之处，下面按作者原样汇编。各作者在自己的文件里已按注明的方式处理；终稿的一致性修订见 [v3-dispositions.md](v3-dispositions.md) 末节。

## ADR-055（15 条）

1. Table count: §14.4 says the migration '建 9 张表与触发器', but §3.1, the §14.1 DDL and the G066 scope say 11 tables and 4 triggers. relay_log_archive and relay_prefs were added in v3 and §14.4 was not updated. The ADR writes 11 tables and 4 triggers and notes the §14.4 wording.
2. Snapshot size limit: §0, §4, §11.1 and G066-C08 say ≤1,024 B per binding and ≤320 B per Run. §20 Q7 still says '上限 512/320 B', and the §18.2 J2 M13 row says binding ≤512 B. The ADR uses 1,024 B.
3. Untrusted-text cap: §5.3 says that when T is not reduced the caps equal v1's 300 / 1,500 / 3,000 / 8,000 / 24,000. TIER_CAP.goal was raised from 2,000 to 2,500, so 0.15 × 2,500 = 375, not 300. The ADR gives only the ratios and standard = 3,000.
4. HTTP mapping: §6.1 says the admit-time codes are all mapped to 409 by server.ts:266 【事实】, and §12.4 lists RELAY_TARGET_UNVERIFIED as 409. Under the actual rule in src/web/server.ts:265–266, RELAY_TARGET_UNVERIFIED matches no 409 condition and would return 502; RELAY_INPUT_LIMIT returns 429, which §9 and §12.4 already say. The ADR states that the mapping must be added (G073 changes server.ts through its owner G050).
5. D9: option (a) in '状态与验收' shows the side-by-side 'new session with packet' only when the return is cold and the whole-life cost gap is ≥$0.10 or the latency gap ≥10 s. §7.3 and O11 say the condition applies warm or cold, and add N/W ≥0.85. Decision 11 follows §7.3; a note under the D-table asks the user to confirm this when deciding D9.
6. Invariant labels: the §14.3 heading says INV-29/30/33 are '改写' and 'INV-01–28 不变', but the repo's invariants.md had only INV-01–28. The '改' is relative to v1 of the design, where these were labeled '新'. The ADR keeps the draft's labels and notes that all of INV-29–36 are new to the repo.
7. HANDOVER: §10.1 and §21 say the HANDOVER.md:184–185 cited by RT4 'is not in this worktree and was not verified'. docs/HANDOVER.md:184–185 does exist and records the 4317 command with --cwd /Users/sd3/Desktop/project/HarnessGateway --data-dir /Users/sd3/Desktop/project/HarnessGateway/data, so the data root is inside the workspace. The ADR cites it as a verified fact.
8. ADR-006 file: §17 has C006 add a 'superseded by ADR-055' status line to docs/decisions/0006-context-handoff.md, but that file does not exist; ADR-006 is only a row in the index's agenda table. The ADR does not link to it and says the file has not been created.
9. Code citations: in the §17 G006 row, 'context.ts:56–58 来源过滤' is wrong. src/contexts/session/domain/context.ts:56–58 is the CONTEXT_TOO_LARGE budget check (R4 D3); the default source filter is at :27–28, and src/contracts/context.ts does not exist. Separately, the draft cites Turn.tsx:170–181, but the file has only 179 lines and SwitchDivider is at :170–179; the ADR uses the latter.
10. capWindow formula: the §0 key-numbers table gives max(0, min(5%·W, W − S_B − 4,096)), while the §6.2 pseudocode also subtracts the current input S_new. The ADR follows §6.2.
11. Probe scope: §13.3 says each of the six Harnesses runs 16 probes, but the same section runs P15 and P16 only on Claude and Codex. G074-R01 covers P1–P14 and R03 lists P14 again. The ADR says six Harnesses run P1–P14 and only these two run P15/P16.
12. Data-root pre-check scope: in §6.1 the admit order lists 'data root in workspace → RELAY_UNAVAILABLE' with no cross-vendor qualifier. §9, §10.1 and INV-36 restrict the refusal to cross-vendor handoffs; same-vendor and single-Harness conversations continue. The ADR writes '（跨厂商时）'.
13. Event list: the extended events listed in §4 omit message.accepted, which §14.2 lists as extended. The ADR follows §14.2.
14. The §18.2 table records second-version dispositions ('8 种形式' for J4 M1; 'warm 用 0.8·TTL 与 endedAt' for J2 M15). These differ from the v3 body text (10 forms; warmth judged from the start of the last request). The ADR follows the body text.
15. relay_prefs keys: §3.1 lists only relay.crossVendor and relay.returnPreference, while the DDL CHECK allows four keys (adding relay.allowUnprobed and relay.localModelsOffline), and D11 calls relay.allowUnprobed '开发用配置'. The draft does not say whether it is a relay_prefs row or a startup setting. The ADR words it neutrally: '经 relay.allowUnprobed（默认 false）放开'.

## 交接内容契约（26 条）

1. Delta user-words extension: §5.3 says it can grow to min(2,000, DELTA_CAP remaining); the §6.3 pseudocode grows the cap itself to min(DELTA_USER_EXT + fixed, T), which can exceed DELTA_CAP. The measured fixed part of a no-base delta is ~1,095 tokens, so under §5.3 only ~400 tokens are left for user words. The contract follows §6.3.
2. Untrusted-text cap: §5.3 says that with T not lowered the caps equal the first version's 300/1,500/3,000/8,000/24,000. But TIER_CAP.goal was raised to 2,500, and 0.15 × 2,500 = 375. The contract states only the ratio formula.
3. The §0 summary gives capWindow as W − S_B − 4,096 with no S_new; §6.2 subtracts S_new. The contract follows §6.2.
4. Index column size: §2 and §4 say about 200 B; §6.3 gives about 1,485 B for this version's shape, with CHECK 2,048 B. The contract uses the latter.
5. RunDigestIndex.counts is commented as 13 fact categories, but OmissionCategory has 16 values and the 13 are not named.
6. need already removes user-excluded turns, yet fold allows excluded{by:"user"} and the identity is written as = |need|. The contract reads |need| as the pre-exclusion candidate count 【推断】.
7. Scan cap: N19 says the part beyond the cap is neither scanned nor sent; §10.2 says omit that one entry. The contract never sends unscanned bytes and omits the whole entry when the range to scan exceeds 64 KiB. The sibling files split here: security.md follows N19's wording, invariants.md follows §10.2's.
8. §5.3 says all caps are in tokens, but G2 (≤4,000 chars; head 2,500 + tail 1,000) and remainder step ③ (≤2,000 chars) still count characters. G2 also needs a 1,000-char tail while RunDigest stores at most 800.
9. The 'complete' label requires zero omissions in four categories including failures, but OmissionCategory has no failure category.
10. Missing templates: English delta, anchor and resend; Chinese resend (marker lines, position of the dedupe line); English unit titles, narration phrases and closing sentence of 未包含. The §5.6 delta sample shortens the 7 conventions to a placeholder, so the s2-delta golden file cannot match it byte for byte until that text is filled in.
11. Disposition F20 says Unicode version (Node ICU) was added to the policyVersion bump triggers, but §0 of the final draft does not list it. The contract includes it, since N2, NFKC and the confusables skeleton depend on it.
12. goal_only consent: the effect on content is never defined. The contract reads it as allowing only goal-tier packets 【推断】.
13. Whether the name-based exclusions (*_MODEL etc.) also apply to set (b), referencedNativeValues ('regardless of name'), is not stated.
14. inputs.noteIncluded: unstated whether it means the user's note or the handoff note.
15. Tail extension 'from n−2 backwards' is read as 0-based, i.e. the unit before the last 【推断】.
16. §5.1 'user words of not_recorded content turns on this binding' reads against O6. The contract follows O6: such a turn is foreign to other bindings and is annotated as not delivered to any Harness.
17. §6.1 applies admit's probe / data-root / consent checks to every 'content input' without requiring that a packet is needed. Read literally, this would block single-Harness conversations on probed=false targets. The contract requires consent only for turns that carry history.
18. The order between lexicon-based sentence picking and the single-message head 4 : tail 1 cut is not stated.
19. The option [只发计数通知] after consent revocation has no packet kind, template or ledger rule.
20. 'Redaction-context change ⇒ new ID + supersedes' cannot hold when the body is unchanged, because the ID derives from the body. Also the manifest holds fields not fully determined by the body (setHmac, keyId, policyVersion), and ON CONFLICT DO NOTHING drops the manifest of a second write with the same body.
21. '10 forms' lists only 7 groups; how sub-variants are counted is not written (the second version counted the first 5 groups as 8).
22. The §10.6 threat table ('second segment treated the same way') contradicts §5.5, O8, D4 and INV-29 (second segment sent verbatim). The contract follows D4.
23. §10.2 puts API-returned bodies in the outbound rescan. If the session secret set grows, the rescan can change bytes, which conflicts with 'ETag = sha256 of the body' and 'identical to the native transcript'.
24. relayRequest.fingerprint is typed Fingerprint (unsalted sha256), covers the note and reveals, and goes into message.accepted. That conflicts with INV-29 and with the Fingerprint type's own comment. The contract asks for an HMAC subkey 【推断】.
25. §10.4 says the packet records consentLogSeq; §4, §14.1 and INV-13 put it in the delivery row. The contract follows the delivery row.
26. Outside content scope: §20 Q7 still says 512/320 B, while §0, §11.1 and §14 set the binding limit at ≤1,024 B.

## 切换与存储契约（16 条）

1. Status of queued Runs after an unconfirmed stop: §9 and §0 say Runs waiting on the failed switch are recorded as SWITCH_NOT_EFFECTIVE (the RT2-04 fix); the run.ended cell in §14.2 says '排队 Run 的 cancelled'. Both contracts follow §9, and ADR-055 says the same. The draft never states the status; failed is inferred from the existing use of this code (runtime.ts:1308–1310).
2. Table count: §14.4 says '迁移事务：建 9 张表与触发器'. The §14.1 DDL has 11 tables and 4 triggers, and §3.1, the G066 scope and the §14.1 backup readback also say 11. Used 11 and noted the change in place (relay_log_archive and relay_prefs were added in the 3rd edition).
3. HTTP status of admission errors: §6.1 ('都由 server.ts:266 的规则映射为 409【事实】'), §12.4 and the §6.2 pseudo-code comment ('同步 409') disagree with the code and with §9/§12.4 on RELAY_INPUT_LIMIT. src/web/server.ts:265–267 maps it to 429, and RELAY_TARGET_UNVERIFIED matches no branch of the rule, so it would get 502. The contract uses 429 for RELAY_INPUT_LIMIT and keeps 409 for RELAY_TARGET_UNVERIFIED as the draft intends; G073/G050 must extend the rule. public-api.md reports the same issue.
4. suspect{unknown_turn} in the §7.2 k column says '不在 → 回到 prior', but the suspect type in §4 (SyncPrior/BindingSync) has no prior field. Also, once a turn that carried a packet goes unknown and becomes suspect{unknown_turn}, both P and pending.prior are lost, and '在 → synced{mark}' does not say whether the mark advances to P.range.
5. SuspectCause values verify_unavailable and vendor_changed have only a release rule (need=∅ is let through). No transition in the §7.2 table produces them: §7.2 now treats outside_window/unavailable as 'unchanged', and §10.4 records relay.vendor_changed and blocks without setting suspect{vendor_changed}.
6. The cause of RELAY_CHOICE_REQUIRED has only two values (marker_absent | delivery_unconfirmed). Yet the §7.2 suspect row, column b, says that causes rewind/unknown_command/clear_unconfirmed/unknown_turn with need=∅ must be verified first, and '无法核对 → 409 选择'. The cause value for that 409 is not defined, and the admission list in §6.1/§9 covers only 'suspect 且无法核对且 need≠∅'.
7. §6.1 lists the admit checks for every content input (RELAY_TARGET_UNVERIFIED, data root, consent, MIN_PACKET) without saying they apply only when relay content will be attached. Read literally, every initial Driver ships with probed=false (G069), so single-Harness use would be blocked; that contradicts INV-30, '作目标时' in §8.1 and the cross-vendor-only data-root rule in §10.1. The contract states the precondition (need≠∅, reanchor, or attach=full) explicitly as an inference.
8. The capWindow formula in the §0 key-numbers table, max(0, min(5%·W, W − S_B − 4,096)), leaves out S_new; the §6.2 pseudo-code includes it. Used §6.2.
9. Snapshot size cap per binding: §20 Q7 says '上限 512/320 B' (a leftover from the 2nd edition), while §0, the §4 comment, §11.1 and G066-C08 say ≤1,024 B per binding. Used 1,024 B.
10. relay_prefs: the DDL CHECK allows 4 keys (relay.crossVendor, relay.returnPreference, relay.allowUnprobed, relay.localModelsOffline), but the prefs API in §3.1/§12.4 lists only the first two. D11/§8.1 call relay.allowUnprobed '开发用配置'. The draft does not say whether it is a config-resolver default or a pref row, or which keys the API may write.
11. §9 says a session whose relay rows fail to write during recovery is marked relay_recovery_failed and refuses relay when opened. §4/§14 never say where that mark is stored (snapshot field, event or memory).
12. D5 (recommended a) moves attachment materialization to a per-Run 0700 directory under os.tmpdir() that is deleted when the Run ends. Today content/files/<id>/<name> is a stable copy kept so that 'a native session can read it again in a later Turn' (content-store.ts:147–150). The draft does not discuss the regression for re-reading an attachment by path in later turns.
13. Retention not defined in the draft: no reclamation for relay_digests rows of an old policy version, for relay_windows, or for relay_log_archive; relay_digests.status='failed' is allowed by the CHECK, but the text only ever marks failures as behind.
14. Name collision: 'K8' means the C2 ruling (fail before the program starts) in §0/D2/§5.3/§6.1/§9/O2/O10, while K1–K18, which also includes a K8 ('authorized 后、dispatched 前'), are the RT2 crash-injection points cited in §9/§13.1/§16 and in G068. The contract tells the two apart.
15. Citations that drift from the code: §7.1 cites hermes.ts:124 for NATIVE_GATEWAY_UNAVAILABLE, but the code returns it at hermes.ts:120–122 (:124 is the unknown-outcome check). The G006 row labels context.ts:56–58 as '来源过滤', but those lines are the CONTEXT_TOO_LARGE budget check; source selection is at context.ts:27–28. The contracts use the actual lines.
16. Minor points: the '新增事件' paragraph in §4 leaves out the message.accepted extension that the §14.2 table lists (the table is followed). §14.3 marks INV-29/30/33 as '改' relative to the 1st/2nd drafts, although invariants.md before ADR-055 had only INV-01–28. §14.1 says the backup readback extends to 11 relay tables, but the v12→v13 backup copies a v12 database that has none of them (the extra checks only make sense for v13 and later sources; inference).

## 公开接口与安全契约（16 条）

1. 【A1 HTTP 状态】终稿 9、12.4 节写 RELAY_TARGET_UNVERIFIED 为 409、且“均经 server.ts:266 的规则映射”。按现码 src/web/server.ts:265–266 的子串规则，这个码不含 LIMIT、UNAVAILABLE、_REQUIRED 等子串，落入 502（我用 node 对该表达式的逐字副本求值，diff 确认副本与源码一致）。另外 6.1 节写受理时的错误“都由 server.ts:266 映射为 409【事实】”，但其中 RELAY_INPUT_LIMIT 实际是 429，9、12.4 节也写 429。处理：契约按 9、12.4 节写 409/429，注明实现时（G073，经 server.ts 的所有者 G050）须为 RELAY_TARGET_UNVERIFIED 显式映射 409。
2. 【A2 阶段表缺项】终稿第 9 节“错误码按阶段”一行，open 之后一栏没有 RELAY_CHOICE_REQUIRED；同一节“需要用户选择”一行却写明返回 A 时核对为 absent，以同一错误码在派发前失败。处理：按后者把它列入 open 之后。
3. 【A3 第二段是否脱敏】终稿 10.6 威胁表“用户贴入的内容”一行写“10.2 三层脱敏（首行、附言、第二段同样处理）”，与 5.5、O8、D4 推荐项和 INV-29（当前输入除外）冲突，是第二版遗留的说法。处理：按 O8、D4、INV-29 写，第二段原样。
4. 【A4 附件副本的生命期】D5 推荐项让附件物化到 os.tmpdir() 下每个 Run 一个目录，并随 Run 结束删除（终稿第 9 节清理表）。这与已 accepted 的 ADR-023 第 3 条冲突：那里规定附件是“数据根内的稳定只读副本，后续回合原生会话再次读取时仍可用”，content-store.ts:147–150 的注释也这样写。终稿和 ADR-055 都没有处理副本的保留期限。处理：按 D5 写入，在“待定”里注明保留期限须与 D5 一并决定。
5. 【A5 relayRequest 指纹】PublicRun.relayRequest.fingerprint 的类型是 Fingerprint（未加盐 sha256），它覆盖的选项含附言与放行，又随 message.accepted 进入事件；现状事件查询原样返回已提交事件（server.ts:1044–1047）。这与 INV-29（接力事件的新增字段不含秘密原值的未加盐哈希）、与 Fingerprint 类型自己的注释“凡可能对应秘密的值一律不用它”、与 provider-web-mvp.md 的“Web DTO 屏蔽 fingerprints”都不一致。处理：API 的 Run 资源不带 fingerprint（标【推断】），算法列为待定。
6. 【A6 换新 ID】终稿 10.2 写“脱敏上下文变化即换新 ID 并写 supersedes”，但 ID 只由正文派生，正文不变时 ID 不会变，两句不能同时成立。invariants.md 的作者在 INV-13 说明里也指出了这一点。处理：列为待定。
7. 【A7 正文复扫与 ETag】10.2 要求“API 返回的正文”在发出前复扫。已知秘密集合变大后，复扫可能改写字节，此时 12.4 的“ETag 为正文 sha256”和 8.1 的“与原生里看到的逐字相同”不能同时成立。处理：两份文件都列为待定。
8. 【A8 字段名】12.4 节的 Run.relay.level 与第 4 节的 PublicRun.relay.continuity 指同一个接续等级，却用了两个名字。处理：API 用 level、快照用 continuity，注明由 C009 统一。
9. 【A9 observation_required】RELAY_PREPARE_FAILED 的 reason observation_required 在终稿只出现在枚举里，没写触发条件；而第 9 节又写“观测失败或超时……不阻塞”。处理：照列，注明待定。
10. 【A10 终稿没给出的值】以下各项终稿只写了含义或选项，没有给出标识符或接口，两份文件都只描述含义、列为待定，没有自行起名：(1) relay.returnPreference 三种取值的标识符；(2) DELETE /api/v1/relay/consents/:vendor 撤回的是 global 还是 session 范围；(3) 同意记录没有读出接口（只有 POST 与 DELETE，详情栏却要列出同意记录）；(4) relay_prefs 里的 relay.allowUnprobed、relay.localModelsOffline 是否经 PUT /api/v1/relay/prefs 写入；(5) 会话被标为 relay_recovery_failed 后“拒绝接力”用哪个错误码；(6) 撤回后返回 A 时的［只发计数通知］在 RelayRequest 里没有对应字段；(7) 本纪元内厂商键变化、撤回后返回 A 这两种 blocked 用哪个错误码；(8) attach:"none" 的请求是否跳过同意与数据根预检（终稿只写明命令与疑似命令跳过）。
11. 【A11 现码承载不了的形状】(1) 事实流的现状帧只有 snapshot、message、run 三种（src/contracts/web.ts:248–252），终稿写“SSE 推 relay.* 事件”，但帧形状没定；(2) 现状错误体只有 {code, message}（web.ts:264、server.ts:1088），RELAY_CHOICE_REQUIRED 的 {binding, cause, options, counts} 与同意的预览计数需要扩展错误体。处理：注明由 G073 与 C009 冻结。
12. 【A12 observe=true 的 CSRF】终稿写新端点“沿用 cookie、CSRF 与 Host/Origin/Sec-Fetch 校验”，但 GET …/relay/preview?observe=true 会启动目标程序并持有租约，是带副作用的 GET；现码只对写请求校验同源 Origin 与 CSRF（server.ts:522、:535），GET 只靠 SameSite=Strict cookie（:531）与拒绝 Sec-Fetch-Site: cross-site（:514）保护。处理：在 public-api.md 的待定里写明这一事实。
13. 【A13 跨厂商的判定口径】“跨厂商 = 目的厂商键 ≠ 来源厂商键”没写多家来源时怎么取来源厂商键。我的假设：任一来源的厂商键与目的不同即算跨厂商。理由：较保守，误判只多一次失败提示，不会让数据根暴露给别家。另外 6.1 节列举受理检查时写“数据根在工作区内 → RELAY_UNAVAILABLE”，没有跨厂商限定，与 9、10.1 节和 INV-36 不一致；处理：按后者，只对跨厂商交接失败。
14. 【A14 admit 时的检查耗时】10.1 要求“启动时与每次 admit”检查数据根与工作区互不包含，另有一次有界标记查找（≤100 ms）。admit 跑在同步受理的 send() 里（runtime.ts:343），终稿没写标记查找是否每次都做、能否复用启动时的结果，与 11.1 节“受理→派发增量 p95 ≤15 ms”存在张力。处理：列为待定，交 G072 决定。
15. 【A15 两处计数口径】(1) “10 种形式”按组列举只有 7 组（原值、JSON 转义、URL 编码、壳转义、折行、base64、十六进制），子变体怎么计数没写，G070 的秘密夹具须先固定形式枚举；(2) 10.4 写“交接单记录依据的 consentLogSeq”，第 4、14.1 节与 INV-13 把它放在送达行；处理：按后者。
16. 【A16 不属于我负责的文件、顺带发现】(1) 终稿 14.4 节写“迁移事务：建 9 张表与触发器”，而 3.1、14.1 节与 G066 都是 11 张表；(2) 终稿第 0、4、11.1 节与 G066-C08 写快照增量“每绑定 ≤1,024 B”，18.2 节 J2 M13 与 Q7 仍写 512 B。

## 不变量（13 条）

1. INV-22: the 14.3 rewrite drops the general clauses "配置与原生状态不能替代公共事实源" and "读模型可重建". But section 1's hard constraint still attributes "公共 Session 是唯一业务权威，派生物可追溯、可重建" to INV-13/INV-22, and plan/test-cases.json tags non-relay cases with INV-22 (G008-C01–C04, G015-C01–C03, G057-C01–C03, G060-NC1, G008-NC2, G008-NC4). ADR-055 line 100 also summarises INV-22 without these clauses. ## 实施计划（12 条）

1. 表数矛盾：第 14.4 节写“迁移事务：建 9 张表与触发器”，第 3.1、14.1、17 节与 DDL 本身都是 11 张表加 4 个触发器（多出的是 relay_log_archive 与 relay_prefs）。计划按 DDL 写 11 张表与 4 个触发器；ADR-055 第 177 行同样以 DDL 为准。
2. HTTP 状态码与实际代码不符：第 6.1 节说受理时的错误“都由 server.ts:266 的规则映射为 409【事实】”。按 src/web/server.ts:266 的实际规则：含 LIMIT 的码映射为 429，所以 RELAY_INPUT_LIMIT 是 429，第 9 节、第 12.4 节与 ADR-055 也写 429；RELAY_TARGET_UNVERIFIED 不匹配任何规则，现状会映射为 502，不是 409。计划里 G072-C02 按第 9 节写成“RELAY_INPUT_LIMIT 为 429，其余 409”。要让 RELAY_TARGET_UNVERIFIED 成为 409，必须改 server.ts:266 的映射规则（文件归 G050，G073 的现有文件里列了 server.ts），但终稿没有写这一处改动。G073 验收里的“409 五种”我照原文登记，没有展开。
3. G073 不变量不一致：第 17 节的 G073 行只列 INV-21、INV-25，第 14.3 节却把 INV-29 的计划用例指向 G073-S01（AP-01–AP-03）。任务级不变量按第 17 节保持不变；G073-S01 的不变量写为 INV-25、INV-29，满足第 14.3 节。计划里本来就有 37 条用例的不变量超出所属任务的列表。
