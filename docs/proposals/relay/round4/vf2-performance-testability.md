## 0 结论

**不通过**：1 个 blocker、12 个 major、3 个 minor。v2 §11.1 说“目标按实测校准”，但下表 18 行里只有确定性与夹具、RunDigest 典型耗时、S1 规模、观测时延四行有对得上的实测；其余引用的是第一版或原型配置的数字，或测不出、进不了 CI。被推翻的结论：

1. “只有 W<12k 才 `RELAY_INPUT_LIMIT`”：窗口 12k 到约 37k 时会在目标程序启动后才失败（VF2-01）。
2. “框架 ≤420 token（o200k）”：v2 自己的中文模板是 448 / 498（VF2-02）。
3. “脱敏 ≤3 ms/MiB”：只在没有熵规则的原型配置下成立（VF2-03）。
4. 缓存、首回合时延、est/2、送达率、RelayBench 假设缺可行口径或样本量（VF2-09 至 13）。

## 3 发现

### VF2-01（blocker）MIN_PACKET 小于固定部分：小窗口与窗口未知时启动之后才 RELAY_INPUT_LIMIT
- **章节**：6.1、6.2 `MIN_PACKET = 600`、6.3 末行、9“超限”。
- **触发**：5%·W 落在 [600, 固定部分 + 末单元单行)；例如上一回合失败（状态节带 ≤400 字错误），交给窗口未知、按 32k 估的本地或未知 Provider（T=1,600）。
- **证据**：【实测】S1 最小状态下固定部分（框架、状态、结束行、账目）o200k 770、est/1×1.3 1,180，末单元单行另需约 120 / 156。【推算】prePlan 只查 hardCap ≥600，plan() 到 finalize 才 `blocked`：o200k 口径 W<17.8k，Claude/未知族 W<26.7k，带中文错误时 W<37k，覆盖 32k 默认值；此时程序已启动（1.3–5 s，R6），违反 C2 的 K8 与 §9“只有窗口 <12k”；§6.2 的属性测试命题为假。
- **修正**：【建议】MIN_PACKET 改为模板渲染的“最小交接单”（含 ≤400 字错误的状态节上界）按目标族保守估算的值，构建期生成、进 `policyVersion`、CI 断言；prePlan 据此在启动前失败并提供“只发这条消息”；属性测试的 W 按对数均匀取 4k–2M。

### VF2-02（major）框架 ≤420 token 被 v2 自己的模板否定
- **章节**：0、5.4、6.2 `FRAME_CAP`。
- **触发**：每份交接单，中文与 Claude 族更明显。
- **证据**：【实测】见第 1 节；×1.3 时中文填入后 788，增量来自约定 3–7 的改写与来源说明。CI 按 o200k 重算即不通过；只作预算常量时固定部分被低估 80–370 token，造成 VF2-01。
- **修正**：按（族、语言、kind）给上限并由 CI 渲染计数；或合并约定 4、5、7，只交目标与增量用短框架，同步 MIN_PACKET 与 U。

### VF2-03（major）脱敏与转义的逐字节目标按缺规则的原型校准，RunDigest 最坏目标随之不成立
- **章节**：0、5.2 N4/N19、6.4、10.2、11.1。
- **触发**：每个 `run.ended` 的摘要脱敏与每次渲染。
- **证据**：【事实】`spikes/relay/proto/redaction.ts:2`：未实现键名、熵规则与排除表；5a–5b 为三种形式、11 条形状规则。【实测】同一脱敏器 50–200 个秘密 2.5–5.1 ms/MiB（八种形式不更慢），加一遍熵规则 6.8–9.7（p95 至 10.3）；朴素混淆骨架 14.7 / 19.7。【推算】N19 在截断前扫原文、两侧各留 8 KiB：最坏 Run 约 0.2 MiB（按窗口）或 1.4 MiB（按整条），仅脱敏就要 1.4–2 ms 或 10–14 ms：按窗口读时最坏摘要约 2.6–3.2 ms，贴着 3 ms，按整条读时远超；§6.4 的“约 0.15 ms”不成立。
- **修正**：N19 写明扫描范围；补齐 egress 规则后按秘密数 {20, 100, 300} × 形式 × 文本类型重测再定目标；CI 断言每 Run 扫描字节数与正则遍数；骨架映射加 ASCII 快路径。

### VF2-04（major）窗口未知的推演漏掉目标固定前缀与模型名归一
- **章节**：6.2 W 的来源与 `ASSUMED_WINDOW`、9、16 S4。
- **触发**：新目标首次交接；模型名带前缀、别名或为 null（Hermes `<provider>:<model>`、OpenCode/OpenClaw `provider/model`）；厂商键 `gateway:*` 等。
- **证据**：【推算】`documented(model)` 按裸名查表会落到 128k：S4 的 V4 Pro（1M）只得 6,400，卡片仍写“标准”；`relay_windows.model` 为 NOT NULL，null 模型学不到窗口；`gateway:*` 等的假设窗口未定义。`5%·W` 不扣目标固定前缀 S_B（R6 取 8–30k），网关后的 32k 模型按 128k 估会在派发后超窗。
- **修正**：Driver 给规范化模型键与已知窗口（`codex.ts:762–764`）；`capWindow = max(0, min(0.05·W, W − S_B − 预留))`；厂商键种类到假设窗口写显式表（非 `local` 也从 32k 起）并做属性测试。

### VF2-05（major）价格悬崖判定用错了量，越线时没有提示
- **章节**：6.2 悬崖分支、7.3、12.1 T0。
- **触发**：返回接近悬崖的绑定（Haiku 5.5 100k、OpenAI 272k）发 delta、brief、resend。
- **证据**：【事实】条件用 `1.2 × TIER_CAP[tier]`，而 delta 上限是 `min(DELTA_CAP, T)`、brief 是 400。【推算】Haiku contextUsed=97.5k：降到只交目标仍越线，1.5k 增量照发，此后整次请求 5 倍价，伪代码只在 contextUsed ≥ cliff 时提示；89k 时本不越线却被降档。`S_new` 未定义。
- **修正**：plan() 之后用 est(本包)×(1+e90) + 输入 + 余量判定；越线时提示［先压缩］［只发这条消息］［照发］并按悬崖价计 π；在 [cliff−5k, cliff+2k] 做属性测试。

### VF2-06（major）CJK 下按字的上限与按 token 的预算冲突
- **章节**：5.1 用户原话、5.3、6.2 `USER_CAP`。
- **触发**：中文会话，目标为 Claude 族或未知族。
- **证据**：【推算】开场按 5.1 留 1,900 字（约 1,900–2,470 token），又被 U/3（833）截到约 640 字；一条长消息（头 3,000 + 尾 800 字）约 4,900 token，U=2,500 连一条也放不下，§5.3 的“5–8 条”出自每条 1 KB 的画像。只交目标档固定部分 1,180 + 单行约 156，原话至多约 664 token，`USER_CAP` 1,200 不可达。
- **修正**：每条上限只按 token 定，按目标族 CJK 系数折算字数；全中文夹具（每条 2,000 字、中文错误）重算“5–8 条”；只交目标档用短框架或调高 `TIER_CAP.goal`。

### VF2-07（major）冷返回只比较首个请求，违反 C7
- **章节**：7.3、12.1 T0、12.3。
- **触发**：A→B→A 返回原生上下文很长的 A。
- **证据**：【事实】C7 要求并列首个请求与之后每个请求的费用；§7.3 算了持续项，T0 只显示首个请求，并列条件也只看首个请求、只在冷时触发。【推算】第 2 节末行：首个请求差只占全程差的 24%；热时首个请求续接更便宜（$0.055 对 $0.115），全程仍贵约 5 倍。R̂ 只在窗口关闭时入库（右删失），“工具调用数 + 1”遇并行调用会高估。
- **修正**：卡片加“每个后续请求 +$x”；并列条件改用全程差、冷热都适用；R̂ 用生存估计，请求数取 Driver 报告值；表驱动单测覆盖四点 (R,k)。

### VF2-08（major）“受理→派发增量”没有可执行的基线，复用路径预算被观测吃掉
- **章节**：6.1、10.6、11.1、14.2“新增事件 ≤3”。
- **触发**：R5 运行时基准；复用保留进程返回 A。
- **证据**：【事实】零延迟假 Harness 下启动≈0，`max(0, 观测 − 启动)` 恒等于观测，并行设计测不到；基线未定义，v12 多出的整份提交（7.6 MiB 约 144 ms）会盖住接力成本。【实测】3k 文件 v2 三段观测 p95 38.2 ms（原型两条命令 19.5；两次串行 spawn 各约 8–9 ms），复用路径只剩 12 ms，渲染目标自身 15 ms；B 改过工作区后“mtime 未变则复用”基本不成立。请求内带 `relay.consent` 时多一条同意镜像，“≤3 条”被打破。
- **修正**：Δ_i 取同一快照下 `relay.attach:"auto"` 与 `"none"` 的 ABBA 成对差，断言 p95(Δ_i − max(0, obs_i − start_i)) ≤15 ms；假 Harness 启动延迟取 {0, 7 ms, 1.3 s}；rev-parse 与 `config --list` 并行、驱动名按配置 stat 缓存（省 8–17 ms），复用目标改为观测 p95 + 15 ms；事件上限写“≤3 + 同意镜像”。

### VF2-09（major）缓存目标在现有用量口径下测不出
- **章节**：11.1“缓存”、13.3 P10、7.3 realized、20 Q12。
- **触发**：P10 探针；`realized.cacheHits` 统计。
- **证据**：【事实】`NativeUsage` 只有回合级 turn、context、cost（`control.ts:70–74`）；ACP 取 `session/prompt` 的回合用量（`acp.ts:538–542`），回合外 `usage_update` 被丢（`acp.ts:635`）；Codex 只用 `last.totalTokens`（`codex.ts:756–764`）；OpenClaw 逐条相加（`openclaw.ts:138–167`）。逐请求用量不在契约与切片里；DeepSeek（dsh、Hermes 默认）无写入计量。厂商参考：写入只计最高命中点后的增量，回合级差值含后续工具结果，不等于 T。
- **修正**：契约加有界 `NativeUsage.requests?` 并定所有者切片；P10 改为两轮单请求、禁用工具、固定长度回复，有工具即作废；DeepSeek 用 cache miss；不上报记“未上报”，不算通过。

### VF2-10（major）首回合时延回归会系统性地测成“没有影响”
- **章节**：11.1“首回合附加时延”、6.2 `prefill`、20 Q13。
- **触发**：按 v2 设计在 Haiku 5.5 与 dsh 上跑。
- **证据**：【事实】工作区内缓存跨会话共享、DeepSeek 自动前缀缓存（R6 §2.2）：同档同文的会话从第 2 个起 T 走缓存，斜率趋 0。“首个任意事件”含非模型事件（OpenClaw 先发 diagnostic，`openclaw.ts:424–426`）；两个时间戳都在提交函数里读（`runtime.ts:1415`、`:1175`）。Haiku 5.5、V4 Flash 非默认目标，Claude 各代分词器不同（Opus 4.7 起约 1–1.35 倍，Haiku 5.5 约多 30%，厂商参考），不能外推；未测族 P̂=8k，本地模型的时延降档永不触发。
- **修正**：每会话首段加随机 nonce，断言缓存读只到 S_B；终点取首个 text/thinking/tool 事件的单调时间；三个默认目标族各 ≥10 会话/档；Theil–Sen 加 bootstrap，记高峰/闲时；本地 P̂ 取保守值。

### VF2-11（major）est/2 校准进不了 CI，“anthropic 族”也不是一个分词器
- **章节**：6.2 est/2、13.1、11.1。
- **触发**：RelayBench-X 的 est/2 门槛（p90 ≤20%，三个族）。
- **证据**：【事实】厂商参考：`count_tokens` 是带凭据的 API，计数随模型变；“离线脚本”与 13.1“进 CI，$0”冲突。RT3 的 17% 只是 o200k 样本内；Claude、DeepSeek 无实测；样例仍是 est/1。预算看整包误差，RT3 测得交接单形态只差 1–7%，按段 p90 与决策无关。
- **修正**：一次性生成按模型 ID 的冻结计数夹具（记日期与分词器代次），CI 只对夹具算误差，定期作业刷新、漂移即升 `policyVersion`；族键按分词器代次；门槛改为整包误差与近 hardCap 的上偏概率。

### VF2-12（major）送达率与重复注入没有可行的验收样本
- **章节**：11.1“unknown 与重复注入”“丢失增量”、13.3 P13。
- **触发**：用每家约 20 回合的 RelayConformance 验收。
- **证据**：【推算】0/20 的单侧 95% 上界约 14%；证明 ≤2% 至少 149 次全无失败，≤1/100 至少 299 次（每家约 $4–30）。P13 的“主题与对照一致”要语义判断，与“确定性”矛盾。
- **修正**：确定性的假 Harness 故障注入矩阵（各证据序列下重复 0、丢增量 0）进 CI；真机比例作上线监控，用 Wilson 上界并写最小样本量；P13 改为标题含预置关键词之一且不含禁用串。

### VF2-13（major）RelayBench 预注册假设没有统计效力
- **章节**：13.2 H1、H7、采纳规则。
- **触发**：v0 每个接收方 72 个配对实例；注入类陷阱约 2–3 道。
- **证据**：【推算】按 20% 不一致率，n=72 时差值标准误约 5.3 pp，单侧下界约 d̂ − 8.7 pp，V3 要比 V5b 高 5.7 pp 以上才算非劣（界值 −3 pp）；d=0、80% 功效约需 1,375 个配对（10% 不一致率约 690）；同题两个交接点不独立。H7 每个接收方约 4–6 个注入实例，0 次服从的单侧上界 39–53%。
- **修正**：预注册写功效分析；加样本或把界值放宽到样本支持的范围，按题聚类算标准误、用序贯设计；H7 改为渲染器确定性用例加 ≥100 个注入实例的专门集合。

### VF2-14（minor）快照增量目标测的是第一版形状
- **章节**：0“存储”、4、11.1。
- **触发**：v2 的 pending 绑定；带附言、排除或放行的消息。
- **证据**：【推算，v2 字段名的紧凑 JSON】pending{prior=synced} 加 range、consentKey、cache 为 571 B（`openai`）到 712 B（长网关主机名），prior 为 suspect 时 618–759 B；RT3 的 476 B 是第一版形状。每 Run 的 relay、contextReadyAt、input 为 282 B，但 `PublicRun.relayRequest` 进快照，带附言时约 4.9 KB/Run。
- **修正**：prior、chain、lastPacketId 移到 relay 表；consentKey 限长或存 ID；附言、放行、排除存 relay 表，快照只留指纹；用最长合法值断言。

### VF2-15（minor）观测、索引列与冷路径的依据与设计不符
- **章节**：10.6、11.1、14.1 `index_json`、6.4。
- **触发**：加固后的观测；读索引；v13 迁移后首次交接。
- **证据**：【实测】2 万文件 v2 流水线 68.3 / 75.4 ms（原型 49.7 / 55.1），只测小文件、热缓存。索引按 v2 形状 1,485 B，CHECK 为 2,048 B，`line.userHead` 经 N2 可见化后每字可到 12–13 B，索引无收紧次序，越界会让派生行反复失败、该 Run 长期 behind。G3 级补建不读详情，算不出 verbatim 尺寸，整份直送会误判；“派发最多等 1 s”不在派发目标里。
- **修正**：观测基准加大文件与冷页缓存；索引字段给字节预算与收紧次序；G3 级补建把 verbatim 尺寸标为未知，冷路径等待计入派发目标。

### VF2-16（minor）统计口径与 CI 设定让毫秒目标不可估或不稳定
- **章节**：11.1、13.1、7.3 warm、11.2。
- **触发**：p95/p99 门槛进 CI；E1 时延；判“热”。
- **证据**：【事实】原型最坏剖面 n=100、病态 n=30（`raw.digest`），p99 不可估；额外堆未测；p95 跑间波动约 ±0.2 ms，是 2 ms 目标的 10%；本项目在本机开发，CI 机器不同。E1 的 `recordedAt − dispatchedAt` 含派发提交（`runtime.ts:1415`）。厂商参考：缓存寿命从请求开始计，§7.3 用 `lastRequestEndedAt` 会把长生成后已过期的缓存判成热。
- **修正**：p99 至少 1,000 样本并报 bootstrap 区间；堆用 `--expose-gc` 后的 heapUsed 增量，另用 `--max-old-space-size` 子进程复核；CI 只断言计数类量，毫秒目标在参考机上跑并记机器指纹；E1 用 Driver 在 `startText` 前的单调时间戳；“热”用最后一个请求开始时刻的代理。
