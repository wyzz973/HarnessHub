# J2 · 性能与成本评审（第二轮）

评审：J2（性能与成本），2026-11-03，基线 `cc/relay-design`（07a0825）。只读评审，没有改代码、没有运行任何 Harness。自算数字来自 scratchpad 里两个小脚本（按各方案的估算公式统计 S1 样例；按 R6 公式算费用），不入库。

标注：【事实】有代码或报告出处；【实测】第一轮（R4、R6）或方案作者的本机测量；【文档常量】厂商文档或代码常量；【推算】由前两者按公式得出；【建议】本评审的主张。

## 0 核算口径

**费用公式**【推算】：取 R6 §2.7 的公式 1，并入公式 3 的冷重写项。一份 T token 的交接单进入目标转录后，生命期费用为 C = T·[p_w·(1+k) + p_r·(R−1−k)]。
- R 是此后重读它的请求数；
- k 是期间空闲超过 TTL、整段前缀按写入价重写的次数。

R6 与四个方案都只取了 R=80、k=0 这一个点。价格用 R6 §2.1（2026-11-02 核实，$/M）。

【推断】k 和 R 都不小：Hermes 源码注释里的单机记录显示 63% 的缓存写入发生在 5–60 分钟的空闲之后（R6 §2.4）；工具密集的回合每回合有十几到几十次请求，而 Claude 的 1M 窗口里交接单可能几百次请求都不被压缩掉。所以四个方案写的“每次 ≤$0.20 / ≤$0.34”只是 R=80、k=0 的一个点，对 API key（5m TTL）用户实际可能是它的 2–6 倍。

**Hub 自身开销**【实测，R6 §2.6】：整份快照提交约 19 ms/MiB（7.6 MiB 时约 144 ms）；全新启动的回合派发前有 6 次提交（runtime.ts:1332、1341、1369、1384、1389、1415）；7.5 MiB 时受理到派发需 1.25–1.41 s，S4 的 6 MiB 插值约 1.0 s【推算】。存储层没有“只追加事件”的小事务：transact 每次都整份重写快照，读快照时还核对事件条数等于 lastSeq（sqlite-store.ts:343–360、156–157）。

**构建单项**【实测】：全量 buildPublicContext 857 KB 用 1.84 ms（R4 M2）；读 2,000 条账本 2 ms；读并校验 500 条工具详情 15.3 ms；sha256 128 KiB 0.05 ms；git status 加 numstat（3k 文件）15–19 ms；精确树哈希 270 ms；独立表追加 0.06 ms（p95 0.75 ms）（R6 §2.6.5）；内容存储写入 8.2 ms/条（R4 §2.4.2）。

**用量口径**【事实】：`NativeUsage.turn` 是回合级聚合（control.ts:70–71）。ACP 四家取 `session/prompt` 结果里的 usage（acp.ts:538–543）；Codex 驱动把 `thread/tokenUsage/updated` 的累计值减去本回合基线（codex.ts:755–765），逐请求的 `last` 只用来算 context.used；OpenClaw 把转录里的逐条调用相加（openclaw.ts:138–163）。因此在 Claude、OpenCode、dsh、Hermes 上，“交接后第 2 次请求起的命中率”和“首个请求的 input 增量”都观测不到。

## 2 致命缺陷

- **P1：无。** 有两处若照原文实现会出大问题，已列入 M3 与 M5：派生写入的上限在存储层触发时，run.ended 会失败、Runtime 会 fatal；每轮的工作区观测进入了回合结束的关键路径。
- **P2：无。**
- **P4：无。**
- **P3：F1，Hermes 的接力 MCP 进程没有 Hub 所有者，违反 INV-26。**
  - 证据：P3 §5 Hermes 一行写明 shim“归网关所有”，在 stdin 关闭、父进程变化、空闲 15 分钟或目录被删时自行退出；§17 第 3 条承认它“不在 Hub 的监督范围内”。INV-26 要求所有进程有所有者、上限和可等待的关闭入口（docs/domain/invariants.md:32），简报第 4 节列为硬约束；R5 风险一节也指出 Hub 无法等待网关持有的 MCP 进程关闭。
  - 叠加问题：Hub 一侧的 shim 只写了“并发 ≤4”的目标，没有准入机制；挂载在建会话时发生、INV-29 禁止中途移除，而现有上限允许 4 个活动回合（contracts/session.ts:315）加 4 个保留进程（runtime.ts:65），即 8 个约 55 MB 的进程。
  - 补救：网关持有的 MCP 客户端一律不挂 shim，只走文件；Hub 持有的 shim 计入全局上限，超限时降为推送。

## 3 最佳想法（值得嫁接进终稿）

1. **P4 §2、§4“增量算法”：RunDigest 带累计前缀和。** 各节从新往旧扫描、填满即停，未放入的条数由前缀和得出，成本 O(预算 + 节数)，与历史长度无关；四家里只有它在结构上保证 256 轮、8 MiB 时构建仍是常数级。
2. **P4 §4、§6：prePlan 加 finalize。** 启动前用保守窗口预算，不够就不启动；open 之后精化窗口并做 E2 核对。既不浪费 1.3–5 s 的启动，又保留 Hermes 回放核对的零成本。
3. **P4 §4“预算分配”：capCost = $X/π 与 capCliff。** 费用与价格悬崖直接进入选档。嫁接时改两处：只许降档、不许升档；π 用实测的 R̂、k̂（M8、M9）。
4. **P4 §13：relay_bodies 以 sha256 为主键，`INSERT OR IGNORE`，同 ID 不同 sha256 即 INVALID_DATA。** 重发去重与渲染确定性的在线检测，零额外成本。
5. **P4 §13 的 INV-30：每个原生纪元至多一份完整交接单**（not_recorded、unknown、diverged 除外），之后只追加增量。重复注入在契约层被堵住，生命期成本有上界。
6. **P4 §7：RelayConformance 的 P3–P8（丢增量 = 0）与 P10（交接后缓存读占比）。** 每家约 $0.5–2，是把性能与正确性目标变成可回归证据的最便宜办法。
7. **P4 §4“构建与维护”：选择器打开时预渲染进 LRU**（全局 ≤32 项、≤8 MiB，单会话 ≤8 项，指纹变即失效），派发时指纹未变就复用字节，只在被 Run 使用时入库。
8. **P2 §2、§4.2–4.3：RunFacts 按 G1/G2/G3 记 ascii/cjk/other 尺寸。** 折叠只读 O(R) 个小索引行即可确定性地两遍定档；G1 片段在回合结束时生成，交接时不读工具详情。
9. **P2 §10、§7 判定 1–2 与 §13 relay_windows。** “第 2 回合起 cachedInput 占比”是唯一可测的缓存指标写法；“费用比 ≤1.6”把成本放进了质量决策；按 Harness、入口、模型缓存观测窗口（30 天），让“窗口未知”只出现在首次接触时。
10. **P1 §5 OpenCode 一行：代价高的 E2 核对只在结果未知且待重发 >4k 时做。** 只在核对比重发便宜时付时延，可推广到所有 `verify: costly` 的驱动。
11. **P1 §6.1、§6.3：增量按来源排除本绑定自己的条目。** S2 返回只需约 330 token，是 A→B→A 最省的增量，可作为增量默认上限 1.5k 的参照。
12. **P3 §5 与 INV-29：工具清单只在建会话时确定、规格字节冻结；P3 §10 的推拉打平公式 q·π + n·c_req < 少推的 token × π。** 前者是任何拉取设计保护前缀缓存的前提，后者应写进拉取通道的准入标准（C6）。

## 4 终稿必须包含（可验证表述）

- **M1 前置修复回归。** 合成的 8 MiB / 256 Run 会话上，同一 Harness 续接、切换校验（runtime.ts:1570）与 blocked 后的恢复切换都不报 CONTEXT_TOO_LARGE；R6 的 66 回合长回复画像作为固定用例。
- **M2 提交预算。** 交接回合与同条件的普通回合相比：派发前的整份快照提交 +0（交接单行与送达记录并入 run.context_prepared）；首个可见输出前的提交 +0（E1 证据先留在内存，并入 run.first_output，它在 runtime.ts:1175 本来就是独立事务，ADR-047 第 5 条允许与首次冲刷合并；或并入本回合下一次既有提交，没有输出时并入 run.ended）；每次交接新增事件 ≤3 条，普通回合 0 条。由运行时基准逐回合断言提交次数与事件计数。
- **M3 派生写入不得拖垮事实。** 同事务的派生行（账本、RunFacts、RunDigest）在 mutate 之前先在内存里按全部上限截断并校验；派生写失败只把派生状态记为 behind、另行补建，绝不让 run.ended 失败。现状下 run.ended 提交失败会进入 fail()（runtime.ts:1507），整个 Runtime fatal 并停止所有对话（runtime.ts:804–816）。用故障注入测试证明。
- **M4 普通回合近乎零成本。** 每个 Run 的派生记录在 run.ended 事务内 p95 ≤2 ms CPU、≤64 KiB；抽取输入事先限定字节（回复 ≤1 MiB、差异 ≤256 KiB、秘密扫描 ≤2 MiB），不靠事后的 20 ms 计时截断；工作区观测不进 run.ended 的关键路径。
- **M5 观测预算。** 派发路径上至多 1 次工作区观测，只在交接回合（及返回 A 的同步核对）做；与启动并行，硬上限 250 ms，到时 SIGKILL 并等待退出；全局并发 ≤ MAX_PARALLEL_CONVERSATIONS（4）；非 git 扫描 ≤2 万项、≤200 ms，内容哈希 ≤64 个文件且合计 ≤32 MiB；超限记“未核验”，不阻塞派发。
- **M6 构建目标与计量点。** Hub CPU（不含观测与 E2）p50 ≤5 ms、p95 ≤25 ms（合成 256 Run、8 MiB），派发路径 Hub CPU 增量 ≤10 ms。buildMs、observeMs、verifyMs 用单调时钟在进程内测，写进 run.context_prepared；不用提交时间戳相减，8 MiB 时单次提交本身就约 144 ms。
- **M7 冷路径。** v13 迁移后或索引缺失的会话，首次交接前的补建（≤256 Run）p95 ≤1 s，切成 ≤20 ms 的片、不走整份快照提交，在打开选择器或空闲时触发；派发最多等 1 s，之后以显式省略账目发出，不报错。
- **M8 预算与档位**（数字见 C2）。默认档 T ≤ min(8k, 5%W, 悬崖余量, 1.5 s × P̂, $0.20/π(R̂, k̂))；费用与时延上限只能降档，升到完整档只能由用户选择或由 RelayBench 对该接收方族的显著结果决定；整段叙述化历史放得进所选上限时整份直送。
- **M9 费用模型与数据。** 代码与界面都按 C = T·[p_w(1+k) + p_r(R−1−k)] 估算，价格表集中、带日期。R̂、k̂ 取自 HH 自己的统计（只计数）：R̂ 用“每回合工具调用数 + 1”作上界代理，Codex 与 OpenClaw 用逐请求用量精确计数；k̂ 按同一绑定相邻回合的间隔与 TTL 类别算。TTL 类别按观测到的模型族与登录方式定，不按 Harness 定。
- **M10 缓存指标按回合定义。** 交接后第 2 个及以后、且与上一回合间隔小于 TTL 的回合，cachedInput/(input + cachedInput + cacheWrite) ≥0.85（只统计上报的驱动）；冷回合单独计数并报告写入 token；驱动暴露 Codex 的 `last` 与 OpenClaw 的逐条用量，供逐请求核对。
- **M11 token 估算。** 只保留一个估算器，离线用各家分词器在交接单语料（中文、英文、代码三种配比）上校准，p90 误差 ≤20%；有逐请求用量的 Codex、OpenClaw 再在线核对。
- **M12 首回合时延。** 用配对基准测：同一目标、同一任务、新会话，带与不带交接单各跑一次，差值即接力造成的时延；不与“同 Harness 中位数”比，后者混入原生续接的热缓存与固定前缀预填充；同时输出各模型族的 P̂。标准档 p50 ≤ +1.5 s。
- **M13 存储与内存上限。** 快照增量每个绑定 ≤300 B、每个 Run ≤150 B，删除全量 sourceRunIds；派生表每会话有总量上限（交接单正文 ≤16 MiB，每 Run 摘要 ≤64 KiB）；派发路径上不写内容存储；单次构建额外堆 ≤16 MiB，预取 LRU 全局 ≤8 MiB；v1 不引入每会话常驻的辅助进程。
- **M14 M2 列为前置切片。** 去掉 commit 前的重复 load、按 version 缓存已校验快照、跳过未变的终态 Run 校验、事件字节改用计数列；目标是 8 MiB 时受理→派发 p95 ≤400 ms（R6 推算）。M2 落地前只承诺增量目标。
- **M15 返回 A 的估算。** 同时给出首个请求的费用与此后每次请求的携带成本 (N_A + Δ − S_A − T)·p_r；缓存已冷且（费用差 ≥$0.10 或时延差 ≥10 s），或 N/W ≥0.85 时，并列两种做法；从不自动切换。

## 6 方案对现状的误读

1. **P4 §13 把 relay.input_recorded 称为“独立小事务”。** 现有存储每个事务都整份重写快照，读取时还核对事件条数等于 lastSeq（sqlite-store.ts:343–360、156–157），没有只写事件的小事务；8 MiB 时这是一次约 144 ms 的提交（R6 §2.6.3）。P1（relay.delivered 在 E1 到达时提交）与 P2（“每次交接 1 次”）也多出这一次。正确做法见 M2。
2. **P3 §10 写“提交次数不增加”，§7、§11 又写“拿到 E1 才画分隔线”。** SSE 只发布已提交事实（INV-06，ADR-047 第 9 条），而 P3 只在 run.ended 时提交送达结论：要么多一次提交，要么分隔线推迟到回合结束。
3. **P2 §3.3 称固定前言“首条消息的前约 400 token 完全相同，可以跨会话命中前缀缓存”。** Anthropic 只在内容块边界命中、每个断点向前至多 20 个位置（R6 §2.2），前言与变化的正文在同一个 text 块里，形不成命中边界；OpenAI 要求前缀 ≥1,024 token、按 128 token 递增，DeepSeek 按 64 token 单元，即使命中也只省 400 × (p_in − p_r)，GPT-6.1 Sol 上约 $0.0008/次。不能作为设计理由。
4. **缓存与 token 的测量点不可观测。** P1、P3、P4 §10 的“交接后第 2 次请求起 ≥85%”“TTL 内返回的首个请求”，以及 P1、P2、P4 的“实际值取首个请求 usage 的增量”：HH 的用量是回合级聚合（control.ts:70–71；acp.ts:538–543；codex.ts:755–765；openclaw.ts:138–163），ACP 四家看不到逐请求数据。只有 P2 的“第 2 回合起”可测。
5. **P4 §4“dsh 与 Hermes（默认 DeepSeek）自动用满档 32k（约 $0.026）”。** $0.026 是 V4 Flash 的价；Hermes 本机默认是 deepseek-v4-pro（native-capability-matrix.md:293），32k 每次约 $0.153。表中 Hermes 的 5m TTL 也只适用于 Anthropic 式缓存标记的提供方，DeepSeek 是自动磁盘缓存（R6 §2.2）；TTL 类别应按模型族定。
6. **P4 §3 与 §11 自相矛盾。** S1 写“约 2.1k tokens”，选择器与交接卡示例却写“约 6.8k tokens · 约 $0.07”；按 P4 自己的估算器，S1 正文约 1.41k（第 0 节）。
7. **P1 §3.2“整份约 2.0k token（按 openai 系数估算）”。** 按 P1 自己的 bytes_family_v1（openai a=4.0、c=0.85）约 1.54k；2.0k 对应的是 anthropic 系数（约 2.13k）。偏保守、无害，但估算器没在自己的样例上跑过。
8. **P1 §10 每轮折叠 p95 ≤5 ms、p99 ≤40 ms 的依据是“追加实测 0.06/0.75 ms”。** 那只是往独立表插入一条约 1 KiB 的条目（R6 §2.6.5），不含差异解析、词表扫描与秘密扫描（P3 实测脱敏约 10 ms/MiB）；单轮输入上限约 9 MiB。
9. **P1 §6.3 把“DeepSeek 2 h”标为【文档常量，R6】。** R6 §2.2 引用的文档写的是“通常几小时到几天内清除、尽力而为”，没有 2 h 常量；应标为假设。
10. **P3 §10 的费用（lean ≈ $0.034）没有计入 4 个 MCP 工具定义的 token。** R6 §4.1 第 4 条：工具定义约 0.5–2k token、随每次请求重读，而它们从接手会话建立起就在前缀里；按 0.6–1.2k、会话总请求 300 次算，Opus 上每次交接另加约 $0.04–0.08。

## 7 遗留风险与需要真机核实的点

1. **R̂、k̂ 的真实分布**（交接后到压缩或会话结束的请求数；回合间空闲与 TTL）决定费用上限是否合理，需从 HH 的 RunTiming 与工具计数统计，不读内容。
2. **当前模型的预填充吞吐 P 没测过**（R6 §6.1）：在 dsh（flash，闲时）与 Haiku 5.5 上用 T ∈ {0, 2k, 8k, 16k} 的配对新会话测 TTFT 斜率，约 $1，结果决定 M8 的时延上限。
3. **ACP 驱动是否上报 cachedReadTokens/cachedWriteTokens**（R6 §6.2）：不上报的驱动上 M10 只能写“未上报”。
4. **E1 的实际到达时刻**（Codex userMessage、Claude 原始回显）与首个可见输出的间隔，决定 E1 并入 run.first_output 后分隔线是否明显滞后。
5. **大仓库观测成本**：2 万到 10 万文件时 git status（关闭 fsmonitor、GIT_OPTIONAL_LOCKS=0）与非 git lstat 扫描在 APFS 上的 p95；R6 只测了 3k 文件。
6. **v13 迁移耗时**：P1 要给 events 加生成列和索引，P2–P4 要重放事件推断水位，P4 还要建 7 张表；需在合成大库（如 1 GiB 事件）上实测，迁移期间服务不可用。
7. **8 MiB 下事件循环饱和**（R6 §5.8）：没有 M2，S4 规模下 Hub 自身派发约 1 s，接力只占 2–5%；M2 若推迟，S4 验收只能报告增量目标。
8. **价格与估算偏差**：价格会漂移，订阅用户的缓存读折算未知（R6 §6.4），美元估算对他们只是相对量；Claude 4.7 起分词器多约 30%（R6 §2.1），估算偏差可能让档位越过 Haiku 5.5 的 100k 或 OpenAI 的 272K 悬崖。
9. **P1 的“回合外改动通知”**（≤300 token）若用户每轮都在编辑器里改文件，会退化为逐轮追加：50 回合、每回合 8 次请求，Opus 上累计约 $0.61（R6 §2.7 公式 6）；需要频率上限。
10. **若保留拉取**：AgentBaton 的证据来自同一脚手架（R9）；Claude 的工具搜索可能延迟加载接力工具（P3 §17）；每次拉取 1–3 s 与思考 token 的开销都未实测。
11. **P1 的账本上限**（8,192 条、4 MiB）在工具密集会话里可达：每 Run 最多约 60 条，256 轮约 1.5 万条；到达上限的行为必须定义，否则账本 failed 后交接无法准备。
12. **P3 的记录搜索 API 在 Hub 进程内线性扫描**：13.4 MiB 时 p95 41.6 ms（实测），64 MiB 约 0.2 s（推算），会阻塞事件循环。
