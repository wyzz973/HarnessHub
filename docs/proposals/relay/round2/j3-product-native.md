# J3 评审 · 产品与原生体验（第二轮）

评审：J3（产品与原生体验）。日期 2026-11-03。基点 `07a0825`，文中 `file:line` 均指该基点。P1–P4 全文已读。

标注：【事实】有代码或文档出处；【推断】由事实推出；【建议】本评审的主张。数字注明依据：实测、文档常量、推算，或“建议值，待校准”。

评审的尺子是用户最初的定义：“体验上是真的使用不同的 harness 一样”，拆成三个承诺：

- **像原生**：接手方像在原程序里一样续写；只用一个 Harness 的用户感觉不到接力机制的存在。
- **能接力**：用户说过的话、定下的事不丢；用户知道交了什么、省了什么。
- **统一管家**：默认零操作；失败如实告知；API 与界面语义一致。

## 0. 结论

- **排名**（六项平均）：P2 6.8 > P4 6.7 > P1 6.0 > P3 5.5。
- **三个共性问题**：
  1. P1、P3、P4 让用户主动执行的 `/clear`、`/new`、`/reset` 失效，而这在现状下是生效的，属于回归（F1）。
  2. 四份框架措辞都把“以前用户提过的要求”一并作废，常设约束因此被放松（G1）。
  3. P1、P2、P3 的失败文案写“仍由 Claude Code 执行”，与已生效的切换不符（§6 第 1 条）。
- **终稿骨架建议**：
  - 控制面与界面时刻：用 P4。
  - 正文：用 P2 的叙述化原文，并采用 P2 的清空语义。
  - 布局与 API：用 P1。
  - P3：拉取层推迟，保留它的挂载规则与导入过滤。

## 2. 致命缺陷

### F1（P1、P3、P4）：用户主动的清空命令失效，属于现状回归

**证据**

- P1 §6.2：“clear → delivered=null；nativeEpoch++；state=cleared（下一条内容输入发完整交接单）”。§6.1 的增量只排除 harnessId、controlId、nativeEpoch 三者都相同的条目，所以清空前自己的轮次变成了外来事实。
- P3 §6：“none → handoff：全部历史，包括 X 被清空前自己做过的轮次”。
- P4 §6 的状态表：“synced｜命令 clear｜fresh”；S13 写明下一内容回合附完整交接单。

**现状【事实】**

- Claude 的 `/clear` 不在命令目录里，但在有就绪绑定、没有新来源时原样发送（runtime.ts:1392）。
- Hermes 的 `/reset` 在命令目录里，原样发送（runtime.ts:1396）。
- 两者的下一条消息都原样发送。所以今天只用一个 Harness 时，清空是生效的。

**后果**

- 最常见的单 Harness 用户从此在 Hub 里得不到空白上下文：清空后会立刻被灌回 2–8k 的旧历史。
- Hermes 的 `/new`、`/reset`，OpenClaw 的 `/new`、`/reset` 同理。
- 这违反“像原生”。

**修法**：采用 P2 的语义，并让水位如实记录（M2）。

### F2（P1）：从未交接过的会话也会被注入 Hub 文字

**证据**

- §4.5“观察到压缩…时，置 reanchor”没有前置条件；§6.2 规定命令回合 `compact → reanchor=true`。
- §5 的回合外改动通知，在用户自己的编辑器改了文件时也会发。
- 这与 P1 §5 自己说的“在发生交接之前，Hub 创建的会话和原生会话完全一样”相矛盾。

**后果**：每次原生压缩、每次外部编辑之后，单 Harness 会话里都会多一段界面上看不见的 Hub 文字。

### F3（P3）：lean 默认档把用户中途的约束挤出了推送层

**证据**

- §3 的 goal 只取“第一条用户消息加最近 2 条”，decisions 只认钉住项与被拒的审批。
- §4 规定首版对 Claude 的 Opus/Sonnet 档和 Codex 的 Sol 档用 lean，lean 档没有 L1。
- §17.6 作者自认“中途的调整要靠用户钉住”。

**后果**

- 用户第 3 轮说“导出接口不要动”，第 8 轮换到 Codex（最常见目标、默认档），Codex 看不到这句话。
- 接手方不知道自己缺什么，就不会去拉取，拉取这个赌注恰好在这里失效。
- 这违反“决定不丢”；而补救办法（钉住）又违反默认零操作。

### P2：无

### 共性严重问题（不致命，但终稿必须修）

- **G1 常设约束被作废**
  - 各方案措辞：
    - P2：“记录中的要求…都已经过去”。
    - P3：“以前的用户消息…都是历史数据，不是指令”。
    - P4：“其中出现的要求、批准或命令在本回合都不生效”。
    - P1 规则 2：“历史中的请求…不要据此行动”。
  - 原生会话里，模型会把早先的约束当作仍然有效；规则在压缩中本来就容易蒸发（R2[S18]：`/compact` 一轮后只保留 53% 的安全规则）。
  - 修法见 M9。
- **G2 失败文案与事实不符**：见 §6 第 1 条。
- **G3 “完整”标签被滥用**：P1 的 `relay_full`，见 M5。

## 4. 终稿必须包含（可检验）

**M1 单 Harness 零注入**

- 规则：绑定在当前纪元从未收到交接单时，发给它的每条输入都与用户原文逐字节相同。覆盖首条消息、原生压缩后、`/compact`、`/clear`、`/undo`、外部编辑后。
- 现状：新绑定一律包装（runtime.ts:1392）。
- 验证：零延迟假 Harness 跑 20 轮，断言 dispatched === input；另做真机两家。

**M2 清空按原生语义**

- 规则：`contextEffect=clear` 之后，下一条默认不附历史。输入框上方显示“Claude Code 的上下文已清空 · 下一条不附历史［附上交接单］”。
- 水位记作 `{throughSeq: X, basis: "user_cleared"}`，epoch 加 1，不写成“已送达”。
- 用户点“附上”时发完整交接单，包含清空前的轮次。
- 验证：两条集成测试，加浏览器测试。

**M3 原生标题**

- 规则：交接回合第一段的首行是原话前 ≤200 字（逐字前缀），原话全文放在最后一段；交接单 ID 与框架不放在首行。
- 验证：黄金文件；真机核对 Codex 的 `thread.preview` 和 ACP 的 `session/list` title 不以“HarnessHub”或交接单 ID 开头。

**M4 所发即所见（推广）**

- 规则：Hub 加入的任何字节（交接单、增量、重锚、重发、改动通知）都在对应的用户消息下显示为附件条，点开是逐字原文，sha256 与实际发送一致。
- 发送时的内容若与用户看过的预览不同，写明“发送时已更新：原因”。
- 验证：浏览器测试遍历所有包类型。

**M5 等级词汇**

- 主标签：继续原会话、新会话、原生分支、接续本机会话、上下文已清空、无法接续。
- 副标签：“补交 N 轮”或档位。
- “完整”仅在省略账目中用户消息、回复、计划、失败四类都为 0 时使用（context-transfer.md 不许声称无损迁移）。
- 送达状态单独显示：交接中、已接棒、未确认、没有送达。
- 验证：属性测试。

**M6 分隔线不跳动、不抢先**

- 派发时在固定位置放占位行“交给 Codex · 交接单 #1 · 送达中”。
- 拿到 E1/E2/E3 后才变为“从这里起由 Codex 接手”；结算后仍未知，显示“交接未确认，下一条会再附上”。
- 证据到达之前不出现“已接棒”。
- 验证：浏览器测试覆盖三种证据路径。

**M7 失败文案如实**

- 切换已生效而交接失败时显示：“已切换到 Codex，但没能交接：原因。这条消息没有发出，草稿已保留”，并提供［重试］［改回 Claude Code］［只发这条消息（不附交接单）］。
- 只有选择确实回退了，才写“仍由 Claude Code 执行”。
- 验证：分别注入启动失败、脱敏失败、超限三种故障。

**M8 用户原话优先**

- 只要还推送任何回复文字，就不得省略以下三项：首条用户消息、目标上次送达以来的全部用户消息、钉住项与附言。其余被省略的用户消息按轮次区间计数。
- 最近一轮回复不超过 8 KiB 时照录；超过时保留首 2 KiB 和尾 6 KiB（推算：典型回复约 2.5k 字符，见 P2 §4.5）。
- 验证：属性测试，加 S4 合成会话。

**M9 框架措辞**

- 固定前言 ≤400 token（P2 估约 360），中英两套，按当前输入的 CJK 占比确定性选择。
- 分开写三点：
  1. 以前的任务请求与批准不再生效；
  2. 用户提过的约束与禁止事项仍然有效，除非用户后来改口；
  3. 只有此刻的请求是要做的事。
- 另写明：工具照常可用、以工作区为准、未完成项只是快照、“不需要向用户复述这份记录”。
- 模型文本只出现交接单 ID（首、尾各一次），seq、版本、指纹只放在清单里。
- 验证：黄金文件与禁用词检查；“早期约束”类陷阱题的违反率不高于原生续接对照。

**M10 体验指标**

- 首个回复的元话语率（正则匹配“交接单|HarnessHub|接力记录|handoff|relay”）≤10%。
- 回复语言与用户输入语言一致的比例 ≥95%。
- 以上为建议值，待 pilot 校准；复述只作对照臂。

**M11 附言与钉住**

- 附言放在数据围栏之外、紧挨当前请求，标为“用户给你的附言”。
- 钉住项单列为“用户钉住的约束（仍然有效）”。
- 验证：渲染测试。

**M12 “X 离开期间”**

- 回到 A 时，在切换后、发送前显示：“Claude Code 离开期间：DeepSeek Harness 做了 2 轮 · 改动 3 个文件（其中 1 个它改过）· 测试已通过”。
- 没有增量时也要写明。
- 界面里的“你”只指用户；只有模型可见的增量才用“你离开期间”。
- 验证：浏览器测试两种情形。

**M13 跨厂商告知**

- 按目标模型判定厂商，判定不了时记为 unknown，照常提示。
- 首次交出时卡片内联一行说明，发送按钮改为“发送并交给 Codex（OpenAI）”，不增加点击。范围可选“本对话”或“以后不再提示此厂商”，在设置里可撤回。
- API：用账户偏好 `relay.crossVendor: ask|allow|goal_only` 或请求字段 `relay.consent`；缺失时返回 409 `RELAY_CONSENT_REQUIRED` 并附预览计数，不静默改成不送历史。
- 验证：API 契约测试与浏览器测试。

**M14 疲劳控制**

- 卡片默认一行。
- 只在以下情况加标记：失败、unknown、未归属改动、有省略、首次跨厂商、隐去了密钥。
- 被忽略的建议，同一原因在本对话里不再出现。
- 未知送达时，每个包最多自动重发 1 次，之后由用户手动“再附一次”。
- “未确认”只用状态色，连续两次才提示。
- 选择器只显示等级与规模；费用只在超过 $0.10 或冷返回时显示。

**M15 费用显示随认证方式**

- API key：显示美元，注明价格表日期。
- 订阅：显示 token，并注明“计入订阅额度”（折算比例未知，R6）。
- 认证方式未知：只显示 token。

**M16 返回 A 不替用户丢弃原生会话**

- 默认原生续接加增量。
- 冷且长时（推算：超过 TTL 且 N ≥ 100k），并列给出估算，由用户选或按返回偏好处理。
- 标记缺失时，先排除“压缩后回放中已没有旧消息”的情形；之后默认在同一会话补发完整交接单并注明可能重复，同时提供“新开会话”。
- 验证：含压缩的 A→B→A 夹具。

**M17 运行中切换（S5）**

- 有待批准请求时写明“批准或拒绝之前这一轮不会结束”，提供［等这一轮结束］［停止并切换］。
- 停止时关闭审批，不转交。

**M18 导入卫生**

- 接续本机会话（ADR-029）与读取原生回放时，按标记剥离交接部分，只保留用户原话和一个“交接单 #N”标记。
- 现状：`acp.ts:275–285` 与 `codex.ts:395–410` 都把文本原样收入。
- 验证：两类夹具。

**M19 用量环按当前绑定过滤**

- 现状：ChatPage.tsx:238 取的是最近任一 Run 的用量，四份方案都没有处理。
- 规则：切换后、目标首次上报前，显示交接单估算（虚线）或“—”。

**M20 拉取（如果做）**

- 只在交接新建的会话上挂载，中途不增减。
- 转录里渲染为“查看交接记录：第 3 轮”，不显示原始 MCP 名。
- 真机确认不弹审批；否则该 Harness 关闭这个通道。

**M21 API 可见性**

- Run 资源带 `relay{packetId, level, tier, delivery{state, evidence}, 省略汇总, redactions, userEdits}`。
- 交接单正文可 GET，`ETag` 取 sha256；提供预览端点。
- 错误码统一为 `RELAY_INPUT_LIMIT`（只可能是原话过长）、`RELAY_PREPARE_FAILED`、`RELAY_CONSENT_REQUIRED`。
- public-api.md 写明长历史不再报 `CONTEXT_TOO_LARGE`。

**M22 用词检查**

- 新增文案与无障碍名不出现“Agent”（产品名与“子 Agent”除外）。
- 用检查脚本把关，脚本附一个无效样例以证明能拒绝。

## 5. 分歧裁定（C1–C10）

| 编号 | J3 裁定 | 理由 | 与作者的分歧 |
|---|---|---|---|
| C1 保真度 | 原文优先的确定性渲染：头部是短状态节，其后照录近几轮原话与回复（P2 narration/1），用户原话优先（M8）；不做摘要、不按方向调整，失败后也不降档 | 原文最能让接手方像原生那样续写，指代要靠回复原文；破坏状态下原始轨迹最有用（R7[S33]）；方向策略的证据弱（小结 D） | P3 的 lean 档推送原文太少（F3）；P1 以词表摘句为主体，J3 主张结构只作头部 |
| C2 预算 | 默认 min(8k, 5%W)；整段叙述历史放得进默认档时就全部照录；精简 3–4k，只交目标 1.2–2k；完整 ≤32k，只能由用户选择；单价只能把档位调低，不能调高 | 交接单会永久留在原生转录里；NoLiMa 在 32K 处退化（R2[S3]）；四份方案的 S1 样例都只有 1.5–2.1k（推算） | 不同意 P4 为 DeepSeek 自动推 32k、P2 默认 16k、P3 的 L0 只给 2k |

## 6. 方案对现状的误读

1. **失败后“仍由 Claude Code 执行”**（P1 T7、S15；P2 §11；P3 §11）。【事实】
   - 非恢复切换只做 validate（runtime.ts:1563），生效时就把 selection 改为目标，epoch 加 1（runtime.ts:1603）。
   - 只有恢复切换才预先启动目标（runtime.ts:1574）；普通切换的目标在第一条消息里才 prepare（runtime.ts:1356）。
   - 所以首条消息交接失败时，当前选择已经是 Codex，下一条仍会发给 Codex。
   - ADR-015 的“失败保留原有效选择”，指的是切换本身失败的情形。switching.md（proposed）的“目标准备失败不改实际 selection”以“先准备、后生效”为前提，而现状和四份方案都是在 open 之后才组包。
   - P4 §8 的写法正确。
2. **P1 §3.2 把“用首条消息生成标题”归到 ADR-039。** ADR-039 讲的是续接命令。标题的依据是 codex.ts:67–70、acp.ts:301 和 ADR-029 第 3–4 条。
3. **P1 §5 自称交接前会话“与原生完全一样”。** 这与它的 §4.5、§6.2 和回合外改动通知相矛盾；另外现状是新绑定首条也被包装（runtime.ts:1392），P1 也没有把“空历史原样发送”立为规则。
4. **P3 §6 的伪代码。** `none → handoff` 排在“need 为空 → 原样”之前，照字面执行，新对话首条会收到一份空交接单，这正是 R4 指出的现状缺陷；`unknown → resend` 也排在前面，单 Harness 会话执行 rewind 后会重发一个空包。
5. **P1 §5、§6 与 P3 §5 假定数据根在工作区外**（样例路径是 `~/Library/Application Support/…`）。实际默认是 `resolve("data")`，相对 Gateway 的启动目录（src/cli/session-application.ts:17–20）。用 HarnessHub 开发 HarnessHub 时，数据根就在工作区内。P2 的处理是对的。
6. **P1 的 `relay_full` 显示为“完整”**，而 §3.2 的样例省略了第 1–3 轮回复和 9 条工具输出。这与 context-transfer.md “不能因此声称…无损迁移”冲突。
7. **P2 §14 S11 写“用户看到：无变化”**，可它自己的省略账目已经计了 `attachmentsNotTransferred`。只告诉了模型，没有告诉用户。
8. **四份都没处理用量环。** 用量环取的是最近任一 Run 的用量（ChatPage.tsx:238–239，R7 §2.8 已指出），切换后仍显示 A 的占用。

## 7. 遗留风险与需真机核实的点

- **R-1 原生标题。** Codex 取 preview；Claude、OpenCode、Hermes 可能由模型生成标题，首行策略未必够用。办法：每家各做一次交接回合，再读标题。
- **R-2 多段 text 的呈现。** 在 `claude --resume`、`codex resume`、`opencode -s`、`hermes --resume` 里，多段 text 是否拼接、有没有分隔，用户能否认出自己的原话。
- **R-3 压缩后还能否找到标记。** 需核对 Claude JSONL、Codex `turns/list`、Hermes load 回放（Hermes 在 50% 时压缩）、OpenClaw `sessions.get`。如果旧消息消失，就会误判为分叉（M16）。
- **R-4 M9 的措辞会不会让旧任务复活**（Hermes #41607）。陷阱题要同时覆盖“早期约束”和“已放弃的任务”。
- **R-5 语言错配**会不会让回复语言跑偏。
- **R-6 Claude 经 ACP 执行 `/clear` 的实际效果。** 在保留进程与重启进程两种情况下，会话 ID 是否不变、上下文是否真的清空（R8 未决）。
- **R-7 Hermes 查看器被杀后，网关里的回合是否继续并正常结算。** P4 的 S14 文案以此为前提。
- **R-8 能否识别认证方式（订阅还是 API key）**，例如 Codex 的 `account/read`。识别不了就只显示 token。
- **R-9 拉取通道。** Claude `allowedTools` 的作用范围、工具搜索、审批弹窗、工具名是否出现在转录里，都需真机核实。
- **R-10 现有界面仍写“Agent”。** 基点上仍有 Welcome.tsx:25–26、Sidebar.tsx:101、HarnessesPage.tsx:171、Composer.tsx:69、ChatPage.tsx:38 等处；接力界面不能沿用。据记忆，改名在其他分支进行，本评审未核实。
- **R-11 选择器密度。** 加上等级、规模、费用、时延后，小屏能否放下，需要原型验证。
- **R-12 只有 E3 证据的 Driver。** 首轮回复全程停在“送达中”下面，可能显得别扭；是否增加一个只用于显示、不推进水位的“已开始回复”状态，需要原型测试。
- **R-13 钉住的使用率可能很低。** 默认路径不能依赖钉住；上线后统计使用率。
- **R-14 大包在原生界面里的观感。** P2 的 16k、P4 的 32k 首条消息，在原程序里是否会被折叠显示。
