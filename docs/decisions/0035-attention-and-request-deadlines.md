# ADR-035：跨对话的待处理提醒与审批期限

状态：accepted，2026-10-12。依据用户授权的审批代理（Fable 5.1）对排序第 2 项 B 的条件，以及它对期限显示的裁决（采纳“服务端给出最早期限并标明来源”）。对应[第一链路调研](../research/first-chain-products-2026-10-11.md)的差距 8。

> 2026-10-12 起由 [ADR-036](0036-approval-wait-budget.md) 部分取代。以下第 5 项“回合期限到期”和“不做”中的两项不再适用：回合期限拆为执行预算和等待预算；`expiresBy: "turn"` 表示等待预算，显示为“等待期限 · 剩余 N 分”；等待预算到期时，请求记为 expired，回合以 `WAIT_EXPIRED` 结算为已取消，而不是 `RUN_TIMEOUT` 未知；不同工作区的对话可以并行。其余各项不变。

## 背景

- 审批和提问只在所属对话里显示。用户在别的对话、别的页面或别的窗口时，不知道有请求在等，也不知道它还能等多久。
- Hermes 0.12.0 的 ACP 审批 60 秒不答就按拒绝处理：`acp_adapter/permissions.py` 的 `timeout` 默认 60 秒，`server.py` 调用时没有传入其他值；它不向客户端撤回请求。Hub 已在期限前 2 秒关闭这个请求（ADR-031）。
- Hub 自己也有回合期限：ACP 的 `session/prompt` 请求、Codex 的回合和 Pi 的运行，都在发出后 `runTimeoutMs`（300 秒）到期。到期时 Hub 结束原程序，回合结果记为未知（DESIGN §5）。所以 Claude、Codex 的审批虽然原程序会一直等，实际上最多也只能等到回合期限。
- Runtime 只有一个执行泵，同一时间只运行一个回合，其他对话的回合排队。所以同一时刻在等的请求只来自一个对话；一个回合可以同时有多个请求，例如 Codex 一次提出的几个问题。

## 决定

1. **期限。** 驱动发出请求时，给出它还能等多久（`expiresInMs`）和这个期限属于谁（`expiresBy`）：原程序自己的期限（Hermes 0.12.x 为 60 秒减去 Hub 提前关闭的 2 秒；Pi 的界面请求用它自带的 `timeout`），或本回合的期限，取较早的一个（`requestExpiry`）。Runtime 按自己的时钟换算为 `requestedAt` 和 `expiresAt`，写入 `permission.requested` 事件，并放在会话视图的审批请求上。驱动两者都不知道时不给出期限；目前的驱动都知道回合期限。
2. **类型。** 请求标明是审批（原程序要执行的操作）还是提问（ACP 表单、Codex 的问题、Pi 的选择、输入和编辑）。
3. **待处理列表。** `attention()` 列出所有尚未决定的请求，每项包括对话、请求、回合、Harness、类型和期限，不包括标题和详情。请求只有在 `permission.requested` 提交成功后才进入列表。列表只在当前服务的内存中：服务重启后，上一服务留下的请求不再列出，它们所在的回合按原有恢复规则记为结果未知。
4. **推送。** 列表可以用 `GET /api/v1/attention` 读取。打开了对话的页面，由该对话的推送流附带 `event: attention` 帧；这些帧不带事件编号，不移动会话游标。没有打开对话的页面订阅 `GET /api/v1/attention/stream`。每帧是完整列表（最多 32 项）和递增的修订号；列表变化时才推送；慢订阅者排空后只收到最新一帧。这样每个页面始终只保持一条长连接（浏览器对同一主机的 HTTP/1.1 连接数有限，两条会使三个标签页就占满）。不新增轮询。
5. **回合期限到期。** 仍在等待的请求记为 `permission.closed`，`reason: "expired"`；回合增加提示“HarnessHub 的回合期限已到，本回合超时结束；原程序没有收到你的决定”；回合以 `RUN_TIMEOUT` 结束，结果未知，对话需要明确恢复（ACP 的 prompt 超时也统一报为 `RUN_TIMEOUT`）。不自动重发，不新建回合。原程序期限到期时沿用原有的“审批已超时”提示。
6. **界面。**
   - 侧栏：等待中的对话在标题下方说明“等待审批”或“等待回答提问”，以及期限来源和剩余时间。原程序期限显示“N 秒后自动拒绝”；回合期限显示“回合剩余 N 分”，最后 60 秒改为秒。悬停说明期限的含义。分区标题显示“待处理 N”。有期限时每秒更新，到期即消失。点击只打开对话，决定在对话内的审批卡中完成；侧栏不提供“允许”“拒绝”。
   - 审批卡：显示同样的期限来源和剩余时间。
   - 浏览器通知：分区标题旁有开关，默认关闭。只有用户打开开关时才向浏览器请求权限；浏览器不支持或拒绝时，开关保持关闭，不发通知。只在页面不可见时为新出现的请求发出。内容只有 Harness 名称和“等待审批／等待回答提问（期限来源，剩余时间）”，不包括对话内容、标题或路径；点击后打开对应对话。不使用 Service Worker 或推送服务，页面关闭后不会有通知。开关状态保存在浏览器本地。

## 影响

- `permission.requested` 事件增加 `expiresAt`、`expiresBy`；`permission.closed` 可以带 `reason: "expired"`。会话视图的审批请求增加 `requestedAt`、`expiresAt`、`expiresBy`、`kind`。这些都不在快照中，业务格式不变。
- `ControlEvent.permission_requested` 增加可选的 `expiresInMs`、`expiresBy`、`kind`。
- 会话推送流在会话事实之外携带待处理帧。界面与服务同一构建发布，旧页面重新载入后即使用新的解析。
- Hermes 0.12.x 固定的 60 秒按 initialize 报告的身份给出，是 [ADR-053](0053-latest-version-baseline.md) 登记的例外（2026-10-22）：只增加信息，不影响任何功能；Hermes 网关视图接入、改读 `approvals.timeout` 或网关报告的等待时间时删除。其他版本读不到它自己的 `approvals.timeout`，只显示回合期限；不按版本号开关任何功能。

## 不做

- 侧栏不提供决定操作。
- 不暂停回合期限。“审批等待是否计入回合期限”另以 ADR 提案（审批代理要求在本项完成后提出）。
- 不并行运行多个对话的回合。
