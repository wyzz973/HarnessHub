# ADR-032：记录并显示回合阶段与首字延迟（Session v10）

状态：accepted，2026-10-11。依据用户授权的审批代理（Fable 5.1）给出的本阶段优先级 P4，以及[第一链路调研](../research/first-chain-products-2026-10-11.md)的差距 6（Multica 记录各阶段耗时并立即推送首个可见事件；Zed 显示加载与认证中等状态）。

## 背景

回合开始后，界面只显示“正在准备回复”或“正在回复”。用户分不清是原程序还在启动、正在恢复会话，还是已经发出、正在等模型。冷启动较慢的 Harness（Hermes 本机实测启动约 4.8 秒）看起来像卡住了。首字延迟也没有记录，无法按 Harness 衡量第一链路的快慢，也无法评估 ADR-030 保留进程能带来多少收益。

## 决定

1. Run 增加 `timing`（Session v10）：受理、开始准备、原生会话就绪、发送、首个可见输出、结束，记录为 Runtime 时钟的毫秒时间。只有 Runtime 写入，原程序不能提供这些值。时间只增不减：时钟回拨时取已记录的最大值，解析器也拒绝倒退。首个可见输出指回复、思考、工具、计划、审批或提问、产物或活动；用量和诊断不算。
2. 发送和首个输出各写一条事件（`run.dispatched`、`run.first_output`），回合的其余阶段沿用已有的提交。
3. 界面按阶段显示：“正在启动 X”“已连接 X，正在发送”“等待 X 回复”。超过 2 秒后附上已用时间；同一对话中，同一 Harness 的上一个回合有启动时间时，附上“上次约 N 秒”。回合结束后，在用量旁边显示“首字 … · 用时 …”（从受理算起）；执行详情里显示“启动原程序”和“发送后首个输出”。
4. v9→v10 只改版本号。旧回合没有 `timing`，不显示这些信息；v9 数据中出现 `timing` 视为损坏，整体回滚。

## 影响

- 业务格式 v10：升级前备份数据目录；回退旧程序前要停止服务，并恢复升级前的备份。
- 后续可以按 Harness 统计首字延迟，作为保留进程（ADR-030）的验收指标。
