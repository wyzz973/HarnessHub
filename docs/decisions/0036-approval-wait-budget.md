# ADR-036：等待用户决定的时间不计入回合期限

状态：accepted，2026-10-12；已实施（见文末“实施”）。审批代理在 ADR-035 的裁决中要求提出，并在审阅后采纳（裁决见“裁决”）。

## 背景

1. **设计。** 运行契约（[lifecycle.md §3](../contracts/lifecycle.md)、INV-10）规定：回合总期限从持久接收输入开始计算，覆盖排队、启动、模型、工具、权限和结果采集。同一文件 §5 还要求“同 Session 串行写执行；多 Session 有界并行”。
2. **实现与设计有两处不一致（现状）：**
   - 期限由驱动在发出 prompt 时才开始计时：ACP 的 `session/prompt` 请求超时，Codex 和 Pi 的计时器，都是 `runTimeoutMs` = 300 秒。排队和启动时间不计入，Runtime 也没有统一的预算。
   - Runtime 全局只有一个执行泵，同一时间只运行一个回合，没有做到多 Session 并行。
3. **原程序自己的行为。** 在终端里，Claude Code、Codex 等会一直等人做决定；Hermes 0.12 等 60 秒（0.12 的 ACP 不读它配置中的 `approvals.timeout`）；Pi 的对话框按自带的 timeout。
4. **问题。** 现在这 300 秒包含等待用户的时间。用户离开几分钟，回合就以 `RUN_TIMEOUT` 结束，结果未知，对话需要明确恢复。ADR-035 已经把这个期限显示出来，但没有改变它。这与“像在原程序里一样使用”有明显差距。

## 提案

1. **拆成两个预算。**
   - 执行预算：300 秒（现值，由配置解析器集中设定），只在回合没有等待用户时消耗。
   - 等待预算：回合中至少有一个请求在等待用户时开始计时，默认 30 分钟，设上限（例如 2 小时，可配置）。所有请求都已决定、撤回或关闭后停止计时，执行预算从剩余处继续。
   - 原程序自己的期限照常生效（Hermes 60 秒、Pi 的 timeout），ADR-035 中“原程序期限”的显示不变。“回合期限”在等待期间显示为等待预算的剩余时间，例如“审批等待剩余 N 分”。
2. **计时改归 Runtime。** 期限不再由驱动内的请求超时实现，改为 Runtime 持有的可暂停计时器（单调时钟），到期由 Runtime 发起停止。驱动的 prompt 请求不再带固定超时，只保留一个远大于两个预算之和的硬上限，防止协议挂死。同时补上“从接收开始计时”的设计要求：排队和启动时间计入执行预算。
3. **等待预算到期。**
   - 先按 ADR-035 把仍在等待的请求记为 `expired`，并用原程序的“取消”或“拒绝”作答，不批准任何操作。
   - 再走正常停止链（ACP `session/cancel`、Codex `turn/interrupt`、Pi `abort`）。在清理宽限期内结算的，回合记为“已取消”而不是“未知”；超过宽限期的，才按现有规则结束进程并记为未知。
   - 提示“等待你的决定超过 N 分钟，本回合已取消；原程序没有收到决定”。不自动重发。
4. **等待期间。** 工作区租约继续由这个回合持有，原生进程保持运行（它本来就在等待）。
5. **前置条件（建议一并决定）。** 等待最长可达 30 分钟时，单一执行泵会让其他所有对话的回合都排在这一个审批后面。建议先实现设计中的“多 Session 有界并行”：不同工作区的回合可以并行（上限例如 4，与保留进程的上限一致），同一工作区仍由租约保证只有一个写入者，同一 Session 仍串行执行。如果暂不实现并行，等待预算应保持较短（例如 5 分钟），并在其他对话的排队状态中说明“正在等待对话 X 中的审批”。

## 对 ADR-030（保留进程与租约冲突）的影响

- 正在等待的回合不是保留进程。它是活动回合，进程和租约都属于这个回合；回合结束后，如果对话开启了保持，才按 ADR-030 交给对话。
- 同一工作区的另一个对话遇到活动回合时，现在返回 `WORKSPACE_BUSY`（不是 `WORKSPACE_KEPT`）。等待可长达 30 分钟后，这种冲突会更常见。建议 `WORKSPACE_BUSY` 也带上持有者（哪个对话，是否在等待你的审批），界面提供“打开那个对话去处理”，不提供结束操作；活动回合只能由用户在那个对话里取消，沿用现有取消链。
- 保留进程的 30 分钟空闲期限和最多 4 个的上限不变；等待时间不算空闲，因为进程属于活动回合。
- 服务异常退出（ADR-030 的清理）：等待中的回合按原有规则记为未知，工作区保持隔离，与保留记录无关。

## 代价与风险

- 等待预算越长，工作区被占用越久；在单一执行泵下，所有对话都会被占用。
- 计时改归 Runtime，会影响三个驱动的超时实现和恢复逻辑，需要逐个驱动补协议测试，并做真实回合验证。
- 两个预算的消耗可以只在内存中计时：服务重启后，进行中的回合本来就记为未知，不需要恢复计时。进入和离开等待的时间点记入事件，供显示和核查。这样业务格式不变。

## 需要决定的问题

1. 是否采纳“执行预算加等待预算”的拆分？等待预算的默认值和上限各是多少？
2. 先实现“多 Session 有界并行”（不同工作区），还是在单一执行泵下把等待预算限制得较短？
3. 等待预算到期后，按“取消（可结算）”处理，还是沿用“超时（结果未知）”？
4. `WORKSPACE_BUSY` 是否带上持有者，并提供“打开那个对话”？

## 裁决（审批代理，2026-10-12）

1. 采纳拆分。执行预算 300 秒（现值），等待预算默认 30 分钟、上限 2 小时，三者都由配置解析器集中设定。等待期间原程序自己的期限照常生效。
2. 先实现“不同工作区有界并行”：上限 4，与保留进程的上限一致；同一工作区由租约保证唯一写入者，同一 Session 串行。等待预算与并行同一批交付。并行落地之前，等待预算维持现状（5 分钟），并在排队的对话中显示“正在等待对话 X 中的审批”。“从受理开始计时”随并行一起补上，不在单一执行泵下先做，否则排队时间会先耗掉执行预算。
3. 等待预算到期按“取消（可结算）”处理：先把等待中的请求记为 `expired`，并以原程序的取消或拒绝作答（绝不批准），再走正常停止链；在宽限期内结算的记为已取消，超过才记为未知。停止原因用独立的 `WAIT_EXPIRED`，不复用 `RUN_TIMEOUT`。
4. `WORKSPACE_BUSY` 带上持有者（哪个对话、是否在等待审批），界面提供“打开那个对话”，不提供结束操作，不含路径。
5. 计时归 Runtime 的可暂停单调计时器；驱动请求只保留远大于两个预算之和的硬上限，作为协议挂死的兜底。进入和离开等待记为事件，业务格式不变。验收：三个驱动各补暂停与恢复的协议测试；真实 Claude 在手动模式下等待超过 5 分钟后批准，回合正常完成；一次真实的 `WAIT_EXPIRED` 取消结算。

### 排队的补充裁决（审批代理，2026-10-12）

1. 只有活动回合（运行中，或在等待审批或回答）持有工作区时才排队。只由空闲的保留进程持有时，仍立即返回 `WORKSPACE_KEPT`。
2. 排队是可见状态。回合显示“排队中：等待对话 X 释放工作区（它正在等待你的审批／它正在运行）”，提供“打开那个对话”和“取消排队”，不含路径。同一工作区按受理先后 FIFO，不抢占。租约原语保持不等待，由 Runtime 在释放时唤醒等待者。
3. 预算语义：
   - 执行预算 300 秒，从派发开始计，覆盖启动、模型、工具和结果采集，等待用户时暂停。
   - 等待预算默认 30 分钟、上限 2 小时，覆盖两种外部等待：等待用户决定和等待工作区。
   - 排队到期以 `WORKSPACE_BUSY` 结束，带上持有者，不自动重试。
   - 这与 lifecycle §3 和 INV-10 的“总期限从受理起算”不同，须在同一提交里修改契约文字并说明理由。
4. 服务重启时，尚未派发的排队回合沿用现有恢复规则，记为中断并提供重试，不自动重新排队。

## 实施（2026-10-12）

1. **调度。** Runtime 的单一执行泵改为每个对话一个工作者，最多 4 个同时执行（`maxParallel`）。同一对话的工作仍串行：原生分支、切换、回合，与原来的顺序相同。
   - Runtime 记录每个工作区由哪个对话的工作者持有。另一个对话在这个工作区的下一回合进入排队，记 `run.waiting`（`kind: "workspace"`，带 `holderSessionId`）。持有者结束时唤醒排队者，并记 `run.waiting_ended`（带 `waitedMs`）。
   - 工作者每做完一项工作就检查：有没有受理更早的对话在等这个工作区，或者在所有空位都占满时等空位。有就让出，空位与工作区都按受理先后分配。
   - 要关闭的保留进程（ADR-030）先于下一项工作关闭，不会让回合遇到即将释放的租约。
2. **预算。** 执行与等待预算由 `--execution-budget <秒>`（30 至 3600）和 `--wait-budget <分钟>`（1 至 120）设定，在配置解析器 `resolveTurnBudgets` 中集中校验，不是整数或超出范围的值明确失败。
   - 回合派发时开始执行预算。第一个请求等待用户时，记 `run.waiting`（`kind: "user"`）并切换到等待预算；所有请求都已决定、撤回或关闭后，记 `run.waiting_ended`，回到执行预算的剩余部分。
   - 到期时记 `run.budget_expired`（`kind: execution|wait`、`budgetMs`），在回合中加提示：“执行期限已到”或“等待期限已到”。等待中的请求记为 `permission.closed`，`reason: "expired"`，然后发起停止。停止宽限默认 15 秒，宽限内结算记为已取消，`error.code` 为 `RUN_TIMEOUT` 或 `WAIT_EXPIRED`；超过宽限则关闭绑定，记为未知。
   - 驱动的回合超时改为硬上限 `NATIVE_TURN_HARD_CAP_MS`，远大于两个预算之和。读取模型目录的超时仍为 300 秒。
3. **请求期限（ADR-035）。** `expiresBy: "turn"` 现在表示等待预算。原程序自己的期限只有在更早时才保留为 `native`。审批卡和侧栏显示“等待期限 · 剩余 N 分”（最后一分钟按秒），悬停时说明到期后本回合取消，原程序不会收到决定。
4. **接口与视图。**
   - 会话视图增加 `queue`：`runId`、`holderSessionId`、`holderWaitsForUser`、`since`、`endsAt`。
   - 会话视图增加 `busyHolders`：每个以 `WORKSPACE_BUSY` 结束的回合对应的持有对话，只在当前服务内存中，最多 256 条。
   - 取消接口原本就接受 `runId`，排队的回合按回合 ID 取消。
   - 界面在排队回合中显示持有者的标题和原因。持有者是否在等待用户，跟随推送的待处理列表实时更新。还显示最多再等多久，以及“打开那个对话”“取消排队”两个操作。以 `WORKSPACE_BUSY` 结束的回合说明消息没有发出、是哪个对话占用，并提供“打开那个对话”。界面不提供结束持有者的操作。
5. **业务格式不变。** 新事件只写进事件流；预算消耗和排队状态只在内存中。服务重启后，排队中的回合按原有规则记为中断（`OWNER_ENDED`），不重新排队；进行中的回合按原规则处理。

### 测试

- `tests/integration/parallel-work.test.ts`：
  - 上限内并行。
  - 工作区排队可见，持有者结束后自动开始。
  - 按回合取消排队，以及同一工作区的 FIFO。
  - 等待空位按受理先后分配（还原为旧逻辑时测试失败）。
  - 执行预算在等待时暂停：ACP、Codex、Pi 各一。
  - 执行预算到期的停止链结算为已取消。
  - 原程序不理会停止时，宽限后为未知。
  - 排队超过等待预算时以 `WORKSPACE_BUSY` 结束并带上持有者。
- `tests/integration/attention.test.ts`：
  - 等待预算到期时，请求记为 expired，原程序收到取消，回合以 `WAIT_EXPIRED` 结算为已取消。
  - 重启后，排队中的回合记为中断。
- `tests/integration/kept-process.test.ts`（原有）：空闲保留进程持有工作区时，仍立即返回 `WORKSPACE_KEPT`。
- 浏览器：
  - 排队回合的文字（等待审批或正在运行）、剩余等待、取消排队、打开那个对话、批准后自动完成。
  - 排队到期后的说明和“打开那个对话”。
  - 审批卡和侧栏的“等待期限 · 剩余 30 分”。

### 未做与限制

- 等待空位时只显示“等待开始”，不说明原因，也不计入预算。空位由其他回合的预算保证释放。
- 同一对话的后续消息在前一回合结束之前等待，这段时间不计入预算。每条消息在派发时开始自己的执行预算。
- 预算只在当前服务进程中计时；服务异常退出后不恢复计时。
- Windows 未验证。
