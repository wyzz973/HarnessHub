# ADR-036（提案）：等待用户决定的时间不计入回合期限

状态：proposed，2026-10-12，待审批代理决定。审批代理在 ADR-035 的裁决中要求在该项完成后提出。

## 背景

1. **设计。** 运行契约（[lifecycle.md §3](../contracts/lifecycle.md)、INV-10）规定：回合总期限从持久接收输入开始计算，覆盖排队、启动、模型、工具、权限和结果采集。同一文件 §5 还要求“同 Session 串行写执行；多 Session 有界并行”。
2. **实现与设计有两处不一致（现状）：**
   - 期限由驱动在发出 prompt 时才开始计时：ACP 的 `session/prompt` 请求超时，Codex 和 Pi 的计时器，都是 `runTimeoutMs` = 300 秒。排队和启动时间不计入，Runtime 也没有统一的预算。
   - Runtime 全局只有一个执行泵，同一时间只运行一个回合，没有做到多 Session 并行。
3. **原程序自己的行为。** 在终端里，Claude Code、Codex 等会一直等人做决定；Hermes 0.12 等 60 秒（0.12 的 ACP 不读它配置中的 `approvals.timeout`）；Pi 的对话框按自带的 timeout。
4. **问题。** 现在这 300 秒包含等待用户的时间。用户离开几分钟，回合就以 `RUN_TIMEOUT` 结束，结果未知，对话需要明确恢复。ADR-035 已经把这个期限显示出来，但没有改变它。这与“像在原程序里一样使用”有明显差距。

## 提案

1. **拆成两个预算。**
   - 执行预算：300 秒（现值，由配置解析器集中设定），只在回合没有等待用户时消耗。
   - 等待预算：回合中至少有一个请求在等待用户时开始计时，默认 30 分钟，设上限（例如 2 小时，可配置）。所有请求都已决定、撤回或关闭后停止计时，执行预算从剩余处继续。
   - 原程序自己的期限照常生效（Hermes 60 秒、Pi 的 timeout），ADR-035 中“原程序期限”的显示不变。“回合期限”在等待期间显示为等待预算的剩余时间，例如“审批等待剩余 N 分”。
2. **计时改归 Runtime。** 期限不再由驱动内的请求超时实现，改为 Runtime 持有的可暂停计时器（单调时钟），到期由 Runtime 发起停止。驱动的 prompt 请求不再带固定超时，只保留一个远大于两个预算之和的硬上限，防止协议挂死。同时补上“从接收开始计时”的设计要求：排队和启动时间计入执行预算。
3. **等待预算到期。**
   - 先按 ADR-035 把仍在等待的请求记为 `expired`，并用原程序的“取消”或“拒绝”作答，不批准任何操作。
   - 再走正常停止链（ACP `session/cancel`、Codex `turn/interrupt`、Pi `abort`）。在清理宽限期内结算的，回合记为“已取消”而不是“未知”；超过宽限期的，才按现有规则结束进程并记为未知。
   - 提示“等待你的决定超过 N 分钟，本回合已取消；原程序没有收到决定”。不自动重发。
4. **等待期间。** 工作区租约继续由这个回合持有，原生进程保持运行（它本来就在等待）。
5. **前置条件（建议一并决定）。** 等待最长可达 30 分钟时，单一执行泵会让其他所有对话的回合都排在这一个审批后面。建议先实现设计中的“多 Session 有界并行”：不同工作区的回合可以并行（上限例如 4，与保留进程的上限一致），同一工作区仍由租约保证只有一个写入者，同一 Session 仍串行执行。如果暂不实现并行，等待预算应保持较短（例如 5 分钟），并在其他对话的排队状态中说明“正在等待对话 X 中的审批”。

## 对 ADR-030（保留进程与租约冲突）的影响

- 正在等待的回合不是保留进程。它是活动回合，进程和租约都属于这个回合；回合结束后，如果对话开启了保持，才按 ADR-030 交给对话。
- 同一工作区的另一个对话遇到活动回合时，现在返回 `WORKSPACE_BUSY`（不是 `WORKSPACE_KEPT`）。等待可长达 30 分钟后，这种冲突会更常见。建议 `WORKSPACE_BUSY` 也带上持有者（哪个对话，是否在等待你的审批），界面提供“打开那个对话去处理”，不提供结束操作；活动回合只能由用户在那个对话里取消，沿用现有取消链。
- 保留进程的 30 分钟空闲期限和最多 4 个的上限不变；等待时间不算空闲，因为进程属于活动回合。
- 服务异常退出（ADR-030 的清理）：等待中的回合按原有规则记为未知，工作区保持隔离，与保留记录无关。

## 代价与风险

- 等待预算越长，工作区被占用越久；在单一执行泵下，所有对话都会被占用。
- 计时改归 Runtime，会影响三个驱动的超时实现和恢复逻辑，需要逐个驱动补协议测试，并做真实回合验证。
- 两个预算的消耗可以只在内存中计时：服务重启后，进行中的回合本来就记为未知，不需要恢复计时。进入和离开等待的时间点记入事件，供显示和核查。这样业务格式不变。

## 需要决定的问题

1. 是否采纳“执行预算加等待预算”的拆分？等待预算的默认值和上限各是多少？
2. 先实现“多 Session 有界并行”（不同工作区），还是在单一执行泵下把等待预算限制得较短？
3. 等待预算到期后，按“取消（可结算）”处理，还是沿用“超时（结果未知）”？
4. `WORKSPACE_BUSY` 是否带上持有者，并提供“打开那个对话”？
