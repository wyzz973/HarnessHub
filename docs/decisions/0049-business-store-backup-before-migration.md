# ADR-049：业务库迁移前用 VACUUM INTO 备份

状态：accepted，2026-10-22。依据 [ADR-048](0048-harness-scope-and-workbuddy.md)“用户决定（2026-10-21）”第 6 项：每次存储版本提升前用 `VACUUM INTO` 备份，保留最近 2 份，超出删最旧；备份失败则迁移不发生。总指挥兼审批代理的裁决：本阶段只做业务库，管理库与能力库在 M2 随 OwnerScopedStore 复用同一做法；本决定合并后，解除“本阶段不批准持久格式升级”的前提。

## 背景

- 业务库 `gateway.sqlite` 保存 Session 快照与事件。它的迁移在 `claimAndRecover` 的一个 `BEGIN IMMEDIATE` 事务里逐级改写每个 Session 并提高 `user_version`，任何一行不合法就整笔回滚。但迁移只进不退：没有降级 SQL，旧构建的 Store 与 `SqliteSessionReader` 都拒绝不认识的版本。回退旧构建只能靠升级前的副本，而此前只有 README 与[公共 Session 契约](../contracts/public-session-mvp.md)里要用户升级前自行备份、回退前恢复的提示，做不做全靠用户。
- 本机磁盘紧张：自动备份的份数要有上限，裁剪不能碰不属于 HarnessHub 的文件。
- `VACUUM INTO` 不能在事务里执行。owner 排他锁（`owner.sqlite` 上的 `BEGIN EXCLUSIVE`）在打开业务库之前已经持有；此后到迁移事务开始之前，没有别的 owner 能写这个数据根。
- 后续的 Session 格式升级（例如 M5 的 T-PERF-03，Session v13）以有自动备份为前提。

## 决定

1. **时机**：`SqliteSessionStore` 构造时，持有 owner 排他锁、打开业务库并设好 WAL 之后，`claimAndRecover` 开始事务之前，在无事务状态下读 `user_version`。只有 1～11（将被迁移到 12）才备份。v0（新库直接建成 v12）、v12（当前）、未知版本（随后以 `INVALID_DATA` 拒绝）与只读的 `SqliteSessionReader` 都不备份。备份只读业务库，不改它。
2. **位置与命名**：`<数据根>/backups/gateway-v<原版本>-<UTC yyyymmddThhmmssZ>-<8 位随机十六进制>.sqlite`，例如 `gateway-v11-20261022T080910Z-3fa9c2d1.sqlite`；时间取 Store 注入的时钟（`now`）。目录不存在时以 0700 新建；已存在时必须是当前用户所有、不对组和其他用户开放的真实目录（不是链接），否则失败。目录里是整份业务库，与数据根一样只对本用户开放。
3. **写出、核对、发布**：以独占方式新建 `<正式名>.partial`，显式 fchmod 为 0600（不受 umask 影响；SQLite 写进这个空文件，而不是自己以 0644 新建）。`VACUUM INTO ?` 以绑定参数传路径，数据根路径含引号也不拼 SQL。随后以只读连接回读：`user_version` 等于原版本，`sessions` 与 `events` 行数等于源库，`PRAGMA quick_check` 为 ok，文件仍是 0600、单链接的普通文件。fsync 后以硬链接取得正式名字（同名已存在则失败，不覆盖），删除 `.partial` 名，再 fsync 目录（目录是本次新建的，连同数据根）。不依赖 SQLite 对 `VACUUM INTO` 输出的同步行为，这里自己 fsync，迁移提交时备份已在盘上；正式名字只出现在完整、核对过的副本上。
4. **保留 2 份**：写新副本之前先裁剪，按文件名中的时间只留最新的 1 份（时间相同时按整个文件名），写完正好 2 份。不按整个文件名排序：版本号位数不同时（`gateway-v9-…` 与 `gateway-v10-…`），按名字倒序会把较旧的 v9 当作最新。之前崩溃留下的 `.partial` 文件同时删除，owner 锁保证此时没有另一次备份在写。只删除符合这两种命名的普通文件；`backups` 里的其他文件、目录与链接原样保留。
5. **失败**：任一步失败时，构造以 `STORAGE_BACKUP_FAILED` 抛出，`cause` 保留原错误。消息写明失败的步骤（准备目录、删除旧备份、写出、核对、发布）和不含路径的原因（HarnessHub 自己的说明、SQLite 的通用错误文字或系统错误码），例如 `could not write the backup before migrating the business database from v1 (EACCES); nothing was migrated`。只删除本次写出的文件，删不掉时消息说明有未完成的备份文件留在目录里。此时迁移事务没有开始，owner 没有接管，业务库的行与版本不变；构造已有的失败路径关闭两个连接，释放排他锁与进程内对这个根的占用。`SessionError.code` 是开放字符串，契约层的类型不用改。
6. **资源责任**：备份归用户，HarnessHub 不读取、不自动恢复；恢复是手动操作，步骤写在[存储契约](../contracts/storage-events.md)的“业务库迁移前备份”一节。备份成功而迁移本身失败（例如 `INVALID_DATA` 整笔回滚）时，这份备份保留，计入 2 份。

## 否决的方案

- **备份到数据根之外**（系统临时目录或用户目录下另一处）：数据根是 HarnessHub 已核对标记与权限、唯一拥有的位置；放到外面要另找私有、耐久、不与其他实例冲突的位置，临时目录还会被系统清理。
- **只保留 1 份**：新备份失败或刚写的那份有问题时，没有另一份可退；多一份的代价是一份库的大小。
- **备份失败仍继续迁移**：违背用户决定 6；迁移只进不退，备份失败还迁移就没有退路。
- **先写新备份再裁剪**：任何时刻都不先删旧备份，但峰值要多放一份库，磁盘紧张时更容易因空间不足失败。先裁剪的代价是：新备份失败时较旧的那份已经删掉，但库本身未动，最新的一份旧备份还在。
- **直接写正式名字**：崩溃留下的半截文件会被下一次裁剪当作最新的一份留下，反而删掉完好的旧备份。
- **在迁移事务里备份，或改用 SQLite 在线备份**：`VACUUM INTO` 不能在事务里执行；`node:sqlite` 的 `backup()` 是异步的，而 Store 构造与迁移都是同步的。

## 影响

- 版本提升后的第一次启动多花一次整库复制与一次回读，需要约一份库大小的空闲空间；日常启动（v12）没有额外开销。
- 解除“本阶段不批准持久格式升级”的前提：此后的 Session 格式升级把版本上限与备份范围（`backupBeforeMigration` 里的 11）一起改，沿用本决定的命名、保留与失败语义。
- M2 的 OwnerScopedStore 把同一做法用于管理库与能力库；本决定只做业务库。备份不含内容存储、Provider、管理库与能力库，恢复业务库不会恢复它们。
- 用户可见的文档（README 中“升级前备份”的几处）可以改为说明自动备份；它们不在本任务的文件范围内，由主代理决定。
- `web` 命令启动失败时只打印错误码，看不到 `STORAGE_BACKUP_FAILED` 消息里的步骤与原因（`chat` 命令会打印消息）；是否让 `web` 打印 SessionError 的消息由主代理决定。

## 验证（合成，2026-10-22）

- `tests/integration/session-store.test.ts`，测试数据都在临时根里，用完即删：
  - `G008-NC9`：v1 库以注入时钟打开后，`backups/` 恰有一个 `gateway-v1-20261022T080910Z-<8 位十六进制>.sqlite`，目录 0700、文件 0600；副本的 `user_version` 为 1，`sessions`、`events` 行数与四张表的全部行都等于迁移前；主库已是 12。按契约的手动恢复步骤把副本放回后，只读 reader 读到 v1 的 Session 与原有事件。同编号的反例：v0 新建、v12 重开、只读 reader 打开 v1 库、未知版本 99 都不产生 `backups`。
  - `G008-NC10`：预先放两份旧备份（`v9` 较旧、`v10` 较新）、四个不符合命名的文件、一个符合命名的目录与一个符合命名的链接、一个崩溃留下的 `.partial`。迁移后恰有 `v10` 与新副本两份，`.partial` 被删，其余原样；把库降回 v1 再迁移一次，留下的是两份新副本，其余仍原样。
  - `G008-NC11`（无效样例）：`backups` 是普通文件、指向别处的链接、对组开放的目录、不可写的目录，以及源库一页损坏、使 `VACUUM INTO` 在 `.partial` 建出之后失败。每种都以 `STORAGE_BACKUP_FAILED` 失败，消息给出步骤与原因且不含路径；`user_version` 仍为 1，快照仍是 v1，`owner_metadata` 的代次与活动标记不变，没有留下备份或 `.partial`。修好后打开成功（代次 2），恰好产生一份备份。
  - 已有用例“后面的坏 Session 让整个迁移回滚”补一条断言：迁移失败后，迁移前的备份仍在。
- 变异核对（人工；在编译产物上一次改一处，只跑本文件，跑完还原）：
  - 不做备份：`G008-NC9` 的迁移用例、`NC10`、`NC11` 与上面补了断言的回滚用例失败（4 个）。
  - 去掉 `VACUUM INTO`：空的 `.partial` 回读不通过（`could not verify the backup … (SQL logic error)`），打开旧版本库的 15 个用例全部失败，含 `G008-NC9` 的迁移用例、`NC10`、`NC11`。
  - 去掉裁剪、改为按整个文件名排序、把目录与链接当作备份、不删崩溃留下的 `.partial`：各自使 `G008-NC10` 失败。
  - 失败时吞掉错误继续迁移（第一个样例就没有抛出）、失败时不删本次写出的文件（损坏页样例留下 `.partial`）、接受对组开放的目录：各自使 `G008-NC11` 失败。
- 没有在 4317 的真实数据根上运行；真实业务库为 v12，不会触发备份。只面向 macOS（ADR-044）。
