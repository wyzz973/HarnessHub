# ADR-030：在回合之间保留原生进程以运行后台任务

状态：accepted，2026-10-11，由用户授权的审批代理（Fable 5.1）决定；2026-10-12 实施（Session v11），同日补上服务异常退出后的清理（Session v12）。依据[ADR-020](0020-complete-native-harness-capabilities.md)。用户要求接出后台任务。

## 背景

- Hub 的每个 Run 准备一个原生进程（ACP 代理、Codex app-server、Pi），回合结束即关闭并记录清理证据；下一回合再以原生会话恢复。原程序在后台启动的工作随进程一起结束：Claude Code 的后台 Bash（`run_in_background`，之后用 BashOutput 读取）、Codex 的后台终端与执行会话。OpenClaw 的后台执行与定时任务运行在用户自己的 Gateway 守护进程里，本来就不受影响，只是 Hub 看不到。
- 要让后台任务继续，原生进程必须在回合之间存活，由对话（而不是 Run）持有。这触及两条既定约束：
  1. **每个 Run 的资源在它结束时清理并留证**（运行契约、`cleanup.closed`）。保留的进程需要改为“交给对话持有”的证据，并在对话层记录最终关闭。
  2. **一个工作区同一时间只有一个写入者**（工作区租约，`WORKSPACE_BUSY`，不等待、不抢占）。后台任务就是在写工作区。

## 待决问题

保留的进程在空闲时如何对待工作区租约：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 继续持有 | 空闲的保留进程仍持有租约；同一工作区的其他对话在它结束前不能运行，界面说明原因并提供“结束后台进程” | 默认工作区相同的多个对话会互相阻塞 |
| B. 空闲时释放 | 回合之间释放租约，其他对话可以在同一工作区运行 | 后台任务可能与另一个对话同时写同一批文件，放宽了唯一写入者约束 |
| C. 需要时询问 | 同 A，但另一个对话要运行时，界面让用户选择“结束对话 X 的后台进程后继续”或“稍后再试” | 实现最复杂；仍不会自动结束任何进程 |

## 建议

C（在 A 的基础上由用户决定是否结束），并且按对话**显式开启**“保持原生进程（允许后台任务）”，默认关闭；空闲 30 分钟后结束并记录证据；Gateway 重启时按现有孤儿进程清理结束保留的进程（不恢复）。

## 实现影响（决定后）

- 契约：Run 的清理证据增加“交给对话持有”；对话层记录保留进程的开始、复用与最终关闭证据（业务格式 v10，迁移只改版本号）；`HarnessControl` 不变（同一连接上顺序发起回合已受支持）。
- Runtime：回合成功结束后按开关把绑定移交给对话；下一回合在选择不变时复用；切换、关闭对话、重建原生会话、分支、Gateway 关闭与空闲超时都先关闭保留进程；进程在空闲时退出则记录并按正常恢复继续。
- 回合之间的原生事件（后台任务完成、自主后续）目前只计数；是否显示为对话层的“后台活动”另行决定。
- 界面：对话设置中的开关、保留中的状态与“结束后台进程”；另一对话被占用时的说明与选择（方案 C）。

## 决定（审批代理，2026-10-11）

采纳 C，并附以下条件：
- 保留的进程继续持有工作区租约。另一对话要使用同一工作区时，由用户选择“结束对话 X 的后台进程后继续”或“稍后再试”；结束走正常的停止链（请求停止 → 等待 → SIGTERM/SIGKILL，并留下证据）。如果 X 正在回合中，仍返回 `WORKSPACE_BUSY`。
- 按对话显式开启，默认关闭；空闲 30 分钟结束；全局最多保留 4 个进程。
- 切换、关闭对话、重建原生会话、分支以及 Gateway 关闭时，都先关闭保留的进程；Gateway 重启时按孤儿进程清理，租约只在确认进程组已终止后释放，否则沿用 `WORKSPACE_QUARANTINED`。
- 回合之间不归属任何回合的原生事件只计数，界面显示“后台活动 N 条”，不展示内容。
- 业务格式 v10 只升版本号。
- 验收：真实的后台 Bash 跨两个回合仍可读取；空闲超时、重启清理与租约冲突时的选择各有集成证据。

## 实施（2026-10-12）

- **格式 v11（只升版本号）**：对话增加 `retainNative`（用户开启）和 `retained`（当前持有的进程：入口、交接它的回合、开始持有的时间）。把进程交给对话的回合标记 `retained`，不带自己的清理证据，状态必须是已完成；复用保留进程的回合标记 `reused`。原生会话的“就绪”证据对这类回合放宽：会话已确认，进程的关闭由对话记录。服务异常退出时留下的保留进程，由下一次启动按下一节处理。
- **交接与复用**：只有开启了该选项、回合正常完成、原生会话已确认、连接健康（`healthy()`）且未超过 4 个时，才把进程交给对话，并记 `native.process_retained`；超过 4 个时照常关闭，并记 `native.retention_skipped`。下一回合选择不变、连接仍健康时直接复用，不再启动程序、握手和恢复会话，记 `native.process_reused`；选择变了或进程已退出时，先关闭并记录，再按正常流程启动并恢复原生会话。
- **关闭**：空闲 30 分钟、关闭选项、用户“结束后台进程”、切换生效、重建原生会话、分支、关闭对话、服务关闭，都会关闭保留的进程。关闭走正常的停止链，并记 `native.process_closed`（原因、清理证据、后台活动条数）。释放由唯一写入者在下一回合或切换之前执行，所以回合不会碰上一个正要释放的租约。
- **方案 C**：另一个对话因同一工作区被保留进程占用而失败时，错误为 `WORKSPACE_KEPT`（没有发出任何内容）。界面提示“结束那个对话的后台进程并重试”；不会自动结束任何进程。
- **回合之间的原生更新**：只计数，界面显示“后台活动 N 条”，不展示内容。
- **界面**：执行配置里有“保持原生进程”开关，默认关闭；新对话可以在第一条消息前打开，创建会话后、发送之前生效。保留期间显示状态、后台活动条数和剩余空闲时间，并提供“结束后台进程”。复用的回合不计入“通常启动用时”。
- **接口**：`POST /api/v1/sessions/:id/retention`、`POST /api/v1/sessions/:id/end-process`、`GET /api/v1/kept-processes`；会话视图带 `retention`。

验收：

- 集成测试（真实存储、真实子进程与工作区租约）：复用与关闭、后台活动计数与空闲超时、各触发点、数量上限、工作区冲突后结束并重试、空闲时退出后恢复、Codex 的保留与复用。
- 浏览器测试：在新对话中先开启，再复用，最后结束。
- 真实 Claude Code：第二回合在后台运行 `sleep 12; echo …`，进程交给对话；第三回合复用进程（启动 7 毫秒），读到后台任务的输出，证据见 `.tmp/cc-kept-process-2026-10-12.json`。
- 未验证：Codex、Hermes、dsh 的真实后台任务；Windows。

## 服务异常退出后的清理（2026-10-12，Session v12）

依据审批代理的排序（第 1 项 H）：重启时找到并结束上一服务保留的进程组，确认结束后才释放工作区租约，否则保持隔离；在对话中记录“服务异常退出，后台进程已被清理（不恢复）”；两种结果都要有证据。

- **识别**：进程交给对话时，记录它的进程组号（组长的 pid）和组长的启动时间，存在 `retained.process`。启动时间由 `ps -o etime=`（`LC_ALL=C`）换算为 Unix 秒，与时区无关。读不到时不记录。这个字段属于业务格式 v12：v11→v12 只升版本号，v11 数据中出现该字段时整笔拒绝。
- **接管**：新服务启动后、接受任何工作之前，逐个处理仍记录着保留进程、且不归本服务持有的对话：
  - 组长仍在，但启动时间与记录相差超过 2 秒：这个 pid 已经属于别的程序。系统不会把仍在使用的进程组号分给新进程，所以原进程组已经不存在。不发信号，结果为 `gone`。
  - 进程组已经没有成员：`gone`。
  - 否则向整个进程组发 SIGTERM，3 秒内没有结束就发 SIGKILL，再等 3 秒。确认没有成员时为 `terminated`，否则为 `unconfirmed`。
  - 没有身份记录（本版本之前写入的记录）：`unconfirmed`，不发任何信号。
- **租约**：只有 `terminated` 或 `gone` 才释放这个对话的工作区租约（`releaseAbandoned`：取得与申请租约相同的 OS 锁；租约仍被活着的持有者占用、记录属于其他对话或没有记录时，都不释放）。`unconfirmed` 时租约保持隔离，下一回合以 `WORKSPACE_QUARANTINED` 失败，按 ADR-014 由人核实处理。
- **记录**：每个结果都记为该对话的 `native.process_lost`（`runId`、入口、`reason: "owner_ended"`、`outcome`、`leaseReleased`），并清除 `retained`。会话视图带 `retention.lost`。在服务这次运行期间、这个对话发出下一条消息之前，输入框下方说明结果：后台进程“已被清理”或“已随之结束”（没有恢复），下一条消息会重新启动原程序并恢复原生会话；无法确认时说明工作区保持隔离。这条说明只保存在内存中，服务再次重启后不再显示；事件保留在对话记录里。
- **启动日志**（审批代理附加）：逐个处理，每个最多约 6 秒。有遗留记录时，服务在 stderr 写明要清理的数量，结束后写明“已结束、已不存在、无法确认”各有几个。

边界：

- 只处理保留进程所在的进程组。原程序放进自己新建的会话或进程组的任务不在其中：真实验证中，Claude Code 的后台 Bash 就是这样运行的（`zsh -c` 是新会话的首进程），它在输入关闭时自己结束了这些任务。不清理自己后台任务的原程序，这类任务在正常关闭和重启清理之后都会留存。
- 组长已经退出、组内仍有成员时，只能按进程组号识别。只有在两次运行之间，这个号码先空出，又被新程序用来建立新的进程组，而且该程序退出时留下了成员，才会认错。
- 服务在回合进行中退出时，进程不在保留记录里（复用的回合开始时已经移出），按原有恢复处理：回合记为结果未知，工作区保持隔离。
- 只在 POSIX 上实现；Windows 未验证。

验收：

- 协议测试（真实进程组）：`etime` 的各种格式；结束整个进程组；组长启动时间不符时不发信号，结果为 `gone`；组长已经退出时仍能结束组内成员。
- 工作区租约测试：只有记录所属的对话能释放隔离；活着的持有者、其他对话、没有记录时都不释放。
- 集成测试：另起一个服务进程保留进程后被 SIGKILL，新服务接管——进程组内的后台任务被结束、租约释放、事件记录，下一回合恢复原生会话；原程序已经自行结束时为 `gone`；没有身份记录时不发信号、租约保持隔离、下一回合为 `WORKSPACE_QUARANTINED`。v10、v11→v12 迁移测试。
- 真实 Claude Code（开发实例，证据 `.tmp/cc-kept-orphan-2026-10-12.json`）：服务被 kill -9 约 60 秒后重启，Claude Code 已在 3 秒内自行退出并结束了后台的 `sleep 600`，结果为 `gone`，租约释放；下一回合重新启动原程序，恢复了原生会话（记得上一条命令）。另一次 kill -9 后立即重启，0.78 秒后接管时进程组还在，结果为 `terminated`，进程组随即为空，租约释放。界面说明见两张截图。
- `unconfirmed` 只有集成测试；真实 Harness 写入的记录都带身份。
- 回退：v12 数据不能由旧程序读取，回退前要停止服务并恢复升级前的备份。

## 补充：离开进程组的后台任务（2026-10-12，审批代理条件）

原程序启动的后台任务可能离开它的进程组，例如 Claude Code 的后台 Bash 自成一组。结束保留进程的组时，信号到不了这些任务。HarnessHub 不结束它们，但要如实记录并告诉用户：

1. **枚举。** 关闭保留进程（任何原因）和服务启动时接管上一服务保留的进程组之前，在发出任何信号前读取一次 `/bin/ps -axo pid=,ppid=,pgid=,etime=,comm=`（2 秒，输出上限 4 MiB）。从组内成员按父进程向下枚举，最多 32 层，取进程组不同的后代，记下进程号、启动时间和命令基名（不含参数和路径）。
2. **复查。** 组结束后，按进程号与启动时间复查哪些仍在运行。
3. **证据。** `native.process_closed` 与 `native.process_lost` 带 `outside`：`{state: "enumerated", found, remaining, commands}`（`remaining` 无法复查时为 null，`commands` 最多 16 个）或 `{state: "unknown"}`。“找到 0 个”与“无法枚举”分开记录。以下情况都记为无法枚举，不能记 0：
   - 组长已经退出（它的后代已被系统收养，无法再归属）；
   - 记录的组已经不是原来那个；
   - 没有记录组身份；
   - 进程表读不到。
4. **界面。** 仍在运行的数量大于 0 时，该对话在下一条消息之前提示一次“原程序的后台任务可能仍在运行（N 个进程）：它们已离开原程序的进程组，HarnessHub 没有结束它们。”。接管时的提示接在原有说明之后。
5. **不发信号。** 对这些任务只读，不发信号。

验证：
- 协议测试 G031-NC1 覆盖枚举规则。
- 集成测试 G028-NC13 使用真实进程，覆盖用户结束与接管：组长仍在、后台任务自成一组时，记为找到 1 个、仍在运行 1 个，不发信号，提示到下一回合；组长仍在、没有离开的后代时记为 0；组长已退出时记为无法枚举。
- 浏览器测试 G054-NC14。
- 真实 Claude Code 2.1.296（开发实例，证据 `.tmp/cc-kept-outside-2026-10-12.json`）：保留进程中用后台模式运行 `sleep 600`，后台的 zsh 与 sleep 自成一组。用户结束后台进程时记为找到 3 个（zsh、node、sleep）、仍在运行 0 个：Claude 在输入关闭后自己结束了它们，因此没有提示。仍在运行大于 0 的情况只在集成测试和浏览器测试中验证。Windows 未验证。
