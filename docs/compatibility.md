# 真实 Agent 兼容性

本页记录 HarnessHub 的全局接线在本机实际安装的 Agent 上是否有效：守护进程把 Agent 接到网关，Agent 以自己的非交互模式真实运行，经网关到达假上游，逐项检查对话、工具往返、流式、取消与用量。表格由一致性套件生成（`pnpm test:conformance`，即 `pnpm build` 后运行 `node tools/conformance.mjs`），套件不属于 `pnpm check`。设计见 [10 第 3.3 节](proposals/oss/10-engineering.md#33-三类一致性套件)的 Adapter 套件在线部分。

## 怎样运行

每个 Agent 一个用例（[tests/conformance/agents.test.ts](../tests/conformance/agents.test.ts)），在 PATH 中找不到该 Agent（cmux 等包装器的目录不算）时跳过并记为未安装：

1. **沙箱**（[support.ts](../tests/conformance/support.ts)）：临时目录中的 HOME、XDG 目录、TMPDIR 与工作目录；Agent 的环境从空开始构造，只有 PATH（Agent 所在目录、本 Node 的目录与系统目录）、语言与终端变量；`HTTP(S)_PROXY`、`ALL_PROXY` 指向被拒绝的回环端口，`NO_PROXY=127.0.0.1,localhost`。Agent 在 macOS 的 Seatbelt 配置（`sandbox-exec`）下运行：除网关端口外拒绝一切外连，拒绝沙箱目录之外的一切写入，拒绝访问钥匙串服务。因此 Agent 无法联网、读不到本账户保存的登录凭据、写不到真实的 home。没有这种沙箱的平台（Linux、Windows）上整个套件跳过。
2. **守护进程**：进程内 `startHub`，`HH_OFFLINE=1`、文件秘密后端，`wiringHome` 为沙箱 HOME 与上述环境。上游是 `tools/fake-provider` 的严格模式，Chat Completions，合成 Key；它按提示中的标记（`[hh:chat]`、`[hh:tools]`、`[hh:cancel]`）选择脚本回合，每个回答都报告同样的用量（输入 1200，输出 80，其中推理 30）。上游拒绝 OpenAI 独有的字段，provider 因此带 `drop-fields` 补丁去掉 `stream_options`（网关为取得用量总会请求）、`parallel_tool_calls` 与 `store`。
3. **接线**：经 `/api/v1/agents` 的预览与接线把 Agent 接到 `fake/upstream-sim`。注释可用的格式（TOML、YAML、dotenv）先写入一行用户自己的内容。
4. **运行**：Agent 的非交互模式（`claude -p`、`codex exec --skip-git-repo-check`、`gemini -p`、`opencode run`、`pi -p`、`hermes chat -Q -q`、`mimo run`）在临时工作目录中运行三次，每次硬超时 120 秒，结束后整个进程组被终止。不使用任何关闭 Agent 安全确认的参数。
5. **判定**，每项一列：
   - **Chat**：上游答复随机的 `PONG-…`。网关账本中有该 Agent 的 `agent:` Key 发出的调用、上游收到请求、Agent 输出了这个词，为“✓”（接线已验证）；请求带着 Agent 的 Key 到达网关、但被上游拒绝或答复没有输出，为“partial”并写明原因；没有任何请求到达网关为“blocked”。Chat 不是 ✓ 时其余各项不运行。
   - **Tools**：工作目录中放一个写有随机 `TOKEN-…` 的文件。上游第一次回答调用该 Agent 自己的读取工具（Claude Code 的 `Read`、Gemini 与 Hermes 的 `read_file`、OpenCode 与 Pi 的 `read`、Codex 的 `exec_command` 执行 `cat`），只有当下一次请求的工具结果里有这个 token 时才在答复中说出它。Agent 输出了 token、账本中至少两条成功的调用，为 ✓。工具调用与结果完成了往返、但结果里没有 token，为 partial 并写明原因。
   - **Stream**：Agent 请求流式的调用在账本中记为流式并有首字节时间（`timing.firstByteMs`），上游也收到了流式请求。
   - **Cancel**：上游每 400 毫秒发一个词，Agent 收到几个词后整个进程组被杀死；网关须关闭上游的响应（假上游记为中断，之后没有进行中的响应与计时器），账本中记下 499 与 `client_cancelled` 或 `engine_disconnected`。能否在 Agent 的输出中看到已流出的词也一并记录。
   - **Usage**：Chat 的每个回答在账本中为输入 1200、输出 50、推理 30（Chat 的输出含推理，账本把推理分开记），真实的 `hh usage --by key --json` 对该 Agent 的 Key 求和一致。
6. **诊断**：设置 `HARNESSHUB_TEST_CONFORMANCE_DEBUG=1` 时打印 Tools 那次运行的输出。
7. **还原**：取消接线后，接线写过的每个文件与接线前逐字节相同（Agent 运行时自己改写了的文件除外，此时只检查 HarnessHub 的条目已去掉，并记入表格）。

## 发现

- **Codex 的托管 web_search 工具**：Codex 0.144.5 每轮都附带托管的 `web_search` 工具，网关只能在原样转发到有该工具的 Responses provider 时服务它，转换到 Chat 等协议时整轮以 `unsupported_feature` 失败。接线因此在所选模型的 provider 不原生接收 Responses 时写入 `web_search = "disabled"`（[全局接线](global-wiring.md#codex-的两种模式)）。
- **Claude Code 2.1.289 直通 Anthropic 兼容上游**：同协议直通时，请求带有 Anthropic 的 beta 字段 `context_management`、`safeguards`、`output_config` 与对话中间的 `system` 角色消息（`anthropic-beta: mid-conversation-system-2026-04-07` 等），严格的 Anthropic 兼容上游拒绝它们（`context_management: Extra inputs are not permitted`）。网关的直通不去掉这些字段；套件因此让 Claude Code 经 Chat 上游（网关转换协议）运行。这是网关问题，不是接线问题。
- **Pi 经 Chat 直通**：Pi 对未知地址按 OpenAI 发送 `max_completion_tokens`（与 `store`）。Chat 直通原样转发，`max-tokens-field` 补丁只做相反方向的改名，严格上游拒绝 `max_completion_tokens`。可由网关在直通时规范化（或给 Pi 写 `compat.maxTokensField`，但 OpenAI 的推理模型需要 `max_completion_tokens`，而 OpenAI 预设没有这个补丁）。
- **MiMo Code**：请求中第二条消息也是 `system`，严格上游要求 system 只出现在第一条。OpenCode 1.1.21 的同类请求没有这个问题。
- **Gemini CLI 0.38.2 与代理**：设置了 `HTTPS_PROXY` 时，对回环网关的请求也走代理（不理会 `NO_PROXY`），代理拒绝连接即失败；套件对它不设代理变量，网络仍由沙箱限制。Gemini 没有可由接线设置的代理开关：代理只取自环境变量，`settings.json` 没有代理设置，`~/.gemini/.env` 不覆盖已有的环境变量。限制与绕过办法见[全局接线](global-wiring.md)。
- **Codex 的命令沙箱不能嵌套**：Codex 在自己的 Seatbelt 沙箱中执行命令，而 macOS 不允许已在沙箱中的进程再应用沙箱（`sandbox-exec: sandbox_apply: Operation not permitted`）。工具调用与结果经网关完成了往返，但 `cat` 没有运行；只有 `--sandbox danger-full-access` 才能让它运行，套件不使用这个参数，因此 Codex 的 Tools 为 partial。在用户自己的终端中（没有外层沙箱）不存在这个问题。
