# 第一阶段：统一 Harness 聚合网关

日期：2026-10-09。状态：需求已由用户明确，以下范围细化与验收为设计建议。

## 1. 用户要得到的产品

用户面向 HarnessGateway 的一个入口持续对话或发送命令。默认由网关根据当前任务、约束、能力和证据选择合适的 Harness；用户需要时可指定执行者。管理员负责接入、增加、停用和移除 Harness，普通使用者不必理解厂商配置与协议差异。

用户的公共 Session 由网关拥有。一次 Session 可以先用 Harness A，再换 B，再回 A；也可以保留 Harness、改换 Provider/模型。公共对话、工作进展与成果保持关联。原生会话能否恢复、模型能否原地更换、工具能否受控都必须由适配器证明，不能由产品口号推断。

“最佳”定义为在给定策略、任务类别、版本、预算和已有评测证据下的最佳可用候选。没有质量证据时只声称满足约束与策略偏好，不声称任务质量最优。

## 2. 基线假设

- 首阶段本机单用户守护进程；界面、CLI 与 SDK 共享认证后的应用服务。远程多租户、集群调度不是默认范围。
- 当前以本机核心为目标，其他平台、发布与多发行版兼容后置。记录实际版本和证据，不虚构支持承诺。
- 首个完整验收使用两个真实 Harness、两个可兼容模型目标。先检测当前安装，再用 OpenCode ACP 与 Codex App Server 等候选接通最小链路；按使用到的能力逐项验证。
- 公共名词采用 Session；Chat 是其用户交互视图。原生 Session/Thread 始终称 BackendBinding，不复用公共 ID。
- 第一版同一公共 Session 只有一个有执行权的 Turn；同一受管理工作区只有一个写执行者。多 Session 可以有界并行。

## 3. 第一阶段必须覆盖

统一入口和公共历史；Harness 注册、版本与排空；能力检查；用户指定与自动路由；命令和文本接收；执行、工具与权限；期限、取消、清理、恢复；上下文接续；手动和自动建议的安全切换；Provider/模型独立选择；持久事件、结果与产物；客户端与程序接口一致。

自动切换只发生在受控交接边界。运行中允许提出切换请求；不自动把未知副作用、被中断的工具或旧进程搬给新 Harness。

## 4. 延后范围

不追求首版接入所有产品或完整模型协议互转。远程 A2A、AG-UI 入口、模型分类器、学习型路由、全模型预设库、订阅复用、图像/视频、工具市场、多 Agent 同时写同一工作区、团队多租户、Workflow 平台、评测产品界面均延后。必要的模型调用记录、权限和隔离责任不延后。

## 5. 对用户有意义的验收

同一个 Session：自动选择 A 处理任务；用户指定 B 接续；只改 Provider/模型继续；回到 A 能看懂 B 已完成的工作。每段都能追到上下文、实际执行者、调用、工作成果与状态。失败、取消、重启、目录停用、权限拒绝和交接失败都给出一致结果。

网关不会用“回复看起来成功”掩盖未知结果。执行正常结束、任务正确性、上下文接续等级和资源清理分别表达。
