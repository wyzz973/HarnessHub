# Relay v1 原型测量（spikes/relay）

> **原型，仅用于测量，不是实现。** 这里的代码只为给 [第一版架构](../../docs/proposals/relay/round3/v1-architecture.md)（下称 v1）的数据模型和性能目标找实测依据，不进入构建、测试或发布：`tsconfig.json:18` 的 `include` 只有 `src/**/*.ts` 与 `tests/**/*.ts`，`src/` 不得引用本目录。全部输入是合成数据，不含任何用户数据、对话内容或真实凭据。

基线：分支 `cc/relay-design`，基点 `07a0825`；文中 `file:line` 指该工作区的实际代码，`v1 §x`（附行号）指 `docs/proposals/relay/round3/v1-architecture.md`。标注：【实测】本目录脚本在本机跑出；【文档】v1 或代码里的常量；【推算】由实测或常量算出；【推断】由事实推出的判断；【建议】本原型的提议。

## 1. 目的

按 v1 §4–7、§10–11 的数据模型实现最小原型，并测七项：

1. 每个 Run 的派生记录（RunDigest）抽取耗时与字节数；
2. 256 Run、约 8 MiB 合成会话上标准档与完整档的投影加渲染耗时，以及同一输入渲染 100 次的 sha256 个数；
3. 各档交接单的字节数与 est/1 token 估算，S1 样例的实际大小；
4. 转义模糊测试 10,000 例；
5. 已知秘密精确匹配脱敏的吞吐与夹具漏检数；
6. （可选）`node:sqlite` 临时库里 `run.ended` 事务追加派生行的提交耗时增量；
7. （可选）本工作区只读执行工作区观测命令的耗时。

原型覆盖：(a) RunDigest 抽取，(b) 预算解析器，(c) 确定性投影与渲染（放得下就照录、放不下就分层、省略账目），(d) A→B→A 增量，(e) 全函数转义与围栏，(f) 已知秘密精确匹配（原值、JSON 转义、URL 编码）加少量形状规则。

## 5. 方法

- **合成数据**：S1、S2 按 v1 §5.6 的场景手工构造（用户原话、回复与命令输出取自文档样例本身）；256 Run 会话沿用 R6 的参数（256 轮、回复约 16 KB、输入约 1 KB、每轮 20 个工具、思考 4 KB、每 4 轮在 Claude Code 与 Codex 之间切换），公共快照序列化后 **7.87 MiB**【实测】；每轮的工具带内存中的 `NativeToolDetail`（输入、输出、diff，`src/contracts/control.ts:49–67` 的形状与上限），另有计划、审批、附件、产物、失败与结果未知的回合。12 个“已知秘密”由确定性伪随机生成，形状仿 `ANTHROPIC_API_KEY` 等环境值，其中一部分被回显进工具输出。
- **计时**：`process.hrtime` 单线程墙钟，每次调用单独计时，先预热；摘要 300 次/档（最坏剖面 100 次、病态剖面 30 次），渲染 300 次/档，脱敏 30 次/配置，SQLite 40–80 对，git 40 次/项。
- **渲染输入两种口径**：摘要对象已在内存；或每次从 256 行规范化 JSON 解析（模拟从 `relay_digests` 读取，不含 SQLite I/O，后者见测量 6）。消息正文取自内存中的快照（Runtime 执行路径手里本来就有）。
- **确定性**：同一输入渲染 100 次（每次重新解析摘要 JSON，排除对象复用），再起 3 个子进程（`TZ`/`LANG`/`LC_ALL` 分别为 UTC/C、Asia/Shanghai/zh_CN、America/Los_Angeles/en_US）各渲染一次，比 sha256。
- **模糊测试**：每例 1–4 轮，所有不可信字段由 60 个保留串（各种长度的反引号与波浪线、伪造的记录区定界符及其大小写/全角/空白变体、伪造的框架行与结束行（中英文、交接单/增量/重锚）、Markdown 标题与表格、C0、DEL、C1、双向与零宽字符、标签字符、变体选择符、CR、CRLF、U+2028/2029 等）和随机词拼成，每个字段在头、中、尾各嵌一个哨兵 `ZQ<id>A/B/C`。70% 为新绑定的交接单（brief/standard/full 档随机，目标 Codex/dsh/Claude 轮换），30% 为 A→B→A 增量；当前输入（可信、无哨兵）也拼入保留串，20% 以保留串开头。检查器不复用渲染器代码：按 CommonMark 规则解析代码围栏，成对解析行内代码，逐行解析记录区定界符并重算 `b`，再把每个哨兵定位到所在槽位。
- **变异对照**：故意弄坏 5 条转义规则（围栏长度恒为 3、不改写 `<<<HH-`、不给框架标记行加前缀、行内保留反引号、行内保留换行），各跑 1,000 例，检查器必须报错（AGENTS.md：新增检查要有无效样例证明能拒绝错误）。
- **脱敏**：1 MiB 合成文本（中英文与代码混排），每 4 KiB 插入一个秘密（轮流三种形式，共 255 处），50 个秘密展开为 70 个不同模式；3 种引擎（按长度降序的字面量交替正则、Aho–Corasick、逐个 indexOf）× 2 种视图（原文、骨架：匹配时跳过 C0/DEL 与不可见字符，再映射回原文）× 形状规则开关。夹具 1,301 例：50 个秘密 × 三种形式 × 8 种上下文（与汉字相邻、整段、紧邻重复、ANSI 着色、CRLF、`export NAME=`、`Bearer`、首尾各一处）+ JSON 文档 + URL 查询串 + 前缀重叠（A 与 A+"XYZ123" 都是已知秘密）。
- **SQLite**：临时目录里新建库，PRAGMA 与表结构照 `src/infrastructure/session/sqlite-store.ts:247`、`:463–465`，`relay_digests` 照 v1 §14.1（`STRICT`、`json_valid`、`≤65536` 字节检查）；每次提交整份重写快照并写一条事件（同现状 `sqlite-store.ts:359`），对照组再插一行摘要（真实的 256 行摘要 JSON，中位 5,344 B）；ABBA 交替成对计时。只测 SQL 层，不含 `parseSession`、`assertSessionTransition` 等应用层校验。
- **git**：白名单环境只有 `PATH`、`HOME`（v1 §1 不许建空 HOME）、`LC_ALL=C`、`GIT_OPTIONAL_LOCKS=0`、`GIT_TERMINAL_PROMPT=0`；命令按任务原样，另测 diff 加 `-c core.fsmonitor=false`；“观测”= 两条命令并行、等两者结束。

### 6.2 补充数据

- **摘要按工具数**【实测】（p50 / p95 ms，字节 p95）：0 个 0.065 / 0.144、2,884 B；16 个 0.130 / 0.208、7,414 B；64 个 0.310 / 0.431、14,907 B；128 个 0.447 / 0.578、16,782 B；中文为主 64 个 0.291 / 0.383、15,566 B；最坏剖面字节 p95 30,656 B。256 Run 会话的 256 行摘要共 1,431 KiB，单行中位 5,344 B、最大 9,978 B。
- **渲染耗时的构成**【实测】：只解析 256 行摘要 JSON 就要 2.32 / 2.48 ms（p50 / p95），占“含解析”口径的一半以上；投影与渲染本身 1.3–2.2 ms。S1 渲染 0.055 / 0.070 ms；增量 p95 0.05–0.38 ms（离开 2–128 轮）。
- **折叠结果**【实测】（256 Run）：标准档 = 头部 1 行 + 249 轮合并为区间行（段长 32）+ 锚点单行 6 + 末单元照录 1；完整档 = 区间行 243 轮（段长 8）+ 精简 9 + 照录 3 + 单行 1；§2 逐字列出 5 条用户原话（必含块份额内），其余 251 条只在单行里出现前 120 字或只计数。五档的省略账目恒等式（每类 已渲染 + 已省略 = 全部，折叠项覆盖每个外来单元恰好一次）全部成立。
- **框架模板**【实测】：v1 §5.4 的中文模板按 est/1 为 451 token（系数 1.0）/ 586（1.3），英文 431 / 560；v1 写“约 330 / 约 300 token（推算）”，J3 M9 要求固定前言 ≤ 400 token。
- **离开轮数与增量**【实测】：2 轮 1,326 token（上限 1,500）；8 轮 2,420（上限扩到 4,000）；32 轮 3,845；128 轮 3,932 且 89 条用户原话只计数。
- **预算向量**【文档常量 + 原型假设的窗口与价格，`bench-budget.ts`】：窗口未知按 128k → 标准档 6,400，用户选完整档也只有 6,400（不可信上限随之变成 6,400，即整单都可以是不可信文本）；Codex 400k → 8,000；GPT-5.5 400k 默认档被费用上限压到 4,494（R̂=80、k̂=0 时生命期单价 $44.5/百万 token，价格取自 R6 的 `cost-model.mjs`，本原型未重新核实）；dsh 1M → 完整档 32,000；Claude Haiku 5.5 新会话 8,000，返回时已用 75k → 价格悬崖使 hardCap = −6,000 → `RELAY_INPUT_LIMIT`；16k 窗口的本地模型 → 800 < 下限 1,200 → `RELAY_INPUT_LIMIT`；Codex 原话 1,040,000 字符 → 交接单只剩 4,480 字符；1,046,000 字符 → 启动前 `RELAY_INPUT_LIMIT`。按 5%·W，标准档要 W ≥ 160k，保真 ≥ 320k，完整 ≥ 640k 才不被压低【推算】。
- **脱敏引擎**【实测】：Aho–Corasick 1.67 ms/MiB、逐个 indexOf 3.00 ms/MiB，都慢于交替正则；骨架视图多约 0.6 ms/MiB，形状规则多约 0.9–1.1 ms/MiB。
- **对抗用例**【实测，不计入“应为 0”】：v1 三种形式漏掉小写百分号编码、表单编码（`+` 表示空格）、JSON 的 `\/` 与 `\uXXXX`、双重 URL 编码；原型的扩展形式（每个秘密 8 种形式）能补上这五种，base64 与 HTML 实体仍漏。零宽字符切开的秘密：原文视图漏，骨架视图命中。NUL 切开的秘密：按 v1 顺序（先脱敏、后删 C0）用原文视图会在删除 C0 后重新拼成原值流出；先删 C0 再脱敏、或用骨架视图都能命中。先截断再脱敏：截断点落在秘密中间时片段流出（所有配置都漏），所以截断必须在脱敏之后。
- **git 执行面**【实测，合成仓库】：`--attr-source=<空树>` 加 `-c core.attributesFile=/dev/null` 能挡住工作树里的 `.gitattributes`，但 `.git/info/attributes` 里的过滤属性仍会触发（见 `results.json` 的 `raw.git.safetyProbe`）；对具体驱动名加 `-c filter.<name>.clean=` 能挡住；diff 加 `-c core.fsmonitor=false` 后 fsmonitor 钩子 0 次；`GIT_OPTIONAL_LOCKS=0` 时 `post-index-change` 钩子 0 次（对照组设为 1 时运行 1 次）。

## 7. 发现（对 v1 的影响）

**F1 必含块的用户原话没有条数上限，长会话的新目标会在启动前失败。**【实测】按 v1 §6.3 第 568–570 行，`mustHave` 含“首条 + 自上次送达以来的用户消息”，`mustHave > budget.T` 即 `blocked(RELAY_INPUT_LIMIT)`；新绑定没有送达水位，“上次送达以来”就是全部历史，256 Run 会话（每条输入约 1 KB）算出 83,112 token，远超标准档 8,000。【推断】这与 v1 §0 第 41 行“历史再长也只分层，不失败”和 §9 第 705 行“只有必需块 + 原话超过通道硬上限才 `RELAY_INPUT_LIMIT`”冲突。另【实测】一条 1,900 字的中文首条消息按 est/1 就是 1,900–2,470 token，加上 451–586 token 的框架，已超过只交目标档的 2,000 与 `MUST_HAVE_CAP` 的大部分。【原型的做法】`userWords: "bounded"`：§2 先放首条，再按新到旧放“上次送达以来”的消息，份额为 `min(MUST_HAVE_CAP, 0.5 × 档上限) − 框架与状态`（只交目标档用满整档），放不下的在单行里留前 120 字或只计数；`"literal"` 保留 v1 字面行为，用于对照。【建议】v1 明确 fresh 目标的“上次送达以来”的含义与上限，并让 `MUST_HAVE_CAP` 与 §5.1 的截断上限按 est/1 自洽（中文 2,000 字 ≈ 2,000 token）。

**F2 长时间离开后的增量放不下全部用户原话。**【实测】离开 128 轮时，即便上限扩到 `DELTA_USER_CAP` 4,000，也只能逐字放 39 条，89 条只计数，违反 J3 M8 的“不得省略”。【建议】v1 规定此时的降级：例如超过 `DELTA_USER_CAP` 就改发完整交接单（kind=packet，复用 F1 的份额规则），或明确允许按新到旧截断并在框架里写明。

**F3 观测命令会执行仓库配置的外部程序。**【实测，git 2.54.0】在合成仓库里，`git diff --numstat --no-ext-diff --no-textconv` 对每个改动文件运行 `.git/config` 里的 `filter.<driver>.clean`（2 次）；`git -c core.fsmonitor=false status --porcelain=v2 -z` 在文件只改 mtime、内容不变时运行 clean 过滤器 1 次；任务给出的 diff 命令没有 `-c core.fsmonitor=false`，会运行 `core.fsmonitor` 指向的钩子 2 次。v1 §10.6 第 774 行把“另一个 Harness 写 `.git/config`”列为威胁，控制里只有 fsmonitor、ext-diff、textconv、`GIT_OPTIONAL_LOCKS` 与“不运行 hook”，没有过滤器。【建议】(1) diff 也加 `-c core.fsmonitor=false`；(2) 观测前先只读列出 `filter.*` 驱动名（`git config --get-regexp '^filter\.'`，含 include），对每个驱动传 `-c filter.<name>.clean= -c filter.<name>.process=`（`clean=` 已实测有效；`process=` 与 include 场景未测）；(3) 加 `--attr-source=<空树> -c core.attributesFile=/dev/null` 只能挡住工作树的 `.gitattributes`，`.git/info/attributes` 仍会触发，不能单独依赖；(4) 进 RelayConformance 或单元测试：合成仓库 + 标记文件，断言 0 次。

**F4 原始 Harness 返回时，v1 状态机给不出 S2 的增量。**【文档】v1 §7.2 第 615–627 行没有 fresh → synced 的边：从未收到过交接单的绑定，自己跑多少回合都停在 fresh；§6.3 第 565 行于是给它 `kind = "packet"`。§5.6 第 454 行的增量样例写“规则与你之前收到的交接单 relay-7q2m… 相同”，§16 第 964 行写“回 Claude 时 synced”，但在 S1/S2 的故事里 relay-7q2m… 是发给接手方的，原始的 Claude Code 从未收到。【原型的做法】(a) 补一行转换：fresh 绑定在本纪元执行了不带包、且当时 need = ∅ 的回合并已记录 → `synced{basis: own_run, throughSeq: contextThroughSeq}`（`proto/delivery.ts`）；(b) 没有基准交接单的增量带上全部 7 条阅读约定（第 3 条改指第 9 节，因为增量里没有第 2 节）。代价【实测】：S2 增量 1,095 token，带基准时 642 token。【建议】v1 补这条边与“无基准增量”的框架。

**F5 v1 列出的转义集合有缺口。**【实测，模糊测试 4c】核心性质（定界符恰好一次、不可信字节不出槽位）在 v1 规则下 0 违例，但 v1 §5.2 第 296 行的字面规则会漏：(1) 不可见字符只列了 U+202A–202E、U+2066–2069、U+200B–200D、U+2060、U+FEFF，没有 U+200E/U+200F（LRM/RLM）、U+061C、U+00AD、标签字符 U+E0000–E007F、变体选择符、U+2028/2029、C1（含 U+0085）——8,519 / 9,433 例残留；(2) 只给以“〔HarnessHub”“〔交接材料结束”开头的行加前缀，增量与重锚的结束行（“〔交接更新结束”“〔重锚结束”，见 §5.6 样例）、英文模板的 `[End of handoff …]` 以及前导空白或不可见字符之后的标记都不处理——5,744 例；(3) 只改写字面的 `<<<HH-`，大小写、全角、中间空白的变体保留——3,329 例。原型的扩展规则（`EXTENDED_RULES`）把这三类都清到 0；代价【实测，单独运行，不在 results.json】：256 Run 标准档渲染 p50 多约 0.05–0.09 ms、完整档多约 0.15 ms，摘要每条多约 0.02 ms。另【文档】框架第 6 条约定本身写着 `<<<HH-DATA … BEGIN>>>`（§5.4 第 332 行），所以“保留串只出现在定界符行”不能作为严格不变量，检查器对这一行做了白名单。【建议】`relay/1` 的转义规则采用扩展集合，并把所有模板的框架行与结束行前缀列入同一张表。

**F6 首行逐字前缀会影响 Markdown 结构。**【实测】用户当前输入以 ```` ``` ```` 开头时，首行（v1 §5.1 第 278 行“逐字前缀”）在 Markdown 里会开出一个代码围栏，把框架行吞进去（177 例）；首行含奇数个反引号时会与下一行的行内代码配对（730 例）。【建议】首行对开头的围栏与框架标记做最小处理（行首围栏改写，或在首行与框架行之间加空行切断段落），原生标题只取原话本身的需求不受影响；需要真机核对 Codex 的 `thread.preview` 与 ACP 标题（v1 §13.3）。

**F7 脱敏的执行顺序。**【实测】v1 §5.2 第 300 行规定“脱敏在 N2 之后、N3 之前”，即先脱敏、后删 C0：一个被 NUL 切开的秘密在原文视图下躲过精确匹配，删 C0 后又拼回原值流出。截断（头尾、尾部 600 字、输出末尾 20 行）若在脱敏之前，切点落在秘密中间时片段流出。原型的顺序是：规范化换行与 CR → 删 C0 → 脱敏（窗口两侧各多留 8 KiB）→ 截断 → 不可见字符可见化与保留串改写 → 围栏。【建议】v1 把顺序改为“删字符类变换在脱敏之前，截断在脱敏之后”，并考虑骨架视图（实测只多 0.6 ms/MiB，能命中被零宽字符或 C0 切开的秘密）；三种形式之外的编码按需扩展（扩展形式实测能补上 5 种，base64 与 HTML 实体仍需另想办法或明确不承诺）。

**F8 逐字段上限之和超过 64 KiB。**【推算】v1 §4 第 212–219 行的上限按“字”计；全中文时 narrated 40×400 字、commands 16×400 字、failures 3×(200+400+1,200) 字、files 64×路径（原型取 256 字）、计划 20×200 字、审批与附件与产物各 16×200 字等合计 181,512 B，约为 64 KiB 的 2.8 倍。【实测】原型在最后加了一步确定性收紧（`proto/digest.ts` 的 `bound()`），病态剖面收紧后 29,790 B、p95 1.51 ms。【建议】v1 写明这一步（v1 §6.4 第 593 行已有“先按全部上限截断再写”，但逐字段上限本身不保证总量）以及收紧顺序。

**F9 RunDigest 的几处形状问题。**【推断，原型据此偏离】(1) narrated 与 size 依赖框架语言，但语言要到交接时按当前输入才定（§5.4 第 317 行）——原型把 narrated 存成与语言无关的结构，size 按中英各存一份；(2) `cumulative` 只有 runs、toolCalls、replyChars、userChars、failures，省略账目要 O(1) 还需要 tool_output、diff、external_output、thinking、attachment、approval、reply 的前缀和——原型补齐；(3) 成功命令的输出尾部（G1 附末尾 3 行）在 RunDigest 类型里没有位置——原型放进 `commands[].tail`；(4) §5.1 第 284 行的“之后另有修改（mtime 晚于该回合结束）”需要 mtime，而 §4 第 261 行 git 观测的 files 没有 mtime——原型未实现这一标注；(5) 摘要的尺寸按未脱敏文本算，已知秘密集合在之后变化时尺寸会过期——原型在渲染后用最终 est/1 复核，超出就收紧重排（本次测量中没有触发）。

**F10 渲染成本主要在解析摘要。**【实测】标准档含解析 3.84 ms 中，解析 256 行（1,431 KiB）占 2.32 ms，投影与渲染 1.3 ms；离 p50 ≤ 5 ms 的余量在完整档只有 0.41 ms。【建议】`relay_digests` 另存一列小的索引 JSON（seq、executedOn、status、尺寸三元组、不可信尺寸、前缀和、G3 所需字段），定档只解析索引，照录与精简的少数单元再解析全文，解析量随预算而不是随历史增长；或 Coordinator 在内存里按会话缓存解析后的摘要（受预取 LRU 的上限约束）。

**F11 预算解析器的几处语义。**【实测，见 6.2】(1) 窗口未知时 5%·128k 把所有 ≥ 标准的档压到 6,400，用户显式选的保真与完整档实际不可得，`untrustedCap = min(档位不可信上限, T)` 还会让被压低的完整档允许整单都是不可信文本——【建议】被压低时不可信上限按档位比例缩放（如 24,000/32,000 × T）或取标准档的比例；(2) 价格悬崖让返回时上下文已较满的 Haiku 绑定直接 `RELAY_INPUT_LIMIT`，连 1,500 token 的增量也发不了——【建议】悬崖只作为告警或只压低档位，不进 hardCap；(3) GPT-5.5 的默认档被费用上限压到 4,494，完全取决于 R̂ 的假设；(4) §6.2 第 542 行 `capWindow` 的条件两支都是 0.05；第 555 行 est/1 把 factor 乘在 ceil 外面，系数 1.3 时得到小数（原型改为 `ceil((…) × factor)`）；第 551 行 `byteCap` 对 `maxInput.unit = "chars"` 的 Driver（Codex）其实是字符数（原型按单位分别计算）。

**F12 存储增量很小，提交耗时由快照重写决定。**【实测】摘要行（中位 5.3 KB）在 `run.ended` 事务里的增量 p50 0.05–0.06 ms、p95 约 0.7 ms，WAL 每行 28,840 B（7 个页：数据页加主键与 `UNIQUE(session_id, run_index)` 两个索引）；SQL 层整份重写 8 MiB 快照约 9.0 ms。【推断】R6 测到的每次提交约 144 ms（v1 §11.1 第 787 行）主要在 SQL 之外（解析与校验），与 v1 §11.2 前置的存储优化方向一致；本原型没有测应用层。

## 8. 简化与局限

**未实现**：重锚包与重发包（resend、supersedes）；钉住与附言只作为输入渲染进 §2（没有命令、事件与写入时的上限检查）；用户编辑、同意、目的厂商；分支与导入的来源历史（origin）；交出方说明（§8 节位）；E1/E2/E3 证据采集、`verifyDelivered`、suspect/rewind/clear 与迁移；余量分配第 ③ 步（中段单行附用户原话）；“之后另有修改”；键名类脱敏规则（`masking.ts:11–13`）、熵规则与排除表、误报放行；HMAC 安装密钥的生成与存储（用固定的合成测试密钥）；预取 LRU；非 git 工作区观测。

**与 v1 类型的偏离**（都在 `proto/types.ts` 注明）：narrated 改为结构化；size 按语言各一份并另存 untrusted 与 userSize；commands 增加 `tail` 与 `failed`；`cumulative` 增加 7 类；`user.head`、`tools` 的若干计数；`DeliveredMark.basis` 增加 `own_run`；清单头增加 `rendered`、`totals`、`escapeRules`（参与 ID 派生）。

**原型参数（不是 v1 常量）**：必含块份额 `min(MUST_HAVE_CAP, 0.5 × 档上限)`；§5/§6/§7 的份额 15% / 10% / 5%；§4 份额 25% 且不超过不可信余量的 50%，条数与尾长按 3×1,200 → 2×1,200 → 2×600 → 1×600 → 1×300 递减；末单元回复同时受 0.6 × 余量约束，放不下照录时退为精简；窗口脱敏的余量 8 KiB；尺寸计算只看回复前 256 KiB；工具输入 >4 KiB 时只在前 4 KiB 里按键名取字段；记录区按节分开（§3、§4、§6 各一个），v1 第 296 行写“整体包在”一个区里，但 §5 位于 §4 与 §6 之间，一个区包不住。

**测量本身的局限**：
- token 全是 est/1 估算，v1 要求的分词器校准（p90 误差 ≤20%）没有做；不同系数（1.0 / 1.3）下的同一份正文相差 30%。
- 渲染输入里的摘要与消息都在内存或内存中的 JSON；没有走真实 Runtime、Store 或 Driver，也没有测 `contextReadyAt` 链路上的其他步骤。
- 256 Run 会话是均匀的合成画像（每轮输入约 1 KB），真实会话的用户消息长短不一，F1 的数字会随之变化，但“条数无上限”的结论不变。
- 模糊测试的保留串表是本原型列的；检查器独立于渲染器，但由同一作者编写。565 例原样发送是生成器的副产物（目标 Harness 恰好执行了全部回合，没有外来事实），不进入检查。
- 测量 7 的工作区只有 495 个跟踪文件，不足 v1 目标里的 3k / 2 万文件；执行面核对只测了 clean 过滤器、fsmonitor 与 `post-index-change`，没有测 `filter.<driver>.process`、include 的配置、子模块与 `core.hooksPath`。
- SQLite 只测 SQL 层；本机 macOS 上 `synchronous=FULL` 不用 `F_FULLFSYNC`（R6 已指出），持久性与 Linux 不同，提交耗时不能直接外推。
- 不涉及 Windows（项目当前只做 macOS）。
- 本目录没有经过 `tsc` 类型检查（工作区没有安装依赖，按任务不安装）；Node 的 type stripping 只剥离类型、不检查。
