# 性能基准

`pnpm bench`（[bench.ts](bench.ts)）在回环上用严格假上游测量网关，对照 [03 第 11 节](../../docs/proposals/oss/03-model-plane.md#11-验证要求)的目标写出 `dist/bench/bench.json` 与 `bench.md`，只报告，不设门槛。被测的守护进程在自己的进程中运行（[hub.ts](hub.ts)，带 `--expose-gc`），基准经 IPC 读取它的 CPU 时间与内存，并在完整垃圾回收之后记录启动时与延迟测量之后的内存。

## 守护进程的内存

2026-10-04 在 macOS arm64、Node 24.20.0 上，连续发出 6000 次延迟调用后常驻内存约 330 MB，而 V8 堆只有约 81 MB。按 2000 次一批的直通 Chat 调用逐批测量（`process.memoryUsage()`、`v8.getHeapSpaceStatistics()`、两份堆快照之差、`vmmap --summary`），结果是一处泄漏、两项有上限的增长，以及常驻内存本身的口径。

**泄漏（已修复）**：读取入站请求体时用 `AbortSignal.any([信号, AbortSignal.timeout(120 s)])` 设期限。Node 24.20 的 `AbortSignal.any` 把每个传入的超时信号放进内部的常驻集合，直到它触发才移除，因此每个请求在结束后仍保留约 0.7 KB（计时器、两个信号、WeakRef、WeakCell、Set 与闭包）整整 120 秒。两份快照之间的 12000 次调用恰好多出 12000 个 `Timeout`、`AbortSignal`、`WeakRef` 与 `Set`，合计约 8.6 MB；130 秒后全部消失。持续每秒 100 个请求时约占 9 MB，每秒 1000 个时约 90 MB。修复后改用由调用方清除的计时器（`deadline()`），回收后的堆在 16000 次调用中保持在 33–35 MB，快照之差中没有逐请求的对象；`count_tokens` 与搜索调用改用同一方式。[request-body.test.ts](../../packages/gateway/test/request-body.test.ts) 在修复前失败（2000 次读取后留下 2000 个信号）。

**有上限的增长与口径**：

| 来源 | 测量 | 说明 |
|---|---|---|
| V8 新生代 | 已提交的新生代从 64 MB 增到 128 MB | 持续分配时 V8 把半空间扩大到按堆上限决定的最大值（堆上限 4 GB 时每个半空间 64 MB），空闲回收后缩回（20 秒空闲后已提交堆从 169 MB 降到 43 MB）；以 `--max-semi-space-size=16` 运行时新生代保持 32 MB，2000 次调用后常驻内存为 231 MB 而不是 286 MB |
| 分配器页 | 默认 malloc 区常驻从 21 MB 增到 68 MB，其中在用的分配只从 8.6 MB 增到 12.4 MB（碎片 82%） | V8 优化编译热点代码时 malloc 的峰值约 47 MB，释放后页面留在分配器中；macOS 之后回收一部分（再 8000 次调用后脏页 34 MB） |
| 常驻内存的口径 | 常驻内存在 2000 次调用后约 285 MB，10000 次后 274 MB；物理占用（`vmmap`）从启动时的 150 MB 到 254 MB，之后回落到 209 MB | macOS 的常驻内存包含已释放而内核尚未收回的页，物理占用更接近实际占用 |

ArrayBuffer 与 external 内存始终只有 4–5 MB，因此不是 undici 的连接缓冲、fastify 的请求体或 zlib；malloc 区中在用的分配合计约 12 MB，SQLite 的页缓存不显著。常驻内存在首批调用后不再随调用次数增长。

基准的 `bench.md` 给出完整回收后的数值：启动时与 4400 次网关调用之后的常驻内存、在用堆与新生代。修复前同一基准中回收后的在用堆从 32 MB 增到 38 MB，修复后增到 35 MB（其余是编译代码与反馈数据，之后不再增长）。

未验证：Linux（glibc 的 malloc 归还页的方式不同）与 Windows；仍以 `AbortSignal.any` 搭配 `AbortSignal.timeout` 的低频调用（图像生成、provider 体检、目录刷新、OTLP 导出）每次调用会在各自的超时内保留同样的对象。

## 账本提交

账本写入（`appendModelCall`）是同步的 SQLite 写入（WAL，`synchronous = FULL`），每次提交都要写 WAL 并 fsync。原来每条记录各自一个事务，200 条同时排队时依次提交，最后一条要等前面所有提交完成：2026-10-04 的基准中这一项 p99 为 15–17 ms（负载高时一次为 68 ms），超过 5 ms 的目标。

2026-10-05 在 macOS arm64、Node 24.20.0 上逐项测量了一条记录的开销：校验与序列化 0.002 ms，准备语句 0.003 ms，自动提交的插入 0.054 ms（p50）；同样 200 条放在一个事务中只需 1.4 ms（p50），而逐条提交需要 17 ms。开销几乎都在每次提交上，因此改为组提交：在事件循环进入 check 阶段之前到达的记录（一次突发，或同一轮 I/O 中结束的多个调用）合成一个事务，按到达顺序写入，事务持久之后各自的 promise 才兑现，先提交后发布不变。事务失败时回滚并逐条重写，只有单独也失败的记录被拒绝；`close()` 先提交等待中的一组。打开 `fullfsync`（macOS 上真正落盘）时单次提交约 3 ms，Linux 上的 fsync 同样昂贵，组提交在这些情况下省得更多。

| 基准项（`pnpm bench`） | 之前 | 之后 |
|---|---|---|
| 逐条提交 p50 / p99 | 0.060–0.086 / 0.42–0.62 ms | 0.070–0.072 / 0.33–0.45 ms |
| 200 条同时排队，提交完成 p99 / 最大 | 15.2–68.6 / 15.2–68.6 ms | 2.9–3.5 / 2.9–3.5 ms |

逐条提交多了一次事件循环的 check 阶段，p50 约多 0.01 ms，p99 没有变差。

上表的“之后”只取 5 次突发，低估了尾部：WAL 达到自动检查点的页数（默认 1000 页）时，触发它的那次提交同时做检查点（把页写回数据库并 fsync），大约每 10 次突发有一次。2026-10-05 起提交不再做检查点：写入连接关闭自动检查点，由一个工作线程用自己的连接在有新写入时每 100 ms 做一次 `PASSIVE` 检查点（[wal-checkpoints.ts](../../packages/store/src/storage/wal-checkpoints.ts)，取舍见 [store 说明](../../packages/store/README.md)）。同一台机器上连续 150 次 200 条的突发、前后交替各三次（1 分钟负载约 3.5）：

| 150 次突发，提交完成 | p50 | p90 | p99 | 最大 |
|---|---|---|---|---|
| 提交路径上的自动检查点（之前） | 1.89–1.95 ms | 7.6–8.4 ms | 9.7–10.3 ms | 11.0–11.8 ms |
| 工作线程的检查点（之后） | 2.32–2.34 ms | 3.6–4.0 ms | 5.4–5.6 ms | 5.5–8.0 ms |

p99 约减半，仍略高于 5 ms 的目标；p50 多约 0.4 ms，因为 WAL 在两次检查点之间更大，提交也与工作线程的检查点争用磁盘（同时保留提交路径上的自动检查点时 p50 回到 1.9 ms，但 p99 又到 10–13 ms）。逐条提交（基准的 2000 次）同样是中位数稍高、尾部更低：p50 0.069 → 0.103 ms，p99 0.32 → 0.18 ms。检查点的 I/O 不再阻塞事件循环。基准中只取 5 次突发的那一行仍然摇摆：之后的一次运行在负载升到 6 时为 6.05 ms（超过目标），因为恰有一次检查点与突发同时进行。进程在检查点进行中被杀死、重新打开后已兑现的写入都在，数据库通过完整性检查（[model-plane-store.test.ts](../integration/model-plane-store.test.ts)）。

## 回归检查

### 2026-10-05：`34f8189` 对比 `fa4c33d`

自上次基准（`fa4c33d`，10 月 4 日）以来，main 加入了组提交、并发位的按 Key 公平与排队期限、每次失败时的去回显分类、安全拒绝的转移规则、每次上游请求经过的出站代理分发器、裸名称解析、Credential 模型过滤、OTLP 观察与用量提醒。在 macOS arm64（Apple M5 Pro × 18）、Node 24.20.0 上，每次运行前 1 分钟负载低于 5（运行时 2.8–4.8；本机同时有其他代理在跑检查）。

`34f8189` 单独运行三次，与上次的数值对照 [03 第 11 节](../../docs/proposals/oss/03-model-plane.md#11-验证要求)的目标：

| 基准项 | 目标 | `fa4c33d` | `34f8189`（三次） |
|---|---|---|---|
| 非流式附加延迟 p99，直通 | ≤ 10 ms | 5.76 | 4.46 / 5.00 / 5.25 |
| 首字节附加延迟 p99，直通 | ≤ 15 ms | 3.85 | 3.97 / 4.32 / 4.43 |
| 非流式附加延迟 p99，转换 | ≤ 10 ms | 5.58 | 4.84 / 5.47 / 5.45 |
| 首字节附加延迟 p99，转换 | ≤ 15 ms | 3.70 | 4.17 / 4.24 / 4.56 |
| 单块成本 p99（最差的方向） | ≤ 50 µs | 2.96 µs | 2.96 / 2.83 / 2.92 µs |
| 200 个流，转换：守护进程 CPU | ≤ 1 核 | 0.247 | 0.283 / 0.287 / 0.306 |
| 200 个流，直通：守护进程 CPU | ≤ 1 核 | 0.190 | 0.273 / 0.269 / 0.232 |
| 200 个流：峰值常驻内存 | ≤ 400 MB | 299 | 304 / 302 / 307 |
| 逐条提交 p99 | ≤ 5 ms | 0.337 | 0.329 / 0.351 / 0.323 |
| 200 条同时排队 p99 | ≤ 5 ms | 2.85 | 5.50 / 2.85 / 2.95 |
| 启动后回收后的在用堆 | — | 33 MB | 37 / 37 / 37 MB |

CPU 看起来高了约 20%，为了分开代码与机器，把两个提交在同一时段交替运行各三次（`fa4c33d` 建在单独的 worktree 中），中位数：非流式附加延迟 p50 直通 2.63 → 2.64 ms、转换 2.72 → 2.72 ms，p99 5.03 → 5.10 ms、5.38 → 5.36 ms；首字节 p99 4.22 → 4.20 ms、4.25 → 4.27 ms；200 个流的 CPU 转换 0.29 → 0.30 核、直通 0.26 → 0.26 核。延迟与 CPU 没有回归，单独运行时 CPU 的差别来自机器的负载。持续的差别只有固定的内存：回收后的在用堆多 3 MB（34 → 37 MB），峰值常驻内存多 7–8 MB，来自新增的代码；其中 `outbound.ts` 导入的 npm `undici` 加载时占 5.7 MB 堆（守护进程入口加载后的堆从 16.4 MB 增到 19.5 MB）。组提交的突发一项与存储代码无关（两个提交的存储代码相同），见上一节的检查点。

**Node 24.20 内置 fetch 的开销**：同一时段在已配置代理（`network.proxy` 指向一个不存在的代理，回环上的假上游按规则直连，经出站模块的自定义连接器）与未配置代理之间交替运行各三次，中位数：非流式附加延迟 p50 2.39 → 0.93 ms、首字节 2.49 → 0.63 ms，p99 5.01 → 3.35 ms、4.34 → 2.38 ms，CPU 与单块成本不变。配置代理时出站模块为每个上游请求使用 npm `undici`（7.29.1）的 Agent，未配置时使用 Node 的全局分发器（Node 24.20 内置的 undici 7.29.0）。单独测量回环上的顺序请求：全局 fetch p50 1.46 ms，同一个 fetch 带 npm `undici` 的 Agent 作为 `dispatcher` p50 0.054 ms；连接都被复用，换成一次写出整个应答的原始 TCP 服务也是 1.4–1.6 ms，所以时间花在客户端；Node 25.9（内置 undici 7.24.4）的全局 fetch 为 0.072 ms。也就是说自定义连接器不是开销，未配置代理时的全局分发器才是：守护进程的每个上游请求多付约 1.4 ms。之后未配置代理时出站模块也使用一个共用的直连 Agent（[ADR 0035 第 8 条](../../docs/decisions/0035-outbound-proxy.md#决定)）；与 `34f8189` 交替各三次的中位数：非流式附加延迟 p50 直通 2.35 → 0.84 ms、转换 2.46 → 0.89 ms，p99 4.86 → 3.16 ms、5.38 → 3.16 ms；首字节 p50 2.24 → 0.51 ms，p99 4.24 → 2.12 ms、4.26 → 2.11 ms；CPU、单块成本与内存不变（基准客户端自己仍用全局 fetch，所以“直接请求”一列仍约 1.6 ms）。
